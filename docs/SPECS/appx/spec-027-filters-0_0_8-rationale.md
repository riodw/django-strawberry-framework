[Decision 3](#decision-3--six-layer-lazy-resolution-pipeline) Layer 5 now defines an internal `FieldSpec` dataclass carried alongside each generated input field with three slots: `python_attr` (the dataclass field name on the Strawberry input class), `graphql_name` (the wire-format name emitted via `strawberry.field(name=...)`), and `django_source_path` (the canonical Django ORM lookup expression — e.g., `"galaxy__name"` for the flat-field case, `"name"` for a same-model field). `_build_input_fields` constructs the `FieldSpec` table at materialization time; `normalize_input_value` consults the `FieldSpec` to reconstruct the form-data dict using `django_source_path` keys, NOT by reverse-mangling the GraphQL name. Test `test_field_spec_maps_galaxy_name_flat_field_to_django_source_path` pins this.
  - **L1 (rev8) — Current-state section reflects TODO-skeleton state.** Rev1–rev7's [Current state][spec-027-current-state] section said `django_strawberry_framework/filters/` "does not exist" and "no production code on disk yet". ## Decision 3 — Six-layer lazy-resolution pipeline

Spec text: [Decision 3][spec-027-d3]. Contract that stays: the six-layer lazy-resolution pipeline ports from `django-graphene-filters`, with Layer 5 Strawberry-adapted to `Annotated["Name", strawberry.lazy(...)]` over real module globals of `filters.inputs`, `LOOKUP_NAME_MAP` pinning every lookup's GraphQL name, and `FieldSpec` carrying the Django source path.

### Justification (moved from the spec)

- The cookbook's six-layer architecture is proven (the working reference per [`START.md`][start]); reinventing it would burn schedule for no architectural gain.
- Five of six layers are library-agnostic Python (on top of the shared `django_filters.filterset.BaseFilterSet` per [Decision 5](#decision-5--django-filter-as-the-foundation)) — the port is mechanical, not creative.
- Layer 5's Strawberry adaptation is pinned to the actual Strawberry API (`Annotated["Name", strawberry.lazy("module")]` over module globals); rev1's draft "lazy on `module.path.ClassName`" or "lazy on `module._registry.Name`" cannot work because Strawberry does not traverse object paths or dict lookups.
- `Meta.fields = "__all__"` narrowing keeps the [Non-goals][spec-027-non-goals] "no implicit `FilterSet` generation from `Meta.fields`" rule self-consistent — `"__all__"` would otherwise need to invent target filtersets for every relation, which IS auto-generation.

### Alternatives considered (and rejected)

- **Design a new lazy-resolution mechanism from scratch.** Rejected: zero benefit over the cookbook's proven architecture; doubles the review surface.
- **Skip Layer 6 (no dynamic-factory plumbing).** Rejected: when [`DjangoConnectionField`][glossary-djangoconnectionfield] lands in `0.0.9`, it would need the cache regardless; lifting it here is cheaper than retrofitting later.
- **Use `typing.ForwardRef` instead of `strawberry.lazy(...)`.** Rejected: Strawberry's documented forward-reference idiom IS `strawberry.lazy(...)`; reaching past Strawberry's API to `typing.ForwardRef` would build on private behavior.
- **Store input classes in a private dict registry and look them up at `LazyType.resolve_type` time via a Strawberry monkey-patch.** Rejected: monkey-patching Strawberry's internals for the sake of preserving rev1's `_registry`-keyed shape is a maintenance hazard; using Strawberry's documented module-globals path is the cleaner shape.
- **`Meta.fields = "__all__"` auto-generates a default `<Target>Filter` for every relation it touches.** Rejected per H7 of the adversarial review: this is the "implicit `FilterSet` generation" path the [Non-goals][spec-027-non-goals] section excludes; relations must come through explicit `RelatedFilter` declarations.

### Changes this Decision underwent

- **rev2 H1** rewrote Layer 5: generated input classes are materialized as real module globals of `django_strawberry_framework.filters.inputs`, because Strawberry's `LazyType.resolve_type` reads `module.__dict__` and cannot traverse an object path or a sidecar dict. rev1's `_registry`-keyed shape could not have worked.
- **rev3 L2** unified `materialize_input_class` to the two-argument `(name, cls)` signature — the destination module is always `filters.inputs`, so it is not a parameter.
- **rev4 H2** corrected the self-referential annotation shape to `list[Annotated["Name", strawberry.lazy(...)]] | None`: the `Annotated[...]` must wrap the forward-reference string itself, not the surrounding `list[...]`.
- **rev4 H3** added `LOOKUP_NAME_MAP`, because Strawberry's auto-camel-case only fires on underscored identifiers and would leave `icontains` unchanged on the wire.
- **rev4 M3** pinned the `Meta.fields = "__all__"` deltas against `django_filters.utils.get_all_model_fields` (include PK / FK, exclude M2M); **rev4 L1** pinned the flat `galaxyName` rendering of a `galaxy__name` path.
- **rev8 M5** added the `FieldSpec` dataclass so the runtime normalizer reads `django_source_path` instead of reverse-mangling the public name.

### Claims this Decision may no longer make

- That the `Meta.fields = "__all__"` override is carried by `FilterSet._get_fields`. The real override is the public `django-filter` classmethod `FilterSet.get_fields`; no `_get_fields` exists at `HEAD`.
- That `FilterArgumentsFactory._ensure_built` **materializes** each built input class as a module global. It never has: the filter-side `materialize_input_class` call site is single and lives in the finalizer (`django_strawberry_framework/types/finalizer.py::_bind_filtersets` hands the helper to the shared `_bind_sidecar_sets`, whose subpass-4 loop invokes it), and `_ensure_built`'s body is a BFS over `pending` with a collision raise and `_build_class_type` calls. Layer 5's bullet asserted both halves for the factory while [Decision 4][spec-027-d4] said twice that `_ensure_built` "only controls the Strawberry input shape" and [Decision 6][spec-027-d6]'s subpass 4 put materialization in the finalizer — so the spec carried the claim and its negation on three surfaces at once, and the surviving half (`_ensure_built` emits the `Annotated[...]` shape) is what made the false half read as checked. **A bullet that states two contracts with an `AND` is audited as one claim**; the true half licensed the false one through eight revisions, three slices, an integration pass and five build passes.

## Decision 4 — Upstream-primitives parity floor

Spec text: [Decision 4][spec-027-d4]. Contract that stays: every verified upstream primitive ships, and `FILTER_DEFAULTS` lives on `FilterSet` as a class attribute whose FK/PK branch is conditional on the target type's Relay shape and owner-aware through `_owner_definition.related_target_for(...)`.

### Justification (moved from the spec)

- ⚛️ parity (the package's positioning claim) requires shipping equivalents for each parity-floor primitive; absence in the first ship is the kind of gap that bites consumers immediately.
- Each primitive is short (~30–80 lines); the cost of porting all five plus `FILTER_DEFAULTS` is much smaller than the cost of explaining why the package is missing one.

### Alternatives considered (and rejected)

- **Ship only `GlobalIDFilter` in `0.0.8`; defer the four `TypedFilter` subclasses.** Rejected: half-shipping the parity floor invites the same churn as not shipping at all; consumers hit the gap immediately.
- **Ship the parity floor under different symbol names (e.g., `DSTArrayFilter`).** Rejected: the upstream naming is the consumer's mental model; renaming for no architectural gain creates friction.

### Changes this Decision underwent

- **rev2 H4** made the FK/PK -> `GlobalIDFilter` mapping conditional on the target `DjangoType`'s Relay shape rather than blanket.
- **rev3 H1** moved `FILTER_DEFAULTS` from `factories.py` to a class attribute on `FilterSet`, because `BaseFilterSet.filter_for_field()` / `filter_for_lookup()` consult `cls.FILTER_DEFAULTS` at runtime filter-instance build time; a factory-only conditional would let the GraphQL input and the runtime filter instance disagree.
- **rev3 L4** narrowed the `graphene-django` claim: the unconditional `GlobalIDFilter` belongs to the filter-connection-field defaults, not to the framework as a whole.
- **rev4 H4** made the conditional owner-aware through `_owner_definition.related_target_for(field_name)` instead of `registry.get(target_model)`, which loses owner context under [`Meta.primary`][glossary-metaprimary].
- **rev4 M1** replaced "or whatever attr the per-primitive port exposes" with the named converter `convert_filter_to_input_annotation(...)` plus its runtime symmetric `normalize_input_value(...)`.
- **rev4 M6** made `GlobalIDFilter` Strawberry-specific: accept `str` and `relay.GlobalID`, validate the decoded `type_name`, pass only `node_id` down.
- **rev5 H3** corrected the `RangeFilter` form-data keys to the positional `<field>_0` / `<field>_1` pair after verifying `RangeWidget.value_from_datadict`; the earlier converter table had claimed named `from_` / `to` keys.

- **rev8 H2** tightened multi-owner reuse from Relay-shape compatibility to an exact `DjangoTypeDefinition` **and** exact `graphql_type_name` match, because GlobalID validation depends on the concrete type name.

### Claims this Decision may no longer make

- That `normalize_input_value` hands `django-filter` a **decoded `node_id`** for a `relay.GlobalID` object. At `HEAD` it re-encodes to the base64 wire string (`django_strawberry_framework/filters/inputs.py::_encode_global_id_input`), because eager decoding strips the `type_name` *before* the validation that depends on it — a wrong-type GlobalID object passed the gate silently under the decoded shape. The `node_id` the Decision does still promise is what `GlobalIDFilter.clean` passes down to the form after validating; that is a later stage, not this one.
- That the range dataclass normalizes to named `{lookup}_from` / `{lookup}_to` keys. **rev5 H3 already retracted this** and corrected the converter table to the positional `<field>_0` / `<field>_1` pair — but only in the table row. The prose sentence four lines below it kept the retracted wording until the integration cohort's final verification corrected it, so the spec asserted the positional keys and their negation on the same page. A partial claim fix reads as a whole one to every later sweep.
- That the `list` return shape has exactly the three producers the bullet named (`GlobalIDMultipleChoiceFilter` / `ListFilter` / `ArrayFilter`). The `BaseCSVFilter` family `django-filter` generates from a `Meta.fields` `in` / `range` lookup is a fourth, and it sits at index 2 of `filters/inputs.py::_FILTER_INPUT_KIND_TYPES` — **ahead** of `(RangeFilter, _DjangoRangeFilter)` at index 3 — so a `range` lookup declared through `Meta.fields` normalizes to a **list** while a filter declared as `RangeFilter` normalizes to the positional **dict**. One lookup name, two shapes, decided by how the filter was declared; the bullet named only the second and the enumeration read as closed.
- That the runtime symmetric's signature is `normalize_input_value(filter_instance, raw_value)`. The shipped signature takes a third parameter, `field_name=None`, and it is what supplies the `<field>` prefix in the multi-key shape the same paragraph specifies — so the two-argument spelling was the form no production caller uses (`filters/sets.py::FilterSet._normalize_input` passes `field_name=form_key` at both call sites). The spelling occurred at **seven** spec sites, and correcting only the one a finding pointed at would have been the partial fix the bullet above records.

## Decision 5 — `django-filter` as the foundation

Spec text: [Decision 5][spec-027-d5]. Contract that stays: `FilterSet` subclasses `django_filters.filterset.BaseFilterSet` and `django-filter` stays a hard dependency; the pinned import shape stays in the spec.

### Justification (moved from the spec)

This Decision is a reversal of rev1's "drop the soft-dep" stance. rev1's posture contradicted three load-bearing facts:

1. [`pyproject.toml #"django-filter>=25.2"`][pyproject] already pins `django-filter` as a hard runtime dep.
2. [`GOAL.md #"The existing django_filters.FilterSet plugs into Meta.filterset_class directly"`][goal-migration-shape] explicitly promises "the existing `django_filters.FilterSet` plugs into `Meta.filterset_class` directly" — a direct migration path that requires `FilterSet` to be a `BaseFilterSet`.
3. The cookbook's `django_graphene_filters/filterset.py::AdvancedFilterSet` IS a `django_filters.filterset.BaseFilterSet` subclass at load-bearing layers; the spec's "five of six layers port verbatim" claim only holds when those layers ride on `BaseFilterSet`.

- The dep is already on the lock file. The cost of removing it is updating [`pyproject.toml`][pyproject], the [`GOAL.md`][goal] promise, the [`README.md`][readme] migration narrative, and any consumer-facing claim that a `django_filters.FilterSet` plugs in directly — a fan-out that nothing in [Goals][spec-027-goals] requires.
- The cost of keeping it is one line of inheritance, plus the cookbook's import path. (The pinned import shape that followed this bullet stays in the spec: it changes how the module is written.)
- The `django-filter` install surface is uncomplicated: `django-filter>=25.2` ships clean on every supported Python / Django combo the package targets; no `ImportWarning` branch is required because the dep is hard, not soft.

### Alternatives considered (and rejected)

- **Drop `django-filter` entirely; re-implement `BaseFilterSet` machinery in the package.** Rejected: re-implementing `BaseFilterSet`, `Filter`, `MultipleChoiceFilter`, `FilterMethod`, form cleaning, lookup generation, and `.qs` is a large net-new code surface for zero functional gain; the dep is already in the lock file and the cookbook's port relies on it.
- **Soft-dep on `django-filter` (`ImportError` branch on first `FilterSet` declaration).** Rejected: the dep is already hard; a soft-dep would surface an `ImportWarning` every import time and add a branch to test against; consumers who don't filter would still pay the warning surface.
- **Accept either a package-`FilterSet` or a `django_filters.FilterSet` at `Meta.filterset_class`.** Rejected: two consumer-facing surfaces for the same wiring create ambiguity about which `check_*_permission` shape applies and which lazy-resolution mechanism runs. The single package `FilterSet` (which IS a `django_filters.filterset.BaseFilterSet` via inheritance) is the boundary class; consumers convert via parent-class swap, not via dual acceptance.

### Changes this Decision underwent

- **rev1** proposed dropping `django-filter` to a soft dependency.
- **rev2 H3** reversed that outright and is the Decision as it now stands.
- **rev3 H3** pinned the import path: `django_filters.BaseFilterSet` does not exist at the top level, so the cookbook's `from django_filters import filterset` + `filterset.BaseFilterSet` shape is the only one that resolves. That correction stayed in the spec.

## Decision 6 — Finalizer phase-2.5 binding seam + materialize-before-`Schema` ordering

Spec text: [Decision 6][spec-027-d6]. Contract that stays: the binding pass runs at finalizer phase 2.5 as four ordered subpasses — bind owners, expand, materialize, orphan-validate — and materialization lands before `strawberry.Schema(...)`.

### Justification (moved from the spec)

- Phase 2.5 is already the synchronization seam for `DONE-015-0.0.5`'s Relay-Node injection; threading the filter binding through the same loop keeps the finalizer's phase ordering coherent.
- Materializing classes as module globals (not as dict entries in a separate registry) matches Strawberry's actual `LazyType.resolve_type` semantics; H1 in the adversarial review verified by direct inspection of the installed Strawberry that dict-keyed registries are not reachable through `strawberry.lazy(...)`.
- The pending-relation registry's record-now-resolve-at-finalization pattern (used for model relations) reuses cleanly for lazy related-filter class references; the `LazyRelatedClassMixin` equivalent reuses the same fail-loud error format ("Cannot finalize ... no registered ...") that the model-relation finalizer already produces.
- Calling `finalize_django_types()` twice is still a no-op via the existing `registry.is_finalized()` guard; the new filter-binding pass is idempotent because (a) materialization is keyed by `(name, filterset_class)` provenance — re-materializing the same `(name, filterset_class)` pair is a no-op, and (b) re-materializing the same `name` from a DIFFERENT `filterset_class` raises [`ConfigurationError`][glossary-configurationerror] per [Decision 9](#decision-9--input-class-namespace-vs-typeregistry-and-lifecycle).
- Partial-finalize lifecycle: if phase 2.5 raises mid-iteration (e.g., an unresolved `RelatedFilter`), `registry.mark_finalized()` is never reached, the lifecycle ledger keeps the partial state, and a subsequent `finalize_django_types()` call resumes the binding pass; the idempotency contract above ensures a clean rerun. `registry.clear()` clears the lifecycle ledger AND removes the materialized module globals (the lifecycle clause in [Decision 9](#decision-9--input-class-namespace-vs-typeregistry-and-lifecycle) pins this), so test-fixture reload patterns (e.g., the one [`examples/fakeshop/test_query/test_library_api.py`][fakeshop-test-library] uses) reset the filter subsystem in the same step.

### Alternatives considered (and rejected)

- **Run filter binding in phase 2 alongside `_attach_relation_resolvers`.** Rejected: filter binding depends on Relay-Node setup (because Relay-aware filters require the `GlobalIDFilter` mapping established in `0.0.5`); phase 2 runs before Relay setup, so binding would land in the wrong order.
- **Run filter binding in a new phase 2.75.** Rejected: invents an extra phase number for one capability; the existing 2.5 is the right grain.
- **Run filter binding at `DjangoType.__init_subclass__` instead of at finalization.** Rejected: `RelatedFilter("CelestialBodyFilter")` cannot be resolved at class-creation time because the target filterset's module may not have been imported yet — same definition-order-independence constraint that `DONE-010-0.0.4` solved for model relations.
- **Inject `filter:` argument into existing root resolvers' Strawberry field metadata after finalize.** Rejected per H2: Strawberry collects field arguments at `@strawberry.type` decoration time; injection-after-collection would require either monkey-patching Strawberry internals or invalidating already-decorated `Query` types. The corrected shape uses `filter_input_type(FilterSet)` on the resolver signature at module-load time (per [Decision 11](#decision-11--filter_input_typefilterset-consumer-helper)) so Strawberry collects the lazy reference naturally.

### Changes this Decision underwent

- **rev2 H1 / H5** added the materialize-before-`Schema` ordering and the input-class lifecycle this Decision depends on.
- **rev8 H1** replaced the per-`DjangoType` "bind owner, then expand" loop with four ordered subpasses, each completing across every wired type before the next begins — the loop was order-dependent and could bind an owner after an expansion had already consulted it.
- **rev8 M4** rewrote the `TypeRegistry.clear()` snippet to match the real `clear()` body and to clear `_helper_referenced_filtersets` as well as the input namespace.

### Claims this Decision may no longer make

- That `registry.clear()` reaches the filter subsystem through a local import inside `TypeRegistry.clear`. At `HEAD` the subsystem registers a callback at import time via `register_subsystem_clear(...)` and `TypeRegistry.clear` replays it; the local-import shape predates that seam.
- That phase 2.5 runs exactly four subpasses. It also runs two filter-only audits — a registered-`RelatedFilter`-target audit and an encode-only-GlobalID-target rejection — that no Decision names.

## Decision 7 — `Meta.filterset_class` promotion gate

Spec text: [Decision 7][spec-027-d7]. Contract that stays: `Meta.filterset_class` is promoted out of `DEFERRED_META_KEYS` only in the same change that makes the subsystem apply it end-to-end.

### Justification (moved from the spec)

- Cross-subsystem invariant pinned in [`docs/GLOSSARY.md`][glossary] ("Deferred `Meta` keys are accepted only when their subsystem applies them end-to-end. This rule resolves entirely at `1.0.0`."); applies to every Layer-3 sidecar.
- Half-promoting (accepting the key but no-oping on it) is the worst-of-both: consumers cannot tell whether their filter declaration is doing anything; debug surface is hidden.
- The promotion is a one-line change at [`django_strawberry_framework/types/base.py::DEFERRED_META_KEYS`][base] (`"filterset_class"` moves to `ALLOWED_META_KEYS`); the validator at `_validate_meta` already gates on `ALLOWED_META_KEYS | DEFERRED_META_KEYS`.

### Alternatives considered (and rejected)

- **Promote `Meta.filterset_class` early in Slice 1 before binding is wired.** Rejected: silently accepting a key whose effect doesn't exist is a maintenance hazard.
- **Keep the key in `DEFERRED_META_KEYS` until `DjangoConnectionField` ships in `0.0.9`.** Rejected: the connection field is the second consumer; root-list resolvers can call `FilterSet.apply_sync(...)` / `apply_async(...)` themselves in the meantime (per the H2 split in [Decision 8](#decision-8--relation-permission-cascade--get_queryset-cooperation)), and the live HTTP coverage in Slice 4 exercises that path.

### Changes this Decision underwent

## Decision 8 — Relation-permission cascade + `get_queryset` cooperation

Spec text: [Decision 8][spec-027-d8]. Contract that stays: the apply pipeline is the `apply_sync` / `apply_async` classmethod pair with a thin `apply` dispatcher; visibility scoping runs before filtering, related constraints land in `self.queryset` before `.qs` is read, `check_permissions` is active-input-only, and `form.is_valid()` is called explicitly.

### Justification (moved from the spec)

- Visibility-before-filter is the security-correct ordering: filtering inside a queryset that hasn't been scoped to the request's user would let a nested filter "see through" the visibility gate (compute `WHERE name LIKE '%admin%'` against rows the user shouldn't see). Step 3's nested visibility-scoping extends this property to the related-filter join (H1).
- Per H1 of the adversarial review, threading `info` through `apply` and into the nested `RelatedFilter` application is what makes the visibility hook's right-hand side coverage possible. Without it, the optimizer's `Prefetch` downgrade covers OUTPUT visibility scoping but the parent-row `WHERE <rel>__in (...)` JOIN bypasses it.
- The cookbook's `_apply_related_queryset_constraints` is the precedent for the related-filter `queryset=` boundary; this card ports its parent-scoping shape, narrowed to active-branch-only per M4.
- The explicit `form.is_valid()` call per M2 closes a real failure mode in `BaseFilterSet.qs` — without the explicit raise, a malformed filter input would silently degrade rather than surface a `GraphQLError`.
- The optimizer cooperation is already documented in [Queryset diffing][glossary-queryset-diffing] — a `.filter(...)` call on the consumer queryset doesn't change the cooperation contract because the optimizer reconciles against whatever queryset shape the resolver returns.

### Alternatives considered (and rejected)

- **Apply filters first, then `get_queryset`.** Rejected: security-incorrect ordering per the reasoning above.
- **Skip step 3 (nested visibility scoping)** and rely on the optimizer's `Prefetch` downgrade to cover related-row visibility. Rejected per H1 of the adversarial review: the optimizer's downgrade covers OUTPUT planning, not parent-row JOIN filtering — the queryset already exists in WHERE-clause form by the time the optimizer walks the selection tree.
- **Skip the active-branch refinement** in step 7 and apply every declared `RelatedFilter(queryset=...)` constraint unconditionally to the parent queryset. Rejected per M4: the unconditional behavior would exclude parent rows without a constrained child even for `filter: {}` or `filter: { name: { ... } }`, which is row loss the consumer never asked for.
- **Skip step 6 (`form.is_valid()`)** and let `BaseFilterSet.qs` consult `self.errors` as the cookbook does. Rejected per M2: the cookbook's behavior silently degrades to "filter what we can clean, drop what we can't" — that's the wrong shape for a GraphQL surface that must return a structured error.
- **Skip step 5 (let nested filters override the `queryset=` boundary).** Rejected: defeats the cookbook's documented security feature; the boundary's whole point is to be inviolable.

### Changes this Decision underwent

- **rev3 H2** defined `apply(input_value, queryset, info)` as the single resolver-facing classmethod and reserved the `django-filter` instance method `filter_queryset(self, queryset)` for the tree-form-logic override.
- **rev3 H4** narrowed the related-queryset boundary to the cookbook's actual behaviour: it filters the PARENT queryset via `parent_qs.filter(<rel>__in=<constraint_qs>)`, and does not scope the nested relation resolver's output.
- **rev4 H1** threaded `info` end-to-end and added step 3, deriving each active `RelatedFilter` branch's child visibility queryset from the target type's `get_queryset`.
- **rev4 M2** added the explicit `filterset.form.is_valid()` call and the `FILTER_INVALID` error shape, because `BaseFilterSet.qs` only consults `self.errors` and otherwise degrades silently.
- **rev4 M4** narrowed the explicit `RelatedFilter(queryset=...)` constraint to active branches only; **rev4 M5** put `<OwnerType>.get_queryset(...)` before `apply(...)` in every example.
- **rev5 H2** split `apply` into `apply_sync` / `apply_async`, because a target's `get_queryset` can be async-only and a sync resolver cannot await it.
- **rev5 M1** decomposed the pipeline into the five named helpers; **rev5 M2** pinned `check_permissions` to active-input-only scope, diverging deliberately from the cookbook's walk-every-declared-filter shape.
- **rev5 M7** pinned `from graphql import GraphQLError`; **rev5 M8** pinned `info.context.request` with an `isinstance(info.context, HttpRequest)` fallback; **rev5 M10** pinned the `ErrorDict.get_json_data()` payload shape.

## Decision 9 — Input-class namespace vs `TypeRegistry` and lifecycle

Spec text: [Decision 9][spec-027-d9]. Contract that stays: the input-class namespace IS the `filters.inputs` module's own globals, separate from the model-to-`DjangoType` registry, with an idempotent `(name, input_class)` ledger and a shared clear point.

### Justification (moved from the spec)

- The `TypeRegistry` is the model-to-`DjangoType` mapping that powers [`Meta.primary`][glossary-metaprimary] / `registry.get(model)` / `registry.types_for(model)`; mixing string-keyed input-class entries into the same dict would weaken the type contract.
- The input-class names are stable and class-derived (e.g., `f"{FilterSet.__name__}InputType"`); two connection fields targeting the same model resolve to the same `FilterInputType` (Apollo cache friendly) without registry collision.
- Sibling Layer-3 subsystems ([`OrderSet`][glossary-orderset] for [`DONE-028-0.0.8`][kanban], [`AggregateSet`][glossary-aggregateset] for `0.1.3`) need their own per-subsystem input-class namespaces; collapsing them into the `TypeRegistry` would put four heterogeneous namespaces in one place. Per-subsystem (each in its own module's globals) keeps responsibilities scoped and matches Strawberry's actual `LazyType.resolve_type` semantics.
- `Meta.primary`'s ambiguity rules (`primary_for(model)`, `types_for(model)`) are model-keyed; the input-class namespace is name-keyed; no read-time predicate from one needs to walk the other.
- The lifecycle clauses above mean a `tests/filters/` test that constructs a `FilterSet`, calls `finalize_django_types()`, asserts behavior, calls `registry.clear()`, and rebuilds with a different filterset shape works correctly; the materialized globals from the first build don't leak into the second.

### Alternatives considered (and rejected)

- **Sidecar `_input_type_registry: dict[str, type]` in `filters.inputs`.** Rejected per H1 of the adversarial review: Strawberry's `LazyType.resolve_type` cannot reach into a dict; the registry must coincide with the module's global namespace.
- **Single shared `TypeRegistry` mapping both `model → DjangoType` and `name → input_class`.** Rejected: heterogeneous key types weaken the contract; sibling Layer-3 subsystems would force the same dict to grow more axes; and Strawberry's lazy mechanism still requires module globals regardless.
- **Per-`DjangoType` input-class namespace (attached as `definition.filter_input_types`).** Rejected: connection fields with `_dynamic_filterset_cache`-generated filtersets don't have a stable `DjangoType` to attach to; the per-module namespace is the natural shape and matches Strawberry's `strawberry.lazy("module-path")` lookup.
- **Per-app input-class namespace (Django-app-scoped).** Rejected: Strawberry schemas span Django apps; the namespace's scope is the Strawberry schema, not the Django app.
- **No clear contract — let test fixtures recover ad hoc.** Rejected per H5 of the adversarial review: a partial-finalize failure plus a fakeshop schema reload would collide on the existing materialized name; the lifecycle clauses above are what make rerun and reload deterministic.

### Changes this Decision underwent

- **rev2 H5** added the whole lifecycle contract: idempotent `(name, filterset_class)` materialization, collision rejection, the shared clear point, and the public `clear_filter_input_namespace()` helper.
- **rev3 M5** pinned the cycle-safe integration as a local import inside `TypeRegistry.clear()`, plus a subprocess test importing `registry` alone.
- **rev4 H4** added the owner-binding rule; **rev8 H2** tightened it to exact `graphql_type_name` equality.
- **rev5 H5** added `_helper_referenced_filtersets` and the orphan check, and required `registry.clear()` to clear that set too.
- **rev8 M4** rewrote the snippet to match the real `clear()` body and to clear both caches behind their own `try / except ImportError`.

### Claims this Decision may no longer make

- That the `TypeRegistry.clear()` code snippet reproduces the integration as shipped — see [Decision 6](#decision-6--finalizer-phase-25-binding-seam--materialize-before-schema-ordering) above; the same retraction applies to `clear_filter_input_namespace` and `_helper_referenced_filtersets`.
- That any clear path removes a materialized class from the `filters.inputs` module namespace, and with it the Justification bullet above claiming "the materialized globals from the first build don't leak into the second". Materialized classes are deliberately left parked; the measurement and the design reason are in `## Post-final residual cohort — the clear path` below.

## Decision 11 — `filter_input_type(FilterSet)` consumer helper

Spec text: [Decision 11][spec-027-d11]. Contract that stays: `filter_input_type(FilterSet)` returns the `Annotated[...]` forward reference for a resolver's `filter:` argument, validates eagerly, and records the filterset for the finalizer's orphan check.

### Justification (moved from the spec)

- Without a helper, consumers would have to spell out `Annotated["GalaxyFilterInputType", strawberry.lazy("django_strawberry_framework.filters.inputs")]` directly on every resolver — a long incantation that ties consumer code to the package's internal module path and bypasses the validation gate.
- A helper-returned `Annotated[...]` is the only consumer-facing shape that satisfies all three requirements: (a) it's a real Python annotation Strawberry collects at `@strawberry.type` time; (b) it defers resolution to schema-build time; (c) it points at a module Strawberry can import to resolve via `module.__dict__[name]`.
- The eager validation (`TypeError` at call time for a non-`FilterSet`) catches misuse at the resolver-declaration site instead of letting Strawberry surface a more cryptic schema-build-time error.
- The helper is mechanical: ~15 lines, no state, returns a value. Adding it costs nothing; not shipping it forces every consumer to spell out the underlying shape and learn the module path. The forward-compatibility shape for [`DjangoConnectionField`][glossary-djangoconnectionfield] in `0.0.9` (which accepts `filterset_class=` and owns the wiring internally) uses the same `filter_input_type(FilterSet)` helper under the hood.

### Alternatives considered (and rejected)

- **No helper; consumers spell out `Annotated[...]` themselves.** Rejected: ties consumer code to the package's internal module path; bypasses validation; not the package's `Meta`-driven shape.
- **Helper returns `<Name>FilterInputType` directly (a class).** Rejected: the class doesn't exist yet at module-load time — it's materialized later by `finalize_django_types()`. Returning a class at module-load time would force the helper to eagerly run the finalizer, which contradicts the definition-order-independence contract.
- **Helper is a method on `FilterSet`: `GalaxyFilter.input_type()`.** Rejected: viable shape, but adds class-method surface to every `FilterSet` for the sake of one call site per resolver. The module-level function form is the smaller import and the more discoverable doc entry.
- **Defer the helper to `0.0.9` (`DjangoConnectionField` accepts `filterset_class=` directly).** Rejected: `0.0.8` consumers cannot wait for `0.0.9` to expose a working `filter:` argument; this card's [Goals][spec-027-goals] item 5 ("expose introspection for what filter surface a type supports") requires a consumer-facing path right now, not next patch.

### Changes this Decision underwent

- **rev2 H2** created the helper, because Strawberry collects field arguments at `@strawberry.type` decoration time and there is no post-hoc argument injection.
- **rev3 L3** softened the timing claim from "at module-load time" to "when Strawberry evaluates the annotation during schema declaration / collection"; **rev3 L7** added the code comment protecting the `Annotated[<name variable>, ...]` ForwardRef shape from being refactored into a literal.
- **rev5 H5** extended the helper to record every filterset into `_helper_referenced_filtersets` for the finalizer's orphan check.
- **rev5 M4** added `test_filter_input_type_returns_forwardref_in_annotation_args`; **rev5 M6** tightened the PEP 563 mechanics and added the idempotency contract; **rev6 M4** pointed the helper's comment at the verifying test.
- **rev8 M3** narrowed the consumer surface to plain `@strawberry.field` resolvers and deferred `DjangoListField` argument injection to `0.0.9`.

### [Decision 9 — Input-class namespace vs `TypeRegistry` and lifecycle][spec-027-d9]

**Claim retracted: the cycle-safe local import inside `TypeRegistry.clear`.** The Decision carried a ````python` block showing two `try: from django_strawberry_framework.filters… except ImportError: pass` guards inside `TypeRegistry.clear()`, plus a subprocess test proving `registry` imports alone. ### [Decision 9 — Input-class namespace vs `TypeRegistry` and lifecycle][spec-027-d9]

**Claim retracted: the clear path strips materialized classes out of the module namespace.** The lifecycle contract's third bullet stated that `registry.clear()` "removes every materialized class from the module's global namespace", and that `clear_filter_input_namespace()` "walks `_materialized_names.items()` and `delattr(sys.modules["django_strawberry_framework.filters.inputs"], name)` for each, then resets the ledger to `{}`". Two further surfaces carried the same claim: the [`## Test plan`][spec-027-test-plan] `tests/filters/test_inputs.py` bullet ("`clear_filter_input_namespace()` removes every materialized global and resets the ledger") and the [`## Edge cases and constraints`][spec-027-edge-cases] reload bullet's closing sentence ("No stale globals leak between test runs"). Three surfaces, one claim, all false at `HEAD`.

**What the code does, measured.** `grep -rn delattr django_strawberry_framework/ --include='*.py'` returns no `delattr` on any clear path — every package hit is either a comment saying why the clear does *not* strip a parked global, `types/finalizer.py`'s removal of generated attributes from a `DjangoType` class, `utils/context.py`'s context-attribute teardown, `views.py`'s per-request marker, or the one live clear-path `delattr` inside `utils/inputs.py::clear_generated_input_namespace`, which drops a `FilterSet` **subclass's** binding attributes and never touches the `inputs` module. `filters/inputs.py::clear_filter_input_namespace` is a one-line delegate to that shared heavy clear, which empties the ledger and the field-spec table, clears the arguments factory's two class-level caches, and drops each set subclass's `_lifecycle.binding_attrs`.

**Why the code is right, and the spec was not.** Both implementation sites state the opposite of the spec as a deliberate contract, with the reason attached: `utils/inputs.py::clear_generated_input_namespace` — "**Materialized class objects are intentionally left parked** in the family `inputs` module `__dict__`" — because `materialize_generated_input_class` overwrites the global via `setattr` on the next finalize, so a parked class is replaced in place, while stripping it would break a `strawberry.lazy(...)` LazyType held by a consumer module whose autouse-reload fixture did not also reload the holder. A per-app live-test fixture that reloads only its own app's schema is exactly that shape, so the hazard is one this repo's own test suite produces rather than a hypothetical. `tests/filters/test_finalizer.py::test_clear_filter_input_namespace_can_be_called_directly` pins the shipped behavior directly — ledger emptied, parked global still present and still identical — and `::test_registry_clear_clears_filter_input_namespace_and_helper_set` pins the same property through the `registry.clear()` entry point. A spec that pinned `delattr` was therefore asking for a regression, not describing one: implementing the retracted sentence would break held LazyTypes and fail both package tests named above.

**The sibling card already states it correctly, which is the strongest evidence this was a spec-027 outlier rather than an unsettled question.** [`spec-028-orders-0_0_8.md`][spec-028] Decision 9's counterpart bullet spells out the parked-globals contract, calls parking "load-bearing", names the same LazyType hazard, and claims to mirror `clear_filter_input_namespace`'s body verbatim — a claim that was true of the code and false of the two specs read side by side. The corrected spec-027 bullets now agree with both the code and the sibling.

**What the correction added beyond deleting the false half.** The old bullet under-enumerated the clear even where it was true: it named only the ledger, where the shipped clear also resets `_field_specs`, the `FilterArgumentsFactory` caches (`input_object_types` and the `_type_filterset_registry` collision map), and every `FilterSet` subclass's phase-2.5 binding state. The corrected text enumerates all four and points at `sets_mixins.py::SetLifecycleAttrs.binding_attrs` as the single source of the attribute names rather than re-spelling the tuple, so a family that adds a binding slot cannot rot the spec. It also records the best-effort submodule lookups, which are what make the clear survive a partially-loaded build state.

**Claims elsewhere in this file that the same measurement falsifies, left standing as moved text.** Decision 9's `### Justification (moved from the spec)` closes with "the materialized globals from the first build don't leak into the second", and [Decision 6](#decision-6--finalizer-phase-25-binding-seam--materialize-before-schema-ordering)'s `### Justification (moved from the spec)` carries a partial-finalize bullet saying `registry.clear()` "clears the lifecycle ledger AND removes the materialized module globals (the lifecycle clause in Decision 9 pins this)" — a pointer at the very bullet retracted here. Both are verbatim moved spec text whose subject is the retracted claim, kept for the same reason the `[fakeshop-test-library-reload]` split is kept: this file is the record of what the spec once said, and rewriting a moved passage would destroy the evidence the retraction is about. This bullet is their retraction.

**Claim retracted: the lifecycle ledger is keyed to the filterset class.** Ten sentences across five spec surfaces — `## Slice checklist`, `### Decision 9` (four), `## Edge cases and constraints` (two), `## Test plan` (two), and the closing summary item — described the ledger as `` `dict[str, type[FilterSet]]` `` tracking `class_name → filterset_class`, made idempotency a property of the `(name, filterset_class)` pair (seven occurrences), and framed the collision as "the same name claimed by a DIFFERENT filterset class" reported "with both filtersets' qualified names". At `HEAD` `filters/inputs.py` declares `_materialized_names: dict[str, type]`, `filters/inputs.py::materialize_input_class(name, cls)` receives the generated **input** class, and `utils/inputs.py::materialize_generated_input_class` compares `existing is cls` and stores `ledger[name] = cls` — so the ledger value is the materialized Strawberry input class, idempotency is `is` identity on it, and the collision is a second **input** class claiming one name. `utils/inputs.py::duplicate_name_message` interpolates the two input classes' `__module__.__qualname__` and closes with rename advice naming the filterset, so the "both filtersets' qualified names" sentence was wrong about which pair of names the consumer sees.

`type[FilterSet]` was not merely imprecise here, it was the wrong type — and the confusion is easy to acquire, because the sibling declarations it sat beside genuinely ARE filterset-keyed: `_field_specs: dict[tuple[type[FilterSet], str], FieldSpec]` and `_helper_referenced_filtersets: set[type[FilterSet]]` both match the code exactly and are untouched. **The observable behavior never changed and the corrected text says so explicitly**: input-class names are derived from the owning `FilterSet`'s `__name__`, so two `FilterSet`s of the same `__name__` in different modules still collide — each produces its own input class, and the second claims a name the first holds. The worked example was part of the same defect: the bullets called their variables `cls_a` / `cls_b` while the prose called them filtersets, so they are now `input_a` / `input_b`.

The spec was not uniformly wrong. The `## Slice checklist`'s Slice-3 phase-2.5 bullet already carried the correct spelling — "the ledger value is the materialized Strawberry input class, uniquely produced by one `FilterSet`; the idempotency check uses `is` identity on the input class", plus "collision against a different input class" — so this was a **half-reconciled** claim with a correct in-document anchor to align the other ten sentences to, not an open contract question. The same checklist's Slice-1 `inputs.py` bullet carried the false spelling: **two slices of one checklist disagreed about the ledger's type, and each bullet was internally consistent**, which is why every sweep that read one of them accepted it.

**The sibling card caught this exact defect in its own review and spec-027 never did.** [`spec-028-orders-0_0_8.md`][spec-028]'s revision history carries it as finding **M1** — "`_materialized_names` typing corrected to `dict[str, type]` storing input class", noting that earlier revisions wrote `dict[str, type[OrderSet]]` storing the source `OrderSet`, that `materialize_input_class(name, input_cls)`'s second argument is what gets `setattr`-ed to the module global, and that **source-class collision detection lives separately** in the factory's `_type_orderset_registry`, "mirrors the filter side's split". So the two-registry split the false spelling collapsed was already documented on the order side: the ledger is input-class-keyed, and the filterset-keyed registry is a different structure in a different module. Both families' code was always split this way; only spec-027's description conflated them.

Three occurrences of the old spelling survive in this file **as moved historical text, deliberately**: [`## Revision history`](#revision-history) rev-2 Pass 1 ("idempotent `(name, filterset_class)` materialization"), [Decision 6](#decision-6--finalizer-phase-25-binding-seam--materialize-before-schema-ordering)'s Justification bullet (twice, in the same sentence), and Decision 9's `### Changes this Decision underwent` rev-2 H5 entry. Each records what a review round decided in the words it used; rewriting them would falsify the history this file exists to hold. The one occurrence that was **not** history — Decision 9's `Spec text: … Contract that stays:` line, which asserts the current contract — is corrected in place, because a live-contract summary in this file is read as true rather than as a record.

**Claim retracted: `tests/filters/test_inputs.py` covers `materialize_input_class`.** The `## Test plan` bullet listed it among that file's surface and attributed three behaviors to it (module-global assignment plus ledger write, pair idempotency, the collision raise), and carried the clear-lifecycle clause as well. `grep -c materialize_input_class tests/filters/test_inputs.py` returns **0**; `tests/filters/test_finalizer.py` returns **11**, and holds `::test_materialize_input_class_is_idempotent_on_same_pair`, `::test_materialize_input_class_rejects_collision_on_distinct_classes`, `::test_phase_2_5_subpass_3_materializes_input_classes_as_module_globals`, and both clear tests. All four clauses moved to the `test_finalizer.py` bullet, named by test. What `test_inputs.py` does own on this surface is `::test_clear_filter_input_namespace_tolerates_unimportable_submodules`, so its bullet now claims that and only that. The other eight symbols the bullet lists were each re-measured rather than assumed — `_build_logic_fields` 10, `_build_input_fields` 31, `construct_search` 7, `LOOKUP_PREFIXES` 1, `LOOKUP_NAME_MAP` 4, `convert_filter_to_input_annotation` 29, `normalize_input_value` 31, `filter_input_type` 17 occurrences in that file — and every one of the nine test functions the bullet names by name resolves there (the two `HIDE_FLAT_FILTERS` twins, the deep-multi-hop twin, the FieldSpec source-path test, and the four `filter_input_type` tests), with its live twin resolving in `examples/fakeshop/test_query/test_library_api.py`. **A coverage list is a claim per entry, and exactly one entry of nine was false** — which is why the list had to be measured symbol by symbol rather than judged as a whole.

**Why no instrument caught it.** Slice 2 swept citation and provenance rot (wrong card id, raw line number, build provenance); the consolidation cohort swept broken `#"substring"` targets in both directions; Slice 3 swept the claims this file's `## Claims the spec may no longer make` inventory named. A sentence describing a retired or never-shipped **mechanism** is invisible to all three, because it cites nothing and every symbol it names still exists. The one instrument that would have found it is the symbol-vs-runtime read recorded above — read the paragraph against the code it describes — and it reached this bullet only because a `.py` docstring cohort followed the citation in the opposite direction, from the test back to the spec.
