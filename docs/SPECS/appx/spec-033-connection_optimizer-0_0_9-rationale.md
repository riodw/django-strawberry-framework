Read this when checking a finished implementation against the reasoning that produced it, or before re-opening a settled question. Worker 2 never reads it ([`docs/builder/BUILD.md`][build-md] `### Who reads it, and when`).

**How later passes append to this file.** Each Decision below carries a `### Changes this Decision underwent` section. A reconciliation pass that finds the spec stale against `HEAD` — a module that moved, a helper that never consolidated where the Decision said it would, a fallback a later card inverted — appends a `**Post-ship:**` bullet there, naming the shipped behavior and the card that changed it. Nothing needs restructuring to take an addition, and the corrections themselves always land in the spec, stated directly and without chronology.

## Decision 3 — Walker recognition is definition-metadata-driven, not name-pattern guessing

Spec: [Decision 3 — Walker recognition is definition-metadata-driven, not name-pattern guessing][spec-033-d3].

### Justification (moved from the spec)

- **The card's DoD demands it**: "Walker recognizes connection edge/node shapes without reaching into `DjangoConnectionField` internals." A definition slot is the same channel the walker already uses for `field_map`, `optimizer_hints`, and relation targets — zero new coupling.
- **The normalization path stays shared**: model fields and synthesized connections use the same selection-name resolver. It keeps the exact reverse lookup as the fast path, then forward-matches Strawberry's authoritative field names through the active schema name converter when the transform is lossy (for example, an underscore before a digit) or the field has an explicit GraphQL name. Connection recognition must not grow a second name-normalization path.
- **Name-pattern guessing is wrong twice.** Stripping a `_connection` suffix would misfire on a consumer-authored field that merely *ends* in `_connection`, and would fire for relations whose synthesis was suppressed (`"list"` narrowing, consumer-authored relation, non-Node target). The synthesis already computed the true mapping; recording it costs one dict.
- **Finalization is the right write point**: relation targets are settled (Phase 1), the synthesis runs in Phase 2.5, and the definition is the canonical per-type record every other Phase-2.5 product (sidecar bindings, strategy stamps) already writes to.

**Nested recognition follows the primary-type contract.** The walker resolves nested-level definitions through `_resolve_field_map(model, source_type=None)` → `registry.get(model)` — the model's **primary** `DjangoType` (the shipped spec-018 nested contract) — so when it descends into a relation it reads the *primary's* `relation_connections` slot, regardless of which `DjangoType` actually shapes that node in the response. For `field_map` this is correct by construction (a model's relations are the model's relations); for `relation_shapes`, which is a **per-type opt-in**, a secondary `DjangoType` that shapes a relation differently from the primary (one synthesizes `booksConnection` while the other narrows `books` to `"list"`, or vice versa) would be recognized against the wrong slot — missing a real connection or recognizing one this type did not synthesize. A divergent secondary type is therefore **out of scope for windowed planning in `0.0.9`**: nested recognition uses the primary's slot, and such a relation falls back per-parent (visible to strictness like any unplanned shape). Routing nested recognition through the resolved target definition instead is a follow-up recorded in [Risks and open questions](#risks-and-open-questions). `test_secondary_type_relation_shapes_nested_recognition` pins the behavior.

### Alternatives considered (and rejected)

- **Reaching into `connection.py`'s `_connection_type_cache` or the field marker at plan time.** Rejected: exactly the internals-coupling the DoD forbids, and field objects are not reachable from the walker's `(model, field_map)` vocabulary.
- **Suffix-stripping with a field-map existence check.** Rejected: still misfires on suppressed synthesis (the `"list"`-narrowed relation has a real `books` in the field map but no connection sibling — planning a window for a field that does not exist would do dead work and stash wrong resolver keys).

### Changes this Decision underwent

- **Revision 2 (finding 3)** — nested recognition follows the **primary-type contract**. The Decision gained its whole closing paragraph: the walker reads the model's *primary* `DjangoType` `relation_connections` slot, so a secondary `DjangoType` whose `relation_shapes` diverges from the primary's would be recognized against the wrong slot. Divergent secondary types are therefore out of scope for windowed planning in `0.0.9` and fall back per-parent, pinned by `test_secondary_type_relation_shapes_nested_recognition`. A scope/expectation pin, not a mechanism change.

## Decision 4 — Windowed-prefetch planning under a package-reserved `to_attr`

Spec: [Decision 4 — Windowed-prefetch planning under a package-reserved `to_attr`][spec-033-d4].

### Justification (moved from the spec)

this is the proven upstream mechanism (parity table) adapted to the package's two structural differences — the plan cache (which forces the cacheability and key-hygiene rules) and the `"both"`-sibling shape (which forces the `to_attr`). Window functions are fully supported at the package's dependency floor ([Current state][spec-033-current-state]).

### Alternatives considered (and rejected)

- **A plain (unwindowed) `Prefetch` + in-Python slicing.** Rejected: fetches every related row for every parent to serve a `first: 3` page — unbounded over-fetch that gets *worse* as data grows; the window is the entire point of the upstream design.
- **Prefetch onto the relation accessor (no `to_attr`).** Rejected: collides with the list sibling under `"both"` (Django's duplicate-lookup error at best, silently windowed list data at worst).
- **Per-alias windows for aliased nested connections with divergent pagination.** Rejected for `0.0.9`: each alias would need its own `to_attr` and the resolver has no per-alias dispatch; the divergent-alias shape falls back per-parent ([Decision 6](#decision-6--refusal-arms-divergent-aliases-hints-and-scalar-only-connections)).
- **Porting upstream's `SliceMetadata` arithmetic by hand.** Rejected: the helper is the engine's own (`strawberry.relay.utils`), already a load-bearing dependency of the shipped connection field; re-implementing it invites drift.

### Changes this Decision underwent

- **Revision 2 (finding 1)** — the ported `apply_window_pagination` dropped upstream's **DISTINCT guard**. SQL evaluates window functions before `DISTINCT` dedup, so `Count(1) OVER (PARTITION BY ...)` over-counts whenever the windowed child queryset carries `.distinct()` — and a visibility `get_queryset` that joins and de-duplicates is a normal shape. The Decision gained the DISTINCT-target guard bullet (leave the selection unplanned, fall back per-parent) and a fourth fallback shape landed in [Decision 6](#decision-6--refusal-arms-divergent-aliases-hints-and-scalar-only-connections). One of the two findings that would otherwise have shipped silently-wrong data.
- **Revision 2 (finding 7)** — the deterministic-order hoist was **promoted** from a module-location note under [Decision 11](#decision-11--module-and-test-file-locations) to a stated cursor-parity invariant here, precisely because the hoist is a correctness prerequisite rather than a tidiness refactor: if plan-time and resolve-time order ever diverge, a fast-path `endCursor` stops round-tripping to an optimizer-less `after:`.
- **Revision 3 (finding 1)** — windowed prefetch **ordering**. The SQL window sets only the row-number *values*, not the order Django hands instances to `to_attr`, so `apply_window_pagination` now applies `queryset.order_by(*order_by)` too; the cursor-parity invariant explicitly covers return order, not just the window expression.
- **Revision 3 (finding 2)** — scalar-only **projection**. The Slice-1 cut accepted a full-column over-fetch for `pageInfo`-only / `totalCount`-only windows (correctness-safe but wasteful); the follow-up fix replaced it with the minimal pk / connector / deterministic-order `.only()` projection (`_project_scalar_only_window`), since the page never reads node columns.
- **Revision 3 (finding 3)** — malformed-slice **strictness locality**. A malformed-pagination fallback now records the connection's resolver identities (window-unplanned but strictness-accounted-for) so the per-parent pipeline raises its own cursor/cap error under `"raise"` instead of a spurious `OptimizerError`. This is the load-bearing distinction from the other Decision 6 fallbacks, which stay fully unplanned so strictness still flags them.
- **Revision 5 (item 1)** — the `"both"`-shape coexistence the `to_attr` isolation exists for was asserted only at the plan-object level; it earned a live pin (`test_list_relation_and_connection_sibling_coexist_live`) over `/graphql/`. The contract was unchanged — only its proof moved live.
- **Post-ship: `_dst_total_count` became conditional** (`57cbd32a`, 2026-07-07, "Pluggable nested-connection fetch strategies + Postgres lateral backend", self-labelled **idea #2**; extended by `744aea93`, 2026-07-09, "count-free `hasNextPage` via an n+1 overfetch probe", and `41008e4c`, 2026-07-17, "FetchMode axis"). The Decision had stated both annotations unconditionally. The partition `Count(1) OVER` is now annotated only when the page's own selection can observe a count, so an ordinary `first: N` edges-only page carries no count at all and answers `hasNextPage` from an n+1 sentinel. `deeb53b4` (2026-07-17, single-parent fast path) makes the absence structural rather than merely common: that strategy synthesizes `_dst_row_number` in Python and never sets a count.
- **Post-ship: the DISTINCT guard moved earlier and generalised.** The Decision placed it at the end of child-queryset construction, after the child plan and before the window, as a single `query.distinct` check. `57cbd32a` moved it onto the **base** child queryset and made `distinct` one of five reasons in `optimizer/nested_fetch.py::unwindowable_child_queryset_reason`, alongside `sliced`, `select_for_update`, `combined`, and `values`. The reason the earlier placement had to go is the strategy seam: a post-build re-check would have to run once per backend, whereas a base-queryset classification is one strategy-independent gate.
- **Post-ship: unsupported relation kinds stopped raising on the planning path.** The Decision said `window_partition_for_prefetch` raises a package-internal planning error for an unsupported kind. Production now derives the partition from `optimizer/join_taxonomy.py::classify_relation_join`, which documents that it never raises and returns `windowable=False` instead; `GenericRelation` also joined the windowable kinds. The raising helper survives with the same contract but **no production caller** — see [Non-Decision deliberation](#non-decision-deliberation), where that is recorded as an open question rather than resolved here.
- **Post-ship: divergent aliases became a planned shape, and the `to_attr` grammar grew a per-key form** (`9580e84e`, 2026-07-10, "batch divergent-alias connections per response key", **idea #2**). The rejected alternative recorded above — "Per-alias windows for aliased nested connections with divergent pagination", rejected for `0.0.9` because "each alias would need its own `to_attr` and the resolver has no per-alias dispatch" — is the shape the tree now implements. Both halves of that reason were retired: Django accepts several `Prefetch`es on one accessor as long as their `to_attr`s differ, and the resolver gained per-key dispatch by probing `_dst_<field>$<response key>_connection` before the shared attribute. `$` rather than `__` because Django splits `prefetch_to` on `LOOKUP_SEP`.
- **Post-ship: the plan-time cap gained a request-policy ceiling** (`567cc6d0`, 2026-08-04, the security program's bounded-execution work). `relay_max_results` from the schema config is now lowered by the request policy's `max_page_size` when that is smaller, in the one shared helper both sides call — so the cap agreement the Decision argues for survives the addition rather than being broken by it.
- **Post-ship: the window became one strategy's rendering rather than the mechanism** (`57cbd32a` for the seam and the Postgres lateral backend, `deeb53b4` for the runtime single-parent fast path). Three fetch backends now feed the `to_attr` this Decision created, selected per extension instance, per setting, or per field. The `0.0.14` cut records the seam in [`CHANGELOG.md`][changelog]; no spec owns it, which is the gap recorded under [Non-Decision deliberation](#non-decision-deliberation).
- **One rule was held back in the spec by this move.** Risks item 6 recorded that `window_partition_for_prefetch` takes the raw Django relation field rather than a `FieldMeta`, because the forward-M2M reverse query name lives only on `field.remote_field`. That is implementation-relevant rationale — the "why" that changes how the partition is derived — and a verified-and-rejected note besides, so it stayed in the spec as a Decision 4 bullet instead of moving here; only its `field_meta.py` fallback moved, under [Risks and open questions](#risks-and-open-questions).

## Decision 5 — Connection-class fast path with annotation-presence detection and a per-parent fallback

Spec: [Decision 5 — Connection-class fast path with annotation-presence detection and a per-parent fallback][spec-033-d5].

### Justification (moved from the spec)

- Annotation-presence probing is upstream's own integrity check (its `resolve_optimized_connection_by_prefetch` falls back on `AttributeError`); pairing it with the package-reserved `to_attr` and the internal wrapper removes the need for upstream's queryset-config flag and `_clone` monkeypatch entirely.
- The fast path skips visibility / filter / order **by construction, not by trust**: visibility is baked into the windowed child queryset at plan time (same as every generated prefetch child), and sidecar input can never reach the fast path because sidecar-carrying selections are never window-planned ([Decision 6](#decision-6--refusal-arms-divergent-aliases-hints-and-scalar-only-connections)).
- Pagination-argument consistency is structural: the window was computed from the *same selection's* resolved arguments `resolve_connection` receives, so cursors and `pageInfo` derived from row numbers agree with what the pipeline would have produced. The sidecar-kwargs guard is a defensive belt for the alias/divergence class of bugs: if a future planner misses a sidecar shape, the resolver refuses to consume the window.

### Alternatives considered (and rejected)

- **A context-stash handshake** (the walker records windowed paths on `info.context`; the resolver checks the stash instead of the rows). Rejected: a second source of truth that can desynchronize from what Django actually prefetched (e.g. a consumer-stripped prefetch); the rows themselves are the ground truth.
- **Building the connection in `_build_relation_connection_resolver`.** Rejected: Strawberry wraps `relay.connection(...)` fields with `ConnectionExtension`; field resolvers return node iterables, not final connection instances. The through-schema test is mandatory because a direct helper call would miss this layer boundary.
- **Re-running the pipeline over the prefetched rows.** Rejected: `FilterSet` / queryset operations on a materialized list are impossible without re-querying — which is the N+1 again; the fallback exists for exactly the shapes that need the pipeline.
- **Raising when annotations are missing.** Rejected: missing annotations are a *cooperation* outcome (consumer prefetch won, optimizer absent), not an error; upstream warns-and-falls-back, the package falls back silently and lets strictness ([Decision 8](#decision-8--strictness-mode-wiring-for-connection-paths)) be the policy voice.

### Changes this Decision underwent

- **Revision 2 (finding 2)** — `_build_relation_connection_resolver` takes the relation field name (or the precomputed `to_attr`) as an **explicit constructor parameter**. The resolver is otherwise handed only the instance accessor, which diverges from the field name for a reverse relation without `related_name` (`field.name == "book"`, accessor `"book_set"`), so deriving the probe from the accessor would have computed the wrong attribute and the fast path would have silently never fired for exactly the shape the package special-cases everywhere else. The second of the two findings that would otherwise have shipped broken.
- **Revision 5 (item 3)** — the nested ambiguous-empty case rounded out the matrix with `test_nested_connection_first_zero_empty_page_live` alongside the existing root pin.
- **Build-time: the wrapper never carried slice metadata.** The Decision described `_WindowedConnectionRows` as storing "the rows plus the resolved `offset`, `limit`, and `reverse` slice metadata used by the planner", and derived `pageInfo` from that metadata. It was not implementable as written: Strawberry's `ConnectionExtension.resolve` consumes `first` / `last` / `before` / `after` and forwards them only to `resolve_connection`, so the resolver has no pagination arguments to record. The shipped wrapper carries `rows` and a `fallback` callable, and every window classification happens in `resolve_connection`, which re-derives the bounds through the same shared helper the walker planned with. The `fallback` field the Decision never mentions exists because `resolve_connection` cannot rebuild the per-parent relation manager the resolver holds. The correction makes the cursor-parity guarantee **stronger** than the Decision claimed: the resolve-time window is computed by the plan-time helper rather than trusted from a stashed value. The adjacent rejected alternative, "a context-stash handshake", is untouched and stays correct — the shipped shape rejects a *second source of truth*, which is what that alternative would have been.
- **Post-ship: `first: 0` and an overshot `after:` are served from marker rows, not fallen back** (`57cbd32a`, **idea #2**, whose message states the change: marker-row windows keep each partition's row 1 for the ambiguous-empty shapes so a childless parent and an empty page stay distinguishable in one query, collapsing 2+2N queries to 2). Three consequences the Decision could not have anticipated: an empty rows list now *proves* the parent has no children, which is a stronger claim than "empty and unambiguous"; the per-parent fallback for those two shapes is gone, and with it the two tests the Test plan named for it; and `last: 0` became the one always-fallback shape, deliberately, because Strawberry's `edges[-0:]` serves every edge and reproducing that from a window is not worth a special case. `04cc9214` (2026-07-15) extended the same `last: 0` parity to the keyset slicer.
- **Post-ship: the page flags became a four-way fork** (`744aea93` + `41008e4c` + `51421e54`). The Decision stated one rule — forward comparisons against `_dst_total_count` for all windows. Today `has_next_page` is the probe-row observation on a count-free page, a value-domain comparison on a counted keyset-seek page, a constant `False` for an unbounded forward page and for the reversed `last`-only page, and the Decision's own comparison on a counted offset page. The Decision's *claim* about the reversed `last`-only window still holds and is still pinned by `test_fast_path_wire_parity_last_only`; it now arrives through the constant-`False` arm.
- **Post-ship: the annotation probe reads the row number only.** The Decision required rows carrying `_dst_row_number` **and** `_dst_total_count`. Because the count is now conditional, demanding it would refuse every count-free page and make the single-parent strategy unconsumable; `connection.py::_window_rows_are_annotated` probes the row number alone and says so in its own docstring.
- **Post-ship: there is one `resolve_connection`, not two** (`de2601e9`, 2026-08-17, "single-site the connection dispatch and the recognized-fetch rebind"). The Decision described `DjangoConnection.resolve_connection` **and** a generated `<TypeName>Connection.resolve_connection` path, with the count path needing its own branch before `_guard_total_count_countable`. `6912ca92` had already factored their shared head into an intermediate helper; `de2601e9` retired the duplicated override, leaving that helper with one caller and inlining it. The count opt-in is now a `ClassVar` the generated total-count class sets. The contract the Decision cares about — the marker is treated as an annotated optimized source and never reaches the non-queryset count guard — is unchanged and pinned; only the two-paths phrasing was stale.
- **Post-ship: the resolver probes a per-response-key `to_attr` first** (`9580e84e`, **idea #2**), then the shared one, and threads whichever attribute held rows into the strictness probe. This is the resolve-time half of the divergent-alias inversion recorded under [Decision 4](#decision-4--windowed-prefetch-planning-under-a-package-reserved-to_attr).
- **Post-ship: keyset cursors fork this Decision's mechanism** (`51421e54`, 2026-07-10, "keyset value-encoded cursors via `Meta.cursor_field`", **idea #3** / BACKLOG-39). The spec listed them under Non-goals and Out of scope, on the reading that the window math "inherits Strawberry's offset-cursor semantics verbatim". It still does for offset targets, but a keyset target forks the bounds derivation at the cursor vocabulary, builds edges with `encode_keyset_cursor` rather than through `resolve_edge` (a direct exception to this Decision's "the cursor prefix stays owned by Strawberry's edge type"), carries its own seek-count annotation family and drift guard, and routes a non-window keyset source to the keyset resolver rather than to `ListConnection`. [`docs/README.md`][docs-readme] already stated the consumer-facing version of this and was the correct document of the two.
- **Post-ship: the degradation list stopped being closed** (`57cbd32a`, `deeb53b4`, `9580e84e`, `51421e54`). The Decision's closing paragraph enumerated the causes of degradation as though exhaustively. New always-fallback shapes have landed since — `last: 0`, `after` with `last`, an inverted `after` / `before` interval, every backward keyset shape, and a same-response-key argument conflict — and two new *window producers* (the Postgres lateral backend and the single-parent fast path) land rows under the same `to_attr` for the same probe to consume. The spec now states the rule ("whenever the window is absent or unsafe to consume") and keeps the examples, rather than implying the list is complete.
- **Retraction: the reversed-cursor scheme this Decision may no longer describe.** An earlier revision of the Decision described a `_dst_total_count - _dst_row_number` reversed-cursor scheme for the `last`-only window. Neither upstream nor Slice 1's port implements that: `_dst_row_number` stays the **forward** row number for every window, and the positional offset cursor is `_dst_row_number - 1` throughout. The spec's parenthetical recording the retraction moved here; the spec keeps the contract and its byte-parity citation to `test_fast_path_wire_parity_last_only`.

## Decision 6 — Refusal arms, divergent aliases, hints, and scalar-only connections

Spec: [Decision 6 — Refusal arms, divergent aliases, hints, and scalar-only connections][spec-033-d6].

### Justification (moved from the spec)

every fallback is the *shipped* behavior — this card strictly adds planned shapes, never changes unplanned ones — so the matrix is monotonic: no query that works today changes results or stops working. Strictness visibility of the fallbacks is deliberate and consistent: an unplanned per-parent access **is** an N+1, whatever the reason, and the shipped strictness contract already treats deliberate skips (e.g. `SKIP`-hinted relations) as flaggable. The remediation story for sidecar-input fallbacks under `"raise"` is recorded in [Risks and open questions](#risks-and-open-questions).

### Alternatives considered (and rejected)

- **Exempting fallback shapes from strictness** (stash them as pseudo-planned). Rejected: would make `"raise"` lie about a real per-parent pattern; strictness exists to surface exactly this, and the consumer's recourses (drop the nested filter, restructure, lower strictness in that test) are all visible ones.
- **Windowing sidecar-filtered connections with `cacheable = False` plans.** Rejected for `0.0.9`: still requires `apply_sync` at walk time with a synthesized request context — the deferred design surface, not just a cache flag.

### Changes this Decision underwent

- **Revision 2 (finding 1)** — the `.distinct()`-target child queryset joined the matrix as a **fourth** fallback shape, for the window/`DISTINCT` evaluation-order reason recorded under [Decision 4](#decision-4--windowed-prefetch-planning-under-a-package-reserved-to_attr).
- **Revision 3 (finding 2)** — the scalar-only text was corrected in both directions: a `pageInfo`-only / `totalCount`-only nested connection is window-**planned**, not a fallback (so `"raise"` does not turn harmless connection metadata into an avoidable per-parent error), and the planned window now carries the minimal projection rather than the full-column load.

- **Post-ship: the matrix is no longer monotonic, and the justification above is the sentence that says so.** "This card strictly adds planned shapes, never changes unplanned ones — so the matrix is monotonic: no query that works today changes results or stops working" was true of this card. It is not true of what happened next. `57cbd32a` (**idea #2**) and `9580e84e` (**idea #2**) between them *inverted* one arm — divergent-argument aliases went from deliberately unplanned to planned, one window per response key — and *added* refusal arms the Decision never listed. The count went from four to nine, and the number four was spelled four different ways across the spec (an opener, two "a fourth ... fallback shape" clauses, a "x4" in a table cell, and a DoD list), which is why correcting it meant sweeping the numeral rather than the phrase.
- **Post-ship: `first: 0` and an overshot `after:` left the fallback matrix entirely**, served from retained partition marker rows (`57cbd32a`); `last: 0` arrived to take their place as the always-fallback shape. Recorded in full under [Decision 5](#decision-5--connection-class-fast-path-with-annotation-presence-detection-and-a-per-parent-fallback).
- **Post-ship: item 3's "the other hint shapes neither suppress nor shape the window" is false of this card's own seam.** [`OptimizerHint`][glossary-optimizerhint]`.strategy(name)` selects the nested-connection fetch backend for one connection field, which is precisely shaping the window; and an `OptimizerHint.prefetch(Prefetch(..., to_attr=...))` on a generated relation now raises [`ConfigurationError`][glossary-configurationerror] at plan time (`57cbd32a`) rather than coexisting with it. The item's *conclusion* — a consumer hint's `to_attr` can never collide with the package's — survives, but for the opposite reason to the one it gave: the pairing is refused outright rather than kept apart by namespacing.
- **Post-ship: the DISTINCT arm generalised into one of five unwindowable-child-queryset reasons**, classified on the base queryset. Recorded under [Decision 4](#decision-4--windowed-prefetch-planning-under-a-package-reserved-to_attr).

## Decision 7 — Plan-cache key hygiene: nested pagination variables hash, root pagination arguments do not

Spec: [Decision 7 — Plan-cache key hygiene: nested pagination variables hash, root pagination arguments do not][spec-033-d7].

### Justification (moved from the spec)

the smallest change that makes windowed plans cache-safe while preserving B1's "variable filtering" property (variables that cannot affect the plan stay out of the key). The cache-key function stays static-shaped (one more frozenset contribution), so the memoized printed-AST fast path is untouched.

### Alternatives considered (and rejected)

- **Mark every windowed plan `cacheable = False`.** Rejected: nested connections are the hot path this card exists to optimize; uncacheable plans re-walk per request and forfeit B1 exactly where it matters most. (Plans whose child querysets bake a request-scoped `get_queryset` are *already* uncacheable — that shipped rule is untouched and orthogonal.)
- **Resolve which non-root fields are genuinely connections before collecting.** Rejected: requires model/registry context inside the AST walk (the key must be computable before the walker runs); the superset rule is strictly safer and simpler.
- **Normalize root pagination literals out of the printed AST** (de-fragment the cache). Rejected: rewriting the printed document for key purposes risks collapsing genuinely distinct operations; recorded as a possible future refinement, not scoped.

### Changes this Decision underwent

- **Revision 2 (finding 4)** — the visibility-bearing library example is **uncacheable** for the shipped request-scope reason, so the Slice-3 cache-key pins use non-visibility synthetic targets and different fixtures from the Slice-5 live pins. A test-design consequence of the Decision, not a change to the key rule.
- **Revision 5 (item 2)** — variable-driven nested pagination earned a live pin: the in-process Slice-3 tests covered only the plan layer, so `test_nested_connection_pagination_from_graphql_variable_live` now drives a GraphQL `$n` variable through a real request and the live `_post_graphql` harness gained a `variables=` parameter.

## Decision 8 — Strictness-mode wiring for connection paths

Spec: [Decision 8 — Strictness-mode wiring for connection paths][spec-033-d8].

### Justification (moved from the spec)

- **Closes the documented hole**: [`spec-032`][spec-032] established that nothing implements strictness for connections — the synthesized connection resolver reaches neither the `DST_OPTIMIZER_STRICTNESS` nor the `DST_OPTIMIZER_PLANNED` sentinel, so its nested access goes unflagged — and assigned the wiring here. Source-verified and recorded under [its Decision 12][spec-032-rationale-d12].
- **The three-condition guard reproduces the list-relation semantics exactly**: planned → silent; prefetch-served → silent (no lazy load happens); unplanned-and-will-query → flag. False positives are structurally excluded the same way `_check_n1`'s cache probes exclude them.
- **Union publication preserves parent strictness and FK-id elision**: nested fallback pipelines are real optimizer runs, but they must not destroy the root plan's `DST_OPTIMIZER_FK_ID_ELISIONS` or `DST_OPTIMIZER_PLANNED` sets. The parent resolver's planned set must still be visible after the nested connection returns, especially in `"warn"` mode where execution continues.
- **Fallback reasons make strictness actionable**: a sidecar-filtered nested connection flagged under `"raise"` should not look like an optimizer defect. The message includes the reason, for example `Unplanned N+1: books (not window-planned: selection carries filter/orderBy; resolving per-parent)`.
- **Root connections need nothing**: planned whenever an optimizer is installed (Current state); sentinel absent otherwise.

### Alternatives considered (and rejected)

- **Wiring strictness into `_pipeline_sync` for ALL connections (root included).** Rejected: a root connection with no optimizer installed has no sentinel (no-op), and with one installed is always planned — the root check could never fire; adding it is dead code with per-request cost.
- **A separate `connection.py`-local checker.** Rejected: two implementations of one contract drift; `_check_n1` already carries the exact probe/flag/raise shape and the parameterization is mechanical.

### Changes this Decision underwent

- **Revision 4 (finding 2)** — **strictness-message vocabulary.** The message examples named the generated `<field>_connection` attribute, but the shipped `_check_n1` keys on and prints the underlying **relation** field name (`books`) — uniform with the list-relation message and the `resolver_key` the planner emits, and the form the tests pin. Documentation-integrity only; no code behavior changed in that revision.

- **Post-ship: condition 1 is read from a `ContextVar`, not from the `DST_OPTIMIZER_PLANNED` stash, and condition 2 reads two publish channels** (`841e56d6`, 2026-08-18, "scope relation visibility per relation and reach strictness in every execution"). The Decision stated condition 1 as "a strictness sentinel is stashed". That was a fail-open shape, and the commit closed it: the stash is unavailable to an execution running without a `context_value`, and it is written at plan-publish time, so an operation whose root resolver returns something the walker cannot plan never publishes it at all — both shapes left a configured N+1 guard silently disarmed. Strictness is now read from a per-execution `ContextVar` armed at `on_execute` entry, with the stash as a fallback, and "planned" is satisfied by the `DST_OPTIMIZER_PLANNED` stash **or** by a per-execution scoped-relations set that every execution publishes. The correction matters in the direction of *understating* the guarantee: a reader implementing against the Decision's original sentence would reintroduce the fail-open. The four observable outcomes the Decision promises — planned silent, window-served silent, unplanned-and-will-query flagged, off / no-optimizer no-op — are unchanged and all four are pinned.
- **Post-ship: `_check_n1` gained a `force_unplanned` parameter** (spec-035's Decision 5) that bypasses the planned-key short-circuit for an unsafe FK-id elision. The connection call site does not pass it, so this Decision's planned-key short-circuit is unconditional *at this seam* — recorded so the restatement does not over-claim it is unconditional everywhere.
- **Build-time: `_build_relation_connection_resolver` took two new parameters, not one.** The Decision states the resolver key's three components but never says the resolver *takes* the declaring type as a constructor parameter, and the module map recorded only the relation-field-name parameter [Decision 5](#decision-5--connection-class-fast-path-with-annotation-presence-detection-and-a-per-parent-fallback) asked for. The shipped signature also takes `declaring_type`, which is this Decision's, not Decision 5's: without it the resolve-time `resolver_key(declaring_type, relation_field_name, runtime_path)` cannot match the walker's emission, and the call site passes the iterated type deliberately rather than the model's primary type so a divergent secondary type's connection stays correctly flagged.
- **Post-ship: `### Error shapes`'s "No new error surface" was false.** The sentence belongs to no single Decision and is recorded under [Non-Decision deliberation](#non-decision-deliberation).

Slice 1's `_plan_connection_relation` must unwrap a nested connection selection's `edges { node }` with the same fragment-aware, directive-aware, runtime-prefix-carrying semantics the root seam uses — one implementation or two drifting ones. ## Decision 10 — The products connections-only conversion lands with this card

Spec: [Decision 10 — The products connections-only conversion lands with this card][spec-033-d10].

### Justification (moved from the spec)

- **The card pins it twice**: "Land the products list->connection replacement together with this card", and the deferral rationale (converting earlier would have regressed the optimizer dogfooding) dissolves the moment Slices 1–2 land. Per the [`docs/SPECS/NEXT.md`][next] prefer-the-card rule, the conversion is in scope here even though [`TODO-BETA-062-0.1.5`][kanban] (fakeshop activation) also names it — the boundary: **this card takes exactly the root-field shape change and its test re-pinning; [`TODO-BETA-062-0.1.5`][kanban] keeps everything else** (root `node(id:)` / `nodes(ids:)` entry points, any `Meta.connection` opt-ins, further Layer-3 activation). The overlap is recorded in [Risks and open questions](#risks-and-open-questions) for the maintainer to reconcile on the [`TODO-BETA-062-0.1.5`][kanban] card body.
- **It is the strongest live proof this card can have**: products is the optimizer-dogfooding surface; if the conversion lands with the SQL-shape pins intact (same query counts through `edges { node }`), the card's "no regression" DoD is demonstrated against the package's own most adversarial example, and the cookbook parity story (`all_object_types = AdvancedDjangoFilterConnectionField(ObjectTypeNode)`, no list resolvers) becomes literally true in the example project.
- **Minimal shape**: no `Meta.connection` additions (products connections ship without `totalCount`, like the cookbook), no root [`DjangoNodeField`][glossary-djangonodefield] / [`DjangoNodesField`][glossary-djangonodesfield] fields, no model or sidecar changes. The four types' relation-connection siblings already exist live (the `032` implicit default) and simply start planning.
- **The re-pin is shape-rewriting plus one semantic shift, not "purely mechanical"**: a list resolver returns *every* row; a `relay.connection` field with no `first`/`last` returns at most `relay_max_results` (default 100) plus `pageInfo`, and the pre-slice queryset gains the deterministic `ORDER BY pk` `_finalize_queryset` appends. The shape rewrite (`{ name }` → `{ edges { node { name } } }`) is mechanical, but any re-pinned assertion that expected the full unbounded set (or a count past the default page) must stay under the cap or pass an explicit `first:`, and the `test_products_optimizer_*` query-count pins must account for the appended order and the connection's slice query. **`relay_max_results` is a hard ceiling, not just a default**: Strawberry's `SliceMetadata.from_arguments` raises `ValueError: Argument 'first' cannot be higher than {max_results}` for any `first:` *above* the cap, so for a collection larger than `relay_max_results` an explicit `first:` cannot recover the full set — the only faithful re-pin is the **capped page** (assert the first `relay_max_results` rows in deterministic pk order). The current products fixtures are small (no bulk creation), so this does not bite today *except* the forward-FK depth-2 `allEntries` pin (177 entries at `seed_data(1)`, over the cap), which asserts the capped default page — but the failure mode is a silently truncated result that still parses, so the conversion is not described as "purely mechanical."

### Alternatives considered (and rejected)

- **Defer the conversion to [`TODO-BETA-062-0.1.5`][kanban] entirely.** Rejected: contradicts the card's explicit sequencing note, and would leave this card's live SQL-shape proof confined to the library graph (M2M-only nested shapes; products adds the reverse-FK depth-2 shapes the dogfooding tests pin).
- **Keep the list resolvers alongside the connections** (additive, no churn). Rejected: the cookbook mirror is connections-only and the card says "replacement"; carrying both indefinitely doubles the live surface and the example stops modeling a real consumer choice. Recorded as the fallback if the test churn proves larger than estimated.

### Changes this Decision underwent

- **Three open questions the cohorts raised that this cycle deliberately did NOT resolve.** In each the shipped code implements the spec's own words, so changing it is a contract choice rather than a defect repair, and the spec was left stating the contract as shipped rather than pre-empting an answer.
  - **The `connection_to_attr` strictness probe answers "attribute present", not "the window was consumed".** [Decision 8](#decision-8--strictness-mode-wiring-for-connection-paths)'s third condition is "the fast-path `to_attr` is absent on `root`", and `types/resolvers.py::_check_n1` implements exactly that. But the resolver reaches `_check_n1` only on a branch where it has *already decided not to consume* whatever sits under `to_attr`, and three conditions produce that decision — the value is not a list, its rows carry no row number, or the resolver's own sidecar kwargs are present. In all three the per-parent pipeline then genuinely queries while the probe reads "present" as "served", so `"raise"` stays silent on a real per-parent access. Demonstrated mechanically with a three-row temp test, not argued. Reachability is narrow — the unannotated-rows shape needs a consumer writing the package-reserved `_dst_` namespace, which the [Edge cases][spec-033-edge-cases] consumer-cooperation bullet already declares unsupported and unguarded, and the sidecar shape needs a planner/resolver desync the sidecar guard exists as a belt against — and no data is wrong in any case; only the diagnostic is silent. Resolution paths: **(1)** thread the boolean `_resolve` already computed into `_check_n1` and restate the third condition as "the resolver did not consume a window for this response key" — smallest change, closes all three shapes, and the two demonstration rows become the pins; **(2)** accept it as designed and record in [Decision 8](#decision-8--strictness-mode-wiring-for-connection-paths) that a `_dst_`-namespace write can silence strictness, consistent with the existing unsupported-namespace posture, at the cost of that guarantee; **(3)** narrow to the sidecar half only — half a fix that looks closed. Path 1 is the cohort's recommendation.
  - **`optimizer/plans.py::window_partition_for_prefetch` has zero production callers.** Production derives the partition from the join descriptor instead, so the helper's six per-relation-kind pins — the most thorough in the tree — exercise a surface no request reaches, and two of them pin an `OptimizerError` no production path can emit while `exceptions.py` documents that raise as a live error mode. This is the existence challenge in its clearest form. Resolution paths: **(a)** delete the shim, move its pins onto `optimizer/join_taxonomy.py::classify_relation_join`'s `partition_expr` / `windowable` fields where `tests/optimizer/test_join_taxonomy.py` already lives, and drop the `exceptions.py` line — smallest surface, loses a name no consumer is documented to use; **(b)** keep it and give it the production caller it implies so the two cannot drift — keeps the pins meaningful but puts an exception back on a hot path that currently returns a bool; **(c)** keep it explicitly as a supported introspection helper and say so in [Decision 4](#decision-4--windowed-prefetch-planning-under-a-package-reserved-to_attr), making the test-only status intentional rather than residual.
  - **Ten of `optimizer/walker.py`'s seventeen back-compat aliases are dead, under a comment asserting live test readers.** The names that look like counter-examples are imported from their real owners (`optimizer.extension`, `optimizer.nested_planner`), not from `walker`. Deleting them is an executable change and an existence question; correcting the false comment is not, and that half is in scope for a `.py` repair pass.
