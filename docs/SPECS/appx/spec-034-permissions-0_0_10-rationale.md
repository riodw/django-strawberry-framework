# Rationale companion: spec-034 (Permissions subsystem — cascade visibility)

Companion to [`docs/SPECS/spec-034-permissions-0_0_10.md`][spec-034]. It carries that spec's **deliberative layer** and nothing else: the eight-revision review history that produced the contract, every Decision's justification, every alternative a Decision rejected and why it lost, and the risk / open-question deliberation that settled the card's design questions. The spec carries the contract; this file carries how the contract was arrived at. Neither duplicates the other — the text here **left** the spec.

Read this when checking a finished implementation against the reasoning that produced it, or before re-opening a settled question. Worker 2 never reads it ([`docs/builder/BUILD.md`][build-md] `### Who reads it, and when`).

**How later passes append to this file.** Each Decision below carries a `### Changes this Decision underwent` section. A reconciliation pass that finds the spec stale against `HEAD` — a predicate that shipped differently, a helper that never landed where the Decision said it would, a fallback a later card inverted — appends a `**Post-ship:**` bullet there, naming the shipped behavior and the card that changed it. Findings belonging to no single Decision go under [Non-Decision deliberation](#non-decision-deliberation). Nothing needs restructuring to take an addition, and the corrections themselves always land in the spec, stated directly and without chronology.

## Decision 2 — Card-scope boundary: the cascade ships end-to-end; the per-field read gate is defined here and implemented with `FieldSet` (`0.1.1`)

Spec: [Decision 2 — Card-scope boundary: the cascade ships end-to-end; the per-field read gate is defined here and implemented with `FieldSet` (`0.1.1`)][spec-034-d2].

### Justification (moved from the spec)

- **The card resolves its own tension.** The card's scope line names "per-field permission hooks declared via `Meta`", but its open question #4 locates the read gate at "`FieldSet.check_<field>_permission(info)`" under the beta FieldSet card ([`TODO-BETA-046-0.1.1`][kanban]; the card body's open question still quotes the older `044`, but the live kanban card is `046`) — the card itself files the implementation under that card. The board agrees: `fieldset/` is a `0.1.1` planned path in [`docs/TREE.md`][tree], the [`FieldSet`][glossary-fieldset] glossary entry is `planned for 0.1.1`, and `fields_class` sits in `DEFERRED_META_KEYS` today. The only artifact claiming `0.0.10` for the hooks is the [Per-field permission hooks][glossary-per-field-permission-hooks] glossary status tag — which contradicts its own body (it hosts the hooks on a `0.1.1` class). Per the [`docs/SPECS/NEXT.md`][next] boundary rule the card is preferred and the conflict is recorded ([Risks and open questions](#risks-and-open-questions)); Slice 5 re-statuses the glossary entry to `planned for 0.1.1`.
- **The DoD line is satisfiable under this reading and only this reading.** "Define the `Meta` surface for per-field permissions and promote keys only when applied end-to-end" — *define* (this Decision) and *don't promote early* (the invariant). Shipping gate code in `0.0.10` without `FieldSet` would require inventing a second, interim host that `0.1.1` would immediately supersede.

### Alternatives considered (and rejected)

- **Ship type-level `check_<field>_permission` classmethods on `DjangoType` now, migrate to `FieldSet` later.** Rejected: creates a soon-to-be-superseded public surface with a migration burden the package would own forever; the upstream cookbook hosts read gates on `FieldSet` (the [`GOAL.md`][goal] astronomy showcase shows exactly that split), and `START.md`'s scope-creep rule says don't quietly mix in extras that bloat the slice.
- **Pull the whole `FieldSet` forward into `0.0.10`.** Rejected: `FieldSet` is an L-sized subsystem of its own (computed fields, resolver overrides, redaction machinery); the board sequenced it post-alpha deliberately, and this card is already L.
- **Ship nothing and strike the bullet.** Rejected: the card demands the surface be *defined* before the implementation pass; leaving it undefined re-opens the design in `0.1.1` with no record of the cascade-composition rule the DoD pins.

### Changes this Decision underwent

- **Revision 1** pinned the per-field-hooks scope boundary that resolves the card-vs-glossary tension: read gates are hosted on [`FieldSet`][glossary-fieldset], a `0.1.1` deliverable, so this card defines the surface and keeps `fields_class` deferred.
- **Revision 2 (L1)** repointed the FieldSet card number to the live `TODO-BETA-046-0.1.1`; the card body's own open question still quotes the older `044`.

## Decision 5 — The cascade walk: call-time model-graph walk, registry primary lookup, every registered target composes, subquery intersection

Spec: [Decision 5 — The cascade walk: call-time model-graph walk, registry primary lookup, every registered target composes, subquery intersection][spec-034-d5].

### Justification (moved from the spec)

this is the upstream mechanism with the package's own registry and hook vocabulary substituted — every deviation (primary lookup, custom-hook gate, and step 1's Django-6.0 `column`-*value* correction + MTI `parent_link` exclusion) tightens semantics without changing the contract; everything else load-bearing (Q-shape, manager choice, guard lifecycle) is ported verbatim because it is the proven, cookbook-documented behavior the card requires. The single-column-scope *invariant* is upstream's, but its second predicate is corrected for Django 6.0 (`getattr(field, "column", None) is not None`, not the upstream `hasattr` — step 1), so the scope test itself is *not* a verbatim port.

### Alternatives considered (and rejected)

- **Walking `registry.iter_definitions()` and matching definitions back to the model's fields.** Rejected: inverts the lookup direction for no gain — the model's `_meta.get_fields()` is the authoritative edge list, and the keyed `get(model)` is O(1) per edge over the same store the card's named surface iterates.
- **Resolving targets through each definition's relation metadata instead of `model._meta`.** Rejected: the cascade must see *model* edges, not *selected* edges — a [`Meta.fields`][glossary-metafields]-excluded FK still joins rows to a hidden target, and visibility is a row property, not a selection property. (Whether an *unexposed* edge should cascade when its target type exists is pinned as an edge case below: it does — same reasoning.)
- **Calling every target's `get_queryset` unconditionally (upstream behavior).** Rejected: identity hooks generate `__in (SELECT pk FROM target)` clauses that constrain nothing and cost real SQL; `has_custom_get_queryset()` is the package's existing, tested sentinel for exactly this distinction (the optimizer's downgrade rule rides it).
- **A finalize-time precomputed cascade plan per type.** Rejected: the walk reads only stable post-finalize state, but `fields=` is a call-site argument and the hook outcomes are request-scoped; precomputing buys one loop over `get_fields()` per call at the cost of a cache layer with invalidation semantics. Measure first ([Risks and open questions](#risks-and-open-questions)).

### Changes this Decision underwent

- **Revision 1** ported the four upstream invariants (cycle guard, single-column scope, nullable preservation, alias pinning) and substituted the package's registry primary lookup and `has_custom_get_queryset()` gate for upstream's graphene registry and unconditional target call.
- **Revision 5 (MTI, MED)** added the third scope predicate — `not getattr(field.remote_field, "parent_link", False)` — after verifying that a multi-table-inheritance `<parent>_ptr` `OneToOneField(parent_link=True)` otherwise passes the two-predicate test. MTI-parent cascade is a deferred opt-in extension.
- **Revision 7 (H1)** retired a false claim this Decision's own justification made. It had listed the scope test among the invariants "ported verbatim," which contradicts step 1: the second predicate is a required Django-6.0 correction (`getattr(field, "column", None) is not None`, because `ManyToManyField` and `GenericRelation` expose a `column` attribute whose value is `None`), not a verbatim port of upstream's `hasattr(field, "column")`. The justification below carries the corrected wording.
- **Post-ship (`c68aecab`, `feat(permissions): harden cascade visibility graph, fail-closed on every SQL boundary`, 2026-07-16):** the walk was hardened on five contract points at once, each a place the `0.0.10` shape failed *open*. The commit's own message enumerates them and `docs/README.md` was updated with it; only the archived spec was left behind, which is why the divergence survived four releases.
  - **The scope predicate.** The Decision stated a three-predicate test (`related_model` present AND a non-`None` `column` AND NOT `parent_link`). The shipped predicate is `isinstance(field, models.ForeignKey) and getattr(field, "column", None) is not None`. The `isinstance` test is the forward-concrete one and subsumes the `related_model` check; it also makes the Django-6.0 `column`-value argument moot for M2M and `GenericRelation` (neither is a `ForeignKey`), leaving the `column` check as a guard against a future non-single-column `ForeignKey` shape. Revision 7's carefully-argued `hasattr`-vs-value correction is therefore no longer load-bearing, though the value test it produced survives.
  - **MTI parent links cascade.** Revision 5 added the `parent_link` exclusion and recorded MTI-parent cascade as a *deferred opt-in extension*. It shipped as the default instead, for the reason the exclusion overlooked: excluding the edge leaves a hidden MTI parent reachable through its child type, which is the leak the row-exclusion contract exists to close. The `test_mti_parent_link_edge_excluded` pin is now `test_mti_parent_link_edge_included`, with three further row-level pins.
  - **`GenericForeignKey` and composite forward relations preflight closed.** The Decision and the edge cases described both as *skipped by construction*, alongside M2M. The distinction the shipped walk draws is whether skipping can hide a leak: a `GenericRelation` selects no parent row's single target and stays skippable, but a GFK (and any composite / multi-column `ForeignObject`) *is* a forward relation selecting one target row, so skipping it lets a row pointing at a hidden target survive. Both are now **unsupported**: a full walk over a model carrying one raises before any hook runs, and naming one in `fields=` raises at validation with a dedicated message.
  - **The `__isnull` disjunct became conditional.** The Decision composed `Q(__in) | Q(__isnull=True)` unconditionally; the shipped walk adds the disjunct only when `field.null`. This narrows the emitted SQL for a non-nullable edge and leaves the nullable-preservation invariant untouched.
  - **Cycles fail closed.** The Decision's step 5 returned the queryset un-narrowed on re-entry (`partial narrow, never a raise`) — the upstream contract, ported verbatim. Re-entry now raises a path-rich `ConfigurationError`, because a silently-broken cycle skips the re-entered type's *outgoing* visibility edges, so a root row whose hidden relation was only reachable through the re-entry could survive. The one permitted re-entrant shape is an explicit zero-edge scope (`fields=[]`), which walks nothing and is therefore provably non-recursive. Reverting the boundary to the contract this Decision stated fails five rows in `tests/test_permissions.py`, measured. **This sentence had eight homes in three grammars** across the Slice checklist, Goals, Error shapes, this Decision, three edge-case bullets and the parity prose (`never a raise` ×2, `partially-narrowed` ×3, `partial narrow` ×1); a grep for any one spelling misses the others, and all eight are now the fail-closed contract.
  - **The mechanism is no longer a seen-set.** The `ContextVar` holds a frozen `_TraversalState` (root alias, active-type tuple, edge-path frames), named `_cascade_state`; upstream's `_cascade_seen` name appears nowhere in the source. The Slice checklist's "the upstream `_cascade_seen` shape verbatim" was the sharpest instance and is retired; `seen-set` had 16 occurrences in the spec.
- **Post-ship — the recorded rejected alternative was re-adopted, for a reason the original deliberation did not weigh.** "Calling every target's `get_queryset` unconditionally (upstream behavior)" is rejected above on dead-SQL grounds, and step 3 shipped a `has_custom_get_queryset()` gate. `c68aecab` removed the gate: **every registered target composes**, identity hooks included. The reason is not that the dead-SQL argument was wrong — it is that the gate is a *visibility* decision wearing an optimization's clothes. A registered proxy type whose filtered `_default_manager` **is** its visibility policy declares no custom hook, so the gate silently bypassed that policy. Registration, not hook declaration, is the visibility contract. The alternative was re-adopted on a security argument the dead-SQL deliberation never reached, so it is not a case of the rejection having been wrong on its own terms.
- **Post-ship (`1dd9273a` / `60998b17`, the sealed visibility boundary, documented after the fact by [`spec-045-visibility_boundary-0_0_14.md`][spec-045]):** two contracts this Decision never had. **(a)** The root is validated and *rebuilt* through the shared boundary before any `.filter(...)` — the helper is called from inside a consumer-owned hook, so its root argument is untrusted query state, and a consumer `QuerySet` subclass (or an instance-shadowed `filter`) must not be able to erase the cascade predicate. The cascade therefore returns a framework-owned plain `QuerySet`, and sliced and combined roots are rejected. **(b)** The per-edge hook invocation moved out of `permissions.py` into `utils/querysets.py::apply_type_visibility_sync`, behind the cascade's `_edge_error_renderer` / `_root_error_renderer` seams, so the package has one owner of the hook-result shape / concrete-table / alias contract and the cascade keeps its own prose on every failure. The spec now states both under step 4 and the root-sealing paragraph.
- **Post-ship (`c68aecab`, `90d1cf14`, `60998b17`) — the hook-return contract inverted.** [Edge cases][spec-034-edge-cases]' **Cascade-target hook return contract** bullet said the cascade "does not defensively rewrite the hook's return (a hook returning a non-row queryset is a consumer bug ... not silently absorbed)", with four worked examples. Returns are now validated and normalized: sliced, combined, grouped, field-`distinct(...)` and target-column-shadowing returns each fail closed with their own message, and everything accepted is re-projected to `.values(field.target_field.attname)`. Two of the bullet's own worked examples became wrong in opposite directions — a `.values("col")` return no longer silently mis-compares (it is re-projected) and a multi-column `.values()` no longer raises `ValueError`. The alias-shadow guard is `90d1cf14`'s and carries its own security argument: Django blocks a bare `annotate(id=Value(pk))` but permits `values("x").annotate(id=Value(pk))`, which stays ungrouped and would otherwise re-project to the injected constant and let a row pointing at a hidden target survive.
- **Post-ship (`bc1a6aaf`, reshaped by `c68aecab`) — a second recorded rejected alternative was adopted, in the lazy form its objection did not weigh.** "A finalize-time precomputed cascade plan per type" is rejected above because precomputing "buys one loop over `get_fields()` per call at the cost of a cache layer with invalidation semantics. Measure first." `HEAD` ships that cache layer: [`permissions.py::_edge_plan`][permissions] is `@lru_cache(maxsize=1024)` over `model._meta.get_fields()`, shared by `fields=` validation, the unsupported-edge preflight and the walk. Of the rejection's two premises only one gave way. The **finalize-time** half stands and is why the shipped shape is not what was rejected: the plan is built lazily on first use, so no type-construction step has to know about it and a model the cascade never reaches is never classified. The **invalidation** half dissolved: what is cached is Django model metadata, immutable after app loading, so there is nothing to invalidate; the size cap exists only to stop synthetic and dynamically-built test models growing a process-wide helper without limit, and eviction is correctness-neutral because the plan can always be recomputed. The helper's own docstring states both. What the rejection correctly protected is still protected — `fields=` is a call-site argument and hook outcomes are request-scoped, so neither is cached; the memo holds the metadata slice and nothing else. "Measure first" was not overridden so much as overtaken: `bc1a6aaf` landed the memo on `_cascadable_edges` the same day the card's last review revision closed, `c68aecab` widened it into `_edge_plan` so the unsupported-edge preflight could share the same slice, and the [Risks](#risks-and-open-questions) item that recorded the memo as deferred went on saying so for four releases.

## Decision 6 — Hidden-FK semantics: row exclusion is the cascade contract; resolver-level nulling stays the relation contract

Spec: [Decision 6 — Hidden-FK semantics: row exclusion is the cascade contract; resolver-level nulling stays the relation contract][spec-034-d6].

### Justification (moved from the spec)

- **Row exclusion is what the upstream cascade does** — the `Q(fk__in=visible) | Q(fk__isnull=True)` filter *is* row exclusion; the cookbook, the [`GOAL.md`][goal] showcase, and the glossary entry all describe this behavior. The card's "the upstream uses sentinels" sentence reads as a reference to graphene-django's *resolver-level* behavior when a relation target is individually hidden (resolve-to-`None` / sentinel at the field), which is a different layer: the cascade decides *which parent rows exist*, the relation resolver decides *what a traversed field returns*. The conflict reading is recorded in [Risks and open questions](#risks-and-open-questions) per the [`docs/SPECS/NEXT.md`][next] rule.
- **Nulling lies about data.** Serving `entry.item: null` for an existing FK teaches clients the row has no item — indistinguishable from genuine `NULL`, corrupting client caches keyed on the relation. Exclusion is honest: the parent is simply not visible *as a whole* when its identity hangs on a hidden target.
- **Sentinels are schema pollution.** A `HiddenItem` sentinel type would have to implement the target interface, appear in unions, and survive Relay refetch — a large, leaky surface for a behavior exclusion provides for free.

Two further justification bullets — **No existence leak** and **The layers stay independent** — were held back in the spec: both state guarantees the shipped contract makes, not arguments against a rejected alternative.

### Alternatives considered (and rejected)

**null-the-FK** and **sentinel** — above. **Making the behavior configurable (`mode="exclude" | "null"`)** — rejected: two security semantics behind a flag doubles the test matrix and invites mode-mismatch bugs between types in one graph; one honest behavior, documented, is the alpha-correct call.

### Changes this Decision underwent

- **Revision 1** pinned row exclusion as the cascade contract and recorded the card's "the upstream uses sentinels" sentence as a layer confusion rather than a conflict.
- **Revision 8** changed the consumer recipe, fixing a runtime bug: the prior `view_<model>` branch returned `queryset.filter(is_private=False)` with no cascade, so a permission user could see a row whose non-null forward FK target the optimizer's `Prefetch` downgrade hides, and selecting that relation raised `RelatedObjectDoesNotExist` on a valid query. Every non-staff branch of the four products hooks now cascades. The **Consumer-recipe divergence** block recording that choice stayed in the spec (see the note under [Provenance of this record](#provenance-of-this-record)).
- **Post-ship (`841e56d6`, `fix(types,optimizer): scope relation visibility per relation and reach strictness in every execution`, 2026-08-18):** the **Consumer-recipe divergence** block's *reason* inverted while its conclusion held. It argued that the package did not port upstream's sentinel tier because `types/resolvers.py::_make_relation_resolver` reads a forward FK "by bare accessor with no `DoesNotExist` / sentinel fallback", citing `#"return getattr(root, field_name)"` — a substring that matches zero occurrences at `HEAD`. The forward-FK branch now routes the read through `types/resolvers.py::_visible_related_object` whenever `types/resolvers.py::_custom_visibility_type` resolves a registered target with a custom hook, so a hidden target *does* resolve to `None` at the field. The conclusion survives on a stronger reason, which the block now states: a **non-null** FK field cannot return `None` without a null violation, so row exclusion at the cascade layer is the only honest shape for such an edge. **No gate could see this**: `scripts/check_citations.py` resolves `path::Symbol` citations in `.py` files and `KANBAN.md` only, so a `path #"substring"` citation inside `docs/` has no mechanical check at all.

## Decision 7 — Cascade performance: lazy subquery composition — zero added round-trips

Spec: [Decision 7 — Cascade performance: lazy subquery composition — zero added round-trips][spec-034-d7].

### Justification (moved from the spec)

lazy composition is upstream's actual design (its docstring's multi-DB note presumes the subquery is compiled into the outer query — "so the outer `__in` stays on a single database"); the "extra round-trip" reading would only be true if the target queryset were evaluated eagerly (e.g. `list(target_qs)`), which neither upstream nor this port does. Recording the correction here, with the query-count pin as proof, is the honest resolution of the open question.

### Alternatives considered (and rejected)

- **A single annotated pass (`Exists()` per edge instead of `__in`).** Not rejected on round-trips (both are single-query) but on fidelity: `__in` against a subquery is the upstream-proven shape with known planner behavior across backends; `Exists()` is the documented *fallback* if real-world nesting depth produces measurably bad plans — recorded in [Risks and open questions](#risks-and-open-questions), not scoped.
- **Eager PK materialization (`pk__in=list(...)`)** — an actual extra round-trip per edge plus an unbounded `IN` list; strictly worse.

### Changes this Decision underwent

- **Revision 1** recorded the card's open-question #2 premise — subquery-per-FK costing one extra round-trip per FK — as a card-premise correction rather than a benchmark gate: lazy `__in` composition compiles into the caller's single query.
- **Revision 2 (L3)** reworded the plan-cache cacheability reason from "reads `info.context.user`" to the coarser shipped rule: any custom `get_queryset` flips the plan uncacheable.
- **Post-ship: that Revision-2 reword never reached [`## Goals`][spec-034-goals] item 3**, which still described a "`cacheable = False` **request-scope** rule" while the [Edge cases][spec-034-edge-cases] plan-cache bullet correctly called the shipped rule "coarser — it flips on the *presence* of a custom hook, not on whether the hook reads `info.context.user`". The two sentences described one rule in two incompatible ways; Goal 3 and the two `## Current state` / `## Key glossary references` sentences carrying the same phrasing now state the custom-hook rule. No code changed — this was a partial application of an accepted correction, which is why it survived the build's own review rounds: every pass that re-read the Decision saw the corrected text.
- **Post-ship: the strictness pin's attribution was wrong, measured rather than reasoned.** The [Edge cases][spec-034-edge-cases] strictness bullet and the Slice 2 checklist read as though `tests/test_permissions.py::test_strictness_raise_silent_across_cascaded_shape` pinned the causal claim "the cascade composes SQL; it cannot lazy-load". It does not: `types/resolvers.py::_check_n1` reports unplanned *relation-resolver* accesses only, so a cascade that began evaluating its target querysets eagerly — the exact regression this Decision's lazy-composition contract exists to prevent — would add queries without making any relation unplanned, and the row would stay green. Established by mutation, not by reading: `_check_n1` carries two independent silencers (the planned-key short-circuit and the already-loaded probe) and removing either alone leaves the row passing; removing both fails it with `OptimizerError: Unplanned N+1: category`. So the row is a live detector of an **optimizer-planning** regression in the composed shape, and the zero-round-trip property is pinned separately and correctly by `test_cascaded_traversal_adds_zero_queries`'s absolute `django_assert_num_queries(1)`. Both spec sentences now say which pin carries which property. No code or test changed.

## Decision 10 — Sync/async contract: `SyncMisuseError` on async hooks from the sync walk; the async variant wraps the walk in `sync_to_async`

Spec: [Decision 10 — Sync/async contract: `SyncMisuseError` on async hooks from the sync walk; the async variant wraps the walk in `sync_to_async`][spec-034-d10].

### Justification (moved from the spec)

the card pre-pins the `sync_to_async` design ("async variant uses `sync_to_async` around the cascade walker to stay event-loop-safe") — per the [`docs/SPECS/NEXT.md`][next] rule it is preserved as the Decision, and it is independently right: one walk implementation (no sync/async fork to drift), thread-sensitive execution (ORM-legal under Django's async rules), and the only capability it forgoes (awaiting async hooks) is one no shipped pipeline grants to nested targets either.

### Alternatives considered (and rejected)

- **Async-native walk awaiting async hooks edge-by-edge** (`apply_type_visibility_async` per edge). Rejected for `0.0.10`: forks the walk into two implementations around a capability with no demonstrated consumer (no fakeshop type has an async hook; the package's async-hook story is uniformly "sync paths raise `SyncMisuseError`, dedicated async paths await") — and a *mixed* graph (sync parent hook calling the sync helper, async target hook below it) still dead-ends, because the cascade is invoked from inside sync `get_queryset` bodies. The real unlock is an async-hooks-everywhere story, which is bigger than this card.
- **Wrapping each hook call individually instead of the whole walk.** Rejected: N thread hops per request instead of one; the walk is short and the wrap's purpose (off-loop execution of blocking hook code) is served strictly better by one hop.

## Decision 11 — The existing `check_<field>_permission` filter/order gates survive unchanged

Spec: [Decision 11 — The existing `check_<field>_permission` filter/order gates survive unchanged][spec-034-d11].

### Justification (moved from the spec)

- **Post-ship: the Cascade-call overhead on hot paths item priced a loop that no longer runs per call, and recorded as deferred a fallback that had already shipped.** Its cost premise read "one `get_fields()` loop plus set ops" per `get_queryset` invocation, and its fallback — a walk-result memo over the edges — read "deferred per the measure-first discipline". Both are false at `HEAD`: [`permissions.py::_edge_plan`][permissions] classifies `model._meta.get_fields()` once per model behind `@lru_cache(maxsize=1024)`, so the per-call work is set ops over that cached plan. Corrected in place, keeping the two things the item still gets right — the querysets half of the fallback did not ship and cannot, because hook outcomes are request-scoped; and the per-`(model, fields)` keying the item names is still the form that would absorb the `fields=` validation's own per-call set diff, which is what [Decision 9][spec-034-d9]'s held-back closing sentences point at from the spec. The change belongs to no single Decision: the memo is Decision 5's rejected alternative 4 arriving (recorded there too) and its cost premise is this item's, so the correction spans both. It stayed unnoticed for a structural reason worth naming — the conformance cohort that read `_edge_plan` was grading the spec, and by the time it ran, both falsified sentences had already left the spec for this file.
