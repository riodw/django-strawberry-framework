# Rationale companion: spec-036 (Mutations — the `DjangoMutation` write-side foundation)

Companion to [`docs/SPECS/spec-036-mutations-0_0_11.md`][spec-036]. It carries that spec's **deliberative layer** and nothing else: the five-revision review history that produced the contract, every Decision's justification, every alternative a Decision rejected and why it lost, and the risk / open-question deliberation that settled the card's design questions. The spec carries the contract; this file carries how the contract was arrived at. Neither duplicates the other — the text here **left** the spec.

Read this when checking a finished implementation against the reasoning that produced it, or before re-opening a settled question. Worker 2 never reads it ([`docs/builder/BUILD.md`][build-md] `### Who reads it, and when`).

**How later passes append to this file.** Each Decision below carries a `### Changes this Decision underwent` section. A reconciliation pass that finds the spec stale against `HEAD` — a guard that shipped differently, a helper that never landed where the Decision said it would, a default a later card inverted — appends a `**Post-ship:**` bullet there, naming the shipped behavior and the card or commit that changed it. Findings belonging to no single Decision go under [Non-Decision deliberation](#non-decision-deliberation). Nothing needs restructuring to take an addition, and the corrections themselves always land in the spec, stated directly and without chronology.

## Decision 2 — Card-scope boundary: the mutation foundation ships; the flavor cards and uploads are out; the `FieldError` envelope is defined here

Spec: [Decision 2 — Card-scope boundary: the mutation foundation ships; the flavor cards and uploads are out; the `FieldError` envelope is defined here][spec-036-d2].

### Justification (moved from the spec)

the card is XL and the form / serializer / upload flavors are separately carded with their own `0.0.12` / `0.0.13` / `0.0.11` targets — pulling any forward would bloat the slice exactly as [`START.md`][start]'s scope-creep rule warns. The base + envelope + model-driven operations are the irreducible foundation the flavors all subclass.

### Alternatives considered (and rejected)

- **Ship the form flavor in this card too** (it is "close").** Rejected: `DjangoFormMutation` is its own `0.0.12` card with its own DoD; the form-validation-to-`FieldError` mapping is a distinct slice, and the base must exist first.
- **Defer the `FieldError` envelope to the first flavor card.** Rejected: the card DoD pins it here precisely so the flavors reuse it unchanged; deferring it forks the contract.

### Changes this Decision underwent

- **Revision 1** pinned the scope boundary — the model-driven foundation ships, the upload / form / DRF-serializer flavors stay on their own cards — and froze the `FieldError` envelope here for the downstream flavors. The scope boundary held; the freeze did not, and the upload seam was consumed — both recorded below.
- **Revision 3** did not change the boundary but widened what is frozen here: write authorization became a first-class `0.0.11` contract the flavor cards inherit ([Decision 15](#decision-15--write-authorization-a-drf-shaped-check_permission--metapermission_classes-seam)) alongside the envelope.

- **Post-ship:** the envelope is **not** frozen, and the spec no longer says it is. `codes: list[str]` and `path: list[str]` were added to `django_strawberry_framework/mutations/inputs.py::FieldError` by commit `951945b7` (2026-07-01; `__version__` was `0.0.12` at that commit and its diff carries `docs/spec-039-serializer_mutations-0_0_13.md`, so the owner is the DRF-serializer flavor card [`DONE-039-0.0.13`][kanban]). Both default to `[]`, so a client selecting only `field` / `messages` is unaffected. What survives — and what the spec now states — is that exactly **one** `FieldError` class exists package-wide and every flavor imports it, extensible only by an additive, default-empty field. The words "frozen" and "byte-identical" are retired from this Decision, from the spec preamble, from Decision 7, and from the [User-facing API][spec-036-user-facing-api] SDL block. Note for a later reader: the `0.0.14`-hardening attribution one conformance cohort offered for this change is wrong; the commit predates `0.0.14` by two months and belongs to `039`.

The Decision now says the seam is filled rather than reserved; the consequence for Decision 6's CR-6 carve-out is recorded there.
- **Post-ship:** nested **serializer** inputs shipped at `0.0.13` ([`DONE-039-0.0.13`][kanban], `django_strawberry_framework/rest_framework/inputs.py::NestedSerializerConfig`) as a descriptor-keyed opt-in, so the spec's `## Out of scope` nested-writes clause was split: nested serializer inputs are the serializer flavor's, bulk / batch mutations remain out.

## Decision 3 — `class Meta` surface, not decorators: borrow the capabilities, reject the decorator surface

Spec: [Decision 3 — `class Meta` surface, not decorators: borrow the capabilities, reject the decorator surface][spec-036-d3].

### Justification (moved from the spec)

this is the package's defining surface contract, stated verbatim in [`START.md`][start] — "Meta classes everywhere on consumer surfaces. If you find yourself writing stacked Strawberry decorators on a consumer-facing class, stop. That is the strawberry-graphql-django API and the explicit reason this package exists." [`GOAL.md`][goal]'s `1.0.0` showcase and DRF-migration diff both spell the write surface as `class CreateCategory(DjangoMutation): class Meta: ...`. The *capabilities* of upstream's decorators (operations, input generation, error capture, optimizer return) are borrowed at the outcome level ([Borrowing posture][spec-036-borrowing-posture]); the decorator mechanism is not.

### Alternatives considered (and rejected)

- **strawberry-django's `create(InputType)` field-verb factories.** Rejected: that *is* the decorator-adjacent surface the package replaces; it also requires the consumer to hand-declare the input type (`@strawberry_django.input`), re-introducing the duplicate-field burden.
- **A `@django_mutation` class decorator** (Meta-shaped config, decorator trigger). Rejected: a decorator on a consumer class is exactly the shape [`START.md`][start] forbids; the base-class form is uniform with `DjangoType` / `FilterSet` / `OrderSet`.

### Changes this Decision underwent

- **Revision 1** pinned the `class Meta` surface and rejected both decorator shapes. Nothing later reopened it.

## Decision 4 — Module and test locations: `mutations/` subpackage mirroring `filters/` / `orders/`

### Justification (moved from the spec)

the card predicts `django_strawberry_framework/mutations/` and `tests/mutations/`; the set-family precedent ([`spec-027`][spec-027] / [`spec-028`][spec-028] Decision 2) is the proven shape for a declarative `class Meta` subsystem with generated input classes and finalizer binding. ### Alternatives considered (and rejected)

- **A flat `mutations.py` module** (like [`permissions.py`][permissions]). Rejected: permissions is two functions; mutations is generation + a metaclass + a resolver pipeline + a field factory + downstream-flavor extension points — a subpackage matches the surface, and the card itself predicts `mutations/`.

The Decision contradicted its own document from the day it shipped; the module list is now five, and `permissions.py` is named with its content (`DjangoModelPermission` plus the shared permission-class walk).

The Decision now names the two files that hold it. The stranded anchor is a source-side repair, not a spec edit.

## Decision 5 — Public surface: `DjangoMutation` base + `DjangoMutationField` factory + `FieldError`, exported from the root

Spec: [Decision 5 — Public surface: `DjangoMutation` base + `DjangoMutationField` factory + `FieldError`, exported from the root][spec-036-d5].

### Justification (moved from the spec)

- **Factory uniformity, with a timing-forced annotation exception.** Every root field the package ships is a factory assigned to a class attribute; `DjangoMutationField` keeps the write side idiomatic with the read side rather than introducing a `.Field()`-style classmethod (graphene-django's shape) or a decorator (strawberry-django's). The one difference is forced by timing, not style: the read-side factories read a consumer annotation that names a type existing at import (`DjangoConnection[CategoryType]`), but the mutation payload is **generated at finalization** ([Decision 12](#decision-12--finalization-seam-register-at-class-creation-bind-at-phase-25-no-deferred_meta_keys-change)) and has no importable name when `@strawberry.type class Mutation` evaluates its annotations — so `DjangoMutationField` carries no class-attribute annotation and types the field itself via a `strawberry.lazy` forward-ref to the generated `<Name>Payload` ([Decision 7](#decision-7--the-shared-fielderror-envelope-and-the-payload-wrapper)).
- **Root export matches the audience.** `DjangoMutation` and `DjangoMutationField` are used in every schema that writes; `FieldError` is referenced in every payload — all belong at the root alongside [`DjangoType`][glossary-djangotype] / [`finalize_django_types`][glossary-finalize_django_types], parallel to how [`apply_cascade_permissions`][glossary-apply_cascade_permissions] ([`spec-034`][spec-034] Decision 4) is root-exported.
- **One `operation` key over three base classes.** A single nested-`Meta` key driving behavior is the most `class Meta`-idiomatic shape (it parallels `filterset_class` / `globalid_strategy` selecting behavior through one key), and keeps the public symbol count at three.

### Alternatives considered (and rejected)

- **Three base classes `DjangoCreateMutation` / `DjangoUpdateMutation` / `DjangoDeleteMutation`.** Rejected: triples the public symbol surface for what one `Meta.operation` selector expresses; graphene-django itself routes all operations through one `ClientIDMutation` lineage with `model_operations`.
- **A `.field()` classmethod accessor on the mutation class** (graphene-django's `.Field()`, `create_item = CreateItem.field()`). Rejected: the no-annotation `DjangoMutationField` form already resolves the payload-timing hazard ([Decision 7](#decision-7--the-shared-fielderror-envelope-and-the-payload-wrapper)) while keeping the single factory symbol, so a `.field()` accessor would add a second exposure idiom for no gain. It remains the fallback if Strawberry rejects a no-annotation factory assignment ([Risks](#risks-and-open-questions)).
- **Exporting only from a `django_strawberry_framework.mutations` namespace.** Rejected: the symbols are used inside schema modules alongside root-exported types; subsystem-namespace imports are for *family* surfaces (`from .filters import FilterSet`), as [`spec-034`][spec-034] Decision 4 settled for the cascade helper.

### Changes this Decision underwent

- **Revision 1** pinned the base + field factory + `FieldError` public surface and the single `Meta.operation` selector.
- **Revision 2 (Major-3)** committed the payload exposure surface to a **no-annotation** `DjangoMutationField` typed through a `strawberry.lazy` forward-ref, resolving what had been an open Risks question: an eager `CreateItem.Payload` annotation cannot exist when `@strawberry.type class Mutation` evaluates its annotations at import.
- **Revision 2 (Medium-5)** added the `_resolve_model(meta)` forward-compat seam, so the `0.0.12` form and `0.0.13` serializer flavors — whose [`GOAL.md`][goal] declaration omits `Meta.model` — supply a model without re-opening the base validation.
- **Revision 3 (AR-H3)** added `DjangoModelPermission` as the fourth net-new public symbol when write authorization became a first-class contract ([Decision 15](#decision-15--write-authorization-a-drf-shaped-check_permission--metapermission_classes-seam)). **The justification above went stale in one numeral and was moved as written:** its "One `operation` key over three base classes" bullet still says the choice "keeps the public symbol count at three", while the Decision body it argues for states four. The argument stands — one selector key against three per-operation base classes — and only the count is wrong; it is recorded here rather than silently repaired inside moved text.
- **Revision 4 (CR-2)** softened this Decision's example wording from wholesale replacement to **merge**: a consumer `Meta.input_class` declares only the fields it customizes and the generator fills the editable remainder (the [`spec-010`][spec-010] relation-override contract).

- **Post-ship:** `select_for_update` is an accepted mutation `Meta` key, making the enumeration eight rather than seven. It entered `django_strawberry_framework/mutations/sets.py` as a serializer-flavor key at commit `951945b7` (2026-07-01) and was promoted to every model-backed flavor, `DjangoMutation` included, by commit `1b06c39e` "span mutation transactions through response completion (BETA-055)" (2026-07-15), which added `::validate_select_for_update`. The spec now names the key, its `True` default, and the class-creation rejection of a non-bool; its full lock semantics belong to the `0.0.14` write hardening, which has no owning spec (see [Non-Decision deliberation](#non-decision-deliberation)).
- **Post-ship:** `FieldError` carries four fields rather than two; the shape is recorded under Decision 2 and Decision 7. Decision 5's bullet listing the public symbol now states all four field names.
- **Post-ship:** the operation vocabulary this Decision inlines is derived at `django_strawberry_framework/mutations/operations.py::_VALID_OPERATIONS` from the descriptors' `supports_model_mutation` flag (commit `7ff97021`). The three literal values are unchanged, so the spec keeps them for readability and adds the symbol citation.

## Decision 6 — Auto-generated `Input` / `PartialInput` types

Spec: [Decision 6 — Auto-generated `Input` / `PartialInput` types][spec-036-d6].

### Justification (moved from the spec)

input generation is the card's headline parity item ([`GOAL.md`][goal] success-criterion 6); reusing the read-side converters guarantees the symmetric wire contract the package's "one configuration surface" pitch promises; the stable-naming + materialize-before-`Schema` discipline is the proven set-family lifecycle ([Decision 12](#decision-12--finalization-seam-register-at-class-creation-bind-at-phase-25-no-deferred_meta_keys-change)).

### Alternatives considered (and rejected)

- **A single `Input` with all-optional fields for both create and update.** Rejected: it loses the create-required contract (a missing required field would only fail at `full_clean()`, not at the GraphQL layer); upstream and graphene-django both keep the required/partial split.
- **FK input as the nested object (strawberry-django's `ParsedObject` connect/create).** Rejected: nested writes are an explicit non-goal for `0.0.11` ([Out of scope][spec-036-out-of-scope]); `<field>_id` is the minimal, unambiguous shape.
- **Reuse the `DjangoType` output type as the input.** Rejected: GraphQL forbids an output type in input position; the input is a distinct `@strawberry.input` type with id-shaped relations.

### Changes this Decision underwent

- **Revision 1** pinned auto-generated `Input` / `PartialInput` derivation and the relation-override obligation.
- **Revision 2 (Major-1 + Medium-4)** moved the field set off the read-side [`DjangoType`][glossary-djangotype] selection and onto the model's **editable** fields, and made create-input required-ness follow Django's `default` / `blank` / `null` rather than a blanket "every editable field required" rule. The blanket rule's rejection is recorded in the Decision body itself, since it is the reason the shipped rule has the shape it has.
- **Revision 3 (AR-H1 / AR-M6)** made a generated input type's identity its **complete shape** — `(model, operation kind, frozenset(effective field names))` — reserved the stable `<Model>Input` / `<Model>PartialInput` names for the canonical full editable shape, gave narrowed shapes deterministic shape-derived names, and made a name clash between distinct shapes a finalize-time [`ConfigurationError`][glossary-configurationerror].
- **Revision 3 (AR-M2)** pinned that a custom `input_class` must follow the generated field-naming scheme, and **(AR-M1)** made an M2M field always optional even in the create input (a parent row cannot carry M2M rows before it has a pk).
- **Revision 4 (CR-2)** realized `Meta.input_class` / `Meta.partial_input_class` as the [`spec-010`][spec-010] relation-override **merge** rather than wholesale replacement, wiring the `overrides` seam Slice 1 had built and left dead.
- **Revision 4 (CR-6)** pinned file / image columns as the one exception to the merge override: the generator raises `NotImplementedError` *before* consulting the override set, so a file column leaves the write surface only via `Meta.exclude`.
- **Revision 5 (DRY-1)** single-sourced the shape identity (selected fields, full field set, effective-name frozenset, generated type name, build-cache key) in one `mutations/inputs.py::mutation_input_shape` descriptor, so the bind cache key can no longer drift from the generated name. No contract change.

- **Post-ship:** the CR-6 file/image carve-out is gone. `django_strawberry_framework/mutations/inputs.py::model_column_write_annotation` maps a `FileField` / `ImageField` to the [`Upload` scalar][glossary-upload-scalar] as a scalar-kind input, and a file column rides the same override-skip, requiredness, and nullability tail as any other scalar — no `NotImplementedError`, and a consumer override of a file column is honoured (`tests/mutations/test_inputs.py::test_file_field_consumer_override_skips_generated_upload_field`). Attribution: [`DONE-037-0.0.11`][kanban], commit `66d01b4a`, recorded in the generator's own docstring.
- **Post-ship:** a relation override is **type-locked** as well as name-locked (`django_strawberry_framework/mutations/sets.py::_validate_relation_override_types`, commit `70d60d4a`). AR-M2 as written constrained only field *names*, so a consumer could follow it to the letter and still be rejected — and, worse, a name-only check let `category_id: int` through, routing the value down the raw-pk path and past both the relation type-check and the visibility confirmation. The spec now states both axes, because the `## User-facing API` promise that a permitted writer can never attach a row they could not see rests partly on this validator.
- **Post-ship:** the input naming and construction mechanics moved to the flavor-neutral `django_strawberry_framework/utils/inputs.py` (`::pascalize_token`, `::name_set_input_type_name`, `::generated_input_type_name`, `::build_strawberry_input_class`, `::materialize_generated_input_class`, `::make_input_namespace`, `::optional_input_field`, `::iter_input_field_collisions`, `::InputFieldSpec`, and the decode-kind constants), leaving `mutations/inputs.py` the domain wrapper that owns the editable-column selector, the required rule, the relation naming scheme, the payload builder, and `FieldError`. Attribution: `spec-039`'s `P2.2` / `P2.3` / `Md5` promotions, named in the moved code's docstrings. Decision 4's module bullet now names the shared owner.

## Decision 7 — The shared `FieldError` envelope and the payload wrapper

Spec: [Decision 7 — The shared `FieldError` envelope and the payload wrapper][spec-036-d7].

### Justification (moved from the spec)

- **The card pins the graphene-django shape.** "Shape mirrors graphene-django's `ErrorType` (field name + list of message strings)"; the payload-with-`errors` surface is graphene-django's `DjangoModelFormMutation` / `SerializerMutation` shape, so the `0.0.12` / `0.0.13` flavors attach the identical `errors` field unchanged.
- **Partial-success representability.** A payload that carries both the object and errors can express "created, with warnings" or "no object, here are the errors" in one type; a disjoint union cannot.

### Alternatives considered (and rejected)

- **strawberry-django's disjoint `Type | OperationInfo` union return.** Rejected: `OperationInfo` is a flat `list[OperationMessage]` (each message carries an optional `field`, but it is **not** the field-keyed `errors: list[FieldError]` shape the card pins); the card pins the graphene-django `ErrorType` shape, and a disjoint union cannot host the shared `errors: list[FieldError]` field the flavor cards reuse.
- **Raising `GraphQLError` for validation failures** (errors in the top-level `errors` array). Rejected: loses the field-keyed structure clients need to attach messages to form fields, and conflates expected validation failures with execution errors.

### Changes this Decision underwent

- **Revision 1** pinned the graphene-django `ErrorType`-shaped `FieldError` and the payload-with-`errors` wrapper, rejecting the disjoint-union return.
- **Revision 2 (Major-3)** pinned the payload exposure timing: `<Name>Payload` materializes at finalize phase 2.5, after `@strawberry.type class Mutation` has evaluated its annotations, so the field carries no class-attribute annotation and types itself through a `strawberry.lazy` forward-ref.
- **Revision 3 (AR-H5)** made the payload's object field a **uniform slot** — `node` for a Relay-Node target, `result` otherwise — never model-derived, so a `Property` -> `property` collision cannot arise.
- **Revision 3 (AR-M6)** extended the distinct-shapes-same-name finalize-time error from inputs to generated payload names, and **(AR-M3)** pinned the non-field bucket to Django's own `"__all__"` sentinel rather than an ad-hoc empty string.

- **Post-ship:** the type carries `codes: list[str]` and `path: list[str]` beside `field` / `messages`, both additive and default-empty (commit `951945b7`, [`DONE-039-0.0.13`][kanban]). `codes` carries structured codes (a DRF `ErrorDetail.code`, a Django `ValidationError.code`, or a framework code — `invalid` for a bad relation id, `null` for an explicit null, `not_found` for a locate miss, `constraint` for the integrity fallback); `path` is the `field` string split into segments, with a **root** non-field error keeping `field="__all__"` and an **empty** `path` while a **nested** one keeps its segments. Decision 7 now states the four-field shape and that rule, and the freeze language is gone (Decision 2).
- **Post-ship:** the envelope **constructors** were promoted out of `mutations/resolvers.py` into the flavor-neutral `django_strawberry_framework/utils/errors.py` (`::validation_error_to_field_errors`, `::field_error`, `::relation_field_error`, `::integrity_error_field_errors`, `::join_error_path`) so the form, serializer, and auth flavors populate one envelope through one code path. Attribution: the `spec-039` integration, named in that module's own docstring. Decision 7 now names the constructor owner; the type itself stays in `mutations/inputs.py`, and whether it should is an open ownership question recorded in the reconciliation artifact.
- **Falsified prediction, removed rather than dated:** the `.field()`-classmethod fallback ("if Strawberry rejects a resolver-typed field with no class annotation"). Strawberry accepted it, the `strawberry.lazy` forward-ref form shipped, and no `.field()` classmethod exists on the mutation base. The sentence and its pointer into the moved [Risks and open questions](#risks-and-open-questions) deliberation are deleted from the spec; the contingency survives only in the Risks item here.

## Decision 8 — Resolver pipeline: decode → `full_clean()` → write → optimizer re-fetch → payload (sync and async)

Spec: [Decision 8 — Resolver pipeline: decode → `full_clean()` → write → optimizer re-fetch → payload (sync and async)][spec-036-d8].

### Justification (moved from the spec)

`full_clean()` is the Django-native validation entry strawberry-django uses; routing its errors into the envelope (rather than raising) is the graphene-django contract; the re-fetch step is where optimizer composition lives; the single-`atomic()` / single-`sync_to_async` boundary keeps the write reasonable under concurrency. A sync path meeting an `async def get_queryset` raises [`SyncMisuseError`][glossary-syncmisuseerror] (coroutine closed first), the package's standing async-misuse discipline.

### Alternatives considered (and rejected)

- **Skip `full_clean()` and rely on DB constraints.** Rejected: loses field-level validation messages and defers errors to opaque `IntegrityError`s; upstream and DRF both validate before write.
- **A single dual-mode resolver that returns a coroutine when needed.** Rejected: the caller must know whether to await; the construction-time sync/async split is the package's settled shape ([`DjangoListField`][glossary-djangolistfield]).
- **No transaction / per-call `sync_to_async` hops on the async path (AR-M4).** Rejected: a write, its relation assignments, and the payload snapshot separated by `await`s are not atomic and are hard to reason about under concurrent requests; one `atomic()` inside one `sync_to_async(thread_sensitive=True)` is the defensible foundation.

### Changes this Decision underwent

- **Revision 1** pinned the sync and async pipeline: decode -> `full_clean()` -> write -> optimizer re-fetch -> payload.
- **Revision 2 (Major-2)** made the unique-constraint create error a `full_clean()` / `validate_constraints()` `ValidationError` (Django 4.1+, package floor `>=5.2`) and demoted `IntegrityError` to a documented concurrent-race fallback; **(Medium-2)** made `delete` load its response-selection relations *before* `delete()`, because the optimizer plans querysets rather than instances; **(Medium-3)** made partial update validate with `full_clean(exclude=<unprovided>)`.
- **Revision 3 (AR-H2)** narrowed that `exclude`: an unprovided field that co-participates in a uniqueness check with a *provided* field is never excluded, so a `name`-only update still validates `unique_item_per_category`. **(AR-H4)** made relation `GlobalID` decode type-checked against the target model — a wrong-model id is a relation `FieldError`, never a cross-model pk lookup. **(AR-M4)** put steps 3-6 inside one `transaction.atomic()` and the async path inside a single `sync_to_async(thread_sensitive=True)` call. **(AR-M5)** made the delete snapshot fully materialize nested and connection-child relations inside that transaction. **(AR-M1)** pinned M2M write as replace-on-provide / clear-on-empty / unchanged-on-omit through the target default manager.
- **Revision 4 (CR-1)** coerced a well-formed `GlobalID` whose `node_id` is not a valid pk literal through the pk field via the shipped `relay.py::_coerce_pk_or_none` **before** any lookup, so an uncoercible literal is the in-band `FieldError` rather than a raw Django `ValueError` surfacing as a top-level `GraphQLError` and leaking the pk column type. **(CR-3)** generalized the save-time `IntegrityError` fallback message to "A database constraint was violated." — the catch is broader than the `UniqueConstraint` race, so the prior "uniqueness" claim over-reached — and dropped the no-op `model` / `provided_attrs` params. **(CR-4)** documented that relation decode runs **after** Authorize for `create` / `update`, which is strictly better: an unauthorized caller triggers no relation visibility query and gets no field-level decode feedback.
- **Revision 5 (DRY-2 / DRY-3)** single-sourced the typed-`GlobalID` decode + model-check + pk-coercion contract as a non-raising `relay.py::decode_model_global_id` primitive consumed by both the root and the relation paths, and extracted the identical create / update write-finalization tail to `_validate_save_assign_refetch_payload`. No contract change.

- **Post-ship:** the transaction boundary changed in extent, owner, and failure surface, and all three are now stated in the Decision. The pipeline's `transaction.atomic()` opens **before** the locate rather than at authorize — the locate takes the row lock, and a lock outside the transaction is not a lock (`django_strawberry_framework/mutations/resolvers.py::run_write_pipeline_sync`, `::locate_instance`); that block is **nested inside** a completion-spanning transaction the schema's execution context opens for the mutation field (`django_strawberry_framework/schema.py::DjangoMutationExecutionContext`, `django_strawberry_framework/utils/write_transaction.py::managed_write_transaction`), so a GraphQL **response-completion** failure also rolls the write back; and every error-envelope return marks the transaction for rollback before building the payload (`::error_payload_builder`), so a `FieldError` envelope can never commit a partial write. Attribution: commit `1b06c39e` "span mutation transactions through response completion (BETA-055)" (2026-07-15) and the `0.0.14` write hardening, whose `CHANGELOG.md` `## [0.0.14]` entry is its only durable record.
- **Post-ship:** a generated mutation now **requires** `DjangoSchema` — reached through a plain `strawberry.Schema` it raises [`ConfigurationError`][glossary-configurationerror] before any database work (`django_strawberry_framework/utils/write_transaction.py::require_managed_write`). This is the most consumer-damaging divergence the reconciliation found, because the spec's Slice 4 instructed the construction that now fails; the spec states `DjangoSchema` at every site that names a schema constructor for the write surface. Attribution: the `0.0.14` cut, `CHANGELOG.md` `#"BREAKING: generated mutations require"`.
- **Post-ship:** step 5's M2M relation lookup no longer goes through the target model's default manager. ## Decision 9 — Optimizer composition and the `spec-035` G2 live-test handoff

Spec: [Decision 9 — Optimizer composition and the `spec-035` G2 live-test handoff][spec-036-d9].

### Justification (moved from the spec)

G2 was shipped pre-emptively in `0.0.10` for this exact path; honoring it is not optional, and the live test is a standing cross-spec obligation, not new scope. The re-fetch-and-plan return mirrors strawberry-django's optimizer-composed mutation return at the outcome level.

### Alternatives considered (and rejected)

- **Return the written instance without re-fetching.** Rejected: a freshly `save()`d instance has no related rows loaded, so any relation in the response selection N+1s; the re-fetch is what makes the response selection planable.
- **Disable the optimizer for mutation returns entirely.** Rejected: the response selection still needs `select_related` / `prefetch_related`; only `.only(...)` is unsafe under a mutation, which is exactly what G2 already gates — re-implementing a coarser disable would regress the join/prefetch planning.

### Changes this Decision underwent

- **Revision 1** pinned the post-write optimizer re-fetch and recorded the [`spec-035`][spec-035] **G2** live-test handoff as a standing cross-spec obligation this card discharges.
- **Revision 2 (Medium-1)** made the re-fetch **by pk without the visibility `get_queryset` filter**, as a deliberate and documented exception to [`GOAL.md`][goal] success-criterion 4: a caller holding `add_item` can create an `is_private=True` row the visibility hook hides, so the literal crit-4 reading would null the payload of a successful, authorized write.
- **Revision 3 (AR-M7)** split the handoff across two tiers — a behavioral bounded-query-count assertion live, the exact empty-`only_fields` plan state in the package optimizer mirror — because an over-`/graphql/` capture is robust for observable behavior and brittle as a column-exact snapshot.

## Decision 10 — Permission composition: `update` / `delete` lookups run through the target `get_queryset`

Spec: [Decision 10 — Permission composition: `update` / `delete` lookups run through the target `get_queryset`][spec-036-d10].

### Justification (moved from the spec)

the [`DONE-034-0.0.10`][kanban] dependency exists for exactly this — "write mutations need to compose with `apply_cascade_permissions`." Routing the lookup through `get_queryset` reuses the shipped visibility contract with zero new permission machinery, and the not-found-equals-hidden semantics match the package's standing no-existence-leak posture ([`spec-034`][spec-034] Decision 6, [`DjangoNodeField`][glossary-djangonodefield]).

### Alternatives considered (and rejected)

- **Look up by raw `Model.objects.get(pk=...)` and check visibility after.** Rejected: a post-hoc check leaks existence (the timing / error differs for hidden vs missing); routing through `get_queryset` makes them identical by construction.
- **Reusing `get_queryset` as the write-authorization gate.** Rejected (AR-H3): the cascade + `get_queryset` gate row *reachability* (visibility), but treating "can see this row" as "can change / delete this row" is the wrong contract — a public read surface would silently grant writes. Write authorization is its own seam ([Decision 15](#decision-15--write-authorization-a-drf-shaped-check_permission--metapermission_classes-seam)), and the `0.1.1` [`FieldSet`][glossary-fieldset] / [Per-field permission hooks][glossary-per-field-permission-hooks] work layers *field*-level read gates on top of both — not a substitute for either.

### Changes this Decision underwent

- **Revision 1** pinned the `update` / `delete` lookup through the target type's `get_queryset`, with a miss mapping to a not-found `FieldError` on `id` so a hidden row is indistinguishable from a missing one.
- **Revision 3 (AR-H3)** added the clause that `get_queryset` scopes *visibility* and never *write permission*, and moved write authorization to its own seam ([Decision 15](#decision-15--write-authorization-a-drf-shaped-check_permission--metapermission_classes-seam)). The second rejected alternative below — reusing `get_queryset` as the write gate — is the one that decision closed.

- **Post-ship:** the pasted lookup expression `target_type.get_queryset(target_type.model._default_manager.all(), info).get(pk=<decoded id>)` is not what runs, and the spelling hid two things the reader needs. `django_strawberry_framework/mutations/resolvers.py::locate_instance` composes `initial_queryset` → `apply_type_visibility_sync` (which also supplies the [`SyncMisuseError`][glossary-syncmisuseerror] discipline) → `pin_write_queryset(..., alias)` → `base_locked_queryset(model, alias, visible)` when `Meta.select_for_update` is on, then fetches by pk. The **contract** is unchanged and still holds exactly — visibility-only, `DoesNotExist` mapped to a not-found `FieldError` on `id`, no existence leak — so the Decision now describes the composition, including the write-alias pinning and the base-manager pk-subquery lock, instead of pasting an expression. Attribution: the `0.0.14` write hardening (alias pinning, row lock); the visibility half is the card's own.

## Decision 11 — Primary-type resolution: return type and input target resolve the model's primary `DjangoType`

Spec: [Decision 11 — Primary-type resolution: return type and input target resolve the model's primary `DjangoType`][spec-036-d11].

### Justification (moved from the spec)

the [`DONE-018-0.0.6`][kanban] dependency exists for this — "explicit primary type drives mutation target resolution." Reusing the primary lookup keeps the mutation return consistent with what relation traversal and node refetch resolve, so a mutated row round-trips through the same type a query would return.

### Alternatives considered (and rejected)

- **An explicit `Meta.return_type` on the mutation.** Rejected: redundant with the registry primary lookup for the common case; recorded as the escape hatch if a mutation must return a *secondary* type (a Risks item), but not the default surface.
- **Resolve the first registered type for the model.** Rejected: violates `Meta.primary` semantics (secondaries never auto-resolve), exactly the ambiguity `Meta.primary` exists to forbid.

### Changes this Decision underwent

- **Revision 1** pinned the return payload and relation target on the model's **primary** [`DjangoType`][glossary-djangotype].
- **Revision 3 (Low-1)** corrected a false claim this Decision made: it had said the primary type drives the generated **input** fields. It does not — inputs derive from the model's editable columns ([Decision 6](#decision-6--auto-generated-input--partialinput-types)); the primary type fixes the return payload and the relation-id strategy only. **(AR-H4)** made that strategy also fix which type a relation `GlobalID` is type-checked against.

- **Wrong when written:** the Decision cited the primary lookup as `TypeRegistry.get(model)` / `primary_for(model)`. `primary_for` has never been on this path: `git show 4b26b94e:django_strawberry_framework/mutations/sets.py`'s primary resolution already called `registry.get(model)` and then `registry.types_for(model)` purely to split the zero-type error from the ambiguous-multiple-types error. The two are not interchangeable — `get` resolves the single-registered-type case without an explicit `Meta.primary` flag, where `primary_for` returns `None` — and it is `get`'s permissive form the mutation tests rely on. The citation now names `get` and `types_for` only.

## Decision 12 — Finalization seam: register at class creation, bind at phase 2.5, no `DEFERRED_META_KEYS` change

### Justification (moved from the spec)

the materialize-generated-classes-before-`Schema` discipline ([`spec-027`][spec-027] / [`spec-028`][spec-028] Decision 6 / Decision 9) is the proven way Strawberry resolves lazily-referenced generated input classes; reusing phase 2.5 keeps one finalization gate. The DoD item now states the split the Decision always stated.
- **Post-ship:** the `## Edge cases` claim that `DEFERRED_META_KEYS` / `ALLOWED_META_KEYS` "are byte-unchanged" was true of this card and false read as the present-tense statement its grammar makes it: `ALLOWED_META_KEYS` has since taken `cursor_field` (commit `51421e54`, keyset value-encoded cursors) and `filesystem_path_fields` (commit `567cc6d0`, the `0.0.14` security program), each from the card that needed it. `DEFERRED_META_KEYS` is unchanged to this day. The bullet is now scoped to what it contracts — **this card** adds no `DjangoType` `Meta` key.

## Decision 15 — Write authorization: a DRF-shaped `check_permission` / `Meta.permission_classes` seam

Spec: [Decision 15 — Write authorization: a DRF-shaped `check_permission` / `Meta.permission_classes` seam][spec-036-d15].

### Justification (moved from the spec)

it matches [`GOAL.md`][goal]'s DRF-shaped, `class Meta`-driven, *layered* permissions north star; it keeps visibility and write authorization as distinct contracts (so "can view" never silently means "can write"); and a safe-by-default model-permission check means the write side is not unauthenticated-by-default the moment a consumer exposes a `Mutation`.

### Alternatives considered (and rejected)

- **Defer create authorization to the consumer / `0.1.1` (the prior draft's stance).** Rejected (AR-H3): it ships a write foundation whose `create` is unauthenticated unless every schema bolts on an ad-hoc resolver gate, and makes the "anonymous cannot mutate" acceptance case underivable from the contract.
- **A single coarse `Meta.login_required` boolean.** Rejected: not DRF-shaped, expresses neither model-permission nor object-level checks, and gives the flavor cards nothing reusable.
- **Routing denials into the `FieldError` envelope instead of raising.** Rejected: conflates authorization (a `403`-shaped failure) with field validation; `permission_classes` raising is the Strawberry-native convention and keeps the two failure modes legible to clients.

### Changes this Decision underwent

- **Revision 3 (AR-H3)** created this Decision. Before it, `create` authorization was deferred to the consumer — the stance recorded as the first rejected alternative below — which would have shipped a write foundation whose `create` is unauthenticated unless every schema bolts on an ad-hoc resolver gate, and would have left "anonymous cannot mutate" underivable from the contract.
- **Revision 4 (CR-7)** documented the argless-construction contract: the pipeline builds the mutation instance and each permission class with no arguments (DRF parity), so a consumer subclass or permission class needs a zero-required-argument `__init__`. Documented, not enforced.
- **Post-ship (recorded, not folded in):** `HEAD` enforces three write-authorization contracts this Decision does not describe — a strict-`bool` authorization result across `has_permission` / `check_permission` / `user.has_perm` (an `async def` hook's truthy coroutine closed and raised rather than read as allow, `django_strawberry_framework/mutations/permissions.py::_require_sync_bool_auth_result`); **point-in-time** authorization (a permission revoked by a concurrent transaction after the check is not re-observed); and an explicit `Meta.permission_classes = []` AllowAny opt-out that resolves no auth state at all. The coroutine-close half landed inside this card's own cut (`c09793ee`, recorded under Decision 8); the rest is `0.0.14` write hardening. Per the maintainer's decision for this reconciliation — **correct claims only** — they are **not** written into `spec-036`, which never scoped that machinery. They are routed as deferred work needing an owning spec; see [Non-Decision deliberation](#non-decision-deliberation).

Each item names a preferred answer for the `0.0.11` cut and a fallback if implementation reveals it is wrong.

- **`Meta.operation` selector vs three base classes.** Preferred answer ([Decision 5](#decision-5--public-surface-djangomutation-base--djangomutationfield-factory--fielderror-exported-from-the-root)): one `DjangoMutation` base with `Meta.operation` ∈ `{"create", "update", "delete"}`, the most `class Meta`-idiomatic shape and the smallest public surface.
