## Key glossary references

Skim these [`docs/GLOSSARY.md`][glossary] entries first — they anchor the vocabulary used throughout the spec:

- [`FilterSet`][glossary-filterset] — the declarative filter class this card ships. Subclasses `django_filters.filterset.BaseFilterSet` per [Decision 5](#decision-5--django-filter-as-the-foundation) and borrows the six-layer lazy-resolution architecture from `django-graphene-filters` per [Decision 3](#decision-3--six-layer-lazy-resolution-pipeline); Graphene's `graphene.InputObjectType` becomes `strawberry.input` and Graphene's `lambda:` forward references become `Annotated["TypeName", strawberry.lazy("django_strawberry_framework.filters.inputs")]` over module globals.
- [`RelatedFilter`][glossary-relatedfilter] — cross-relation filter traversal. Accepts a target `FilterSet` class, an absolute import path string, or an unqualified name for circular references; lazy-resolved at finalizer time.
- [`Meta.filterset_class`][glossary-metafilterset_class] — the consumer-facing key that points a [`DjangoType`][glossary-djangotype] at its `FilterSet`. Promoted from `DEFERRED_META_KEYS` to `ALLOWED_META_KEYS` per [Decision 7](#decision-7--metafilterset_class-promotion-gate).
- [`DjangoType`][glossary-djangotype] — the model-backed Strawberry type this card extends with a filter sidecar. The `Meta`-driven shape is what makes `Meta.filterset_class = ItemFilter` legible to a Django audience.
- [`finalize_django_types`][glossary-finalize_django_types] — the synchronization point where the filter subsystem's lazy-resolution pipeline runs (phase 2.5, the same seam [`Meta.interfaces = (relay.Node,)`][glossary-metainterfaces] uses).
- [`DjangoOptimizerExtension`][glossary-djangooptimizerextension] — the optimizer this card composes with. Filter clauses applied to a queryset must not break the optimizer's [Queryset diffing][glossary-queryset-diffing] cooperation; covered by [Decision 8](#decision-8--relation-permission-cascade--get_queryset-cooperation) and a live HTTP test.
- [`get_queryset` visibility hook][glossary-get_queryset-visibility-hook] — pre-filter visibility scoping. Composes with filter `check_*_permission` gates ([Decision 8](#decision-8--relation-permission-cascade--get_queryset-cooperation)).
- [`OrderSet`][glossary-orderset] — sibling [`DONE-028-0.0.8`][kanban] subsystem. Mentioned only as the second consumer of the same lazy-resolution architecture this card ships; out of scope here.
- [`AggregateSet`][glossary-aggregateset] / [`get_child_queryset`][glossary-get_child_queryset] / [`apply_cascade_permissions`][glossary-apply_cascade_permissions] — future Layer-3 sidecars referenced as the forward composition surface; not implemented here.
- [`DjangoConnectionField`][glossary-djangoconnectionfield] — `0.0.9`; the consumer-facing surface that threads `filter:` arguments through. The factory machinery this card ships is the input it will consume, so the `0.0.8` deliverable is the back-end half of the `0.0.9` connection field's filter surface.
- [`Meta.primary`][glossary-metaprimary] — the multi-`DjangoType`-per-model design from `0.0.6` whose `TypeRegistry` keying convention this card respects per [Decision 9](#decision-9--input-class-namespace-vs-typeregistry-and-lifecycle).
- [`ConfigurationError`][glossary-configurationerror] — raised at type-creation and finalization time for unknown filter target classes, invalid lookup names, circular references that exhaust the resolution guard, etc. — see [Edge cases](#edge-cases-and-constraints).
- [`Meta.search_fields`][glossary-metasearch_fields] — the search-input surface ([planned for `0.1.2`][glossary-metasearch_fields]); the `LOOKUP_PREFIXES` map (`^` / `=` / `@` / `$`) ported verbatim from `django-graphene-filters` lives in the filter subsystem because `construct_search` belongs in the filter pipeline.

Foundational invariants and cross-cutting surfaces a new dev will hit while reading this spec — all defined in [`docs/GLOSSARY.md`][glossary]:

- [Choice enum generation][glossary-choice-enum-generation] — the existing pipeline `convert_filter_to_input_annotation` consults for `ChoiceFilter` input shape; ensures choice-enum filter inputs round-trip through Strawberry enums.
- [Scalar field conversion][glossary-scalar-field-conversion] — the `SCALAR_MAP` that Decision 4's non-Relay FK / PK conditional reads to derive scalar PK filter shapes.
- [Specialized scalar conversions][glossary-specialized-scalar-conversions] — Decimal / Date / DateTime / Time / UUID conversions the named filter-to-input converter handles per Decision 4 M1.
- [BigInt scalar][glossary-bigint-scalar] — one of the scalar PK shapes Decision 4's non-Relay branch can produce (alongside `int` and `uuid.UUID`).
- [Input type generation][glossary-input-type-generation] — the package's general input-type-generation surface; this card's `FilterArgumentsFactory` is the filtering-specific instance built on top of the existing input-type pipeline.
- [OptimizerHint][glossary-optimizerhint] — the hint primitive `Meta.optimizer_hints` declarations carry; filter clauses compose with hints at queryset-translation time.

## Slice checklist

Each top-level item maps to one commit in the [Implementation plan](#implementation-plan). Six slices total.

- [ ] Slice 1: Foundation — module layout + `Filter` primitives + `FilterSet` metaclass
  - [ ] Create [`django_strawberry_framework/filters/`][filters] subpackage with `__init__.py`, `base.py`, `sets.py`, `factories.py`, `inputs.py` per [Decision 2](#decision-2--subpackage-layout-and-public-export-surface). Module-level docstrings on each file pin the responsibility (`base.py` = `Filter` / `RelatedFilter` / primitives; `sets.py` = `FilterSet` (subclasses `django_filters.filterset.BaseFilterSet`) + metaclass; `factories.py` = `FilterArgumentsFactory` + `get_filterset_class` + `_dynamic_filterset_cache`; `inputs.py` = filter input classes materialized as module globals + input-data adapters + lifecycle ledger).
  - [ ] `base.py` ships the five verified upstream primitives per [Decision 4](#decision-4--upstream-primitives-parity-floor): `TypedFilter`, `ArrayFilter` + `ArrayFilterMethod`, `RangeFilter` + `RangeField` + `validate_range`, `ListFilter` + `ListFilterMethod`, `GlobalIDFilter` + `GlobalIDMultipleChoiceFilter`, and re-exports `Filter` from `django_filters` unchanged (a plain re-export, not a port — see [Decision 2](#decision-2--subpackage-layout-and-public-export-surface)). Each ported primitive is a port of the matching `graphene_django/filter/filters/*.py` primitive (sourced from `~/projects/django-graphene-filters/.venv/lib/python*/site-packages/graphene_django/filter/filters/` — tilde + Python-version glob so the path resolves across maintainers' machines and survives future Python upgrades); the port is library-agnostic where possible and Strawberry-adapted only at the input-type-construction boundary.
  - [ ] `base.py` also ships `RelatedFilter` (the `BaseRelatedFilter` port from `django_graphene_filters/filters.py::BaseRelatedFilter`) and re-exports `LazyRelatedClassMixin` — Layers 1 + 2 of [Decision 3](#decision-3--six-layer-lazy-resolution-pipeline). The mixin itself lives at [`django_strawberry_framework/sets_mixins.py::LazyRelatedClassMixin`][sets-mixins], the package-root module every set family shares; `filters/base.py` re-exports it so the `filters` public surface carries the name.
  - [ ] `sets.py` ships `FilterSetMetaclass` (port from `django_graphene_filters/filterset.py::FilterSetMetaclass`) and `FilterSet` (port from `django_graphene_filters/filterset.py::AdvancedFilterSet`, with `get_filters` doing Layer-4 cycle-safe expansion) — Layers 3 + 4 of [Decision 3](#decision-3--six-layer-lazy-resolution-pipeline). `FilterSet` accepts [`Meta.model`][glossary-metamodel], [`Meta.fields`][glossary-metafields] (dict form `{"name": ["exact", "icontains"]}` or `"__all__"` with the override on `__all__` pinned in [Decision 3](#decision-3--six-layer-lazy-resolution-pipeline)), and per-field `check_<field>_permission` hooks. Adds the `_owner_definition: DjangoTypeDefinition | None` slot bound at finalizer phase 2.5; `apply(input_value, queryset, info)` classmethod carries `info` end-to-end and explicitly calls `filterset.form.is_valid()` (raising `GraphQLError("Invalid filter input")` with `extensions.code == "FILTER_INVALID"` on failure).
  - [ ] `inputs.py` IS the input-class namespace per [Decision 9](#decision-9--input-class-namespace-vs-typeregistry-and-lifecycle) — generated filter input classes are materialized as real module globals of `django_strawberry_framework.filters.inputs` via `materialize_input_class(name, cls)` (sets `sys.modules["django_strawberry_framework.filters.inputs"].<name> = cls`), keyed by stable class-derived names (e.g., `"GalaxyFilterInputType"`); a private `_materialized_names: dict[str, type]` ledger maps each name to the materialized input class, which is what makes re-materialization idempotent. This module namespace is NOT the same surface as `django_strawberry_framework.registry.registry` (the model-to-`DjangoType` registry). The two namespaces do not collide because their key types are disjoint (Django model class vs string class name). The shape is module-globals-keyed (not dict-keyed) because Strawberry's [`LazyType.resolve_type`][filters] reads `module.__dict__[name]`, not a sidecar dict.
- [ ] Slice 2: Factories — `FilterArgumentsFactory` BFS + dynamic-filterset cache
  - [ ] `factories.py` ships `FilterArgumentsFactory` (port from `django_graphene_filters/filter_arguments_factory.py::FilterArgumentsFactory`) — Layer 5 of [Decision 3](#decision-3--six-layer-lazy-resolution-pipeline). BFS walk that builds every reachable `strawberry.input` type; `_build_class_type` emits `@strawberry.input`-decorated classes via `django_strawberry_framework.filters.inputs.build_input_class(name, field_specs)` (the Strawberry-adapted analogue of Graphene's `type(name, (graphene.InputObjectType,), fields)`); `build_input_class` is this module's alias for the shared [`utils/inputs.py::build_strawberry_input_class`][utils-inputs].
  - [ ] `factories.py` ships `get_filterset_class` (port from `django_graphene_filters/filterset_factories.py::get_filterset_class`, NOT the same-named `graphene_django/filter/utils.py::get_filterset_class` — the spec pins this distinction in [Decision 4](#decision-4--upstream-primitives-parity-floor)) plus `_dynamic_filterset_cache` (Layer 6) keyed by `(model, fields, extra_meta)`. The cache prevents duplicate-`__name__` collisions when two connection fields target the same model without declaring an explicit `filterset_class`.
  - [ ] `sets.py` carries `FILTER_DEFAULTS` as a **class attribute on `FilterSet`** (NOT in `factories.py`, because `django_filters.filterset.BaseFilterSet.filter_for_field()` / `filter_for_lookup()` consult `cls.FILTER_DEFAULTS` directly during the runtime filter-instance build). The same map is the Strawberry-adapted analogue of `graphene_django/filter/filterset.py::GrapheneFilterSetMixin.FILTER_DEFAULTS`. `FilterSet` also overrides `filter_for_field()` / `filter_for_lookup()` to apply the conditional Relay-vs-scalar selection per [Decision 4](#decision-4--upstream-primitives-parity-floor): Relay-Node targets → `GlobalIDFilter`; non-Relay targets → the scalar PK filter derived from the target PK column conversion. `factories.py::FilterArgumentsFactory._ensure_built` then derives the Strawberry input field type from the **resolved filter instances on the FilterSet**, not from a parallel map — input shape stays downstream of filter shape.
  - [ ] `inputs.py` ships the input-data adapter functions: `_build_logic_fields` (`and` / `or` / `not` self-references — `list[Annotated["Name", strawberry.lazy(...)]] | None` for `and_` / `or_`, `Annotated["Name", strawberry.lazy(...)] | None` for `not_`), `_build_input_fields` (target-filterset references via `strawberry.lazy(...)` over module globals; per-lookup field names emitted via `strawberry.field(name=<graphql_name>)` whenever `LOOKUP_NAME_MAP[lookup].python_attr != LOOKUP_NAME_MAP[lookup].graphql_name`), `construct_search` (the `LOOKUP_PREFIXES` map — `^` → `istartswith`, `=` → `iexact`, `@` → `search`, `$` → `iregex` — ported verbatim), `LOOKUP_NAME_MAP` (the `<lookup> → (python_attr, graphql_name)` map), `convert_filter_to_input_annotation(filter_instance, model_field, owner_definition)` (the named filter-to-Strawberry-input converter), `normalize_input_value(filter_instance, raw_value, field_name=None)` (the runtime symmetric of the converter).
- [ ] Slice 3: Wiring — `Meta.filterset_class` promotion + finalizer phase 2.5 binding
  - [ ] [`django_strawberry_framework/types/definition.py::DjangoTypeDefinition`][definition] grows a `filterset_class: type | None = None` field. The slot is populated by `DjangoType.__init_subclass__` from `Meta.filterset_class` once the key is promoted out of `DEFERRED_META_KEYS`.
  - [ ] [`django_strawberry_framework/types/definition.py::DjangoTypeDefinition`][definition] also grows a `related_target_for(field_name: str) -> tuple[DjangoTypeDefinition, models.Field] | None` method. The method looks up `field_name` on `self.model._meta` and, if it resolves to a relation (`ForeignKey`, `OneToOneField`, `ManyToManyField`, reverse FK / OneToOne / M2M, GenericForeignKey), returns the `(target_definition, model_field)` pair — where `target_definition` is resolved via `registry.primary_for(target_model)` falling back to the only `DjangoType` registered for that model. Returns `None` for non-relation fields. This is the lookup [Decision 4](#decision-4--upstream-primitives-parity-floor)'s owner-aware FK/PK conditional consults; without it the conditional cannot run.
  - [ ] [`django_strawberry_framework/types/base.py::DEFERRED_META_KEYS`][base] drops `"filterset_class"`. [`ALLOWED_META_KEYS`][base] grows `"filterset_class"`. The `_validate_meta` function validates the supplied class is a `FilterSet` subclass and raises [`ConfigurationError`][glossary-configurationerror] otherwise.
  - [ ] [`django_strawberry_framework/types/finalizer.py::finalize_django_types`][finalizer] grows a per-type filter-binding pass in phase 2.5 (immediately after `apply_interfaces` / `install_relay_node_resolvers` and before phase 3's `strawberry.type` decoration). The pass runs as ordered subpasses over ALL wired `DjangoType`s, never as one per-type loop: (1) validate and **bind the owner via `filterset_class._owner_definition = definition`** (raising [`ConfigurationError`][glossary-configurationerror] when a prior binding's `related_target_for(...)` resolves to a different-Relay-shape type for any FK / PK / M2M field); (2) call `filterset_cls.get_filters()` to trigger Layer-4 expansion; (2.5) run the two filter-only audits in `_audit_filterset_subpass_2_5`; (3) orphan-validate against the `_helper_referenced_filtersets` set; (4) call `FilterArgumentsFactory(filterset_cls).arguments` to trigger Layer-5 BFS and materialize each built input class as a module global of [`django_strawberry_framework.filters.inputs`][filters] via `materialize_input_class(name, cls)`. The materialization is idempotent for `(name, input_class)` pairs (the ledger value is the materialized Strawberry input class, uniquely produced by one `FilterSet`; the idempotency check uses ``is`` identity on the input class) and raises [`ConfigurationError`][glossary-configurationerror] on name collision against a different input class (per [Decision 9](#decision-9--input-class-namespace-vs-typeregistry-and-lifecycle)). The filter subsystem registers its own teardown at import time via `registry.py::register_subsystem_clear` (owners `filters.input_namespace` and `filters.helper_references`), and `registry.clear()` replays every registered callback, so the model-to-`DjangoType` clear and the filter-side clears share one entry point without `registry.py` importing `filters` at all. Calling `finalize_django_types()` twice is still a no-op via the existing `registry.is_finalized()` guard.

  - [ ] [`examples/fakeshop/apps/library/schema.py`][fakeshop-library-schema] grows `Meta.filterset_class = filters.BranchFilter` (etc.) on the corresponding `DjangoType` classes including `ShelfType` (so `BookFilter.shelf` has a target `ShelfFilter` to resolve against under [Decision 3](#decision-3--six-layer-lazy-resolution-pipeline) Layer 4). Sibling library root-list resolvers (`all_library_branches`, `all_library_books`, etc.) annotate `filter:` via `filter_input_type(filters.BranchFilter)` per [Decision 11](#decision-11--filter_input_typefilterset-consumer-helper). Each resolver **calls the owning type's `get_queryset(queryset, info)` BEFORE `FilterSet.apply_sync(...)` / `apply_async(...)`** per the sync/async split in [Decision 8](#decision-8--relation-permission-cascade--get_queryset-cooperation): e.g., `queryset = BranchType.get_queryset(models.Branch.objects.order_by("id"), info); queryset = filters.BranchFilter.apply_sync(filter, queryset, info)` (sync because fakeshop library types use sync `get_queryset`; async-only types would use `apply_async`). Skipping the `get_queryset` call would let the filter clause see through the type's visibility hook to hidden rows — a security regression the fakeshop instructions defend against by example. The resolver-facing API is the `apply_sync` / `apply_async` classmethod pair per [Decision 8](#decision-8--relation-permission-cascade--get_queryset-cooperation)'s sync/async split; same shape `DjangoConnectionField` will reuse in `0.0.9`.
  - [ ] [`examples/fakeshop/test_query/test_library_api.py`][fakeshop-test-library] grows **exactly 14 new live `/graphql/` HTTP tests**. Thirteen of them cover: scalar-field filter (`name: { iContains: "..." }`), choice-enum filter (`circulationStatus: { exact: AVAILABLE }`), **non-Relay forward-FK filter** against `ShelfType`'s scalar `int` PK (`shelf: { id: { exact: 1 } }`), **Relay forward-M2M filter** against `GenreType`'s GlobalID (`genres: { id: { exact: "<global-id-string>" } }`), reverse-FK filter (`shelves: { code: { iContains: "..." } }`), logical-and / logical-or filter combinations, optimizer cooperation (filtered queryset still receives `select_related` / `prefetch_related` for nested selections — pinned by `assertNumQueries(N)`), related-queryset boundary using an existing `Shelf` field (`Shelf.objects.filter(topic="permanent collection")` as the `RelatedFilter` `queryset=` constraint — no model change needed), the absolute-import-path `RelatedFilter` resolution path, nested `RelatedFilter` visibility scoping, root `get_queryset` honoring (via `BranchType.get_queryset` hiding `city == "restricted"`), wrong-`type_name` Relay GlobalID rejection, and form-validation rejection through `PatronFilter.email_must_have_at_sign` (a custom filter whose input bypasses GraphQL enum coercion and so actually fires `_validate_form_or_raise`). The fourteenth test (`test_apply_passes_graphql_enum_coercion_before_form_validation`) pins the GraphQL-coercion-layer error shape distinct from the `FILTER_INVALID` form-validation shape. The Relay-vs-scalar split confirms the [Decision 4](#decision-4--upstream-primitives-parity-floor) conditional `FILTER_DEFAULTS` mapping end-to-end.
- [ ] Slice 4a: Tree-form logic substrate — `FilterSet.filter_queryset` `django-filter` instance-method override
  - [ ] [`django_strawberry_framework/filters/sets.py::FilterSet`][filters] grows the `filter_queryset(self, queryset)` instance-method override per [Decision 8](#decision-8--relation-permission-cascade--get_queryset-cooperation) step 8 and [Definition of done](#definition-of-done) item 4(d). The method evaluates the `and` / `or` / `not` tree carried in `self.form.cleaned_data` (the keys `_normalize_input` already emits at the top level of the form data): `and` is a `list[<NestedFilterInput>]` whose child querysets are intersected via `Q(...) & Q(...)`; `or` is a `list[<NestedFilterInput>]` whose child querysets are unioned via `Q(...) | Q(...)`; `not` is a single nested input whose child queryset is negated via `~Q(...)`. The substrate must compose with the existing `_apply_related_constraints` step 4a output (the parent queryset passed in already carries any active-branch `RelatedFilter(queryset=...)` intersection) and must preserve the visibility-before-filter ordering — `filter_queryset` runs against the visibility-scoped queryset, not against the unscoped model manager. ## Problem statement

`django-strawberry-framework`'s `0.0.7` surface ships a model-backed Strawberry type ([`DjangoType`][glossary-djangotype]), the [`DjangoOptimizerExtension`][glossary-djangooptimizerextension], the non-Relay [`DjangoListField`][glossary-djangolistfield], and the [Schema export management command][glossary-schema-export-management-command] — but consumers cannot filter the returned querysets through the GraphQL surface today. The package's `0.0.7` audience (Django teams migrating from `graphene-django` or `strawberry-graphql-django`) reaches for `Meta.filterset_class = ItemFilter` the moment they wire up a real schema, and the package's response is a [`ConfigurationError`][glossary-configurationerror] from [`django_strawberry_framework/types/base.py::DEFERRED_META_KEYS`][base] ("`Meta keys not supported yet: ['filterset_class']`").

Filtering is the first ⚛️&🍓 parity-required Layer-3 capability for two reasons:

1. **Audience expectation.** Both upstreams (`graphene-django` via `DjangoFilterConnectionField`+`filterset_class`, and `strawberry-graphql-django` via `@strawberry_django.filter_type(Model)`) ship a filter surface in their core API. A Django GraphQL package without filters is not a credible alternative to either; the gap shows up in the first ten minutes of schema authoring.
2. **Foundation for other Layer-3 work.** Sibling [`OrderSet`][glossary-orderset] ([`DONE-028-0.0.8`][kanban]) reuses the same lazy-resolution architecture; [`AggregateSet`][glossary-aggregateset] reuses it again at `0.1.3`; [Meta.search_fields][glossary-metasearch_fields] reuses the `LOOKUP_PREFIXES` map; the eventual [`DjangoConnectionField`][glossary-djangoconnectionfield] (`0.0.9`) consumes the `FilterArgumentsFactory` output as the connection's `filter:` argument source. Shipping filters first establishes the lazy-resolution pattern the next four cards reuse without redesign.

`django-graphene-filters` (the working reference per [`START.md`][start] "Working reference") has already solved the hard part — a cycle-safe six-layer lazy-resolution pipeline that handles circular `RelatedFilter` references across modules. Five of six layers are library-agnostic Python and port verbatim; only Layer 5 (the cycle-safe forward reference in the GraphQL schema build) needs Strawberry adaptation. The card body's "Recommended architectural direction" block pre-pins this answer; the spec preserves it as [Decision 3](#decision-3--six-layer-lazy-resolution-pipeline) without re-litigation, and the rest of the work is mechanical: port the five reusable layers, adapt Layer 5 to `strawberry.lazy(...)`, wire the binding into the finalizer's phase 2.5, and promote `Meta.filterset_class` once the end-to-end path is live.

## Goals

1. Ship `FilterSet` + `RelatedFilter` + per-field `check_*_permission` gates + cross-relation traversal with cycle-safe lazy resolution, mirroring the `django-graphene-filters` six-layer pipeline minus Layer 5's GraphQL-engine substitution.
2. Promote [`Meta.filterset_class`][glossary-metafilterset_class] out of `DEFERRED_META_KEYS` only when the filter subsystem applies the configured class end-to-end — same gate as [`Meta.interfaces`][glossary-metainterfaces] in `DONE-015-0.0.5`.
3. Establish the registration / factory / lazy-resolution pattern the four sibling Layer-3 subsystems ([`OrderSet`][glossary-orderset], [`AggregateSet`][glossary-aggregateset], [`FieldSet`][glossary-fieldset], [Meta.search_fields][glossary-metasearch_fields]) reuse without redesign.
4. Stay composable with [`DjangoOptimizerExtension`][glossary-djangooptimizerextension]'s [Queryset diffing][glossary-queryset-diffing] / [Plan cache][glossary-plan-cache] / [FK-id elision][glossary-fk-id-elision] / [Strictness mode][glossary-strictness-mode] — a filter clause is just another `.filter(...)` call on the consumer queryset; the optimizer cooperates.
5. Expose enough introspection (`FilterSet.get_filters()`, `FilterArgumentsFactory(cls).arguments`) for a maintainer to ask "what filter surface does this type support?" from the REPL in one call.
6. Earn package coverage through live fakeshop HTTP flows per [Decision 12](#decision-12--live-http-coverage-strategy); the package coverage gate (`fail_under = 100`) is reached because the live HTTP tests exercise the package end-to-end.

## Non-goals

- **Ordering / aggregation / fieldsets / permissions cascade.** Each ships in its own card. Composition with this card is forward-only; no Layer-3 sibling is implemented here.
- **`DjangoConnectionField` integration.** The `0.0.9` connection field consumes the factory machinery this card ships; the connection-field surface itself is out of scope.
- **`DjangoListField` filter-argument integration.** [`DjangoListField`][glossary-djangolistfield] (shipped `0.0.7`) currently wraps resolvers with a two-argument `(root, info)` callable that does NOT preserve or expose arbitrary resolver arguments. Adding a `filter:` argument to `DjangoListField` requires an argument-injection design that is explicitly **deferred to `0.0.9`** alongside `DjangoConnectionField`'s filter integration. `0.0.8` consumers reach for `filter_input_type(...)` through plain `@strawberry.field` resolvers ONLY.
- **A `Meta.filterset_class = MyDjangoFilter` shape that accepts an arbitrary `django_filters.FilterSet` subclass without re-parenting.** Per [Decision 5](#decision-5--django-filter-as-the-foundation), `FilterSet` IS a `django_filters.filterset.BaseFilterSet` subclass, so any consumer who has `class MyFilter(django_filters.FilterSet):` today migrates by swapping the parent class to `django_strawberry_framework.filters.FilterSet`; the migration is one line and inherits the lazy-resolution + GraphQL-input layers for free. Accepting a plain `django_filters.FilterSet` at `Meta.filterset_class` without re-parenting would mean two consumer-facing surfaces for the same wiring (one with `RelatedFilter` / `check_*_permission` recursion, one without), so the package validates that `Meta.filterset_class` is specifically a `django_strawberry_framework.filters.FilterSet` subclass — but the package's class IS a `django_filters.filterset.BaseFilterSet`, so the [`GOAL.md #"Coming from DRF + django-filter"`][goal-migration-shape] migration promise holds via parent-class swap.
- **Replacing the optimizer's queryset-diffing contract.** Filters land as `.filter(...)` calls before the optimizer walks the selection tree; the existing cooperation contract is untouched.
- **Auto-generation of `FilterSet` from `Meta.fields` without declaring an explicit class.** Deferred; the dynamic-factory machinery (Layer 6) exists for the connection-field path where the connection field can pre-declare `model=Item, fields="__all__"` without a sibling `FilterSet` class. Direct consumer-facing implicit generation lands when [`DjangoConnectionField`][glossary-djangoconnectionfield] ships in `0.0.9`.
- **The version bump.** Owned by the last `0.0.8` card to ship per [Decision 10](#decision-10--joint-008-cut).

## Borrowing posture

Filtering is the most heavily-borrowed surface in the package. The architectural answer is pre-pinned by the [`KANBAN.md`][kanban] card body's "Recommended architectural direction" block; this spec preserves it without re-litigation.

### From `django-filter` — embrace as the foundation

`django-filter` is already a hard dependency at [`pyproject.toml #"django-filter>=25.2"`][pyproject], and [`GOAL.md #"Coming from DRF + django-filter"`][goal-migration-shape] promises consumers a one-line parent-class swap onto `Meta.filterset_class`. Re-implementing those layers would be a large net-new code surface for zero gain when the dependency is already in the lock file. Per [Decision 5](#decision-5--django-filter-as-the-foundation), this card embraces the dep; the [`docs/GLOSSARY.md`][glossary] entry for [`FilterSet`][glossary-filterset] documents the inheritance contract for consumers.

The cookbook's `AdvancedFilterSet` (the working reference per [`START.md`][start]) inherits from `django_filters.filterset.BaseFilterSet`; the package's `FilterSet` mirrors that exact inheritance. The added value is the cycle-safe lazy-resolution layer (Layers 1–4 of [Decision 3](#decision-3--six-layer-lazy-resolution-pipeline)), the Strawberry-adapted GraphQL-input layer (Layer 5), and the dynamic-factory cache (Layer 6) — none of which `django-filter` ships.

Local source path: `~/projects/strawberry-django-main/strawberry_django/filters.py`. The upstream's single-file decorator-driven implementation is conceptually parallel at the runtime layer (`process_filters` compiles input values into queryset arguments) but the declaration surface diverges per the package's DRF-shaped positioning. Borrow the runtime contract loosely; don't borrow the decorator-on-input-type surface:

- `filters.py::FilterLookup` — the generic typed lookup descriptor (`exact`, `i_exact`, `contains`, ...) is conceptually similar to this card's lookup-pair generation but the Strawberry adaptation lands differently because the cookbook's BFS factory drives the lookup expansion.
- `filters.py::process_filters` — the runtime side of the filter pipeline. This card's `FilterSet.apply_sync(input_value, queryset, info)` / `apply_async(...)` classmethod pair (per the sync/async split in [Decision 8](#decision-8--relation-permission-cascade--get_queryset-cooperation)) is the equivalent consumer-facing entry point (the `django-filter` instance method `filter_queryset(self, queryset)` is reserved for the tree-form-logic override path and has a different signature); both compile a Strawberry/Graphene input into queryset args.
- `filters.py::FILTERS_ARG` (`= "filters"`) — module-level constant for the GraphQL argument name. This card's equivalent is `FILTER_ARG = "filter"` (singular per the cookbook's convention; the upstream's plural form is a documented difference).
- `filters.py::filter_type` decorator — NOT borrowed (the package's `Meta`-driven surface forbids decorator-on-input-type per [`START.md`][start] "Style they care about").
- `filters.py #"def __getattr__"` legacy `filter` alias with `DeprecationWarning` — NOT borrowed; the package's first-ship surface does not need a legacy alias.

### Explicitly do not borrow

- **Graphene's `lambda: target_input_type` cycle-safe forward references.** Replaced by `Annotated["{TargetFilterSet}InputType", strawberry.lazy("django_strawberry_framework.filters.inputs")]` at Layer 5 (per [Decision 3](#decision-3--six-layer-lazy-resolution-pipeline)). Strawberry's `LazyType.resolve_type` imports the named module and reads `module.__dict__[type_name]` — it does NOT traverse object paths — so the generated input classes MUST be real module globals of `django_strawberry_framework.filters.inputs`, not dict entries on a private registry (verified by inspection of the installed Strawberry).
- **`graphene-django`'s `setup_filterset` wrapper-avoidance.** Strawberry's eager annotation resolution does not have the "Graphene{X}Filter" wrapping problem that motivated this in the reference; the wrapper is dropped.
- **`graphene-django`'s `replace_csv_filters`.** Strawberry's typed input handles `list[T]` natively without comma-separated-string workarounds; the function is dropped.
- **`@strawberry_django.filter_type(Model, lookups=True)` decorator surface.** The package's `Meta`-driven shape per [`START.md`][start] "Meta classes everywhere on consumer surfaces" forbids decorator-on-input-type for consumer-facing classes.

## User-facing API

The shipped consumer surface adds four new symbols re-exported from `django_strawberry_framework.filters` — `FilterSet`, `RelatedFilter`, [`filter_input_type`][glossary-filter_input_type], and (internally registered) the input-class module-globals registry. The [`Meta.filterset_class`][glossary-metafilterset_class] hook is the consumer-facing wiring on the existing [`DjangoType`][glossary-djangotype] surface; `filter_input_type(FilterSet)` is the resolver-annotation helper that lets a normal `@strawberry.field` resolver accept a `filter:` argument that resolves to the generated input class at schema-build time.

**Resolver-facing API split:** Consumers call `FilterSet.apply_sync(...)` from sync resolvers and `FilterSet.apply_async(...)` from async resolvers per the sync/async split in [Decision 8](#decision-8--relation-permission-cascade--get_queryset-cooperation). The `django-filter` `filter_queryset(self, queryset)` instance method is an internal override (for tree-form logic only) and is NOT the consumer surface. A single thin dispatcher `FilterSet.apply(...)` exists for backward compatibility but always picks the sync variant.

### Default usage — declaring a `FilterSet`

```python
from django_strawberry_framework.filters import FilterSet, RelatedFilter

from . import models

class GalaxyFilter(FilterSet):
    # Reverse FK — referenced lazily by string so Galaxy and CelestialBody
    # filtersets can live in the same file without an import cycle.
    celestial_bodies = RelatedFilter("CelestialBodyFilter", field_name="celestial_bodies")

    class Meta:
        model = models.Galaxy
        fields = {
            "name": "__all__",
            "description": ["exact", "icontains"],
        }

class CelestialBodyFilter(FilterSet):
    # Filter-scope constraint (NOT a security boundary — visibility and
    # security are the job of GalaxyType.get_queryset, not
    # RelatedFilter.queryset=). When the `galaxy` branch is present in
    # the input, the nested filter operates on `is_private=False` galaxies.
    # When the `galaxy` branch is absent (active-branch scoping), parent
    # rows are unconstrained — so any visibility gate MUST be enforced by
    # the target type's get_queryset hook.
    galaxy = RelatedFilter(
        GalaxyFilter,
        field_name="galaxy",
        queryset=models.Galaxy.objects.filter(is_private=False),
    )

    class Meta:
        model = models.CelestialBody
        fields = {
            "name": ["exact", "icontains"],
            "body_type": ["exact", "in"],
            "galaxy__name": ["exact"],
        }
```

`FilterSet` subclasses `django_filters.filterset.BaseFilterSet` (per [Decision 5](#decision-5--django-filter-as-the-foundation)), so consumers familiar with `django-filter` keep every primitive they already know — `declared_filters`, `base_filters`, `Filter.method`, `form`, `qs`, lookup parsing — and add the package's `RelatedFilter` lazy-resolution layer plus the GraphQL-input layer on top.

### Wiring into a `DjangoType`

```python
from django_strawberry_framework import DjangoType

from . import filters, models

class GalaxyType(DjangoType):
    class Meta:
        model = models.Galaxy
        fields = "__all__"
        filterset_class = filters.GalaxyFilter
```

`Meta.filterset_class` is the only wiring required at the `DjangoType` site. The finalizer-phase-2.5 binding (per [Decision 6](#decision-6--finalizer-phase-25-binding-seam--materialize-before-schema-ordering)) takes care of input-class materialization (as module globals of [`django_strawberry_framework.filters.inputs`][filters]), lazy-related-filter resolution, and registry registration.

### Exposing the `filter:` argument on a resolver

```python
import strawberry

from django_strawberry_framework.filters import filter_input_type

from . import filters, models

@strawberry.type
class Query:
    @strawberry.field
    def all_galaxies(
        self,
        info: strawberry.Info,
        filter: filter_input_type(filters.GalaxyFilter) | None = None,
    ) -> list[GalaxyType]:
        # Visibility scoping ALWAYS runs before any filter clause (per
        # Decision 8): GalaxyType.get_queryset() applies the
        # request-scoped permissions / staff visibility / per-tenant filtering.
        # Filter clauses then operate on the already-scoped queryset, so a
        # filter cannot see through the visibility gate to hidden rows.
        queryset = GalaxyType.get_queryset(models.Galaxy.objects.all(), info)
        if filter is not None:
            # apply_sync because GalaxyType.get_queryset is sync; an async-only
            # get_queryset hook would require apply_async per Decision 8's
            # sync/async split.
            queryset = filters.GalaxyFilter.apply_sync(filter, queryset, info)
        return queryset
```

`filter_input_type(filters.GalaxyFilter)` returns `Annotated["GalaxyFilterInputType", strawberry.lazy("django_strawberry_framework.filters.inputs")]`, the canonical Strawberry forward-reference idiom. At `@strawberry.type` decoration time, Strawberry stores the annotation unresolved; at `strawberry.Schema(...)` construction time, Strawberry's `LazyType.resolve_type` imports `django_strawberry_framework.filters.inputs` and reads `GalaxyFilterInputType` from `module.__dict__` — which the finalizer's phase-2.5 binding pass has materialized as a real module global by then. The consumer never touches `Annotated[...]` directly; the helper hides it.

`GalaxyFilter.apply_sync(input_value, queryset, info)` and `GalaxyFilter.apply_async(input_value, queryset, info)` are the **resolver-facing classmethod pair** per the sync/async split in [Decision 8](#decision-8--relation-permission-cascade--get_queryset-cooperation) (sync resolvers call `apply_sync`; async resolvers `await apply_async`). The thin `GalaxyFilter.apply(...)` dispatcher exists for backward compatibility and always picks the sync variant, catching the typed [`SyncMisuseError`][querysets] and rethrowing it as a `RuntimeError` naming `apply_async`. Both methods carry `info` end-to-end so nested `RelatedFilter` branches can derive the target type's visibility scope (see [Decision 8 step 3](#decision-8--relation-permission-cascade--get_queryset-cooperation)). The shared apply pipeline normalizes the Strawberry input dataclass into the form-data dict `django-filter` expects (walking nested `RelatedFilter` input objects, mapping `and_` / `or_` / `not_` Python attrs back into the logical-operator keys, mapping every per-lookup Python attribute back to its `django-filter` lookup name through `LOOKUP_NAME_MAP` per [Decision 3](#decision-3--six-layer-lazy-resolution-pipeline)); extracts the Django request through `FilterSet._request_from_info(info)`, which reads `info.context.request` when present and otherwise accepts `info.context` itself when it `isinstance(..., HttpRequest)`; any other shape raises [`ConfigurationError`][glossary-configurationerror] naming the unsupported `info.context` shape; instantiates `cls(data=data, queryset=queryset, request=request)`; runs the active-input permission pass `_run_permission_checks(input_value, request)` **with active-input-only scope** (per-field `check_<field>_permission` gates fire ONLY for fields present in the normalized input, NOT for every declared field — `check_name_permission` does not raise on `filter: { title: { iContains: ... } }`); **explicitly calls `filterset.form.is_valid()` and raises `from graphql import GraphQLError; GraphQLError("Invalid filter input", extensions={"code": "FILTER_INVALID", "errors": filterset.errors.get_json_data()})` when validation fails** (`BaseFilterSet.qs` only consults `self.errors` and falls through to `filter_queryset` otherwise, so an explicit raise is required; the `errors` payload uses `ErrorDict.get_json_data()` so consumers see the stable `{field: [{"message": str, "code": str}, ...]}` shape); constrains the queryset per active `RelatedFilter` branches (visibility-scoping the target then intersecting with any explicit `queryset=` filter-scope constraint); and returns `filterset.qs` — the `django-filter` instance's `.qs` property after all gates pass. The `apply_sync` / `apply_async` pair is the consumer surface; the inherited instance method `filter_queryset(self, queryset)` is reserved for the `django-filter` tree-form-logic override path (it has the `django-filter` signature `(self, queryset) -> QuerySet`, not the resolver signature `(input_value, queryset, info)`) and is not what consumer code calls.

When [`DjangoConnectionField`][glossary-djangoconnectionfield] ships in `0.0.9`, it accepts `filterset_class=` and owns the argument injection AND the `apply_sync(...)` / `apply_async(...)` call internally (selecting the variant based on the resolver's sync/async shape); the manual `filter_input_type(...)` annotation + `Filter.apply_sync(...)` / `Filter.apply_async(...)` body shown above is the explicit shape `0.0.8` consumers reach for at the resolver level and the same machinery the connection field reuses under the hood one card later.

### Per-field permission gates

```python
from graphql import GraphQLError

class GalaxyFilter(FilterSet):
    class Meta:
        model = models.Galaxy
        fields = {"name": "__all__", "description": ["exact", "icontains"]}

    def check_name_permission(self, request):
        """Only staff users may filter by Galaxy.name.

        Active-input-only scope:
        this gate fires ONLY when the consumer's filter input includes a
        ``name:`` clause. A query like ``{ allGalaxies { id name } }`` with
        no ``filter`` argument, OR a query like
        ``{ allGalaxies(filter: { description: { iContains: "..." } }) ... }``
        that filters only by ``description``, does NOT trigger this gate.
        Permissions gate USE of the filter, not its declaration.
        """
        user = getattr(request, "user", None)
        if not user or not user.is_staff:
            raise GraphQLError("You must be a staff user to filter by Galaxy name.")
```

The framework calls `check_<field>_permission(request)` before applying the corresponding filter — **but only for fields present in the normalized input** (active-input-only scope; see [Decision 8](#decision-8--relation-permission-cascade--get_queryset-cooperation) step 5). A `GraphQLError` raised inside the gate surfaces as an `errors` entry on the response. Use `from graphql import GraphQLError`.

### Logical-and / logical-or / logical-not

The factory auto-generates the three logical-operator fields on every `<TypeName>FilterInputType`. Python attribute names use the trailing-underscore convention (`and_`, `or_`, `not_`) because `and` / `or` / `not` are Python keywords and cannot appear as dataclass field names; the GraphQL surface names are exactly `and`, `or`, `not` via `strawberry.field(name="and")` / `name="or"` / `name="not"`. The same Python-keyword-vs-GraphQL-name pattern applies to the `in` lookup (Python attr `in_`, GraphQL name `in`) per [Decision 3](#decision-3--six-layer-lazy-resolution-pipeline) Layer-5's `LOOKUP_NAME_MAP`. Consumer-facing GraphQL shape:

```graphql
{
  allGalaxies(
    filter: {
      and: [
        {
          name: {
            iContains: "andromeda"
          }
        }
        {
          not: {
            isPrivate: {
              exact: true
            }
          }
        }
      ]
    }
  ) {
    id
    name
  }
}
```

The self-referential nature of the input type is handled by Layer 5's Strawberry-adapted forward reference per [Decision 3](#decision-3--six-layer-lazy-resolution-pipeline). The correct annotation shapes are:

- `and_: list[Annotated["<TypeName>FilterInputType", strawberry.lazy("django_strawberry_framework.filters.inputs")]] | None`
- `or_: list[Annotated["<TypeName>FilterInputType", strawberry.lazy("django_strawberry_framework.filters.inputs")]] | None`
- `not_: Annotated["<TypeName>FilterInputType", strawberry.lazy("django_strawberry_framework.filters.inputs")] | None`

The `Annotated[...]` MUST wrap the forward-reference string directly (`Annotated["Name", strawberry.lazy(...)]`), not the surrounding `list[...]`. Strawberry's `LazyType.resolve_type` only resolves the annotated argument when that argument itself is a `ForwardRef`; wrapping `list["Foo"]` in `Annotated[..., strawberry.lazy(...)]` leaves the inner `"Foo"` unresolved at schema build and surfaces a `NameError` from Strawberry's type evaluation. The shape above pushes the `Annotated[...]` inside the `list[...]`, where Strawberry sees the forward reference at the leaf and resolves it through `LazyType.resolve_type`.

### Error shapes

- `Meta.filterset_class = <non-FilterSet-class>` → [`ConfigurationError`][glossary-configurationerror]("`Meta.filterset_class` must be a `FilterSet` subclass; got `<class>`") at type creation.
- `RelatedFilter("UnknownFilter")` where `"UnknownFilter"` cannot be resolved by Layer 2's module-fallback → [`ConfigurationError`][glossary-configurationerror]("Cannot finalize ... no registered FilterSet named `'UnknownFilter'`") at finalization.
- Cycle-safe expansion exhausts the recursion guard (Layer 4's `_is_expanding_filters` re-entry detection) → [`ConfigurationError`][glossary-configurationerror]("Cycle detected in `FilterSet` related-filter graph; offending class: `<class>`") at finalization.
- `Meta.fields = {"unknown_field": ["exact"]}` where `"unknown_field"` is not a model field → [`ConfigurationError`][glossary-configurationerror]("`<FilterSet>.Meta.fields` references unknown model field: `'unknown_field'`") at type creation.
- `Meta.fields = {"name": ["unsupported_lookup"]}` where the lookup is not registered for the field type → [`ConfigurationError`][glossary-configurationerror]("Lookup `'unsupported_lookup'` not supported for field `'name'` on model `<Model>`") at type creation.
- `filter_input_type(<non-FilterSet>)` → `TypeError("filter_input_type() requires a FilterSet subclass; got <class>")` at call time (the helper is a function, validation runs eagerly even though the returned `Annotated[...]` shape itself is lazy).

### Decision 2 — Subpackage layout and public export surface

The filter subsystem ships as a subpackage at **[`django_strawberry_framework/filters/`][filters]** (NOT a flat single-file module). Five files:

- `__init__.py` — re-exports `FilterSet`, `RelatedFilter`, `filter_input_type` (the consumer helper per [Decision 11](#decision-11--filter_input_typefilterset-consumer-helper)), and (for advanced uses) `Filter`, `TypedFilter`, `ArrayFilter`, `RangeFilter`, `ListFilter`, `GlobalIDFilter`.
- `base.py` — `TypedFilter`, `ArrayFilter`, `RangeFilter`, `RangeField`, `validate_range`, `ListFilter`, `GlobalIDFilter` (Strawberry-specific: accepts both `str` and `relay.GlobalID` inputs; validates decoded `type_name` against the owner's related target), `GlobalIDMultipleChoiceFilter`, `RelatedFilter`. Two names on this surface are re-exports rather than package classes: **`Filter` IS `django_filters.Filter` itself** — a plain re-export, no subclass, deliberately shadowing the upstream name so a consumer writing a custom `method=` filter imports one base class from `django_strawberry_framework.filters`; and `LazyRelatedClassMixin` is re-exported from [`django_strawberry_framework/sets_mixins.py`][sets-mixins].
- `sets.py` — `FilterSetMetaclass`, `FilterSet` (with `Meta.model`, `Meta.fields`, `FILTER_DEFAULTS` class attr + `filter_for_field` / `filter_for_lookup` overrides per [Decision 4](#decision-4--upstream-primitives-parity-floor), `_owner_definition: DjangoTypeDefinition | None` slot bound at finalizer phase 2.5 per [Decision 9](#decision-9--input-class-namespace-vs-typeregistry-and-lifecycle), the resolver-facing classmethod **pair** `apply_sync(input_value, queryset, info) -> QuerySet` / `apply_async(input_value, queryset, info) -> Awaitable[QuerySet]` per [Decision 8](#decision-8--relation-permission-cascade--get_queryset-cooperation) sync/async split + [Decision 11](#decision-11--filter_input_typefilterset-consumer-helper) (both carry `info` into nested `RelatedFilter` application for visibility scoping; sync resolvers call `apply_sync`, async resolvers `await apply_async`), plus the thin `apply(...)` dispatcher kept for backward compatibility (calls `apply_sync` internally, catching the typed [`SyncMisuseError`][querysets] and rethrowing a `RuntimeError`); five named internal helpers reachable on `FilterSet` (`_normalize_input`, `_derive_related_visibility_querysets_sync` / `_async`, `_run_permission_checks` — inherited from [`sets_mixins.py::ActiveInputPermissionMixin`][sets-mixins] — `_validate_form_or_raise`, `_apply_related_constraints`); `get_filters`, `get_fields` (the public `django-filter` classmethod, overridden to pin the `Meta.fields = "__all__"` semantics — INCLUDE PK / FK columns, EXCLUDE M2M), `filter_queryset` (the `django-filter` instance-method override for tree-form logic), `check_permissions` (active-input-only scope), `_apply_related_constraints` (active-branch scoping — runs only when the related filter branch is present in normalized input)).
- `factories.py` — `FilterArgumentsFactory` (input shape derived from the resolved filter instances via the named converter `convert_filter_to_input_annotation(filter_instance, model_field, owner_definition)`), `get_filterset_class`, `_dynamic_filterset_cache`. (Note: `FILTER_DEFAULTS` lives in `sets.py` on the `FilterSet` class; runtime `django-filter` consults `cls.FILTER_DEFAULTS` and the factory consults the resolved filter instances through the named converter, so the two cannot drift.)
- `inputs.py` — per-module input-class namespace, `build_input_class`, `_build_logic_fields`, `_build_input_fields`, `construct_search`, `LOOKUP_PREFIXES` (the `^` / `=` / `@` / `$` search prefixes), `LOOKUP_NAME_MAP` (the `<django-filter-lookup> → (python_attr, graphql_name)` map covering every supported lookup — `icontains → ("i_contains", "iContains")`, `iexact → ("i_exact", "iExact")`, `istartswith → ("i_starts_with", "iStartsWith")`, `iendswith → ("i_ends_with", "iEndsWith")`, `iregex → ("i_regex", "iRegex")`, `isnull → ("is_null", "isNull")`, `in → ("in_", "in")`, `range → ("range", "range")`, etc.), `FieldSpec` dataclass + `_field_specs: dict[tuple[type[FilterSet], str], FieldSpec]` table (carries `(python_attr, graphql_name, django_source_path)` per generated input field so the runtime normalizer can rebuild ORM paths like `galaxy__name` from the flattened `galaxyName` field without reverse-mangling), `convert_filter_to_input_annotation(filter_instance, model_field, owner_definition)` (the named filter-to-Strawberry-input converter handling choice enums, `relay.GlobalID`, `in` / `range` list shapes, nullable values, decimal / date / datetime / time / UUID, custom `Filter(method=...)` fields), `normalize_input_value(filter_instance, raw_value, field_name=None)` (the runtime symmetric of `convert_filter_to_input_annotation` — normalizes Strawberry input dataclass values back into the form-data shape `django-filter` expects; consults the `_field_specs` table for `django_source_path` keys), `materialize_input_class`, `clear_filter_input_namespace`, `_materialized_names`.

**Where the mechanics live.** Several names this Decision pins are **domain-local aliases or inherited mixin members** rather than filter-owned implementations: the generated-input substrate is single-sited so the filter and order families share one implementation, and the `filters/` names stay addressable because tests and `factories.py` import them from there. The six rows below are the ones a reader chasing an implementation is most likely to go looking for, and they are not the whole set — `materialize_input_class`, `clear_filter_input_namespace`, `_materialized_names` and `_field_specs` are likewise produced by [`utils/inputs.py::make_set_input_namespace`][utils-inputs], which returns the ledger / field-spec-table / materialize / clear quartet that `filters/inputs.py` binds under those spec-named wrappers.

| --- | --- |
| `filters/inputs.py::FieldSpec` | [`utils/inputs.py::GeneratedInputFieldSpec`][utils-inputs] |
| `filters/inputs.py::build_input_class` | [`utils/inputs.py::build_strawberry_input_class`][utils-inputs] |
| `filters/inputs.py::_input_type_name_for` | [`utils/inputs.py::set_input_type_name`][utils-inputs] |

Public re-export from `django_strawberry_framework` is opted-in by the subpackage's `__init__.py`, NOT by the top-level package: consumers `from django_strawberry_framework.filters import FilterSet, RelatedFilter, filter_input_type` (matching the import shape in [`GOAL.md`][goal]'s astronomy showcase). The top-level package's `__all__` is unchanged in `0.0.8` — adding the filter symbols to the top-level surface widens it for every consumer including those who never use filters; the subpackage import path is the right grain.

### Decision 3 — Six-layer lazy-resolution pipeline

The pre-pinned architectural answer (from the [`KANBAN.md`][kanban] card body's "Recommended architectural direction" block) is borrowed verbatim and preserved here. Five of six layers port from `django-graphene-filters` library-agnostic (with `django_filters.filterset.BaseFilterSet` as the shared foundation per [Decision 5](#decision-5--django-filter-as-the-foundation)); only Layer 5 is Strawberry-adapted.

**Layer 1 — Lazy class references in `RelatedFilter`** — port verbatim from `django_graphene_filters/filters.py::BaseRelatedFilter`. `RelatedFilter` accepts target as class, absolute import path string (`"myapp.filters.ManagerFilter"`), or unqualified name (`"ManagerFilter"`). `_filterset` stores it unresolved; the `.filterset` property triggers resolution.

**Layer 2 — Module-fallback resolution** — port verbatim from `django_graphene_filters/mixins.py::LazyRelatedClassMixin.resolve_lazy_class`. Two-step resolution: try as absolute path via `django.utils.module_loading.import_string`; on `ImportError`, retry with `bound_class.__module__` prefix. Handles circular-import scenarios in the same module.

**Layer 3 — Metaclass discovery, deferred expansion** — port pattern from `django_graphene_filters/filterset.py::FilterSetMetaclass`. Metaclass collects `BaseRelatedFilter` declarations into `cls.related_filters`, calls `f.bind_filterset(new_class)` so the module-fallback resolver knows the owning module, and **does not** expand. Expansion is deferred to `get_filters()`.

**Layer 4 — Cycle-safe expansion + cache** — port verbatim from `django_graphene_filters/filterset.py::AdvancedFilterSet.get_filters`. `cls.__dict__["_expanded_filters"]` cache plus `cls.__dict__["_is_expanding_filters"]` recursion guard. Two-condition cache write: `"related_filters" in cls.__dict__` AND no string `_filterset` remaining on any related filter. Breaks `A → B → A` cycles cleanly.

**Layer 5 — BFS schema build with module-global materialization (Strawberry-adapted)** — port the BFS algorithm in `django_graphene_filters/filter_arguments_factory.py::FilterArgumentsFactory._ensure_built` verbatim; the cycle-safe forward reference changes shape because Strawberry's lazy mechanism is module-path-only, NOT object-path. Specifically:

- Strawberry's [`strawberry.types.lazy_type.LazyType.resolve_type`](https://strawberry.rocks) imports the module named in `strawberry.lazy("<module-path>")` and reads `module.__dict__[type_name]`. It does NOT traverse object paths (`module.attr.subattr`) and does NOT look up entries in a dict named `_registry`. Verified by direct inspection of the installed Strawberry.
- Consequence: every generated filter input class MUST be a **real module global** of [`django_strawberry_framework.filters.inputs`][filters] (i.e., set via `setattr(sys.modules["django_strawberry_framework.filters.inputs"], name, cls)` or by direct attribute assignment), not an entry in a private dict.
- The Strawberry idiom is `Annotated["{TargetFilterSet}InputType", strawberry.lazy("django_strawberry_framework.filters.inputs")]` — a string forward-reference combined with the module-path marker. At schema-build time, Strawberry imports the module, looks up the unquoted name in `module.__dict__`, and resolves the forward reference.
- The `Annotated[...]` MUST directly wrap the forward-reference string. For list-typed fields (`and_` / `or_` logical operators, `in` / `range` value shapes, multi-value `RelatedFilter` inputs), push the `Annotated[...]` INSIDE the `list[...]`: `list[Annotated["Name", strawberry.lazy(...)]] | None`, NOT `Annotated[list["Name"], strawberry.lazy(...)] | None`. Strawberry's `LazyType.resolve_type` only resolves the annotated argument when that argument itself is a `ForwardRef`; wrapping the outer `list[...]` leaves the inner `"Name"` unresolved at schema-build time.
- `FilterArgumentsFactory._ensure_built` emits the `Annotated[...]` shape in field annotations so cycle-safe references between filtersets keep working; it does **not** write module globals. Materialization is the finalizer's: the helper [`materialize_input_class(name, cls)`][filters] in `inputs.py` — two-argument signature; the destination module is always `django_strawberry_framework.filters.inputs` so it is not a parameter — is called once per built class at phase-2.5 subpass 4 (per [Decision 6](#decision-6--finalizer-phase-25-binding-seam--materialize-before-schema-ordering)), whose filter-side entry point is [`django_strawberry_framework/types/finalizer.py::_bind_filtersets`][finalizer] and whose materialize loop is the shared `_bind_sidecar_sets` one level down. This is what [Decision 4](#decision-4--upstream-primitives-parity-floor) states from the other side — `_ensure_built` "only controls the Strawberry input shape".
- Per-lookup field names are pinned through a `LOOKUP_NAME_MAP` constant in `inputs.py`. Strawberry's default auto-camel-case only fires on underscored Python identifiers — `icontains` stays `icontains` because there is no underscore to transform. The map enumerates every supported `django-filter` lookup as `lookup_name → (python_attr, graphql_name)`:

  | django-filter lookup | Python attr (dataclass field) | GraphQL name (explicit) |
  | --- | --- | --- |
  | `exact` | `exact` | `exact` |
  | `iexact` | `i_exact` | `iExact` |
  | `contains` | `contains` | `contains` |
  | `icontains` | `i_contains` | `iContains` |
  | `startswith` | `starts_with` | `startsWith` |
  | `istartswith` | `i_starts_with` | `iStartsWith` |
  | `endswith` | `ends_with` | `endsWith` |
  | `iendswith` | `i_ends_with` | `iEndsWith` |
  | `regex` | `regex` | `regex` |
  | `iregex` | `i_regex` | `iRegex` |
  | `gt` / `gte` / `lt` / `lte` | `gt` / `gte` / `lt` / `lte` | `gt` / `gte` / `lt` / `lte` |
  | `isnull` | `is_null` | `isNull` |
  | `in` | `in_` | `in` |
  | `range` | `range` | `range` |
  | `date` / `year` / `month` / `day` / `week_day` / `quarter` / `hour` / `minute` / `second` | mirror | camelCase |

  Both the factory (`_build_input_fields`) and the runtime input-data normalizer (`normalize_input_value`) consult `LOOKUP_NAME_MAP` so the GraphQL surface and the form-data conversion never disagree. `_build_input_fields` emits each lookup field via `strawberry.field(name=<graphql_name>)` when `python_attr != graphql_name`. The `in` lookup uses `in_` as Python attr because `in` is a Python keyword and cannot appear as a dataclass field name; `normalize_input_value` maps `in_` → `in` when constructing the form-data dict.

**Per-field source-path mapping via `FieldSpec`.** `Meta.fields = {"galaxy__name": ["exact"]}` renders as the flat GraphQL field `galaxyName: { exact: ... }`, so the generated input field has to carry the Django source path `galaxy__name` for the runtime normalizer to rebuild. `LOOKUP_NAME_MAP` covers `(python_attr, graphql_name)` for lookups and is silent on Django source-path-vs-public-name for the parent field, so every generated input field carries a `FieldSpec` record alongside it. The dataclass is the shared generated-input substrate's [`utils/inputs.py::GeneratedInputFieldSpec`][utils-inputs], re-exported as `FieldSpec` by `filters/inputs.py` (and, identically, by `orders/inputs.py`) so both families map between the same three names:

```python
# django_strawberry_framework/utils/inputs.py
from dataclasses import dataclass

@dataclass(frozen=True)
class GeneratedInputFieldSpec:
    """Mapping from a generated Strawberry input field to its Django source path.

    The runtime normalizer must NOT reconstruct the
    Django ORM lookup path from the GraphQL / Python field name (which loses
    information when paths like `galaxy__name` flatten to `galaxyName`). It
    consults the FieldSpec table instead.
    """
    python_attr: str          # dataclass field name on the Strawberry input class (e.g., "galaxy_name")
    graphql_name: str         # wire-format name via strawberry.field(name=...) (e.g., "galaxyName")
    django_source_path: str   # canonical Django ORM lookup expression (e.g., "galaxy__name", or "name" for same-model)
```

`_build_input_fields` constructs the `FieldSpec` table at materialization time, keyed by `(filterset_class, python_attr)`. `normalize_input_value(filter_instance, raw_value, field_name=None)` consults the `FieldSpec` for each active filter branch to look up `django_source_path` AND emits form-data keys using that source path (e.g., the form-data dict for an active `galaxyName` branch carries `{"galaxy__name": <value>}`, NOT `{"galaxyName": <value>}` or a reverse-mangled `{"galaxy_name": <value>}`). The test plan covers this end-to-end with `test_field_spec_maps_galaxy_name_flat_field_to_django_source_path` — pins that the flat field's runtime normalizer produces the expected `galaxy__name` ORM expression regardless of the mangling between Django path → Python attr → GraphQL name.

**`HIDE_FLAT_FILTERS` — the one setting attached to the flat-field contract.** The flat rendering above is the default, and the default is what every other clause in this spec pins. A consumer who wants only the nested `RelatedFilter` surface sets `DJANGO_STRAWBERRY_FRAMEWORK["HIDE_FLAT_FILTERS"] = True`, read through the named reader [`conf.py::hide_flat_filters_setting`][conf] (default `False`). When set, `_build_input_fields` skips every grouped entry that is an **expanded child** of a declared `RelatedFilter` — a flat relational traversal path whose first segment names the relation (`category__name`, `entries__property__category__name`) — at every depth, not just one hop. Nothing becomes unreachable: those paths are still filterable through the nested branch, which stays visible. A same-model path (`name`, or a `__` lookup that traverses no relation) is never an expanded child and stays visible either way. The key is opt-in and the default preserves the shape pinned here, so this widens the contract rather than changing it; the upstream analogue is the same `is_expanded_child` skip in `django_graphene_filters/connection_field.py::_get_trimmed_filterset_class`.

Graphene's `graphene.InputField(lambda tn=target_name: input_object_types[tn])` and the new Strawberry idiom (`Annotated["...", strawberry.lazy("...")]` over a module-global namespace) are conceptual twins — both defer the type reference until schema walk; only the lookup mechanism differs (dict-keyed for Graphene; `module.__dict__` keyed for Strawberry).

**Layer 6 — Memoized dynamic FilterSet generation** — port verbatim from `django_graphene_filters/filterset_factories.py::_dynamic_filterset_cache`. Cache keyed by `(model, fields, extra_meta)` for connection fields declared without an explicit `filterset_class`; prevents duplicate-`__name__` collisions when two connection fields target the same model. (This card lands the cache plumbing; the connection-field consumer is `0.0.9`.)

**`Meta.fields = "__all__"` scope and intentional override of django-filter's default.** The shorthand expands to scalar fields plus their default lookups AND each FK / PK column under the conditional `FILTER_DEFAULTS` per [Decision 4](#decision-4--upstream-primitives-parity-floor). Relation traversal under `"__all__"` is **explicitly excluded** — a relation appears in the generated input only when the consumer declares `RelatedFilter(...)` for it. This is an **intentional override** of `django-filter`'s default `get_all_model_fields` behavior, which differs in two ways:

- `django-filter`'s `django_filters.utils.get_all_model_fields` walks `opts.fields + opts.many_to_many` and **excludes** `AutoField` primary keys; the package's `get_fields` override **includes** PK / FK columns because Relay-aware filtering (`GlobalIDFilter` for Relay targets, scalar PK for non-Relay targets per [Decision 4](#decision-4--upstream-primitives-parity-floor)) MUST be reachable via `Meta.fields = "__all__"` — otherwise the most common "filter by ID" use case would be unreachable through the shorthand.
- `django-filter` **includes** M2M relations; the package's `get_fields` override **excludes** M2M because traversing a M2M without an explicit target `FilterSet` would either auto-generate one (the [Non-goals](#non-goals) "no implicit `FilterSet` generation" rule forbids this) or expose a bare-PK filter against a M2M, which is a different shape from what consumers want when filtering through a relation.

`FilterSet.get_fields` carries the override — the package overrides the public `django-filter` classmethod rather than adding a private one — and the cookbook's recursion-protected walk with `visited: set[type]` lands on top. Tests pin both deltas: `id` IS generated for `"__all__"` AND a M2M relation is NOT generated without an explicit `RelatedFilter`.

### Decision 4 — Upstream-primitives parity floor

The package ships parity equivalents for every verified upstream filter primitive named in the [`KANBAN.md`][kanban] card body:

- `ArrayFilter(TypedFilter)`, `ArrayFilterMethod(FilterMethod)` (from `graphene_django/filter/filters/array_filter.py`).
- `RangeFilter(TypedFilter)`, `RangeField(Field)`, `validate_range` (from `graphene_django/filter/filters/range_filter.py`).
- `ListFilter(TypedFilter)`, `ListFilterMethod(FilterMethod)` (from `graphene_django/filter/filters/list_filter.py`).
- `TypedFilter(Filter)` (from `graphene_django/filter/filters/typed_filter.py`) — base class for the four above.
- `GlobalIDFilter(Filter)`, `GlobalIDMultipleChoiceFilter(MultipleChoiceFilter)` (from `graphene_django/filter/filters/global_id_filter.py`).

The `FILTER_DEFAULTS` map is a **class attribute on the package `FilterSet`** (not a factory-side parallel map) so the `django-filter` runtime AND the Strawberry input factory agree on the chosen filter primitive. The mapping is **conditional on the target `DjangoType`'s Relay shape AND owner-aware**:

- FK / PK whose **owning `FilterSet`'s target `DjangoType`** (resolved through the filterset's `_owner_definition`, NOT the model's primary type) implements `relay.Node` (per `Meta.interfaces = (relay.Node,)`, shipped in `DONE-015-0.0.5`) → `GlobalIDFilter` (the Relay-`GlobalID`-aware primitive); the filter input accepts the Strawberry `relay.GlobalID` string shape and the factory decodes it back to the underlying PK before applying the queryset filter.
- FK / PK whose owning filterset's target `DjangoType` is **non-Relay** (the default — most `DjangoType`s today, e.g., `ShelfType` in the fakeshop library app) → the scalar PK filter derived from the target PK column's Django scalar conversion (per [`django_strawberry_framework/types/converters.py::SCALAR_MAP`][filters]); the filter input accepts the raw PK value (typically `int`, sometimes `uuid.UUID` or `BigInt`).

**Owner awareness.** Under [`Meta.primary`][glossary-metaprimary], a model can have multiple `DjangoType`s — for example, a primary `PublicGenreType` (non-Relay scalar `int` PK) AND a secondary `AdminGenreType` (Relay-Node-shaped via `Meta.interfaces = (relay.Node,)`). If `BookFilter.genres` (bound to `BookType`'s `_owner_definition`) is generated by consulting `registry.get(Genre)` alone, it would resolve to the primary `PublicGenreType` regardless of which type the filter is exposed on — so `AdminBookType.genres` could expose a scalar-`int` filter against a Relay-shaped admin genre type (wire-shape mismatch). The rule: the FK/PK conditional consults `owner_definition.related_target_for(field_name)`, which walks the owning `DjangoType`'s relation map (NOT the global registry) to find the related target type.

**Multi-owner reuse — strict exact-type-name match.** A compatible Relay/scalar shape on every related target is **not** sufficient for a second owner to bind the same `FilterSet`. Relay GlobalID runtime validation depends on the concrete GraphQL type name (`graphql_type_name`), not just whether the target is Relay-shaped. Two owners can both expose Relay nodes via different GraphQL type names — e.g., `PublicGenreType` vs `AdminGenreType` over the same `Genre` model under `Meta.primary` — and reusing the first owner's `_owner_definition` for the second would validate / encode GlobalIDs against the wrong type name (a `GenreType` ID encoded for the public surface would be silently accepted by the admin filter, or vice versa). The rule for second-owner binding (applied at finalizer phase-2.5 subpass 1 per [Decision 6](#decision-6--finalizer-phase-25-binding-seam--materialize-before-schema-ordering)):

- Second-owner binding is allowed ONLY when, for EVERY owner-sensitive target (every FK / PK / M2M that hits the `FILTER_DEFAULTS` conditional or `GlobalIDFilter` validation), the new owner's `related_target_for(field_name)` returns the EXACT same `DjangoTypeDefinition` AND the EXACT same `graphql_type_name` as the first owner's.
- Any divergence (different `DjangoTypeDefinition` instance OR different `graphql_type_name` even if same definition) raises [`ConfigurationError`][glossary-configurationerror] naming both owners, the offending field, and BOTH resolved target type names. Consumers wanting per-owner surfaces declare two separate `FilterSet` subclasses (`PublicBookFilter` / `AdminBookFilter`) — the input-class namespace is name-keyed so the two generate two distinct input types per [Decision 9](#decision-9--input-class-namespace-vs-typeregistry-and-lifecycle).
- Forward path: caching by `(filterset_class, owner_definition)` to produce per-owner input classes (and a single declared `FilterSet` that binds to multiple owners with diverging targets) is documented as a follow-up shape for `0.0.9` if real consumer demand surfaces; the `0.0.8` shape is the stricter reject.

The validation runs at finalizer phase 2.5 subpass 1 when both owners are visible per [Decision 6](#decision-6--finalizer-phase-25-binding-seam--materialize-before-schema-ordering); tests cover both the same-`graphql_type_name` accept case AND the diverging-`graphql_type_name` reject case explicitly.

**Where the conditional runs.** The conditional runs on the `FilterSet`, NOT inside `FilterArgumentsFactory._ensure_built`: `_ensure_built` only controls the Strawberry input shape, while `django-filter` instantiates the actual filter instances earlier via `filterset.BaseFilterSet.filter_for_field()` / `filter_for_lookup()`, which read `cls.FILTER_DEFAULTS`. A factory-only conditional would let the GraphQL input expose `relay.GlobalID` for `BookFilter.genres` while the runtime filter instance is whatever vanilla `django-filter` generated — wire-shape disagreement at the queryset translation step. The shape:

- `FilterSet.FILTER_DEFAULTS` is the same dict shape `django-filter` consumes (`{django.db.models.Field: {"filter_class": ..., "extra": ...}}`).
- `FilterSet.filter_for_field(cls, field, field_name, lookup_expr)` and `FilterSet.filter_for_lookup(cls, field, lookup_type)` override the cookbook ancestors. For relation fields, they consult `cls._owner_definition.related_target_for(field_name)` to find the owning type's related target `DjangoType` (falls back to `registry.get(target_model)` only when `_owner_definition` is `None` — the dynamic-factory path before owner binding completes), then check `implements_relay_node(target_type)` (the same predicate used by [`finalize_django_types`][finalizer]'s phase 2.5 Relay-Node injection) to pick the `GlobalIDFilter` branch vs the scalar PK branch.
- The chosen filter primitive lands in the FilterSet's `declared_filters` / `base_filters` via the standard `django-filter` machinery. `get_filters()` (Layer 4 of [Decision 3](#decision-3--six-layer-lazy-resolution-pipeline)) expands them with the cycle-safe guard.
- `FilterArgumentsFactory._ensure_built` derives the Strawberry input field type **from the resolved filter instances** via the named converter `convert_filter_to_input_annotation(filter_instance, model_field, owner_definition)`, NOT from a parallel `FILTER_DEFAULTS` lookup. The input shape is downstream of the filter shape, so the two cannot drift.

**`convert_filter_to_input_annotation(filter_instance, model_field, owner_definition)` contract.** Standard `django-filter` filters do not expose an `input_type` attribute; they expose Django form fields through `filter_instance.field`. The named converter handles the form-field-to-Strawberry-annotation translation for every primitive the package ships:

| `filter_instance` shape | Strawberry input annotation |
| --- | --- |
| `CharFilter` / scalar `*Filter` with `lookup_expr` other than `in` / `range` | the scalar Python type (`str`, `int`, `bool`, `decimal.Decimal`, `datetime.date`, `datetime.datetime`, `datetime.time`, `uuid.UUID`) derived from the model field's `to_python` |
| `ChoiceFilter` / `TypedChoiceFilter` | Strawberry `Enum` member generated by the existing converter pipeline at [`django_strawberry_framework/types/converters.py::SCALAR_MAP`][filters] (which wraps Django `TextChoices` / `IntegerChoices` into a Strawberry enum whose `.value` is the DB value); runtime normalizes the member back to the DB value via `enum_member.value`. `convert_filter_to_input_annotation` consults the converter pipeline AND raises [`ConfigurationError`][glossary-configurationerror] for any choice filter whose source is not a `Choices`-derived enum, with a suggestion to wrap the choices through the existing pipeline. |
| `GlobalIDFilter` (Relay branch) | `str` (the GlobalID string form); runtime accepts both `str` and `relay.GlobalID` objects |
| `ListFilter` (`in` lookup) | `list[<scalar>]`; runtime passes the list through to `django-filter`'s form clean |
| `RangeFilter` (`range` lookup) | a Strawberry input dataclass `{start: T \| None, end: T \| None}`; runtime emits the two **positional** form-data keys `<field>_0` (start) and `<field>_1` (end) — verified by direct inspection: `django_filters.RangeFilter.field` is a `RangeField` whose `RangeWidget.value_from_datadict` reads `name_0` / `name_1`, NOT named `_from` / `_to` keys (the cookbook follows the same positional shape). The package's `normalize_input_value` for `RangeFilter` constructs the two positional keys; tests pin the form-data layout. |
| `Filter(method=<callable>)` (custom-method filters) | the converter inspects `filter_instance.field.__class__` and maps form-widget shape to Strawberry annotation; if the form field is unknown, raises [`ConfigurationError`][glossary-configurationerror] naming the filter and method |
| Nullable filters (`required=False`) | the converter wraps the chosen annotation in `T \| None` |

`normalize_input_value(filter_instance, raw_value, field_name=None)` is the runtime symmetric: it consumes the Strawberry-shaped input value and produces the form-data shape `django-filter`'s `BaseFilterSet.form.is_valid()` expects. `field_name` is the form-data key the caller resolved for this branch and is what supplies the `<field>` prefix in the multi-key shape below; both production call sites in `sets.py::FilterSet._normalize_input` pass it, and the default covers the direct-filter case where `filter_instance.field_name` already carries the same string. It returns one of **three** shapes, and the multi-key one is why it returns a value rather than writing into the form-data dict itself:

- a **scalar**, when the filter consumes a single form-data key — an Enum member normalizes to `enum.value`; a `relay.GlobalID` object normalizes to its base64 **wire string**, re-encoded rather than pre-decoded to a bare `node_id`, so the bound `GlobalIDFilter` can validate the `type_name` against the owner-aware expected type before any decode (see the Strawberry-specific `GlobalIDFilter` block below — passing a pre-decoded `node_id` here would strip the `type_name` ahead of the validation that depends on it);
- a **`list`**, for `GlobalIDMultipleChoiceFilter` / `ListFilter` / `ArrayFilter`, and for the `BaseCSVFilter` family `django-filter` generates from a `Meta.fields` `in` / `range` lookup (`BaseInFilter` / `BaseRangeFilter` subclasses, including this package's `IntegerInFilter` / `IntegerRangeFilter` reroutes) — every one of which `django-filter` consumes as a list. The `BaseCSVFilter` entry precedes the `RangeFilter` entry in `inputs.py`'s `_FILTER_INPUT_KIND_TYPES` dispatch order, so a `range` lookup declared through `Meta.fields` takes this **list** shape while a filter declared as `RangeFilter` takes the **dict** shape below — one lookup name, two normalized shapes, decided by how the filter was declared;
- a **`dict[str, Any]` patch the caller merges into the form-data dict**, when the filter consumes more than one positional form-data key — the Strawberry range dataclass normalizes to `{<field>_0, <field>_1}` per the `RangeFilter` row above, `<field>` being the `field_name` argument rather than the Strawberry attribute name. `None`-valued axes are omitted, so a start-only range yields `{<field>_0}`, an end-only range `{<field>_1}`, and an all-`None` range `{}` — the form-data "axis not supplied" convention `django-filter` consumes. The patch shape is what lets `_normalize_input` merge a multi-key filter's contribution without inventing a sentinel-pair object to carry the two halves.

**Strawberry-specific `GlobalIDFilter`.** The ported `GlobalIDFilter` / `GlobalIDMultipleChoiceFilter` are NOT verbatim copies of `graphene_django/filter/filters/global_id_filter.py` — the graphene primitive parses a raw string and discards the decoded `type_name`, which means a `GenreType`-filter accepting `relay.GlobalID(type_name="LoanType", node_id="42")` would silently filter `Book.genres__id=42` (matching against a `Loan` row's PK that happens to coincide with a `Genre` row's PK). The Strawberry adaptation:

- Accepts both raw `str` and `strawberry.relay.GlobalID` objects: `isinstance(value, relay.GlobalID)` short-circuits the decode; otherwise the filter calls `relay.GlobalID.from_id(value)` to parse the encoded string.
- Validates the decoded `type_name` against the expected target GraphQL type name. The expected name is resolved through `owner_definition.related_target_for(field_name).graphql_type_name` (the same owner-aware lookup as the FK/PK conditional above). Mismatch raises `GraphQLError("GlobalID type mismatch: filter expects <expected> but received <actual>")` before any queryset clause runs.
- Passes only `node_id` to `django-filter`'s form clean — the form sees a scalar PK, not the encoded string.
- `GlobalIDMultipleChoiceFilter` validates every element of the list independently; a single wrong-type element rejects the whole input with the offending index named in the error.
- Rejects an input that does not decode to a usable identifier with the coded error `GraphQLError(..., extensions={"code": "GLOBALID_INVALID"})` — the uniform coded error the node-refetch path also emits (`relay.py::_decode_or_graphql_error`). Two well-formedness rejections share this code: (a) a **malformed wire string** (unparseable base64 / not a `type_name:node_id` payload), surfaced instead of leaking Strawberry's raw `GlobalIDValueError`; and (b) — the sibling rule — a **well-formed GlobalID whose decoded `node_id` is empty** (e.g. `to_base64("BookNode", "")`), which passes decode / strategy / `type_name` validation but is not a valid resource identifier. Accepting an empty decoded id would silently widen a restrictive predicate (a scalar no-op, or a dropped list element turning `{in: ["type:"]}` into an unfiltered query), so it is rejected as the same class of bad input as a malformed payload rather than treated as a no-op or silently dropped. Both rejections apply consistently to the scalar `GlobalIDFilter` and the multiple `GlobalIDMultipleChoiceFilter`; for the multiple filter the offending list index is named in the message (the `index=` argument threaded through `django_strawberry_framework/filters/base.py::_decode_and_validate_global_id`). Only a `None` value (omission) and an explicit `[]` (match-none, `GlobalIDMultipleChoiceFilter`) remain non-error paths. This is a general GlobalID input contract, independent of the [row-preserving to-many predicate machinery][part1-plan] that shares the same decode boundary. The empty-decoded-`node_id` rejection is exercised by THREE live `/graphql/` acceptance tests in [`examples/fakeshop/test_query/test_library_api.py`][fakeshop-test-library] — a scalar `exact` filter, an all-empty `in` list, and a mixed `in` list whose offending index is named — that are ADDITIONAL to this card's original "exactly 14" contracted live tests, which predate this contract and do not count them.

**Why this matters.** A blanket "FK/PK → `GlobalIDFilter`" mapping (mirroring `graphene-django`'s unconditional shape) would break non-Relay filters: a consumer filtering `Book.shelf` by ID against a non-Relay `ShelfType` would have to pass a GlobalID-encoded string even though the exposed GraphQL type uses an integer ID — a wire-shape mismatch the consumer would discover at the first query. Consulting `registry.get(target_model)` instead would break multi-`DjangoType` setups where the primary and secondary types differ in Relay shape. The owner-aware shape pinned above closes both gaps. `graphene-django`'s filter-connection-path defaults are unconditional because that path Relay-shapes by construction (its `DjangoFilterConnectionField` always returns a Relay connection); but `graphene-django`'s `DjangoObjectType` itself supports non-Relay shapes too — the unconditional `GlobalIDFilter` is specifically tied to the filter-connection path's defaults, not the framework as a whole. The package's default is non-Relay (`Meta.interfaces = (relay.Node,)` is opt-in), the package supports multi-`DjangoType`-per-model, and the package's filter surface is the FilterSet itself (not a connection-field wrapper yet — that's `0.0.9`), so the conditional + owner-aware shape matches the actual GraphQL surface the consumer sees.

**Name-collision note:** `graphene_django/filter/utils.py::get_filterset_class` and `django_graphene_filters/filterset_factories.py::get_filterset_class` are different functions with the same name. The card body's "Verified upstream factory machinery" section flags this; this card mirrors the cookbook's shape (the `BaseFilterSet`-aware get-or-create helper), NOT graphene-django's shape (the explicit-vs-dynamic dispatcher). Reason: the cookbook's `get_filterset_class` is the entry point the BFS factory uses; graphene-django's is a different shape pinned to connection-field declaration. We need the cookbook's, the connection field needs neither in `0.0.8`.

Rationale companion — this Decision's justification, its two rejected alternatives, and the owner-awareness tightening history: [Decision 4][rationale-d4].

### Decision 5 — `django-filter` as the foundation

The package's `FilterSet` **subclasses `django_filters.filterset.BaseFilterSet`** and `django-filter` remains a **hard dependency** at [`pyproject.toml #"django-filter>=25.2"`][pyproject]. The cookbook's `AdvancedFilterSet` is built on `django_filters.filterset.BaseFilterSet` and reuses its load-bearing machinery (`declared_filters`, `base_filters`, `.filters`, `.form`, `.qs`, `get_filters()`, `Filter.method`, form cleaning, lookup generation); porting the cookbook verbatim without that inheritance would mean re-implementing all of those layers, which is a large net-new surface for zero gain when the dependency is already locked in [`pyproject.toml`][pyproject].

Pinned import shape (`django_filters.BaseFilterSet` does NOT exist at the top-level import path; the class lives at `django_filters.filterset.BaseFilterSet`):

```python
from django_filters import filterset

class FilterSetMetaclass(filterset.FilterSetMetaclass):
    ...

class FilterSet(filterset.BaseFilterSet, metaclass=FilterSetMetaclass):
    ...
```

An implementer who reaches for `from django_filters import BaseFilterSet` or `class FilterSet(django_filters.BaseFilterSet, ...):` gets an `ImportError` at module import — the cookbook's `from django_filters import filterset` + `filterset.BaseFilterSet` shape is the documented one and the only path that actually resolves.

Consumer migration shape: a consumer who has `class MyFilter(django_filters.FilterSet)` today writes `class MyFilter(FilterSet)` after the upgrade (changing the parent class), and inherits the package's `RelatedFilter` / lazy-resolution surface for free. The cookbook's pattern is the same. The dep is hard rather than soft, so no `ImportWarning` branch exists on the filter path.

Rationale companion — this Decision's justification, its three rejected alternatives, and the soft-dep stance it reversed: [Decision 5][rationale-d5]. The pinned import shape above stays in the spec because it changes how the module is written.

### Decision 6 — Finalizer phase-2.5 binding seam + materialize-before-`Schema` ordering

The filter subsystem's lazy-resolution pipeline runs inside [`django_strawberry_framework/types/finalizer.py::finalize_django_types`][finalizer]'s phase 2.5, immediately after the existing `apply_interfaces` / `install_relay_node_resolvers` loop and before phase 3's `strawberry.type` decoration.

**Four ordered subpasses.** A single per-`DjangoType` loop that binds an owner and then calls `get_filters()` is order-dependent: if `BookFilter.get_filters()` expands `RelatedFilter("GenreFilter")` before the finalizer loop reaches `GenreType`, `GenreFilter._owner_definition` is still unset, and any owner-aware work in that expansion falls back to `registry.get(target_model)` — which can resolve to the wrong owner under `Meta.primary`. The ordering therefore separates owner binding from filter expansion into four ordered subpasses (plus one filter-only audit step between the second and third), each of which must complete across ALL wired `DjangoType`s before the next subpass begins:

**Subpass 1 — Collect and bind every owner.** Walk every `definition` in the registry whose `definition.filterset_class is not None`:

1. Validate `filterset_class` is a `FilterSet` subclass (raise [`ConfigurationError`][glossary-configurationerror] otherwise).
2. **Bind the owner.** Set `filterset_class._owner_definition = definition` (the owning `DjangoTypeDefinition`). If `filterset_class._owner_definition` is already set, apply the strict compatibility check (see below + [Decision 4](#decision-4--upstream-primitives-parity-floor)): allowed only when EVERY owner-sensitive target (every FK / PK / M2M that hits the `FILTER_DEFAULTS` conditional or `GlobalIDFilter` validation) resolves to the EXACT same `DjangoTypeDefinition` AND the EXACT same `graphql_type_name`. Relay-vs-scalar compatibility alone is not sufficient; mismatch raises [`ConfigurationError`][glossary-configurationerror] naming both owners and the offending field. (Two owners with truly identical target resolution — e.g., the same model exposed twice with both `DjangoType`s registered under the same primary in `Meta.primary` — are allowed; the owner slot stores the FIRST binding.)

No `get_filters()` calls happen during subpass 1; the loop terminates with every wired `FilterSet` carrying a validated `_owner_definition`.

**Subpass 2 — Expand every filterset.** For every `FilterSet` bound in subpass 1, call `filterset_cls.get_filters()` to trigger Layer-4 expansion (resolves lazy refs, expands related filters with cycle guards). Now that every reachable `_owner_definition` is bound, `filter_for_field` / `filter_for_lookup` consult the correct owner-scoped related-target lookup regardless of expansion order. Cycle guards from Layer 4 remain in force.

**Subpass 2.5 — Filter-only audits.** Immediately after subpass 2 and before any orphan check or materialization, [`types/finalizer.py::_audit_filterset_subpass_2_5`][finalizer] runs two audits over the wired filtersets, in this order:

1. **Registered-`RelatedFilter`-target audit** (`_audit_unregistered_related_filter_targets`). Every reachable `RelatedFilter` target must be a registered `DjangoType`. A related branch's visibility scoping runs the target type's `get_queryset` (step 3 of [Decision 8](#decision-8--relation-permission-cascade--get_queryset-cooperation)), so an unregistered target makes the branch unfulfillable even though its input field would still be materialized into the schema. The walk is transitive with a visited set — cyclic cross-references (`BookFilter` <-> `ShelfFilter`) are legal — and raises [`ConfigurationError`][glossary-configurationerror] naming the filterset. The runtime sibling of this error lives in `FilterSet._iter_visibility_steps`; the audit moves the failure from the first request that activates the branch to schema build.
2. **Encode-only-GlobalID-target rejection** (`_audit_globalid_filter_strategies`). Every `GlobalIDFilter` / `GlobalIDMultipleChoiceFilter` on a bound filterset resolves the target definition it would validate against — the owner itself for the own-PK branch, the relation target otherwise — through the same single-sited resolver the runtime path uses. When that target's effective GlobalID strategy is `callable` or `custom`, the strategy is **encode-only**: there is no decode path for it, so a typed filter input of the target's GlobalID could never validly consume the IDs the target emits. That mismatch raises [`ConfigurationError`][glossary-configurationerror] naming the filterset and the field, rather than surfacing as the runtime backstop reject on the first request that hits the input.

The related-target audit runs first: an unregistered relation target makes the relation head unresolvable, so ordering it first keeps the GlobalID audit's target resolution operating on a validated relation graph. Both are filter-family audits and have no order-family twin.

**Subpass 3 — Orphan `filter_input_type` validation.** Compare `_helper_referenced_filtersets` (the set of FilterSets passed to `filter_input_type` per [Decision 11](#decision-11--filter_input_typefilterset-consumer-helper)) against the set of FilterSets bound in subpass 1. For every orphan (in the helper set but never wired via `Meta.filterset_class`), raise [`ConfigurationError`][glossary-configurationerror] with the stable message: `"FilterSet '<Name>' is referenced via filter_input_type(...) but never assigned to a DjangoType via Meta.filterset_class. Add 'filterset_class = <Name>' to the relevant DjangoType's Meta."` Orphans are reported sorted by qualified class name, all of them in one message rather than one per finalize attempt.

**Subpass 4 — Materialize input classes.** For every `FilterSet` that survived subpass 3, call `FilterArgumentsFactory(filterset_cls).arguments` to trigger Layer-5 BFS (builds every reachable `strawberry.input`-decorated class via the named converter `convert_filter_to_input_annotation(filter_instance, model_field, owner_definition)` per [Decision 4](#decision-4--upstream-primitives-parity-floor) M1). For each built class, **materialize as a real module global** of [`django_strawberry_framework.filters.inputs`][filters] via the helper `materialize_input_class(name, cls)`. The helper sets `sys.modules["django_strawberry_framework.filters.inputs"].<name> = cls` and records `name → filterset_class` provenance in the lifecycle ledger (per [Decision 9](#decision-9--input-class-namespace-vs-typeregistry-and-lifecycle)). Materialization is what makes the `Annotated["Name", strawberry.lazy("django_strawberry_framework.filters.inputs")]` references on consumer resolver signatures resolvable at `strawberry.Schema(...)` time — Strawberry's `LazyType.resolve_type` imports the named module and reads `module.__dict__[name]`, so the class MUST exist as a module global by then. `FilterArgumentsFactory(filterset_cls).arguments` is read for its BFS side effect rather than for its value: the property returns the **root** filterset's own input class ([`utils/inputs.py::GeneratedInputArgumentsFactory.arguments`][utils-inputs]), while the materialize loop iterates the factory's `input_object_types` ledger, so every class the BFS built for a reachable `RelatedFilter` target is materialized too — and a sibling root's factory sees those builds through the class-level cache.

**Subpass 3 runs BEFORE subpass 4, and that order is load-bearing.** Orphan validation is a whole-schema check that can only fail; materialization writes module globals and lifecycle-ledger rows. Validating first means an orphan failure leaves no partial state in `_materialized_names` or in the factory's built-class ledger, so re-running `finalize_django_types()` after fixing the orphan does not meet stale entries from the failed attempt.

By phase 3, when `strawberry.type(cls, ...)` runs on the `DjangoType`, every referenced filter input class is a module global of `django_strawberry_framework.filters.inputs`. By `strawberry.Schema(query=Query, ...)` time, every `filter:` argument annotation on a `@strawberry.field`-decorated root resolver (introduced via `filter_input_type(FilterSet)` per [Decision 11](#decision-11--filter_input_typefilterset-consumer-helper)) resolves cleanly through `LazyType.resolve_type`.

Materialization MUST land before `strawberry.Schema(...)` runs. Injecting the `filter:` argument into an already-decorated `@strawberry.field` resolver after the fact is not a real path: Strawberry collects field arguments at `@strawberry.type` decoration time, well before `finalize_django_types()` runs. The ordering is: resolvers use `filter_input_type(FilterSet)` (a string forward reference) at module-load time → `@strawberry.type` collects the lazy annotation → `finalize_django_types()` runs and materializes the input class as a module global → `strawberry.Schema(query=Query, ...)` resolves the lazy reference via `LazyType.resolve_type` → schema build succeeds. The package-recommended call ordering in [`docs/README.md`'s Schema setup boundary][docs-readme] already pins `finalize_django_types()` before `strawberry.Schema(...)`; this card adds the materialization step under that ordering without changing the consumer-facing call sequence.

### Decision 7 — `Meta.filterset_class` promotion gate

`Meta.filterset_class` is promoted out of [`DEFERRED_META_KEYS`][base] only when:

2. The finalizer-phase-2.5 binding pass is wired (Slice 3).
3. The promotion to `ALLOWED_META_KEYS` is applied at the same commit as the validator-acceptance test (Slice 3).

Same gate as [`Meta.interfaces`][glossary-metainterfaces] in `DONE-015-0.0.5` — a deferred `Meta` key is accepted only when the subsystem applies it end-to-end. ### Decision 8 — Relation-permission cascade + `get_queryset` cooperation

A `FilterSet`'s `check_<field>_permission(request)` gate composes with the target type's [`get_queryset`][glossary-get_queryset-visibility-hook] hook and with `FilterSet._apply_related_constraints` (which applies the explicit `queryset=` parameter on a related filter, which is a **filter-scope constraint** — NOT a security boundary; visibility is the job of `get_queryset`, not `RelatedFilter(queryset=...)`). The composition flows through the resolver-facing classmethods `FilterSet.apply_sync(input_value, queryset, info)` and `FilterSet.apply_async(input_value, queryset, info)` — two methods, not one. Resolvers pick the variant matching their own sync/async shape. The generic `FilterSet.apply(...)` is kept as a thin dispatcher that runs `apply_sync` and translates the typed [`SyncMisuseError`][querysets] — raised when a target's `get_queryset` turns out to be async-only — into a `RuntimeError` that tells the consumer to use `apply_async`.

**`GraphQLError` import path.** Every `GraphQLError` raised in this Decision and in [Decision 11](#decision-11--filter_input_typefilterset-consumer-helper) is `from graphql import GraphQLError` (the class Strawberry's response builder honors for the `extensions` payload). NOT `strawberry.exceptions.StrawberryGraphQLError` (a private subclass).

**Recommended internal decomposition.** `apply_sync` / `apply_async` are not monolithic 100+ line methods — they decompose into named helpers so the test plan can target each seam:

- `_normalize_input(input_value, owner_definition) -> dict` — Strawberry input dataclass → `django-filter` form-data dict; consults `LOOKUP_NAME_MAP` for per-lookup name mapping; consults `normalize_input_value(filter_instance, raw_value, field_name=None)` for per-primitive value normalization (per [Decision 4](#decision-4--upstream-primitives-parity-floor) M1).
- `_derive_related_visibility_querysets_sync(input_value, info) -> dict[str, QuerySet]` / `_derive_related_visibility_querysets_async(...)` — for every ACTIVE `RelatedFilter` branch, derive the target type's visibility-scoped queryset. The two variants dispatch through [`django_strawberry_framework/utils/querysets.py::apply_type_visibility_sync`][querysets] and [`::apply_type_visibility_async`][querysets] — the package-wide visibility-hook dispatch, shared with every other consumer of the hook.
- `_run_permission_checks(input_value, request)` — runs the per-field `check_<field>_permission(request)` gates ONLY for fields present in the normalized input (active-input-only); recurses through `RelatedFilter`s into child filtersets' `_run_permission_checks` calls.
- `_validate_form_or_raise(filterset)` — explicit `filterset.form.is_valid()` plus `GraphQLError` raise.
- `_apply_related_constraints(input_value, parent_qs, child_qs_by_branch) -> QuerySet` — applies explicit `RelatedFilter(queryset=...)` constraints under active-branch scoping, intersected with the visibility-scoped child querysets from `_derive_related_visibility_querysets_*`. **This helper runs BEFORE the FilterSet is instantiated** so the constrained queryset becomes the filterset instance's stored `self.queryset` and propagates through to `.qs`; constraining a local variable AFTER `cls(...)` runs would let `.qs` ignore the constraints because `django-filter`'s `.qs` reads `self.queryset`, not any local the caller might mutate.

`apply_sync` / `apply_async` are then thin compositions of these helpers in step order below.

**Reading the step list:** Below, "the apply pipeline" refers to the shared algorithm run by both `apply_sync` and `apply_async`; the two methods differ only in step 3's sync vs async dispatch (and in step 4 / 5 / 7 inheriting that dispatch for any helper that touches `get_queryset`). Where a step mentions "apply" without a sync/async qualifier, it refers to the pipeline shape, not a specific method.

The 9-step pipeline:

1. **The consumer resolver calls `<OwnerType>.get_queryset(queryset, info)` first** on the consumer-shaped root queryset — visibility scoping happens BEFORE any filter clause runs. Every user-facing resolver example, every fakeshop instruction, and every doc update in this spec pins this ordering explicitly: `queryset = BranchType.get_queryset(models.Branch.objects.order_by("id"), info)` THEN `queryset = BranchFilter.apply_sync(filter, queryset, info)` (or `await BranchFilter.apply_async(...)` from an async resolver). Skipping the `get_queryset` call lets the filter clause see through the visibility gate to hidden rows — a security regression every consumer-facing example must defend against by example.
2. The consumer resolver then calls `FilterSet.apply_sync(input_value, queryset, info)` or `await FilterSet.apply_async(input_value, queryset, info)`. Internally, the apply pipeline normalizes the Strawberry input dataclass (walking nested `RelatedFilter` input objects, mapping `and_` / `or_` / `not_` Python attrs back to the logical-operator keys, mapping per-lookup Python attrs through `LOOKUP_NAME_MAP` per [Decision 3](#decision-3--six-layer-lazy-resolution-pipeline), converting Strawberry input values back to form-data shape via `normalize_input_value(filter_instance, raw_value, field_name=None)` per [Decision 4](#decision-4--upstream-primitives-parity-floor) M1) into the form-data dict `django-filter` expects.
3. **Nested `RelatedFilter` visibility scoping.** For each ACTIVE `RelatedFilter` branch in the normalized input (active-branch scoping — the branch's key is present in the input), `apply` derives the child visibility queryset by calling the **target `DjangoType`'s `get_queryset(child_model._default_manager.all(), info)`**, reusing the package-wide sync/async visibility dispatch at [`django_strawberry_framework/utils/querysets.py::apply_type_visibility_sync`][querysets] / `::apply_type_visibility_async`. The child visibility queryset is intersected with the explicit `RelatedFilter(queryset=...)` constraint when one was declared on the related filter. The result is what the parent queryset's `.filter(<rel>__in=<child_qs>)` join uses as its right-hand side, so a nested filter cannot use a hidden related row to make the parent match. Without this step, a query like `{ branches(filter: { shelves: { code: { exact: "secret-code" } } }) { id } }` would match `Branch` rows that own a `Shelf` whose `ShelfType.get_queryset` would normally hide it; with this step, the join's right-hand side is the visibility-scoped child queryset, so the hidden shelf cannot leak the parent.
4. The apply pipeline extracts the Django request. The canonical shape is `info.context.request` matching the Strawberry-Django convention; the dispatcher detects the wrapper-less alternative via `isinstance(info.context, HttpRequest)` and treats it as the request directly. Concretely: `request = info.context.request if hasattr(info.context, "request") else info.context if isinstance(info.context, HttpRequest) else None`; a `None` outcome raises [`ConfigurationError`][glossary-configurationerror] naming the unsupported `info.context` shape.
4a. **Apply related constraints to the queryset BEFORE constructing the FilterSet instance.** `_apply_related_constraints(input_value, queryset, child_qs_by_branch)` runs here, intersecting the visibility-scoped child querysets from step 3 with any explicit `RelatedFilter(queryset=...)` filter-scope constraint (active-branch only) and producing `constrained_queryset = parent_qs.filter(<rel>__in=<intersected_child_qs>)` for every active branch. The reason the constraints land before instantiation: `django_filters.filterset.BaseFilterSet.qs` derives from the instance's *stored* `self.queryset`, NOT from any local variable the calling code might mutate after construction. If the pipeline constructed the filterset against an un-constrained queryset and then mutated a separate local variable, `filterset.qs` would silently ignore the constraints. Constraining BEFORE construction ensures `self.queryset` carries them through to `.qs`. (Equivalent fallback for designs that need an instance to compute the constraints: instantiate with `queryset` first, compute constraints from `cls.related_filters` against `cls(data=normalized_data).form.cleaned_data` after form validation, then assign `filterset._queryset = constrained_queryset` BEFORE accessing `.qs` — the contract is "constraints land in `self.queryset` before `.qs` is read", not the specific code shape.) The apply pipeline then instantiates `cls(data=normalized_data, queryset=constrained_queryset, request=request)`.
5. The apply pipeline calls `cls._run_permission_checks(input_value, request)` (the active-input pass; `check_permissions(self, request, requested_fields=None)` remains the public `django-filter`-shaped instance method) — denial gates raise `from graphql import GraphQLError; GraphQLError(...)` before any filter clause touches the queryset. The per-field `check_<field>_permission(request)` gate runs **only for fields present in the normalized input** (active-input-only), NOT for every declared field. This diverges from the cookbook's `AdvancedFilterSet.check_permissions(request)` which walks every declared filter; the rationale: permissions gate USE of the filter, not its declaration — a `check_name_permission` should not raise on a query that never touched `name`. The check still recurses through `RelatedFilter`s into child filtersets' `check_*_permission` methods, but only for active branches.
6. **The apply pipeline explicitly calls `filterset.form.is_valid()`** and raises `GraphQLError("Invalid filter input", extensions={"code": "FILTER_INVALID", "errors": <serialized filterset.errors>})` when validation fails. This explicit call is required because `django_filters.filterset.BaseFilterSet.qs` only consults `self.errors` and falls through to `filter_queryset` regardless — so without the explicit raise, invalid input would degrade into a partially-filtered or unfiltered queryset instead of a GraphQL error. The `extensions.errors` payload is `filterset.errors.get_json_data()` (the `django.forms.utils.ErrorDict.get_json_data()` method — verified to exist in the package's supported Django range `>=5.0`); the resulting structure consumers can rely on is `{<field_name>: [{"message": <str>, "code": <str>}, ...], ...}` per the Django form contract.
7. **Active-branch related-queryset scoping — applied in step 4a.** See step 4a above. The constraint applies ONLY when the related branch is present in the normalized input; an empty `filter: {}` or `filter: { name: { iContains: "..." } }` (no `shelves` branch) returns the unconstrained parent queryset; a `filter: { shelves: { code: { iContains: "..." } } }` activates the constraint. The cookbook's `_apply_related_queryset_constraints` applies all declared constraints unconditionally; the package narrows that to active-branch only to keep the empty-filter case behavior obvious. The intersected queryset (visibility-scoped from step 3 + explicit constraint) is what the parent filterset's `self.queryset` carries, so `filterset.qs` produces a queryset that already has the `parent_qs.filter(<rel>__in=...)` join baked in.
8. The instance's `.qs` property runs `cls.filter_queryset(self, queryset)` (the `django-filter` instance-method override; the tree-form-logic application path) and returns the final queryset. The apply pipeline (whichever of `apply_sync` / `apply_async` invoked it) returns `cls(...).qs` to the resolver.
9. The optimizer ([`DjangoOptimizerExtension`][glossary-djangooptimizerextension]) walks the selection tree on the post-filter queryset; [Queryset diffing][glossary-queryset-diffing] cooperates with any consumer `select_related` / `prefetch_related` work already present.

<a id="sync-async-api-split"></a>**Sync / async API split.** A single `FilterSet.apply(input_value, queryset, info)` classmethod cannot serve step 3's nested-visibility work: a target `DjangoType.get_queryset(...)` can be async-only (returns a coroutine), and a sync resolver cannot synchronously await it. The shape (matching the precedent of `apply_type_visibility_sync` / `apply_type_visibility_async` in [`utils/querysets.py`][querysets]):

- `FilterSet.apply_sync(input_value, queryset, info) -> QuerySet` — the sync-resolver entry point. Dispatches through `_derive_related_visibility_querysets_sync`, which calls [`apply_type_visibility_sync`][querysets] for every active `RelatedFilter` branch. If the target's `get_queryset` returns a coroutine, `apply_type_visibility_sync` raises [`SyncMisuseError`][querysets] — a typed marker subclassing BOTH [`ConfigurationError`][glossary-configurationerror] and `RuntimeError`, so a consumer catching either base class still matches.
- `FilterSet.apply_async(input_value, queryset, info) -> Awaitable[QuerySet]` — the async-resolver entry point. Dispatches through `_derive_related_visibility_querysets_async`, which awaits the target's `get_queryset` regardless of sync / async shape (Strawberry's async bridging handles both).
- `FilterSet.apply(input_value, queryset, info)` — kept as a thin dispatcher that calls `apply_sync(...)` (the common case). The dispatch is **class-based, never a substring match against a message**: `apply` calls `apply_sync` inside a `try / except SyncMisuseError as exc:` block and re-raises `RuntimeError("FilterSet.apply called against async get_queryset; use apply_async instead.") from exc`. The message carries no interpolated target type — `from exc` already puts the original [`SyncMisuseError`][querysets] on `__cause__`, and the standard traceback machinery surfaces it, so restating the cause here would print it twice. Any other `RuntimeError` (and any other `ConfigurationError`) propagates unchanged. **Partial side-effect semantics:** the `SyncMisuseError` fires inside `apply_type_visibility_sync` during step 3, AFTER `_normalize_input` (step 2) has run but BEFORE `check_permissions` (step 5), `form.is_valid()` (step 6), or `_apply_related_constraints` (step 7). At that point no filterset has been instantiated, no queryset clauses have been applied, and no lifecycle ledger updates have happened — `apply_sync` itself does not mutate the filterset module globals or the input-class namespace. Any per-target visibility queryset derivations that ran in step 3 before the misuse are pure reads against the target's `get_queryset` (no mutations); they are silently discarded when the `RuntimeError` propagates. Consumers are encouraged to call `apply_sync` / `apply_async` directly; `apply` exists for backward compatibility and for one-off cases where the consumer is certain no target uses an async `get_queryset`.

Consumer pattern: sync resolvers call `BranchType.get_queryset(qs, info)` and `BranchFilter.apply_sync(filter, qs, info)`. Async resolvers `await` the same hook through [`apply_type_visibility_async`][querysets] (a `DjangoType.get_queryset` may be declared `async def`; there is no separate `aget_queryset` name) and then `await BranchFilter.apply_async(filter, qs, info)`. The fakeshop examples in [Slice 4](#slice-checklist) and [User-facing API](#user-facing-api) use `apply_sync` throughout, because every fakeshop library type uses a sync `get_queryset` hook — **the live HTTP tier exercises no async path, and this card's 14 contracted live tests do not include one.** The `apply_async` contract is earned in the package tier instead, at [`tests/filters/test_sets.py`][test-filters] (see [Test plan](#test-plan)): that is where an async-only `get_queryset` fixture is declarable without a second fakeshop type whose only purpose is to be async.

<a id="related-queryset-boundary-scope"></a>**`_apply_related_constraints` scope.** The cookbook ancestor this helper ports (`AdvancedFilterSet._apply_related_queryset_constraints`) filters the parent queryset using `parent_qs.filter(<related_name>__in=<constraint_qs>)`. It does NOT filter the nested relation resolver's output. That means a `Branch` row with one shelf inside the constraint AND one shelf outside the constraint will pass the parent `Branch` filter and still surface BOTH shelves through `BranchType.shelves` (which is a consumer-authored resolver that runs after queryset filtering). The contract this card pins is: "branches without any matching constrained shelf are excluded from the parent result; nested filter clauses cannot use shelves outside the constraint to make a branch match." It is **not** "shelves outside the constraint never appear in the response." Output-shape scoping at the nested-relation level would require either rewriting consumer relation resolvers or extending the optimizer's `Prefetch` planner to honor a per-relation constraint — both are out of scope for `0.0.8`; tracked as a follow-up if real consumer demand surfaces. The active-branch refinement further narrows the contract: the constraint applies ONLY when the related branch is present in the normalized input, so an empty filter or a filter that names other relations doesn't accidentally pre-exclude parent rows that lack a constrained child.

Forward composition contract: when [`apply_cascade_permissions`][glossary-apply_cascade_permissions] ships in `0.0.10`, it slots into step 1 (the `get_queryset` hook); when [Per-field permission hooks][glossary-per-field-permission-hooks] ship, they slot into the field-resolver layer that runs AFTER step 8 (queryset traversal completes before field resolvers fire). The five layers compose without retrofit.

### Decision 9 — Input-class namespace vs `TypeRegistry` and lifecycle

The card body's "Decide whether the input-type factory's namespace shares the `TypeRegistry` or has its own" question is answered: **the input-class namespace is the [`django_strawberry_framework.filters.inputs`][filters] module's own global namespace**, separate from the model-to-`DjangoType` registry at [`django_strawberry_framework.registry.registry`][registry] (which powers [`Meta.primary`][glossary-metaprimary]).

Implementation: every generated filter input class is a real module global of `django_strawberry_framework.filters.inputs`, set at finalize time via `setattr(sys.modules["django_strawberry_framework.filters.inputs"], name, cls)`. The class names are stable and class-derived (e.g., `f"{FilterSet.__name__}InputType"` → `"GalaxyFilterInputType"`). The "registry" IS the module's `__dict__` — there is no separate `_input_type_registry: dict[str, type]`, because Strawberry's `LazyType.resolve_type` reads `module.__dict__` directly and cannot traverse a sidecar dict (verified by direct inspection of the installed Strawberry). A lifecycle ledger (a private `dict[str, type]` at `django_strawberry_framework.filters.inputs._materialized_names`) tracks `class_name → input_class` provenance — each value is the materialized Strawberry input class, uniquely produced by one `FilterSet` — so re-materialization is idempotent and clears cleanly.

The registry must coincide with the module's global namespace because Strawberry's lazy mechanism is module-path-only, not object-path. The two namespaces (model-to-`DjangoType` registry and input-class module globals) remain disjoint by key type (Django model class vs string class name).

Lifecycle contract:

- **Registration is idempotent for the same `(name, input_class)` pair.** Calling `materialize_input_class("GalaxyFilterInputType", input_a)` twice with the same `input_a` is a no-op: the check is `is` identity against the input class the ledger already holds under that name, so the second call neither raises nor reassigns the module global.
- **Registration raises [`ConfigurationError`][glossary-configurationerror] when the same name is claimed by a DIFFERENT input class.** `materialize_input_class("GalaxyFilterInputType", input_a)` followed by `materialize_input_class("GalaxyFilterInputType", input_b)` raises with both input classes' qualified names in the message and rename advice naming the filterset. Because each input-class name is derived from its owning `FilterSet`'s `__name__`, this is what catches accidental duplicate-`__name__` collisions between two `FilterSet`s declared in different modules: each produces its own input class, the second claims a name the first holds, and the raise names both.
- **`registry.clear()` (the model-to-`DjangoType` registry's clear) resets the filter input lifecycle ledger and every piece of generated-build state hanging off it.** The shared clear point lets test-fixture reload patterns reset both subsystems in one call. `clear_filter_input_namespace()` is the family wrapper over the shared heavy clear at [`utils/inputs.py::clear_generated_input_namespace`][utils-inputs]: it empties `_materialized_names` and `_field_specs`, clears the `FilterArgumentsFactory` class-level caches (`input_object_types` plus the `_type_filterset_registry` collision map), and drops every `FilterSet` subclass's phase-2.5 binding state — `_owner_definition`, `_expanded_filters`, `_is_expanding_filters`, and the candidate-metadata snapshot published alongside the expansion cache, read off the family's lifecycle descriptor at `django_strawberry_framework/sets_mixins.py::SetLifecycleAttrs.binding_attrs` rather than re-spelled at the clear site. Each attribute is dropped only where the subclass set it directly, so an inherited default is restored rather than masked and a subclass that never bound tolerates the clear. Both submodule lookups the clear needs are best-effort: an unimportable `filters.factories` or `filters.sets` skips only its own dependent reset and never prevents the reachable ledger reset.
- **Materialized class objects stay parked in the `django_strawberry_framework.filters.inputs` module `__dict__`; no clear path strips them.** Parking is load-bearing, not an omission: `materialize_input_class` overwrites the module global via `setattr`, so the next finalize replaces a parked class in place, and it is the ledger reset — never a deletion from the namespace — that drives the rebuild. Stripping a global with `delattr` would break any `strawberry.lazy(...)` LazyType held by a consumer module whose autouse-reload fixture did not also reload the holder (a per-app fixture reloading only its own app's schema is exactly that shape); leaving the class parked lets such a LazyType keep resolving to the prior class until the next finalize replaces it.
- **Import-cycle-safe integration via subsystem registration.** [`django_strawberry_framework/registry.py`][registry] is a low-level module imported by `types/`, `optimizer/`, and the package's `__init__.py`, so it may not import the filter subsystem at all — not at module top (a cycle) and not from inside `TypeRegistry.clear()` (an import path spelled as a string, which a rename silently rots). The dependency runs the other way: the owning module announces its own teardown at import time, and `TypeRegistry.clear()` replays whatever announced itself.

  ```python
  # django_strawberry_framework/filters/__init__.py
  register_subsystem_clear(
      _clear_helper_referenced_filtersets,
      owner="filters.helper_references",
  )

  # django_strawberry_framework/filters/inputs.py
  register_subsystem_clear(
      clear_filter_input_namespace,
      owner="filters.input_namespace",
      before_bind=True,
  )

  # django_strawberry_framework/registry.py
  class TypeRegistry:
      def clear(self) -> None:
          ...  # the registry's own state
          for clear in iter_subsystem_clears():
              clear()
  ```

  Three properties follow, and they are why `registry.py` must reach into `filters` by no route at all — not a module-top import, and not a function-local one inside `clear()`. **Laziness is preserved**: only an imported owner can register, so a consumer who never imports `filters` has nothing to clear and `registry.clear()` does no work — with no `except ImportError: pass` branch to keep covered. **A rename cannot rot silently**: registration resolves the function object at the owner's import, so a renamed or moved callable fails at the owner rather than leaving stale state behind in the registry. **`owner` is a stable logical identity, not an import path**, so `importlib.reload` on a fixture-reload path replaces the old callback instead of accumulating duplicates. `before_bind=True` additionally marks the input-namespace reset as generated state the finalizer re-runs before rebuilding generated types; the helper-reference ledger is a full-clear-only callback.

  A package test imports `django_strawberry_framework.registry` alone (before importing `django_strawberry_framework.filters`) and verifies `registry.clear()` runs cleanly with no filter callback registered.
- **Partial-finalize recovery.** If `finalize_django_types()` raises mid-phase-2.5 (e.g., an unresolved `RelatedFilter`), the lifecycle ledger and the module globals retain whatever was materialized before the raise. A subsequent `finalize_django_types()` call re-runs the binding pass; the idempotent `(name, input_class)` check above lets already-materialized classes pass through cleanly while the failed type's binding completes on the retry.
- **Public `clear_filter_input_namespace()` helper.** Exposed from `django_strawberry_framework.filters.inputs` so tests that need to clear the filter namespace WITHOUT clearing the full `TypeRegistry` (e.g., when validating partial-finalize recovery) have a dedicated entry point. `registry.clear()` calls this helper internally.

### Decision 11 — `filter_input_type(FilterSet)` consumer helper

The package ships a small public helper at [`django_strawberry_framework.filters.filter_input_type`][filters]:

```python
from typing import Annotated, TYPE_CHECKING

import strawberry

if TYPE_CHECKING:
    from django_strawberry_framework.filters import FilterSet

def filter_input_type(filterset_class: type["FilterSet"]) -> object:
    """Return the Annotated[...] forward-reference for the filterset's GraphQL input class.

    The returned annotation is the canonical Strawberry forward-reference
    idiom: ``Annotated["<Name>FilterInputType", strawberry.lazy("django_strawberry_framework.filters.inputs")]``.
    Consumer resolvers use it as the type annotation for a ``filter:`` argument; Strawberry
    collects the annotation at @strawberry.type decoration time, defers resolution, and
    resolves it via LazyType.resolve_type at schema-build time — by which point
    finalize_django_types() has materialized the input class as a module global of
    django_strawberry_framework.filters.inputs (per Decision 6).
    """
    # Validation runs eagerly even though the returned annotation is lazy.
    from django_strawberry_framework.filters.sets import FilterSet
    if not (isinstance(filterset_class, type) and issubclass(filterset_class, FilterSet)):
        raise TypeError(
            "filter_input_type() requires a FilterSet subclass; got "
            f"{filterset_class!r}"
        )
    # Record the FilterSet for the orphan check at finalize time
    # (filter_input_type-referenced filtersets that are never wired via
    # Meta.filterset_class raise ConfigurationError at finalize per Decision 11).
    _helper_referenced_filtersets.add(filterset_class)
    name = f"{filterset_class.__name__}InputType"
    # Annotated[<str_variable>, ...] wraps the runtime-computed string as a
    # typing.ForwardRef in the first __args__ position — verified directly
    # (see test_filter_input_type_returns_forwardref_in_annotation_args;
    # that test pins the typing contract this code relies on against
    # future Python typing regressions).
    # Do NOT refactor this into a literal string interpolated outside the
    # Annotated call; Strawberry's LazyType.resolve_type requires the
    # ForwardRef-wrapped form to resolve via module.__dict__ at schema build.
    return Annotated[name, strawberry.lazy("django_strawberry_framework.filters.inputs")]
```

Consumers use it as a normal Python type annotation in a resolver signature:

```python
@strawberry.field
def all_galaxies(
    self,
    info: strawberry.Info,
    filter: filter_input_type(GalaxyFilter) | None = None,
) -> list[GalaxyType]:
    ...
```

`filter_input_type(GalaxyFilter)` evaluates **when Strawberry evaluates the annotation during schema declaration / collection** (the function body runs, validation succeeds, and the `Annotated[...]` shape is returned). The exact evaluation moment depends on the consumer's import style:

- **With normal annotations** the call evaluates at module-load time. The function body runs once, validation succeeds, and the `Annotated[...]` shape is stored on the resolver's `__annotations__`.
- **With `from __future__ import annotations`** (PEP 563), Python stores the ENTIRE annotation expression as a string in `__annotations__`. Strawberry resolves it by calling `typing.get_type_hints(resolver, ...)` (or equivalent) at type-collection time, which evaluates the string in the resolver's function `__globals__`. THAT call invokes `filter_input_type(GalaxyFilter)`, runs validation, and returns `Annotated[...]`. Two implications: (a) `GalaxyFilter` MUST be importable from the resolver module's globals at type-processing time (not just at module-load); (b) Strawberry may evaluate the annotation more than once during a single schema build, so **`filter_input_type` is safe to call repeatedly with the same `FilterSet`** — re-call returns a new but equivalent `Annotated[...]` instance; the helper-referenced set ledger (per the orphan-validation block below) is idempotent on repeated calls.

Either way, the `"GalaxyFilterInputType"` string forward-reference inside the `Annotated[...]` stays unresolved until `strawberry.Schema(...)` time — which is when `finalize_django_types()` has already materialized the class as a module global per [Decision 6](#decision-6--finalizer-phase-25-binding-seam--materialize-before-schema-ordering).

**Orphan `FilterSet` validation.** A `FilterSet` referenced via `filter_input_type(MyFilter)` but never wired via `Meta.filterset_class = MyFilter` on any `DjangoType` would not be materialized by finalizer phase 2.5 — Strawberry's `LazyType.resolve_type` would raise `KeyError` for `MyFilterInputType` at `strawberry.Schema(...)` time. The package fails loud at finalize:

- `filter_input_type` records every `FilterSet` it is called with into a module-level `_helper_referenced_filtersets: set[type[FilterSet]]` in [`django_strawberry_framework.filters`][filters] (a module-level private next to the helper itself).
- Finalizer phase 2.5 (after iterating `Meta.filterset_class`-wired filtersets) compares the helper-referenced set against the set of wired filtersets; for every orphan, it raises [`ConfigurationError`][glossary-configurationerror] with a stable message: `"FilterSet '<MyFilter>' is referenced via filter_input_type(...) but never assigned to a DjangoType via Meta.filterset_class. Add 'filterset_class = <MyFilter>' to the relevant DjangoType's Meta."`
- `registry.clear()` replays the `filters.helper_references` teardown callback, clearing `_helper_referenced_filtersets` along with the model-to-`DjangoType` registry and the filter-input namespace, so the orphan check is consistent across test-fixture reloads.
- New test `test_orphan_filter_input_type_reference_raises_at_finalize` pins this.

### Decision 12 — Live HTTP coverage strategy

Package coverage is earned through fakeshop live `/graphql/` HTTP flows where practical per the [`docs/TREE.md`][tree] coverage-priority rule ("Any package coverage line in `django_strawberry_framework/` that can be earned by a real-world GraphQL query against fakeshop MUST be earned in `examples/fakeshop/test_query/`").

## Edge cases and constraints

- **Same-module `RelatedFilter` references** (e.g., `GalaxyFilter` and `CelestialBodyFilter` declared in the same `filters.py` with `RelatedFilter("CelestialBodyFilter")` and `RelatedFilter(GalaxyFilter)` respectively). The Layer-2 module-fallback resolution handles this; the absolute-path lookup fails (the module isn't fully loaded yet) and the `bound_class.__module__` retry succeeds.
- **Cross-module `RelatedFilter` references via absolute path** (e.g., `RelatedFilter("apps.products.filters.CategoryFilter")`). The Layer-2 absolute-path lookup succeeds; the `bound_class.__module__` retry is never reached.
- **Circular `RelatedFilter` cycles** (`A → B → A`). The Layer-4 `_is_expanding_filters` recursion guard breaks the cycle; the cache writes only when no string `_filterset` remains on any related filter (the two-condition guard). A genuine cycle exhausts the guard and raises [`ConfigurationError`][glossary-configurationerror] with the offending class named.
- **`Meta.fields = "__all__"`** (the shorthand). Expands to every **scalar** model field plus each FK / PK column under the conditional `FILTER_DEFAULTS` per [Decision 4](#decision-4--upstream-primitives-parity-floor) — **NOT** relations / M2M. Relations only become filterable when the consumer declares an explicit `RelatedFilter(...)`. The narrower scope keeps the [Non-goals](#non-goals) "no implicit `FilterSet` generation from `Meta.fields`" rule self-consistent — `"__all__"` would otherwise need to invent target filtersets for every relation, which IS auto-generation. This is an **intentional override** of `django-filter`'s `django_filters.utils.get_all_model_fields` default: that default excludes `AutoField` primary keys (the package includes them, because Relay-aware filtering and scalar PK filtering MUST be reachable through `"__all__"`) and includes M2M relations (the package excludes them, because traversing a M2M without an explicit target `FilterSet` would either auto-generate one or expose a bare-PK filter against the M2M — neither matches the package's [Non-goals](#non-goals)). `FilterSet.get_fields` carries the override; tests pin both deltas.
- **`Meta.fields = {"galaxy__name": ["exact"]}`** (the double-underscore lookup-path shorthand). Pinned GraphQL shape: **renders as a flat field named `galaxyName` with a nested lookup input** (`filter: { galaxyName: { exact: "..." } }`) — NOT as a nested-relation shape `filter: { galaxy: { name: { exact: "..." } } }`. The cookbook's `FilterArgumentsFactory.filterset_to_trees` splits on `__` for its INTERNAL tree representation, but the package's `_build_input_fields` flattens the path back into a single GraphQL field name at the schema-build step so the consumer sees a clean flat surface (the rationale: the nested-relation shape would conflict with the user's mental model when an explicit `RelatedFilter(GalaxyFilter)` IS also declared on the same filterset). Consumers reaching for a nested-relation surface should declare an explicit `RelatedFilter(GalaxyFilter)` instead of relying on the `__` shorthand — or set `HIDE_FLAT_FILTERS` (per [Decision 3](#decision-3--six-layer-lazy-resolution-pipeline)) to drop the flat rendering of relation-traversing paths schema-wide while keeping the nested branch.
- **`Meta.fields = {"created": ["date__year"]}`** (multi-level transform chains). **Deferred — Slice 2 flat-grouping shape does NOT support nested-transform chains.** The Slice-2 `_build_input_fields` port uses a flat `OrderedDict[top_name, OrderedDict[lookup, filter_instance]]` grouping rather than the cookbook's recursive `filterset_to_trees` / `try_add_sequence` / `sequence_to_tree` tree-form. Single-hop double-underscore paths (`galaxy__name` per the bullet above) render as flat fields with the path baked into `FieldSpec.django_source_path`; multi-level transform chains (`date__year`, `date__month`, `time__hour`, …) require the recursive tree-form to produce the corresponding nested operator-bag input. The `LOOKUP_NAME_MAP` carries `date` / `year` / `month` / `day` / `hour` / `minute` / `second` etc. for the LOOKUP vocabulary, NOT to license multi-level chains in this card. Surfacing a real consumer demand for this shape is the trigger to port the tree-form algorithm; per [Decision 12](#decision-12--live-http-coverage-strategy) the Slice-4 live HTTP coverage does not exercise multi-level chains. Forward path: when a consumer needs this surface (likely first surfaced by [`DjangoConnectionField`][glossary-djangoconnectionfield] in `0.0.9` or a follow-up filter card), port the cookbook's `filterset_to_trees` / `try_add_sequence` / `sequence_to_tree` algorithm into `_build_input_fields`, threading the path through `FieldSpec.django_source_path` as the runtime normalizer already expects.
- **`Meta.filterset_class = AdminGalaxyFilter` on a secondary `Meta.primary = False` `DjangoType`**. Per [`Meta.primary`][glossary-metaprimary], the secondary type is registered and reverse-discoverable; the filter binding runs on the secondary type's definition exactly the same way it runs on the primary's. The input-type namespace per [Decision 9](#decision-9--input-class-namespace-vs-typeregistry-and-lifecycle) is name-keyed so two `DjangoType`s on the same model with different `filterset_class`es generate two distinct input types.
- **`Meta.filterset_class` on a `DjangoType` that also declares `Meta.interfaces = (relay.Node,)`**. The filter binding runs at phase 2.5 after the Relay-Node injection; the `GlobalIDFilter` mapping in `FILTER_DEFAULTS` covers the Relay-aware filtering case.
- **Filter on a field that is NOT in the `DjangoType`'s `Meta.fields`** (e.g., the type exposes `name` but the filterset declares `description` as filterable). The filter clause still applies to the queryset; the consumer can filter on columns they cannot select. This matches the cookbook's behavior and is intentional.
- **Filter that raises a Django ORM error at queryset-translation time** (e.g., a JSON-field filter against a SQLite backend that doesn't support the lookup). The Django `FieldError` / `NotImplementedError` propagates as a `GraphQLError`; the framework does not pre-validate the SQL backend's supported lookups.
- **Recursion-protected `get_fields`**. When a `FilterSet`'s `Meta.fields` references a relation that loops back to itself (e.g., `RelatedFilter("Self")` for a self-referential model), the `visited: set[type]` guard breaks the loop; the expanded fields stop at one level of self-reference.
- **`construct_search` lookup-prefix handling**. `^foo` becomes `<field>__istartswith=foo`, `=foo` becomes `<field>__iexact=foo`, `@foo` becomes `<field>__search=foo` (PostgreSQL full-text only), `$foo` becomes `<field>__iregex=foo`. The map ports verbatim from `django_graphene_filters`; consumers writing the `^`/`=`/`@`/`$` prefixes get the same behavior they did in the cookbook.
- **`Meta.fields` with no lookups** (e.g., `{"name": []}`). Rejected at type creation with [`ConfigurationError`][glossary-configurationerror]; an empty lookup list is meaningless.
- **Filter input position empty** (`filter: {}`). The factory returns the unfiltered queryset; no `.filter(...)` call is made. The optimizer's [Queryset diffing][glossary-queryset-diffing] cooperation is unaffected.
- **Async resolver returning a filtered queryset**. Strawberry's async path awaits the resolver; the queryset's filter clauses apply normally. The optimizer's async-path support (shipped in `0.0.2`) cooperates without retrofit.
- **`Meta.fields` referencing a model property (not a field)**. Rejected at type creation with [`ConfigurationError`][glossary-configurationerror]; only model fields are filterable. Filtering on a property requires a custom `Filter` declaration with an explicit `method=` (the cookbook's `FilterMethod` shape, ported per [Decision 4](#decision-4--upstream-primitives-parity-floor)).
- **Filter against a queryset that's already been `.values(...)`-projected**. Filters apply; the projection persists. The framework does not pre-validate; the consumer is responsible for the projection vs filter cooperation.
- **Two consumer schemas with two `<TypeName>FilterInputType`s of the same string name**. Rejected by the per-module input-class namespace's name uniqueness check (per [Decision 9](#decision-9--input-class-namespace-vs-typeregistry-and-lifecycle) lifecycle clause): same `(name, input_class)` pair is idempotent; the same name claimed by a different input class raises [`ConfigurationError`][glossary-configurationerror] with both input classes' qualified names and rename advice naming the filterset. Catches consumers who accidentally declare two `FilterSet`s with the same `__name__` across different modules.
- **`RangeFilter`-derived sub-input class names across two filtersets that share a `field_name`** (e.g., two filtersets each declaring `Meta.fields = {"lifetime_fines_cents": ["range"]}` against different models). **Slice-2 scope: derived from `filter_instance.field_name` alone — `f"{PascalCase(field_name)}RangeInputType"`.** When two filtersets share the same `field_name` for a `RangeFilter`, both per-instance caches stamp the same GraphQL name (e.g., `LifetimeFinesCentsRangeInputType`); Strawberry surfaces this at schema-build time as a duplicate-type-name error rather than silently. The collision is NOT subject to [Decision 9](#decision-9--input-class-namespace-vs-typeregistry-and-lifecycle)'s `_materialized_names` lifecycle ledger because Range sub-input classes are nested inputs cached on the filter instance, NOT materialized as module globals of `django_strawberry_framework.filters.inputs`. **Deferred:** the per-filterset-scoped name shape — `f"{filterset_cls.__name__}{PascalCase(field_name)}RangeInputType"`, matching the existing `_build_input_fields` per-path operator-bag naming — lands when a real consumer surfaces the collision (likely in [Slice 4](#slice-checklist)'s live HTTP coverage or a follow-up card). The fix is mechanical (route the cache key + class-name derivation through the owning filterset). Forward path: when porting, the converter's `_build_range_input_class` helper takes the owning filterset class alongside the `filter_instance` and the cache key becomes `(filterset_cls, field_name)` rather than the bare `filter_instance` attribute.
- **Python keywords `and` / `or` / `not` in dataclass field positions**. Strawberry input types are dataclass-backed; dataclasses cannot generate an `__init__` with keyword-only parameters named `and`, `or`, or `not`. The package uses Python-safe attribute names (`and_`, `or_`, `not_`) and pins the GraphQL surface names via `strawberry.field(name="and")` / `name="or"` / `name="not"`. Consumer GraphQL queries see `and:` / `or:` / `not:`; Python tests / library code see `result.and_` / `result.or_` / `result.not_`.
- **Lookup names + Python keyword `in`.** Strawberry's default auto-camel-case only fires on underscored Python identifiers, so a raw `icontains` Python attr would stay `icontains` on the GraphQL surface even though every consumer expects `iContains`. Per [Decision 3](#decision-3--six-layer-lazy-resolution-pipeline) Layer 5's `LOOKUP_NAME_MAP`, the package generates `i_contains` as the Python attr AND pins `iContains` as the GraphQL name via `strawberry.field(name="iContains")`. Same shape for every initial-`i` case (`iExact`, `iStartsWith`, `iEndsWith`, `iRegex`), for `isNull`, and for the Python keyword `in` (Python attr `in_`, GraphQL name `in`). The runtime input-data normalizer (`normalize_input_value`) maps Python-side `in_` back to `in` when building the form-data dict; the form data, the lookup name `django-filter` sees, and the `<field>__<lookup>` ORM expression all line up.
- **Multi-`DjangoType`-per-model filterset binding.** When a model is exposed via multiple `DjangoType`s (per [`Meta.primary`][glossary-metaprimary]) with different Relay shapes — e.g., a primary non-Relay `PublicGenreType` AND a secondary Relay-Node-shaped `AdminGenreType` — a single `FilterSet` assigned to both owners would expose conflicting ID input shapes (scalar `int` for one owner, `relay.GlobalID` string for the other). Per [Decision 4](#decision-4--upstream-primitives-parity-floor), the filterset's `_owner_definition` slot is bound at finalizer phase 2.5; the validator rejects assignment to a second owner whose `related_target_for(<field>)` would resolve to a type with a different Relay shape ([`ConfigurationError`][glossary-configurationerror] with both owners' qualified names in the message). Consumers wanting separate Relay / non-Relay surfaces declare two separate `FilterSet` subclasses (`PublicBookFilter` and `AdminBookFilter`) — the input-class namespace is name-keyed so the two generate two distinct input types per [Decision 9](#decision-9--input-class-namespace-vs-typeregistry-and-lifecycle).
- **Partial-finalize recovery for the input-class namespace.** If `finalize_django_types()` raises mid-phase-2.5 (e.g., on an unresolved `RelatedFilter`), already-materialized classes stay in the `django_strawberry_framework.filters.inputs` module's `__dict__` and the lifecycle ledger keeps their provenance. A subsequent `finalize_django_types()` call resumes; idempotent `(name, input_class)` keys let the already-materialized classes pass through cleanly. `registry.clear()` resets the filter-input namespace too (per [Decision 9](#decision-9--input-class-namespace-vs-typeregistry-and-lifecycle) lifecycle clause), so test-fixture reload patterns work.
- **Fakeshop schema-reload pattern with already-materialized filter inputs.** The reload pattern (`registry.clear()` → reload app schema modules → reload project schema and URLconf) resets both the model-to-`DjangoType` registry AND the filter-input lifecycle state in the same `registry.clear()` call; reload then re-runs `finalize_django_types()`, which re-materializes the input classes and overwrites the parked module globals in place. No stale ledger entry, field spec, factory cache entry, or binding attribute survives into the next run, and a global left parked by the prior run is replaced in place the moment its name is re-materialized.
- **`filter_input_type(filterset_class)` validation**. The helper validates eagerly (`TypeError` at call time for a non-`FilterSet`) even though the returned `Annotated[...]` annotation is lazy. This catches misuse at the resolver-declaration site instead of letting Strawberry surface a more cryptic schema-build-time error.

## Risks and open questions

Each item names a preferred answer for the current cut and a fallback if implementation reveals the preferred answer is wrong.

- **Layer 5's forward-reference shape against Strawberry releases.** The idiom is `Annotated["{Name}FilterInputType", strawberry.lazy("django_strawberry_framework.filters.inputs")]` resolved via `LazyType.resolve_type` reading `module.__dict__` (per [Decision 3](#decision-3--six-layer-lazy-resolution-pipeline) Layer 5). Preferred answer: pin Strawberry to a version that supports this idiom (the package's existing `strawberry-graphql>=0.262.0` pin in [`pyproject.toml`][pyproject] already covers it); `tests/filters/test_inputs.py` constructs a minimal schema with a lazy `Annotated[...]` forward reference and asserts resolution succeeds, catching any future Strawberry regression at CI time. Fallback: if Strawberry deprecates the module-globals path in a future release (no signal that this is coming), the package re-evaluates; today's shape is the documented Strawberry idiom.
- **`Annotated["NotYetMaterialized", strawberry.lazy(...)]` resolution timing.** The materialize-before-`Schema` ordering ([Decision 6](#decision-6--finalizer-phase-25-binding-seam--materialize-before-schema-ordering)) depends on consumers calling `finalize_django_types()` BEFORE `strawberry.Schema(...)` — the canonical setup order pinned in [`docs/README.md`'s Schema setup boundary][docs-readme]. Preferred answer: consumers who follow the documented order get materialization in time; consumers who construct `strawberry.Schema(...)` before `finalize_django_types()` get a `LazyType.resolve_type` failure naming the missing class, which surfaces the ordering bug at schema-build time. Fallback: if real consumer reports surface "I called Schema first" confusion, a follow-up card adds an explicit check at `FilterSet.__init_subclass__` time that materializes a stub-class placeholder so `Schema(...)` resolves a clear "this class is being finalized" error instead of an opaque `KeyError`.
- **`filter_input_type(FilterSet)` against future `DjangoConnectionField` AND current `DjangoListField`.** [`DjangoConnectionField`][glossary-djangoconnectionfield] (`0.0.9`) will accept `filterset_class=` directly and own the argument injection — but **`0.0.8` consumers reach for `filter_input_type(...)` through plain `@strawberry.field` resolvers ONLY**. `DjangoListField` (shipped `0.0.7`) wraps resolvers with a two-argument `(root, info)` callable and does NOT preserve or expose arbitrary resolver arguments — so `filter_input_type(...)` is unreachable through `DjangoListField` in `0.0.8` without a new argument-injection design that is explicitly out of scope here. The `DjangoListField` filter-argument integration is **deferred to `0.0.9`** alongside `DjangoConnectionField`; both root-field surfaces grow filter-argument support in the same card cohort. Preferred answer: the `0.0.9` connection field (and the `0.0.9` extension of `DjangoListField`) uses `filter_input_type(FilterSet)` internally under the hood (no duplicate machinery); the `0.0.8` consumer-facing helper is the same shape `0.0.9` builds on. Fallback: if the connection field's argument-injection path turns out to need a different annotation shape (e.g., a wrapped `FilterSetWrapper[T]` generic for connection-field internals), the helper grows a `filter_input_type(FilterSet, *, connection_wrap=True)` parameter; the bare helper signature stays compatible.
- **Input-type namespace under per-`Meta.primary` secondary `DjangoType`s.** Preferred answer per [Decision 9](#decision-9--input-class-namespace-vs-typeregistry-and-lifecycle): the input-class namespace is name-keyed, so two `DjangoType`s on the same model with two different `filterset_class`es generate two distinct input types (`PrimaryGalaxyFilterInputType` and `AdminGalaxyFilterInputType`). Fallback: if a real consumer scenario surfaces where two filtersets on the same model should share an input type (e.g., shared queries against two roles), a follow-up card adds an optional `Meta.filter_input_alias` key that lets the consumer alias the generated input-type name; deferred until demand surfaces.
- **`Meta.filterset_class = MyDjangoFilter` accepting a `django_filters.FilterSet` subclass without re-parenting.** Preferred answer per [Decision 5](#decision-5--django-filter-as-the-foundation): the package's `FilterSet` IS a `django_filters.filterset.BaseFilterSet` subclass, so consumers migrate via parent-class swap (`class MyFilter(FilterSet):` instead of `class MyFilter(django_filters.FilterSet):`); the validator at `_validate_meta` rejects a plain `django_filters.FilterSet` that isn't a `django_strawberry_framework.filters.FilterSet` because the lazy-resolution + GraphQL-input layers don't run otherwise. [`GOAL.md #"Coming from DRF + django-filter"`][goal-migration-shape] states the migration as that one-line parent swap, inheriting every `django-filter` primitive. Fallback: if real consumer adoption pressure surfaces for accepting `django_filters.FilterSet` directly (without re-parenting), a follow-up card ships an opt-in `DjangoFilterAdapter` helper that wraps a `django_filters.FilterSet` in a thin `FilterSet`-shaped subclass.
- **Filter applied to a relation that has a custom `get_queryset`.** Preferred answer per [Decision 8](#decision-8--relation-permission-cascade--get_queryset-cooperation) step 3: `FilterSet.apply` derives the child visibility queryset from the target `DjangoType.get_queryset(child_model._default_manager.all(), info)` for every ACTIVE `RelatedFilter` branch BEFORE the parent's `<rel>__in=<child_qs>` join runs. The visibility-scoped child queryset is what the parent JOIN sees on the right-hand side, so a nested filter cannot match a parent through a child the visibility hook would hide. The optimizer's `Prefetch` downgrade ([Queryset diffing][glossary-queryset-diffing]) is unaffected — it covers OUTPUT planning for the selection set, which runs AFTER the parent queryset has already been WHERE-filtered. The `Prefetch` downgrade does NOT preserve the target type's `get_queryset` for parent-row filtering: it only fires during selection-tree walking, well after the parent queryset's WHERE clauses are baked in. Fallback: if a specific composition shape (e.g., a `RelatedFilter` whose target type's `get_queryset` is async-only and runs against a sync-only resolver context) breaks under the step-3 contract, a follow-up card refactors the visibility-scoping step to gate on the resolver's sync/async context.
- **Logical-and / logical-or input shape — flat vs nested.** Preferred answer: the cookbook's flat shape (`filter: { and: [...] }`) ports verbatim; nested per-field structures (`filter: { name__icontains: "...", and: [...] }`) are accepted at the top level only; nesting `and` / `or` / `not` inside per-field input is rejected. Fallback: if real consumer feedback wants nested operators, a follow-up card lifts the restriction.
- **`Meta.fields = "__all__"` performance AND schema-size growth**. Preferred answer: the BFS factory walks every model field; for models with many fields this is O(field_count × lookup_count) at finalize time but the result is cached, so per-request cost is unaffected. The more material concern is **schema-size growth**: the produced input type's SDL grows linearly with `field_count × lookup_count` — a 30-field model × ~8 default lookups = 240 input fields per type, and two such types on a schema = 480 fields. Apollo / GraphiQL introspection responses inflate accordingly; client codegen tooling slows; SDL diff review becomes harder. Consumers using `__all__` on wide models should expect noticeable schema-size growth; the workaround is to declare an explicit `Meta.fields` dict with narrower lookup sets, e.g., `{"name": ["exact", "icontains"], "status": ["exact"]}` instead of `"__all__"`. Fallback: if real-world consumer schemas with very-wide models surface measurable schema-size pain, a follow-up card adds a `Meta.lookup_subset` shorthand or a per-app field-set policy.
- **`Meta.search_fields` planned for `0.1.2`** but `LOOKUP_PREFIXES` ships in this card. Preferred answer: the `LOOKUP_PREFIXES` map + `construct_search` helper land in `filters/inputs.py` so the future `Meta.search_fields` card consumes them without retrofit; no consumer surface for search lookups exists today. Fallback: if `Meta.search_fields` ships earlier or the cookbook's `search_fields` shape diverges from `LOOKUP_PREFIXES`, that card adjusts; this card's surface is unaffected.
- **Glossary entry parity.** `LazyRelatedClassMixin`, `FilterArgumentsFactory`, `_dynamic_filterset_cache`, `FILTER_DEFAULTS`, and `LOOKUP_PREFIXES` are internal symbols not currently in [`docs/GLOSSARY.md`][glossary]. Preferred answer: keep them internal — the consumer surface is `FilterSet` / `RelatedFilter` / `filter_input_type` / `Meta.filterset_class`; the internal symbols are documented via this spec's body and via module docstrings, not the glossary. Fallback: if a future card surfaces one (e.g., a public `LOOKUP_PREFIXES` re-export for consumers writing custom search resolvers), the glossary entry lands with that card.
- **`filter_input_type` CSV row timing.** `filter_input_type` is a public symbol this card introduces, so its [`docs/GLOSSARY.md`][glossary] `## filter_input_type` heading and its [`docs/SPECS/appx/spec-027-filters-0_0_8-terms.csv`][spec-027-terms] row are both Slice 5 deliverables and land in the same commit (mirroring spec-020's [`strawberry_config`][glossary-strawberry-config] pattern). A term whose glossary heading does not exist yet cannot carry a CSV row, so the row is written when the heading is — never earlier, which would fail the gate for the whole authoring cycle. The shipped state: the CSV carries 48 rows including `filter_input_type`, the glossary heading exists, and [`scripts/check_spec_glossary.py`][check-spec-glossary] exits 0. Fallback: if a future maintainer prefers the over-zealous discipline (CSV row in the spec-author cycle, accepting checker failure until Slice 5), add the row at `filter_input_type,filter_input_type,The consumer helper this card introduces; GLOSSARY entry created in Slice 5.` and document the failure mode in this entry.
