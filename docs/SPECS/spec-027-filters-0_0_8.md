## Key glossary references

Skim these [`docs/GLOSSARY.md`][glossary] entries first — they anchor the vocabulary used throughout the spec:

- [`FilterSet`][glossary-filterset] — the declarative filter class. Subclasses `django_filters.filterset.BaseFilterSet` per [Decision 5](#decision-5--django-filter-as-the-foundation) and ports Layers 1–5 of `django-graphene-filters`' lazy-resolution pipeline per [Decision 3](#decision-3--six-layer-lazy-resolution-pipeline); Graphene's `graphene.InputObjectType` becomes `strawberry.input` and Graphene's `lambda:` forward references become `Annotated["TypeName", strawberry.lazy("django_strawberry_framework.filters.inputs")]` over module globals.
- [`RelatedFilter`][glossary-relatedfilter] — cross-relation filter traversal. Accepts a target `FilterSet` class, an absolute import path string, or an unqualified name for circular references; lazy-resolved at finalizer time.
- [`Meta.filterset_class`][glossary-metafilterset_class] — the consumer-facing key that points a [`DjangoType`][glossary-djangotype] at its `FilterSet`. In `ALLOWED_META_KEYS` per [Decision 7](#decision-7--metafilterset_class-promotion-gate).
- [`DjangoType`][glossary-djangotype] — the model-backed Strawberry type the filter sidecar attaches to. The `Meta`-driven shape is what makes `Meta.filterset_class = ItemFilter` legible to a Django audience.
- [`finalize_django_types`][glossary-finalize_django_types] — the synchronization point where the filter subsystem's lazy-resolution pipeline runs (phase 2.5, the same seam [`Meta.interfaces = (relay.Node,)`][glossary-metainterfaces] uses).
- [`DjangoOptimizerExtension`][glossary-djangooptimizerextension] — filter clauses applied to a queryset do not break the optimizer's [Queryset diffing][glossary-queryset-diffing] cooperation; covered by [Decision 8](#decision-8--relation-permission-cascade--get_queryset-cooperation) and a live HTTP test.
- [`get_queryset` visibility hook][glossary-get_queryset-visibility-hook] — pre-filter visibility scoping. Composes with filter `check_*_permission` gates ([Decision 8](#decision-8--relation-permission-cascade--get_queryset-cooperation)).
- [`OrderSet`][glossary-orderset] — the sibling ordering family; it reuses the same lazy-resolution architecture and the shared set-family substrate.
- [`AggregateSet`][glossary-aggregateset] / [`get_child_queryset`][glossary-get_child_queryset] — planned Layer-3 sidecars that will reuse the same architecture; [`apply_cascade_permissions`][glossary-apply_cascade_permissions] — the shipped cascade helper a `get_queryset` hook can call before any filter clause runs.
- [`DjangoConnectionField`][glossary-djangoconnectionfield] — reads the wrapped type's `Meta.filterset_class`, builds its `filter:` argument through `filter_input_type(...)`, and calls `apply_sync` / `apply_async` itself.
- [`Meta.primary`][glossary-metaprimary] — the multi-`DjangoType`-per-model design whose `TypeRegistry` keying convention this subsystem respects per [Decision 9](#decision-9--input-class-namespace-vs-typeregistry-and-lifecycle).
- [`ConfigurationError`][glossary-configurationerror] — raised at type-creation and finalization time for a non-`FilterSet` `Meta.filterset_class`, unresolvable `RelatedFilter` targets, unregistered related targets, multi-owner conflicts, orphan helper references, and unsupported relation lookups — see [Error shapes](#error-shapes) and [Edge cases](#edge-cases-and-constraints).
- [`Meta.search_fields`][glossary-metasearch_fields] — the planned search-input surface; the `LOOKUP_PREFIXES` map (`^` / `=` / `@` / `$`) ported verbatim from `django-graphene-filters` lives in the filter subsystem because `construct_search` belongs in the filter pipeline.

Foundational invariants and cross-cutting surfaces — all defined in [`docs/GLOSSARY.md`][glossary]:

- [Relation handling][glossary-relation-handling] — the FK / OneToOne / M2M / reverse-relation traversal `RelatedFilter` plugs into.
- [Relay Node integration][glossary-relay-node-integration] — the `Meta.interfaces = (relay.Node,)` surface that Decision 4's Relay-vs-scalar conditional consults; relation targets implementing `relay.Node` route through `GlobalIDFilter`.
- [Definition-order independence][glossary-definition-order-independence] — the invariant the lazy-resolution pipeline preserves so cross-module `RelatedFilter("...")` references work regardless of import order.
- [Cross-subsystem invariants][glossary-cross-subsystem-invariants] — the deferred-Meta-key promotion rule; Decision 7's promotion gate is one instance of it.
- [Choice enum generation][glossary-choice-enum-generation] — the pipeline `convert_filter_to_input_annotation` consults for choice-backed filter inputs, so choice-enum filter inputs round-trip through Strawberry enums.
- [Scalar field conversion][glossary-scalar-field-conversion] — the `SCALAR_MAP` the converter reads to type scalar and raw-primary-key filter inputs from the model column.
- [Specialized scalar conversions][glossary-specialized-scalar-conversions] — Decimal / Date / DateTime / Time / UUID conversions the converter handles per Decision 4.
- [BigInt scalar][glossary-bigint-scalar] — one of the scalar key shapes a 64-bit column produces.
- [Input type generation][glossary-input-type-generation] — the package's general input-type-generation surface; `FilterArgumentsFactory` is the filtering-specific instance built on the shared generated-input substrate.
- [OptimizerHint][glossary-optimizerhint] — the hint primitive `Meta.optimizer_hints` declarations carry; filter clauses compose with hints at queryset-translation time.
- [only() projection][glossary-only-projection] — the optimizer's projection contract; queryset filters compose with `.only(...)` projections.

- [ ] Slice 1: Foundation — module layout + `Filter` primitives + `FilterSet` metaclass
  - [ ] [`django_strawberry_framework/filters/`][filters] is a subpackage with `__init__.py`, `base.py`, `sets.py`, `factories.py`, `inputs.py` per [Decision 2](#decision-2--subpackage-layout-and-public-export-surface). Module docstrings pin each file's responsibility (`base.py` = filter primitives + `RelatedFilter`; `sets.py` = `FilterSet` + metaclass + apply pipeline; `factories.py` = `FilterArgumentsFactory`; `inputs.py` = the input-class namespace, input-data adapters and lifecycle ledger).
  - [ ] `base.py` ships the upstream primitives per [Decision 4](#decision-4--upstream-primitives-parity-floor): `TypedFilter`, `ArrayFilter` + `ArrayFilterMethod`, `RangeFilter` + `RangeField` + `validate_range`, `ListFilter` + `ListFilterMethod`, `GlobalIDFilter` + `GlobalIDMultipleChoiceFilter`, plus the raw-primary-key relation pair `RelationPkFilter` / `RelationPkMultipleFilter` and `RelatedFilter`. `Filter` is `django_filters.Filter` itself, re-exported from `filters/__init__.py` (not a port). Each ported primitive mirrors the matching `graphene_django/filter/filters/*.py` primitive (under `~/projects/django-graphene-filters/.venv/lib/python*/site-packages/graphene_django/filter/filters/`), Strawberry-adapted only at the input-type-construction boundary.
  - [ ] `RelatedFilter` is the `BaseRelatedFilter` port from `django_graphene_filters/filters.py::BaseRelatedFilter` (Layer 1 of [Decision 3](#decision-3--six-layer-lazy-resolution-pipeline)). Its owner-bind / lazy-target machinery is [`django_strawberry_framework/sets_mixins.py::RelatedSetTargetMixin`][sets-mixins], a subclass of the Layer-2 [`sets_mixins.py::LazyRelatedClassMixin`][sets-mixins] every set family shares; `filters/base.py` re-exports `LazyRelatedClassMixin` so the `filters` public surface carries the name.
  - [ ] `sets.py` ships `FilterSetMetaclass` (port from `django_graphene_filters/filterset.py::FilterSetMetaclass`) and `FilterSet` (port from `django_graphene_filters/filterset.py::AdvancedFilterSet`, with `get_filters` doing Layer-4 cycle-safe expansion) — Layers 3 + 4 of [Decision 3](#decision-3--six-layer-lazy-resolution-pipeline). `FilterSet` accepts [`Meta.model`][glossary-metamodel], [`Meta.fields`][glossary-metafields] (dict form `{"name": ["exact", "icontains"]}`, a per-field `"__all__"` value, or the top-level `"__all__"` shorthand with the override pinned in [Decision 3](#decision-3--six-layer-lazy-resolution-pipeline)), and per-field `check_<field>_permission` hooks. It carries the `_owner_definition: DjangoTypeDefinition | None` slot bound at finalizer phase 2.5 and the resolver-facing `apply_sync` / `apply_async` classmethod pair per [Decision 8](#decision-8--relation-permission-cascade--get_queryset-cooperation), which carry `info` end-to-end and call `filterset.form.is_valid()` explicitly (raising `GraphQLError("Invalid filter input")` with `extensions.code == "FILTER_INVALID"` on failure).
  - [ ] `inputs.py` IS the input-class namespace per [Decision 9](#decision-9--input-class-namespace-vs-typeregistry-and-lifecycle) — generated filter input classes are materialized as real module globals of `django_strawberry_framework.filters.inputs` via `materialize_input_class(name, cls)`, keyed by stable class-derived names (e.g., `"GalaxyFilterInputType"`); the private `_materialized_names: dict[str, type]` ledger maps each name to its materialized input class, which is what makes re-materialization idempotent. This module namespace is NOT the same surface as `django_strawberry_framework.registry.registry` (the model-to-`DjangoType` registry); the two cannot collide because their key types are disjoint (Django model class vs string class name). The shape is module-globals-keyed (not dict-keyed) because Strawberry's `LazyType.resolve_type` reads `module.__dict__[name]`, not a sidecar dict.

## Problem statement

A Django GraphQL package without a filter surface is not a credible alternative to either upstream: `graphene-django` ships `DjangoFilterConnectionField` + `filterset_class`, and `strawberry-graphql-django` ships `@strawberry_django.filter_type(Model)`. Consumers reach for `Meta.filterset_class = ItemFilter` the moment they wire a real schema.

Filtering is also the foundation for the other Layer-3 sidecars: [`OrderSet`][glossary-orderset] reuses its lazy-resolution architecture, [`AggregateSet`][glossary-aggregateset] is planned to reuse it again, [Meta.search_fields][glossary-metasearch_fields] is planned to reuse the `LOOKUP_PREFIXES` map, and [`DjangoConnectionField`][glossary-djangoconnectionfield] builds its `filter:` argument from the same factory output.

`django-graphene-filters` (the working reference per [`START.md`][start]) solved the hard part — a cycle-safe lazy-resolution pipeline that handles circular `RelatedFilter` references across modules. Layers 1–4 are library-agnostic Python and port verbatim; Layer 5 (the cycle-safe forward reference in the GraphQL schema build) needs Strawberry adaptation; Layer 6 (dynamic `FilterSet` generation) is not ported. [Decision 3](#decision-3--six-layer-lazy-resolution-pipeline) pins this.

- [`django_strawberry_framework/types/finalizer.py::finalize_django_types`][finalizer] phase 2.5 runs `apply_interfaces` / `install_relay_node_resolvers`, then `_bind_filtersets`, then `_bind_ordersets`.
- [`examples/fakeshop/apps/library/schema.py`][fakeshop-library-schema] wires filtersets onto its library types (including `Meta.interfaces = (relay.Node,)` on `GenreType` and [`Meta.optimizer_hints`][glossary-metaoptimizer-hints] on `LoanType`) and is the host for the live HTTP filter coverage per [Decision 12](#decision-12--live-http-coverage-strategy).
- Upstream cookbook: `~/projects/django-graphene-filters/django_graphene_filters/` — the six-layer pipeline whose Layers 1–4 port verbatim and whose Layer 5 is Strawberry-adapted.
- Upstream `graphene-django`: `~/projects/django-graphene-filters/.venv/lib/python*/site-packages/graphene_django/filter/` — the parity-floor primitives (per [Decision 4](#decision-4--upstream-primitives-parity-floor)).
- Upstream `strawberry-graphql-django`: `~/projects/strawberry-django-main/strawberry_django/filters.py` — the decorator-driven implementation. Its runtime pipeline (`process_filters`) is conceptually parallel to `FilterSet.apply_sync(...)` / `apply_async(...)`; the declaration surface (`@strawberry_django.filter_type(Model, lookups=True)` vs `class ItemFilter(FilterSet): class Meta: model = Item`) differs per the package's DRF-shaped positioning.

## Goals

1. Ship `FilterSet` + `RelatedFilter` + per-field `check_*_permission` gates + cross-relation traversal with cycle-safe lazy resolution, porting Layers 1–5 of `django-graphene-filters`' pipeline with Layer 5 Strawberry-adapted.
2. Keep [`Meta.filterset_class`][glossary-metafilterset_class] out of `DEFERRED_META_KEYS` only because the filter subsystem applies the configured class end-to-end — same gate as [`Meta.interfaces`][glossary-metainterfaces].
3. Establish the registration / factory / lazy-resolution pattern the sibling Layer-3 families ([`OrderSet`][glossary-orderset], [`AggregateSet`][glossary-aggregateset], [`FieldSet`][glossary-fieldset], [Meta.search_fields][glossary-metasearch_fields]) reuse without redesign.
4. Stay composable with [`DjangoOptimizerExtension`][glossary-djangooptimizerextension]'s [Queryset diffing][glossary-queryset-diffing] / [Plan cache][glossary-plan-cache] / [FK-id elision][glossary-fk-id-elision] / [Strictness mode][glossary-strictness-mode] — a filter clause is just another `.filter(...)` call on the consumer queryset.
5. Expose enough introspection (`FilterSet.get_filters()`, `FilterArgumentsFactory(cls).arguments`) for a maintainer to ask "what filter surface does this type support?" from the REPL in one call.
6. Earn package coverage through live fakeshop HTTP flows per [Decision 12](#decision-12--live-http-coverage-strategy).

## Non-goals

- **Ordering / aggregation / fieldsets / permissions cascade.** Each is its own card.
- **A `filter:` argument on `DjangoListField`.** [`DjangoListField`][glossary-djangolistfield] exposes `offset` / `limit` / `orderBy`, not `filter:`. Filtered root fields are plain `@strawberry.field` resolvers annotated with `FilterInput[...]` / `filter_input_type(...)`, or a [`DjangoConnectionField`][glossary-djangoconnectionfield], which reads `Meta.filterset_class`.
- **A `Meta.filterset_class = MyDjangoFilter` shape that accepts an arbitrary `django_filters.FilterSet` subclass without re-parenting.** Per [Decision 5](#decision-5--django-filter-as-the-foundation), `FilterSet` IS a `django_filters.filterset.BaseFilterSet` subclass, so a consumer with `class MyFilter(django_filters.FilterSet):` migrates by swapping the parent class to `django_strawberry_framework.filters.FilterSet` and inherits the lazy-resolution + GraphQL-input layers. Accepting a plain `django_filters.FilterSet` would mean two consumer-facing surfaces for one wiring (one with `RelatedFilter` / `check_*_permission` recursion, one without), so the validator requires a package `FilterSet` subclass.
- **Replacing the optimizer's queryset-diffing contract.** Filters land as `.filter(...)` calls before the optimizer walks the selection tree.
- **Auto-generation of `FilterSet` from `Meta.fields` without declaring an explicit class.** Not shipped: the package carries no dynamic-factory machinery (upstream's Layer 6). Every filtered surface, [`DjangoConnectionField`][glossary-djangoconnectionfield] included, reads an explicit `Meta.filterset_class` on the target `DjangoType`.

## Borrowing posture

Filtering is the most heavily-borrowed surface in the package.

### From `django-filter` — embrace as the foundation

`django-filter` is a hard dependency at [`pyproject.toml #"django-filter>=25.2"`][pyproject], and [`GOAL.md #"migrates with a one-line parent-class swap"`][goal-migration-shape] promises consumers a one-line parent-class swap onto `Meta.filterset_class`. The package's `FilterSet` subclasses `django_filters.filterset.BaseFilterSet` and inherits the load-bearing machinery — `declared_filters`, `base_filters`, `.filters`, `.form`, `.qs`, `get_filters()`, `Filter.method`, form cleaning, lookup generation. Per [Decision 5](#decision-5--django-filter-as-the-foundation) the package embraces the dependency.

The cookbook's `AdvancedFilterSet` inherits from `django_filters.filterset.BaseFilterSet`; the package's `FilterSet` mirrors that inheritance. The added value is the cycle-safe lazy-resolution layer (Layers 1–4 of [Decision 3](#decision-3--six-layer-lazy-resolution-pipeline)) and the Strawberry-adapted GraphQL-input layer (Layer 5), neither of which `django-filter` ships.

### From `django-graphene-filters` — borrow heavily (the cookbook is the working reference)

Local source path: `~/projects/django-graphene-filters/django_graphene_filters/`. The goal is to recreate "what the package enables for the schema author," not to port Graphene internals. Layers 1–4 are library-agnostic Python and port on top of the shared `django_filters.filterset.BaseFilterSet` foundation:

- `django_graphene_filters/filters.py::BaseRelatedFilter` → `django_strawberry_framework.filters.base::RelatedFilter` (Layer 1).
- `django_graphene_filters/mixins.py::LazyRelatedClassMixin` → [`django_strawberry_framework/sets_mixins.py::LazyRelatedClassMixin`][sets-mixins] (Layer 2), re-exported through `django_strawberry_framework.filters.base`.
- `django_graphene_filters/filterset.py::FilterSetMetaclass` → `django_strawberry_framework.filters.sets::FilterSetMetaclass` (Layer 3).
- `django_graphene_filters/filterset.py::AdvancedFilterSet` → `django_strawberry_framework.filters.sets::FilterSet`, subclassing `django_filters.filterset.BaseFilterSet` exactly as the cookbook does. `FilterSet.get_filters` runs Layer-4 cycle-safe expansion with the `_expanded_filters` cache and `_is_expanding_filters` re-entry guard read off the class's own `__dict__`.
- `django_graphene_filters/filterset.py::AdvancedFilterSet._apply_related_queryset_constraints` → `django_strawberry_framework.filters.sets::FilterSet._apply_related_constraints` — the explicit `queryset=` boundary that nested filters, and flat filters walking the branch, cannot escape, narrowed to active-branch scoping.
- `django_graphene_filters/filterset.py::AdvancedFilterSet.check_permissions` → recursion through `RelatedFilter`s into child filtersets' `check_*_permission` methods, narrowed to active-input-only scope ([Decision 8](#decision-8--relation-permission-cascade--get_queryset-cooperation)).
- `django_graphene_filters/filter_arguments_factory.py::FilterArgumentsFactory` → the BFS that builds every reachable input class. Its per-lookup `filterset_to_trees` / `try_add_sequence` / `sequence_to_tree` tree-form is not ported: `_build_input_fields` groups by top-level field name (see [Edge cases](#edge-cases-and-constraints)).
- `django_graphene_filters/filterset_factories.py::_dynamic_filterset_cache` → **not ported**. Upstream's Layer 6 (memoized dynamic `FilterSet` generation) serves connection fields declared without an explicit `filterset_class`; the package has no such surface.
- `LOOKUP_PREFIXES` map for `construct_search` (`^` → `istartswith`, `=` → `iexact`, `@` → `search`, `$` → `iregex`) → ported verbatim.

### From `graphene-django` — borrow the user-facing primitives only

Local source path: `~/projects/django-graphene-filters/.venv/lib/python*/site-packages/graphene_django/filter/`. The cookbook builds on `graphene-django`'s filter primitives; the package carries the same parity floor per [Decision 4](#decision-4--upstream-primitives-parity-floor):

- `graphene_django/filter/filters/array_filter.py::ArrayFilter`, `ArrayFilterMethod`.
- `graphene_django/filter/filters/range_filter.py::RangeFilter`, `RangeField`, `validate_range`.
- `graphene_django/filter/filters/list_filter.py::ListFilter`, `ListFilterMethod`.
- `graphene_django/filter/filters/typed_filter.py::TypedFilter` (base class for the three above).
- `graphene_django/filter/filters/global_id_filter.py::GlobalIDFilter`, `GlobalIDMultipleChoiceFilter` (Relay-aware filtering against `relay.Node`-shaped types).
- `graphene_django/filter/filterset.py::GrapheneFilterSetMixin.FILTER_DEFAULTS` (FK/PK → `GlobalIDFilter`) — the source of the package's `FILTER_DEFAULTS`. The package's FK/PK → `GlobalIDFilter` mapping is **conditional on the target `DjangoType`'s Relay shape** ([Decision 4](#decision-4--upstream-primitives-parity-floor)): the upstream mapping is unconditional because `DjangoFilterConnectionField` (the path `FILTER_DEFAULTS` is tied to) always returns a Relay connection, while the package's `DjangoType` is non-Relay by default.

### From `strawberry-graphql-django` — borrow the runtime-pipeline pattern (not the surface)

Local source path: `~/projects/strawberry-django-main/strawberry_django/filters.py`. The runtime layer is conceptually parallel (`process_filters` compiles input values into queryset arguments); the declaration surface diverges per the package's DRF-shaped positioning:

- `strawberry_django/filters.py::FilterLookup` — the generic typed lookup descriptor (`exact`, `i_exact`, `contains`, ...) is conceptually similar to the package's lookup-bag generation, but the BFS factory drives the lookup expansion.
- `strawberry_django/filters.py::process_filters` — the runtime side of the pipeline. `FilterSet.apply_sync(input_value, queryset, info)` / `apply_async(...)` is the equivalent consumer-facing entry point (the `django-filter` instance method `filter_queryset(self, queryset)` is the tree-form override, with a different signature).
- `strawberry_django/filters.py::FILTERS_ARG` (`= "filters"`) — NOT borrowed. The package ships no argument-name constant; Strawberry derives the GraphQL `filter:` argument from the resolver's Python parameter name.
- `strawberry_django/filters.py::filter_type` decorator — NOT borrowed (the package's `Meta`-driven surface forbids decorator-on-input-type per [`START.md`][start] "Style Rio cares about").
- The legacy `filter` alias with `DeprecationWarning` (`strawberry_django/filters.py #"def __getattr__"`) — NOT borrowed.

### Explicitly do not borrow

- **Graphene's `lambda: target_input_type` cycle-safe forward references.** Replaced by `Annotated["{TargetFilterSet}InputType", strawberry.lazy("django_strawberry_framework.filters.inputs")]` at Layer 5 (per [Decision 3](#decision-3--six-layer-lazy-resolution-pipeline)). Strawberry's `LazyType.resolve_type` imports the named module and reads `module.__dict__[type_name]` — it does NOT traverse object paths — so the generated input classes MUST be real module globals of `django_strawberry_framework.filters.inputs`, not dict entries on a private registry.
- **`graphene-django`'s `setup_filterset` wrapper-avoidance.** Strawberry's annotation resolution does not have the "Graphene{X}Filter" wrapping problem that motivated it.
- **`graphene-django`'s `replace_csv_filters`.** Strawberry's typed input handles `list[T]` natively.
- **`@strawberry_django.filter_type(Model, lookups=True)` decorator surface.** The package's `Meta`-driven shape forbids decorator-on-input-type for consumer-facing classes.

## User-facing API

The consumer surface is re-exported from `django_strawberry_framework.filters` (see [Decision 2](#decision-2--subpackage-layout-and-public-export-surface) for the full `__all__`): `FilterSet`, `RelatedFilter`, the parity-floor primitives, and the resolver-annotation helper in two spellings, [`filter_input_type`][glossary-filter_input_type] and `FilterInput`. [`Meta.filterset_class`][glossary-metafilterset_class] is the wiring on the existing [`DjangoType`][glossary-djangotype] surface; `FilterInput[MyFilter]` / `filter_input_type(MyFilter)` lets a normal `@strawberry.field` resolver accept a `filter:` argument that resolves to the generated input class at schema-build time.

**Resolver-facing API split:** consumers call `FilterSet.apply_sync(...)` from sync resolvers and `await FilterSet.apply_async(...)` from async resolvers per [Decision 8](#decision-8--relation-permission-cascade--get_queryset-cooperation). The `django-filter` instance method `filter_queryset(self, queryset)` is an internal override (tree-form logic) and is NOT the consumer surface. The thin `FilterSet.apply(...)` dispatcher always runs `apply_sync`.

### Default usage — declaring a `FilterSet`

```python
from django_strawberry_framework.filters import FilterSet, RelatedFilter

from . import models

class GalaxyFilter(FilterSet):
    # Reverse FK — referenced lazily by string so Galaxy and CelestialBody
    # filtersets can live in the same file without an import cycle.
    celestial_bodies = RelatedFilter("CelestialBodyFilter", field_name="celestial_bodies")

    class Meta:
        model = models.Galaxy
        fields = {
            "name": "__all__",
            "description": ["exact", "icontains"],
        }

class CelestialBodyFilter(FilterSet):
    # Explicit queryset acts as a scope boundary: nested filters
    # (`galaxy: {name: ...}`) and flat filters walking the branch
    # (`galaxyName`) can narrow it but cannot escape "public galaxies
    # only". It is not a visibility gate: with no `galaxy` predicate in
    # the input (active-branch scoping), parent rows are unconstrained,
    # so hiding rows is the job of GalaxyType.get_queryset.
    galaxy = RelatedFilter(
        GalaxyFilter,
        field_name="galaxy",
        queryset=models.Galaxy.objects.filter(is_private=False),
    )

    class Meta:
        model = models.CelestialBody
        fields = {
            "name": ["exact", "icontains"],
            "body_type": ["exact", "in"],
            "galaxy__name": ["exact"],
        }
```

`FilterSet` subclasses `django_filters.filterset.BaseFilterSet` (per [Decision 5](#decision-5--django-filter-as-the-foundation)), so consumers keep every `django-filter` primitive they know — `declared_filters`, `base_filters`, `Filter.method`, `form`, `qs`, lookup parsing — and add the `RelatedFilter` lazy-resolution layer plus the GraphQL-input layer on top.

### Wiring into a `DjangoType`

```python
from django_strawberry_framework import DjangoType

from . import filters, models

class GalaxyType(DjangoType):
    class Meta:
        model = models.Galaxy
        fields = "__all__"
        filterset_class = filters.GalaxyFilter
```

`Meta.filterset_class` is the only wiring required at the `DjangoType` site. The finalizer-phase-2.5 binding (per [Decision 6](#decision-6--finalizer-phase-25-binding-seam--materialize-before-schema-ordering)) takes care of owner binding, lazy-related-filter resolution, and input-class materialization as module globals of [`django_strawberry_framework.filters.inputs`][filters].

### Exposing the `filter:` argument on a resolver

```python
import strawberry

from django_strawberry_framework.filters import FilterInput

from . import filters, models

@strawberry.type
class Query:
    @strawberry.field
    def all_galaxies(
        self,
        info: strawberry.Info,
        filter: FilterInput[filters.GalaxyFilter] | None = None,
    ) -> list[GalaxyType]:
        # Visibility scoping ALWAYS runs before any filter clause (per
        # Decision 8): GalaxyType.get_queryset() applies the
        # request-scoped permissions / staff visibility / per-tenant filtering.
        # Filter clauses then operate on the already-scoped queryset, so a
        # filter cannot see through the visibility gate to hidden rows.
        queryset = GalaxyType.get_queryset(models.Galaxy.objects.all(), info)
        if filter is not None:
            # apply_sync because GalaxyType.get_queryset is sync; an async-only
            # get_queryset hook would require apply_async per Decision 8's
            # sync/async split.
            queryset = filters.GalaxyFilter.apply_sync(filter, queryset, info)
        return queryset
```

`FilterInput[filters.GalaxyFilter]` (equivalently `filter_input_type(filters.GalaxyFilter)`) evaluates to `Annotated["GalaxyFilterInputType", strawberry.lazy("django_strawberry_framework.filters.inputs")]`, the canonical Strawberry forward-reference idiom. Strawberry stores the annotation unresolved at `@strawberry.type` decoration time; at `strawberry.Schema(...)` construction, `LazyType.resolve_type` imports `django_strawberry_framework.filters.inputs` and reads `GalaxyFilterInputType` from `module.__dict__` — which the finalizer's phase-2.5 pass has materialized by then.

`GalaxyFilter.apply_sync(input_value, queryset, info)` and `GalaxyFilter.apply_async(input_value, queryset, info)` are the **resolver-facing classmethod pair** per [Decision 8](#decision-8--relation-permission-cascade--get_queryset-cooperation). Both carry `info` end-to-end so nested `RelatedFilter` branches can derive their target type's visibility scope. The shared pipeline derives the visibility-scoped querysets of every active `RelatedFilter` branch; normalizes the Strawberry input dataclass into the form-data dict `django-filter` expects (walking nested `RelatedFilter` inputs, mapping `and_` / `or_` / `not_` back to the logical-operator keys, mapping every per-lookup Python attribute back to its `django-filter` lookup name through `LOOKUP_NAME_MAP`); resolves the Django request through `FilterSet._request_from_info(info)` (a delegate to [`utils/permissions.py::request_from_info`][utils-permissions], which accepts `info.context.request`, a bare `HttpRequest` context, a mapping context whose `"request"` is an `HttpRequest`, and Strawberry's Channels context, and raises [`ConfigurationError`][glossary-configurationerror] naming the unsupported `info.context` shape otherwise); constrains the queryset by every active branch; instantiates `cls(data=data, queryset=queryset, request=request)`; runs the active-input permission pass `_run_permission_checks(input_value, request)` **with active-input-only scope** (per-field `check_<field>_permission` gates fire ONLY for fields present in the input — `check_name_permission` does not raise on `filter: { title: { iContains: ... } }`); **explicitly calls `filterset.form.is_valid()` and raises `GraphQLError("Invalid filter input", extensions={"code": "FILTER_INVALID", "errors": filterset.errors.get_json_data()})` when validation fails** (`BaseFilterSet.qs` only consults `self.errors` and falls through to `filter_queryset` otherwise; `ErrorDict.get_json_data()` gives consumers the stable `{field: [{"message": str, "code": str}, ...]}` shape); and returns `filterset.qs`.

[`DjangoConnectionField`][glossary-djangoconnectionfield] reads the target type's `Meta.filterset_class`, builds its `filter:` argument through `filter_input_type(...)`, and calls `apply_sync(...)` / `apply_async(...)` itself; the hand-written resolver above is the explicit shape for a plain `@strawberry.field`.

### Per-field permission gates

```python
from graphql import GraphQLError

class GalaxyFilter(FilterSet):
    class Meta:
        model = models.Galaxy
        fields = {"name": "__all__", "description": ["exact", "icontains"]}

    def check_name_permission(self, request):
        """Only staff users may filter by Galaxy.name.

        Active-input-only scope:
        this gate fires ONLY when the consumer's filter input includes a
        ``name:`` clause. A query like ``{ allGalaxies { id name } }`` with
        no ``filter`` argument, OR a query like
        ``{ allGalaxies(filter: { description: { iContains: "..." } }) ... }``
        that filters only by ``description``, does NOT trigger this gate.
        Permissions gate USE of the filter, not its declaration.
        """
        user = getattr(request, "user", None)
        if not user or not user.is_staff:
            raise GraphQLError("You must be a staff user to filter by Galaxy name.")
```

The framework calls `check_<field>_permission(request)` before applying the corresponding filter — **but only for fields present in the input** (active-input-only scope; see [Decision 8](#decision-8--relation-permission-cascade--get_queryset-cooperation) step 5). A `GraphQLError` raised inside the gate surfaces as an `errors` entry on the response. The gate must be a plain `def`: an awaitable return is rejected with `SyncMisuseError` by [`utils/permissions.py::invoke_permission_method`][utils-permissions].

### Logical-and / logical-or / logical-not

The factory generates the three logical-operator fields on every `<TypeName>FilterInputType`. Python attribute names use the trailing-underscore convention (`and_`, `or_`, `not_`) because `and` / `or` / `not` are Python keywords and cannot be dataclass field names; the GraphQL surface names are exactly `and`, `or`, `not` via `strawberry.field(name="and")` / `name="or"` / `name="not"`. The same pattern applies to the `in` lookup (Python attr `in_`, GraphQL name `in`) per [Decision 3](#decision-3--six-layer-lazy-resolution-pipeline) Layer 5's `LOOKUP_NAME_MAP`. Consumer-facing GraphQL shape:

```graphql
{
  allGalaxies(
    filter: {
      and: [
        {
          name: {
            iContains: "andromeda"
          }
        }
        {
          not: {
            isPrivate: {
              exact: true
            }
          }
        }
      ]
    }
  ) {
    id
    name
  }
}
```

The self-referential input type is handled by Layer 5's Strawberry-adapted forward reference per [Decision 3](#decision-3--six-layer-lazy-resolution-pipeline):

- `and_: list[Annotated["<TypeName>FilterInputType", strawberry.lazy("django_strawberry_framework.filters.inputs")]] | None`
- `or_: list[Annotated["<TypeName>FilterInputType", strawberry.lazy("django_strawberry_framework.filters.inputs")]] | None`
- `not_: Annotated["<TypeName>FilterInputType", strawberry.lazy("django_strawberry_framework.filters.inputs")] | None`

The `Annotated[...]` MUST wrap the forward-reference string directly (`Annotated["Name", strawberry.lazy(...)]`), not the surrounding `list[...]`. Strawberry's `LazyType.resolve_type` only resolves the annotated argument when that argument itself is a `ForwardRef`; wrapping `list["Foo"]` leaves the inner `"Foo"` unresolved and surfaces a `NameError` from Strawberry's type evaluation.

### Error shapes

- `Meta.filterset_class = <non-FilterSet>` → [`ConfigurationError`][glossary-configurationerror] (`"<Model>.Meta.filterset_class must be a FilterSet subclass; got <value>"`) at type creation.
- `RelatedFilter("UnknownFilter")` that neither Layer-2 attempt resolves → [`ConfigurationError`][glossary-configurationerror] (`"Cannot finalize Django types: filterset <qualified name> references an unresolved related-filter target. <ImportError text>"`) at finalize subpass 2, with the `ImportError` on `__cause__`.
- A `RelatedFilter` whose target model has no registered `DjangoType` → [`ConfigurationError`][glossary-configurationerror] at finalize subpass 2.5 naming the filterset and the field.
- `Meta.fields = {"unknown_field": ["exact"]}` (a name that is not a model field, including a model property) → `django-filter`'s own `TypeError("'Meta.fields' must not contain non-model field names: unknown_field")` at `FilterSet` class creation.
- `Meta.fields = {"name": ["unsupported_lookup"]}` on a scalar column → `django-filter`'s `FieldLookupError("Unsupported lookup 'unsupported_lookup' for field '<app>.<Model>.name'.")` at class creation. On a framework-owned relation key (or a Relay owner's own PK), any lookup outside `{exact, in, isnull}` → [`ConfigurationError`][glossary-configurationerror] at class creation naming the filterset, the field and the lookup.
- `filter_input_type(<non-FilterSet>)` → `TypeError("filter_input_type() requires a FilterSet subclass; got <value>")`, and `FilterInput[<non-FilterSet>]` → `TypeError("FilterInput[...] requires a FilterSet subclass; got <value>")`, both at evaluation time (validation is eager even though the returned `Annotated[...]` is lazy).
- Logical or related nesting deeper than `FilterSet._MAX_LOGIC_DEPTH` → [`ConfigurationError`][glossary-configurationerror] at request time.

## Architectural decisions

### Decision 1 — Spec filename and canonical naming

The spec file is **`docs/SPECS/spec-027-filters-0_0_8.md`** (this document); the card body's `docs/spec-filters.md` predates the structured name. `docs/SPECS/` is where [`docs/SPECS/NEXT.md`][next] Step 8 archives a completed spec, together with its `-terms.csv` and `-rationale.md` companions under `docs/SPECS/appx/`; the `spec-<NNN>-<topic>-<0_0_X>` stem is the canonical name at either location.

Rationale companion — this Decision's justification and its two rejected alternatives: [Decision 1][rationale-d1].

### Decision 2 — Subpackage layout and public export surface

The filter subsystem is a subpackage at **[`django_strawberry_framework/filters/`][filters]** (NOT a flat single-file module). Five files:

- `__init__.py` — `__all__` is `ArrayFilter`, `ArrayFilterMethod`, `Filter`, `FilterInput`, `FilterSet`, `FilterSetMetaclass`, `GlobalIDFilter`, `GlobalIDMultipleChoiceFilter`, `LazyRelatedClassMixin`, `ListFilter`, `ListFilterMethod`, `RangeField`, `RangeFilter`, `RelatedFilter`, `TypedFilter`, `filter_input_type`, `validate_range`. `Filter` IS `django_filters.Filter` itself — a plain re-export, deliberately shadowing the upstream name so a consumer writing a custom `method=` filter imports one base class from `django_strawberry_framework.filters`. The module also hosts the orphan-tracking ledger `_helper_referenced_filtersets` next to the helper that writes it ([Decision 11](#decision-11--filter_input_typefilterset-consumer-helper)). `FilterArgumentsFactory` is not re-exported; advanced callers import it from `django_strawberry_framework.filters.factories`.
- `base.py` — `TypedFilter`, `ArrayFilter`, `ArrayFilterMethod`, `RangeFilter`, `RangeField`, `validate_range`, `ListFilter`, `ListFilterMethod`, `GlobalIDFilter` (Strawberry-specific: accepts both `str` and `relay.GlobalID` inputs; validates the decoded `type_name`), `GlobalIDMultipleChoiceFilter`, `RelationPkFilter`, `RelationPkMultipleFilter`, the `IntegerInFilter` / `IntegerRangeFilter` reroutes for integer `in` / `range` lookups, and `RelatedFilter`; it re-exports `LazyRelatedClassMixin` from [`django_strawberry_framework/sets_mixins.py`][sets-mixins].

- `factories.py` — `FilterArgumentsFactory` (input shape derived from the resolved filter instances through the named converter `convert_filter_to_input_annotation`). `FILTER_DEFAULTS` lives on `FilterSet`, so runtime `django-filter` and the factory read the same resolved filter instances and cannot drift.
- `inputs.py` — the per-module input-class namespace, `INPUTS_MODULE_PATH`, `build_input_class`, `_build_logic_fields`, `_build_input_fields`, `construct_search`, `LOOKUP_PREFIXES` (the `^` / `=` / `@` / `$` search prefixes), `LOOKUP_NAME_MAP` (the `<django-filter-lookup> → (python_attr, graphql_name)` map — `icontains → ("i_contains", "iContains")`, `iexact → ("i_exact", "iExact")`, `istartswith → ("i_starts_with", "iStartsWith")`, `iendswith → ("i_ends_with", "iEndsWith")`, `iregex → ("i_regex", "iRegex")`, `isnull → ("is_null", "isNull")`, `in → ("in_", "in")`, `range → ("range", "range")`, etc.), the `FilterLookupTable` built by `filter_lookup_table` (each operator-bag lookup's `django-filter` form key, decided once per filter set; see "Per-field form keys via the lookup table" below), the `FieldSpec` dataclass + `_field_specs: dict[tuple[type[FilterSet], str], FieldSpec]` table (carries `(python_attr, graphql_name, django_source_path)` per generated input field; on the filter side `django_source_path` is the field's `check_<path>_permission` gate path), `convert_filter_to_input_annotation` (choice enums, `relay.GlobalID`, raw relation keys, `in` / `range` list shapes, nullable values, decimal / date / datetime / time / UUID, custom `Filter(method=...)` fields), `normalize_input_value(filter_instance, raw_value, field_name=None)` (the runtime symmetric — normalizes Strawberry input values back into the form-data shape `django-filter` expects, under the form key the lookup table holds for each lookup), `materialize_input_class`, `clear_filter_input_namespace`, `_materialized_names`.

### Decision 3 — Six-layer lazy-resolution pipeline

The pipeline is upstream's six layers, of which the package ships five: Layers 1–4 port from `django-graphene-filters` library-agnostic (with `django_filters.filterset.BaseFilterSet` as the shared foundation per [Decision 5](#decision-5--django-filter-as-the-foundation)), Layer 5 is Strawberry-adapted, and Layer 6 is not shipped.

**Layer 1 — Lazy class references in `RelatedFilter`** — port of `django_graphene_filters/filters.py::BaseRelatedFilter`. `RelatedFilter` accepts the target as a class, an absolute import path string (`"myapp.filters.ManagerFilter"`), an unqualified name (`"ManagerFilter"`), or a zero-arg factory. `_filterset` stores it unresolved; the `.filterset` property resolves it, and a resolved value that is not a `FilterSet` subclass raises [`ConfigurationError`][glossary-configurationerror] (`RelatedFilter._validate_target`).

**Layer 2 — Module-fallback resolution** — port of `django_graphene_filters/mixins.py::LazyRelatedClassMixin.resolve_lazy_class`. Two-step resolution: try as absolute path via `django.utils.module_loading.import_string`; on `ImportError`, retry with the `bound_class.__module__` prefix. Handles circular references within one module.

**Layer 3 — Metaclass discovery, deferred expansion** — port of the `django_graphene_filters/filterset.py::FilterSetMetaclass` pattern. The metaclass collects `RelatedFilter` declarations into `cls.related_filters` through the shared [`sets_mixins.py::collect_related_declarations`][sets-mixins] walk and binds each declaration to the new class so the module-fallback resolver knows the owning module (`bind_filterset` is the public spelling of that bind). It **does not** expand; expansion is deferred to `get_filters()`.

**Layer 4 — Cycle-safe expansion + cache** — port of `django_graphene_filters/filterset.py::AdvancedFilterSet.get_filters`. The `_expanded_filters` cache and `_is_expanding_filters` re-entry guard are read off the class's own `__dict__` through the shared [`sets_mixins.py::expanded_once`][sets-mixins]; a re-entry returns the unexpanded filters, which breaks `A → B → A` cycles without caching a half-built result. Two-condition cache write ([`sets_mixins.py::should_cache_expansion`][sets-mixins]): `related_filters` is in the class's own `__dict__` AND no string `_filterset` remains on any related filter. The expansion itself (`filters/sets.py::_expand_related_filter`) copies each child filter onto the parent under `<relation>__<child name>` with `field_name` rebound to the relation path, which reproduces the child filter exactly as long as its behavior is the filter object's own. A child filter whose behavior the child filter set owns (`filters/sets.py::_owner_bound_child`: a `method=` filter, every filter of a child that overrides `__init__` — `FilterSet._customizes_instances`, the same seam the row-preserving optimizer refuses — and an already projected copy expanded again) is copied as a `filters/sets.py::ProjectedChildFilter` instead: an instance of the child filter's own class, so input typing, value normalization and family recognition are unchanged, whose form field is the one a child filter set instance builds (one instance per parent filter set instance and child class, built on first use by `filters/sets.py::FilterSet._projection_child` and shared by every projected leaf of that parent; a child `__init__` customization and a request-aware callable `queryset` apply, and the child carries the parent's request) and whose `filter` runs the child filter inside that instance over the branch's visible child rows (the target type's `get_queryset` over the child model's rows on the parent's database alias, as the nested branch scopes them in [Decision 8](#decision-8--relation-permission-cascade--get_queryset-cooperation) step 3), then keeps the parent rows whose relation reaches a matching child row the declaration's explicit `queryset=` admits (`filters/sets.py::FilterSet._apply_relation_leaf`, restricting through `filters/sets.py::FilterSet._reaches_hop`, the correlated `EXISTS` the nested branch restricts through). A child filter returning its input unchanged (django-filter's empty-value skip) leaves the parent unchanged and runs no `get_queryset`. A child filter that is itself a flat leaf walking a declared hop of the child set walks it the same way. Each flat leaf stays its own predicate — two owner-bound leaves may be satisfied by different child rows. An expanded copy that is not owner-bound walks, through its rebound `field_name`, the branch it was expanded from, so Decision 8's flat-leaf scoping applies to it by path. A `RelatedFilter` entry of the child is a branch, not a flat leaf, and is copied as is.

**Layer 5 — BFS schema build with module-global materialization (Strawberry-adapted)** — the BFS from `django_graphene_filters/filter_arguments_factory.py::FilterArgumentsFactory`, single-sited on [`utils/inputs.py::GeneratedInputArgumentsFactory`][utils-inputs]. The cycle-safe forward reference changes shape because Strawberry's lazy mechanism is module-path-only, NOT object-path:

- Strawberry's `strawberry.types.lazy_type.LazyType.resolve_type` imports the module named in `strawberry.lazy("<module-path>")` and reads `module.__dict__[type_name]`. It does NOT traverse object paths (`module.attr.subattr`) and does NOT look up entries in a sidecar dict.
- Consequence: every generated filter input class MUST be a **real module global** of [`django_strawberry_framework.filters.inputs`][filters], not an entry in a private dict.
- The Strawberry idiom is `Annotated["{TargetFilterSet}InputType", strawberry.lazy("django_strawberry_framework.filters.inputs")]` — a string forward reference combined with the module-path marker.
- The `Annotated[...]` MUST directly wrap the forward-reference string. For list-typed fields (the `and_` / `or_` operators), push the `Annotated[...]` INSIDE the `list[...]`: `list[Annotated["Name", strawberry.lazy(...)]] | None`, NOT `Annotated[list["Name"], strawberry.lazy(...)] | None`.
- The factory emits the `Annotated[...]` shape in field annotations so cycle-safe references between filtersets keep working; it does **not** write module globals. Materialization is the finalizer's: [`materialize_input_class(name, cls)`][filters] — two arguments; the destination module is always `django_strawberry_framework.filters.inputs` — is called once per built class at phase-2.5 subpass 4 (per [Decision 6](#decision-6--finalizer-phase-25-binding-seam--materialize-before-schema-ordering)), whose filter-side entry point is [`django_strawberry_framework/types/finalizer.py::_bind_filtersets`][finalizer] and whose materialize loop is the shared `_bind_sidecar_sets`.
- Per-lookup field names are pinned through `LOOKUP_NAME_MAP` in `inputs.py`. Strawberry's default auto-camel-case only fires on underscored Python identifiers — `icontains` stays `icontains` because there is no underscore to transform. The map enumerates every supported `django-filter` lookup as `lookup_name → (python_attr, graphql_name)`:

  | django-filter lookup | Python attr (dataclass field) | GraphQL name (explicit) |
  | --- | --- | --- |
  | `exact` | `exact` | `exact` |
  | `iexact` | `i_exact` | `iExact` |
  | `contains` | `contains` | `contains` |
  | `icontains` | `i_contains` | `iContains` |
  | `startswith` | `starts_with` | `startsWith` |
  | `istartswith` | `i_starts_with` | `iStartsWith` |
  | `endswith` | `ends_with` | `endsWith` |
  | `iendswith` | `i_ends_with` | `iEndsWith` |
  | `regex` | `regex` | `regex` |
  | `iregex` | `i_regex` | `iRegex` |
  | `gt` / `gte` / `lt` / `lte` | `gt` / `gte` / `lt` / `lte` | `gt` / `gte` / `lt` / `lte` |
  | `isnull` | `is_null` | `isNull` |
  | `in` | `in_` | `in` |
  | `range` | `range` | `range` |
  | `date` / `year` / `month` / `day` / `week_day` / `quarter` / `hour` / `minute` / `second` | mirror | camelCase |

  Both the factory (`_build_input_fields`) and the runtime input-data normalizer (`FilterSet._normalize_input`) read one per-class lookup table, `filters/inputs.py::filter_lookup_table`, which names each lookup's Python attr through `LOOKUP_NAME_MAP` and holds that lookup's `django-filter` form key, so the GraphQL surface and the form-data conversion never disagree. `_build_input_fields` emits each lookup field via `strawberry.field(name=<graphql_name>)` when `python_attr != graphql_name`, and an `in_` value lands under the `in` filter's own form key when the form-data dict is built.

**Per-field form keys via the lookup table.** `Meta.fields = {"galaxy__name": ["exact"]}` renders as the flat GraphQL field `galaxyName: { exact: ... }`. `filters/inputs.py::filter_lookup_table` groups `get_filters()` by head once per `get_filters()` result: a declared filter, and a `RelatedFilter` expansion of a child's declared filter, is its own head (its name is its form key even when it ends in its own lookup token, `name__exact`); a generated `<path>__<lookup>` filter joins the `<path>` head under `<lookup>`. Each head maps every lookup to `(form key, filter)`, where the form key is the filter's own `get_filters()` name, and the table is keyed by both the head's spelling (`galaxy__name`) and its flattened input attr (`galaxy_name`). The form-data dict for an active `galaxyName: { exact: ... }` therefore carries `{"galaxy__name": <value>}`, NOT `{"galaxyName": <value>}` or a reverse-mangled `{"galaxy_name": <value>}`, and a head that is both declared and generated (`name = CharFilter(lookup_expr="iexact")` beside `Meta.fields = {"name": ["icontains"]}`) binds `iExact` to `name` and `iContains` to `name__icontains`. A hand-built mapping passed to `apply_sync` / `apply_async` reads the same table, under either spelling, whether or not the input class was ever built.

The generated-input substrate's [`utils/inputs.py::GeneratedInputFieldSpec`][utils-inputs], re-exported as `FieldSpec` by `filters/inputs.py` (and by `orders/inputs.py`), still records each generated input field:

```python
# django_strawberry_framework/utils/inputs.py
@dataclass(frozen=True)
class GeneratedInputFieldSpec:
    python_attr: str          # dataclass field name on the Strawberry input class (e.g., "galaxy_name")
    graphql_name: str         # wire-format name via strawberry.field(name=...) (e.g., "galaxyName")
    django_source_path: str   # filter side: the check_<path>_permission gate path (e.g., "galaxy__name")
```

`_build_input_fields` fills the `FieldSpec` table as it builds the input fields, keyed by `(filterset_class, python_attr)`. On the filter side `django_source_path` is read only by the permission gates (`utils/permissions.py::active_permission_targets`): a declared head, and an expansion of a child's declared filter, gates on its own name, and any other head gates on its filter's `field_name`, so `name` and `name__icontains` share the `name` gate. A walked leaf then fires exactly the gates its nested twin fires, whatever lookup, `isnull` or `exclude` it applies. The gate path fires the owner's own gate and, through `utils/permissions.py::_fire_flat_relation_path_gates`, the gates `utils/permissions.py::relation_path_gates` reads off it: each branch `utils/permissions.py::walk_declared_relation_path` walks (keyed on the public attr, as `check_<branch>_permission`), then the last resolved target set's gate for the path the walk leaves there, the gate path the twin's leaf on that set carries. That remainder may cross an undeclared relation and gates on the whole remainder (`property__name`), and a relation-key path leaves none, so its target gate is the target's primary key: `Meta.fields` key `shelves` beside `visible_shelves = RelatedFilter(ShelfFilter, field_name="shelves")` fires `check_visible_shelves_permission` and `ShelfFilter.check_id_permission`, as `visibleShelves: { id: ... }` does. A leaf whose gate path is not its ORM path also fires its nested twin's gates through `filters/sets.py::FilterSet._permission_walk_gates`, read by `utils/permissions.py::run_active_input_permission_checks`, which collects `filters/sets.py::FilterSet._leaf_gates` per supplied leaf: a `ProjectedChildFilter` or an expanded copy of a child filter answers for its child filter in the child set, recursively, and any other leaf walking declared hops (`FilterSet._flat_leaf_walk`, the hops its row scoping reads) fires `relation_path_gates` over its own `field_name`. So `ShelfFilter.home_branch` over `branch` fires `check_home_branch_permission`, `check_branch_permission` and `BranchFilter.check_id_permission`, and `GenreFilter.without_book_titled` over `books__title` fires `check_without_book_titled_permission`, `GenreFilter.check_books_permission` and `BookFilter.check_title_permission`. A `method=` filter declared on the parent walks no hop and fires only its own gate (its Python owns its scoping; [`GOAL.md`][goal] "Trust boundary"). Every gate shares the per-class dedup, so each fires at most once per request. Form keys never come from it.

**`HIDE_FLAT_FILTERS` — the one setting attached to the flat-field contract.** The flat rendering above is the default. A consumer who wants only the nested `RelatedFilter` surface sets `DJANGO_STRAWBERRY_FRAMEWORK["HIDE_FLAT_FILTERS"] = True`, read through [`conf.py::hide_flat_filters_setting`][conf] (default `False`). When set, `_build_input_fields` skips every grouped entry that is an **expanded child** of a declared `RelatedFilter` — a flat relational traversal path whose first segment names the relation (`category__name`, `entries__property__category__name`) — at every depth. Nothing becomes unreachable: those paths stay filterable through the nested branch. The setting shapes the schema only; it is not a visibility control, since a shown flat field walking a declared branch answers over the same visible rows its nested spelling reads ([Decision 8](#decision-8--relation-permission-cascade--get_queryset-cooperation) step 3). A same-model path (`name`, or a `__` lookup that traverses no relation) and an explicit `Meta.fields` traversal with no `RelatedFilter` root stay visible either way. The upstream analogue is the `is_expanded_child` skip in `django_graphene_filters/connection_field.py::_get_trimmed_filterset_class`.

Graphene's `graphene.InputField(lambda tn=target_name: input_object_types[tn])` and the Strawberry idiom (`Annotated["...", strawberry.lazy("...")]` over a module-global namespace) are conceptual twins — both defer the type reference until schema walk; only the lookup mechanism differs (dict-keyed for Graphene; `module.__dict__` keyed for Strawberry).

**Layer 6 — Memoized dynamic FilterSet generation** — **not shipped.** Upstream's `django_graphene_filters/filterset_factories.py::_dynamic_filterset_cache` memoizes a generated `FilterSet` per `(model, fields, extra_meta)` for connection fields declared without an explicit `filterset_class`. Every filtered surface in the package names `Meta.filterset_class`, so there is nothing to generate and no cache to key.

**`Meta.fields = "__all__"` scope and intentional override of django-filter's default.** The shorthand expands to the model's scalar fields and forward FK / OneToOne / `ForeignObject` relations plus the primary key (a `ForeignObject` leaf matches the target's pk through every link column), under the conditional `FILTER_DEFAULTS` per [Decision 4](#decision-4--upstream-primitives-parity-floor). Relation traversal under `"__all__"` is **explicitly excluded** — a relation becomes a nested branch only when the consumer declares `RelatedFilter(...)` for it. This overrides `django-filter`'s `django_filters.utils.get_all_model_fields` in two ways:

- `django-filter` **excludes** `AutoField` primary keys; `FilterSet.get_fields` **adds** the primary key (with `exact`), because filtering by ID (`GlobalIDFilter` on a Relay owner, a scalar key otherwise) must be reachable through the shorthand.
- `django-filter` **includes** M2M relations; `FilterSet.get_fields` **removes** every `ManyToManyField`, because traversing a M2M without an explicit target `FilterSet` would either auto-generate one (the [Non-goals](#non-goals) "no implicit `FilterSet` generation" rule forbids this) or expose a bare-key filter the consumer did not ask for.

`FilterSet.get_fields` — the public `django-filter` classmethod — carries both deltas, and also expands a per-field `"__all__"` value (`{"name": "__all__"}`) to the field's concrete lookups, which upstream would otherwise pass through as a literal lookup expression. Tests pin both `"__all__"` deltas: the PK IS generated AND a M2M relation is NOT generated without an explicit `RelatedFilter`.

### Decision 4 — Upstream-primitives parity floor

The package ships parity equivalents for every upstream filter primitive:

- `ArrayFilter(TypedFilter)`, `ArrayFilterMethod(FilterMethod)` (from `graphene_django/filter/filters/array_filter.py`).
- `RangeFilter(TypedFilter)`, `RangeField(Field)`, `validate_range` (from `graphene_django/filter/filters/range_filter.py`).
- `ListFilter(TypedFilter)`, `ListFilterMethod(FilterMethod)` (from `graphene_django/filter/filters/list_filter.py`).
- `TypedFilter(Filter)` (from `graphene_django/filter/filters/typed_filter.py`) — base class for the three above.
- `GlobalIDFilter(Filter)`, `GlobalIDMultipleChoiceFilter(MultipleChoiceFilter)` (from `graphene_django/filter/filters/global_id_filter.py`).

The `FILTER_DEFAULTS` map is a **class attribute on the package `FilterSet`** (not a factory-side parallel map) so the `django-filter` runtime AND the Strawberry input factory agree on the chosen filter primitive. The relation mapping is **conditional on the target `DjangoType`'s Relay shape**:

- An FK / PK / M2M whose target type — resolved from the field on the **owning `FilterSet`'s target `DjangoType`** (`_owner_definition.related_target_for(field_name)`, falling back to `registry.get(target_model)` before owner binding) — implements `relay.Node` (per `Meta.interfaces = (relay.Node,)`) → `GlobalIDFilter` for a single-valued relation, `GlobalIDMultipleChoiceFilter` for a multi-valued one; the input accepts the Relay GlobalID string and the filter decodes it before applying the queryset clause.
- An FK / PK / M2M whose target type is **non-Relay** (the default, e.g. `ShelfType` in the fakeshop library app), or whose target model no `DjangoType` exposes → `RelationPkFilter` (single-valued `exact`) / `RelationPkMultipleFilter` (`in`, and `exact` on a multi-valued relation), which accept the target's raw primary key typed from its key column (typically `int`, sometimes `uuid.UUID` or `BigInt`).
- The owner's **own primary key** under a Relay-Node owner → a GlobalID filter typed to the owner.
- On a framework-owned relation key, `exact` / `in` map to the identity filters above, `isnull` stays a boolean filter, and any other lookup raises [`ConfigurationError`][glossary-configurationerror] at class creation. A consumer-selected override (`Meta.filter_overrides` or a shadowed `FILTER_DEFAULTS`) is returned unchanged and is never subject to this policy.
- A single-valued forward relation whose link targets columns other than the target's primary key (a `ForeignKey` / `OneToOneField` with `to_field=`, a `ForeignObject` whose `to_fields` are not the pk) stores and joins on those columns, while a Relay GlobalID and a raw-pk value both carry the target's primary key, so `filter(<relation>=<pk>)` would compare the wrong column. `FilterSet.filter_for_field` marks the generated identity filter (`GlobalIDFilter` / `GlobalIDMultipleChoiceFilter` / `RelationPkFilter` / `RelationPkMultipleFilter`) when `django_strawberry_framework/filters/base.py::_relation_uses_non_pk_to_field` holds: the relation is `forward_single` and its link's target columns, read through `django_strawberry_framework/utils/relations.py::relation_link`, are not exactly the target model's pk fields. A marked filter compiles against `<field_name>__pk`, derived from its live `field_name` at filter time so a `RelatedFilter` expansion that rebases `field_name` keeps the qualification. An FK onto the pk, a `ForeignObject` over every `CompositePrimaryKey` member, M2M, reverse relations and a `GenericForeignKey` keep the raw `<relation>` predicate.

**What is owner-dependent.** `related_target_for` resolves the relation on the owner's model, but the target type itself comes from `registry.get(target_model)` (primary-first), so it does not vary between two owners of the same model. The genuinely owner-dependent axes are the own-PK GlobalID identity (`_is_own_pk_under_relay_owner` reads the owner's `origin`) and the visibility hook a `RelatedFilter` branch is scoped through (`_target_type_for_related_filter` reads the child filterset's bound owner).

**Multi-owner reuse — strict.** Only the first binding is stored, so a second owner may bind the same `FilterSet` only when nothing the shared filterset reads at query time would differ. The rule for second-owner binding (applied at finalizer phase-2.5 subpass 1 per [Decision 6](#decision-6--finalizer-phase-25-binding-seam--materialize-before-schema-ordering)):

- The owner's model must BE the filterset's `Meta.model` or derive from it (checked on every binding).
- Both owners must agree on own-PK Relay identity: both non-Relay, or both Relay with the same `graphql_type_name`.
- Neither owner may carry a custom `get_queryset` (function identity is not visibility equivalence, so any custom hook fails closed).
- For every declared `RelatedFilter`, both owners' `related_target_for(field_name)` must return the EXACT same `DjangoTypeDefinition` AND the same `graphql_type_name`.
- Any divergence raises [`ConfigurationError`][glossary-configurationerror] naming both owners (and, for the relation axis, the offending field and both resolved target type names). Consumers wanting per-owner surfaces declare two separate `FilterSet` subclasses (`PublicBookFilter` / `AdminBookFilter`); the input-class namespace is name-keyed, so the two generate two distinct input types per [Decision 9](#decision-9--input-class-namespace-vs-typeregistry-and-lifecycle). Re-binding the same `(filterset, definition)` pair is idempotent.

**Where the conditional runs.** The conditional runs on the `FilterSet`, NOT inside the factory: the factory only controls the Strawberry input shape, while `django-filter` instantiates the actual filter instances earlier via `filterset.BaseFilterSet.filter_for_field()` / `filter_for_lookup()`, which read `cls.FILTER_DEFAULTS`. A factory-only conditional would let the GraphQL input expose a GlobalID for `BookFilter.genres` while the runtime filter instance is whatever vanilla `django-filter` generated. The shape:

- `FilterSet.FILTER_DEFAULTS` is the dict shape `django-filter` consumes (`{django.db.models.Field: {"filter_class": ..., "extra": ...}}`), a package-authored table rather than a snapshot of `django-filter`'s process-shared global.
- `FilterSet.filter_for_field` / `FilterSet.filter_for_lookup` override the `django-filter` classmethods. For relation fields they consult `cls._owner_definition.related_target_for(field_name)` to find the related target `DjangoType` (falling back to `registry.get(target_model)` while `_owner_definition` is `None`, before phase-2.5 binding), then check `implements_relay_node(target_type)` (the predicate [`finalize_django_types`][finalizer]'s phase 2.5 uses for Relay-Node injection) to pick the GlobalID branch vs the raw-key branch.
- The chosen primitive lands in the FilterSet's `declared_filters` / `base_filters` through the standard `django-filter` machinery; `get_filters()` (Layer 4) expands them with the cycle-safe guard.
- The factory derives the Strawberry input field type **from the resolved filter instances** via the named converter `convert_filter_to_input_annotation`, NOT from a parallel `FILTER_DEFAULTS` lookup.

**`convert_filter_to_input_annotation(filter_instance, model_field, owner_definition, filterset_cls)` contract.** Standard `django-filter` filters do not expose an `input_type` attribute; they expose Django form fields through `filter_instance.field`. The converter walks `inputs.py`'s `_FILTER_INPUT_KIND_TYPES` (most-specific first, shared with `normalize_input_value` so the two cannot disagree):

| `filter_instance` shape | Strawberry input annotation |
| --- | --- |
| `GlobalIDMultipleChoiceFilter` / `GlobalIDFilter` | `list[str]` / `str` (the GlobalID wire form); runtime accepts `str` and `relay.GlobalID` objects |
| `RelationPkMultipleFilter` / `RelationPkFilter` | `list[<key scalar>]` / `<key scalar>`, typed from the target's key column |
| consumer `ModelMultipleChoiceFilter` / `ModelChoiceFilter` | the identity scalar of the column its form field cleans (a list for the multiple form) |
| `BaseCSVFilter` family (`in` / `range` declared through `Meta.fields`, including `IntegerInFilter` / `IntegerRangeFilter`) | `list[<element>]` |
| `RangeFilter` (declared) | a Strawberry input dataclass `{start: T \| None, end: T \| None}`; runtime emits the two **positional** form-data keys `<field>_0` (start) and `<field>_1` (end), because `django_filters.RangeFilter.field` is a `RangeField` whose `RangeWidget.value_from_datadict` reads `name_0` / `name_1` |
| `ListFilter` / `ArrayFilter` | `list[<element>]` |
| `ChoiceFilter` / `TypedChoiceFilter` | the Strawberry enum the [Choice enum generation][glossary-choice-enum-generation] pipeline builds from the model field's choices (shared with the `DjangoType` reading the same column); runtime normalizes the member back to the DB value. A choice filter not backed by a Django `Choices` model field raises [`ConfigurationError`][glossary-configurationerror] |
| anything else (scalar `*Filter`, `isnull`, custom `Filter(method=...)`) | the scalar from the model field (`str`, `int`, `bool`, `decimal.Decimal`, `datetime.date`, `datetime.datetime`, `datetime.time`, `uuid.UUID`, `BigInt`); `bool` for `isnull`; a `method=` filter with no model field is typed from its form field, and one that exposes no form field raises [`ConfigurationError`][glossary-configurationerror] |
| not `required=True` | the chosen annotation wrapped in `T \| None` |

The model field is the source of truth for the element type; the form field is consulted only for a `method=` filter with no backing model field (so a CSV / list `method=` filter yields `list[str]` unless it is backed by a model field). `filterset_cls` qualifies a nested `RangeFilter` sub-input class name (`f"{filterset_cls.__name__}{Pascal(field_name)}RangeInputType"`) so two filtersets sharing a `field_name` cannot mint two classes under one GraphQL type name.

`normalize_input_value(filter_instance, raw_value, field_name=None)` is the runtime symmetric: it consumes the Strawberry-shaped input value and produces the form-data shape `django-filter`'s `BaseFilterSet.form.is_valid()` expects. `field_name` is the form-data key the caller resolved for this branch and supplies the `<field>` prefix in the multi-key shape below; its one call site, `sets.py::FilterSet._normalize_input`, passes the form key the lookup table holds for the lookup. It returns one of **three** shapes:

- a **scalar**, when the filter consumes a single form-data key — an Enum member normalizes to `enum.value`; a `relay.GlobalID` object normalizes to its base64 **wire string**, re-encoded rather than pre-decoded to a bare `node_id`, so the bound `GlobalIDFilter` can validate the `type_name` before any decode;
- a **`list`**, for `GlobalIDMultipleChoiceFilter` / `RelationPkMultipleFilter` / `ListFilter` / `ArrayFilter`, and for the `BaseCSVFilter` family `django-filter` generates from a `Meta.fields` `in` / `range` lookup. The `BaseCSVFilter` entry precedes the `RangeFilter` entry in `_FILTER_INPUT_KIND_TYPES`, so a `range` lookup declared through `Meta.fields` takes this **list** shape while a filter declared as `RangeFilter` takes the **dict** shape below — one lookup name, two normalized shapes, decided by how the filter was declared;
- a **`dict` patch the caller merges into the form-data dict**, when the filter consumes more than one positional form-data key — the range dataclass normalizes to `{<field>_0, <field>_1}`, `<field>` being the `field_name` argument. `None`-valued axes are omitted, so a start-only range yields `{<field>_0}`, an end-only range `{<field>_1}`, and an all-`None` range `{}`.

**Strawberry-specific `GlobalIDFilter`.** The ported `GlobalIDFilter` / `GlobalIDMultipleChoiceFilter` are NOT verbatim copies of `graphene_django/filter/filters/global_id_filter.py` — the graphene primitive parses a raw string and discards the decoded `type_name`, so a `GenreType` filter accepting `relay.GlobalID(type_name="LoanType", node_id="42")` would silently filter `Book.genres__id=42`. The Strawberry adaptation:

- Accepts both raw `str` and `strawberry.relay.GlobalID` objects: a `relay.GlobalID` short-circuits the parse; a string goes through `relay.GlobalID.from_id(value)`.
- Validates the decoded `type_name` against the accepted set for the target definition — the relation target (`owner_definition.related_target_for(field_name)`) or the owner itself for its own PK — which is strategy-aware per [`docs/SPECS/spec-031-globalid_encoding-0_0_9.md`][spec-031] Decision 13. A mismatch raises `GraphQLError("GlobalID type mismatch: filter expects <expected> but received <actual>")` before any queryset clause runs. A target on an encode-only (`callable` / `custom`) strategy is rejected at finalize ([Decision 6](#decision-6--finalizer-phase-25-binding-seam--materialize-before-schema-ordering) subpass 2.5), with a coded `GLOBALID_UNVALIDATABLE` reject as the runtime backstop for hand-built filtersets.
- The form field cleans the wire string; the filter's `filter()` decodes it and applies the predicate with the decoded `node_id`.
- `GlobalIDMultipleChoiceFilter` validates every element of the list independently; a single wrong-type element rejects the whole input with the offending index named in the error.
- Rejects an input that does not decode to a usable identifier with the coded error `GraphQLError(..., extensions={"code": "GLOBALID_INVALID"})` — the uniform coded error the node-refetch path also emits (`relay.py::_decode_or_graphql_error`). Two well-formedness rejections share this code: (a) a **malformed wire string** (unparseable base64 / not a `type_name:node_id` payload), surfaced instead of leaking Strawberry's raw `GlobalIDValueError`; and (b) a **well-formed GlobalID whose decoded `node_id` is empty** (e.g. `to_base64("BookNode", "")`). Accepting an empty decoded id would silently widen a restrictive predicate (a scalar no-op, or a dropped list element turning `{in: ["type:"]}` into an unfiltered query). Both rejections apply to the scalar and the multiple filter; for the multiple filter the offending list index is named (the `index=` argument threaded through `django_strawberry_framework/filters/base.py::_decode_and_validate_global_id`). Only a `None` value (omission) and an explicit `[]` (match-none, `GlobalIDMultipleChoiceFilter`) remain non-error paths. This is a general GlobalID input contract, independent of the [row-preserving to-many predicate machinery][part1-plan] that shares the same decode boundary. The empty-decoded-`node_id` rejection is pinned live in [`examples/fakeshop/test_query/test_library_api.py`][fakeshop-test-library] by `test_library_genres_filter_empty_id_scalar_global_id_raises_globalid_invalid`, `test_library_genres_filter_empty_id_in_list_raises_globalid_invalid_at_index_0`, and `test_library_genres_filter_mixed_empty_id_in_list_rejects_whole_input_at_index_1`.

**Why this matters.** A blanket "FK/PK → `GlobalIDFilter`" mapping (mirroring `graphene-django`'s unconditional shape) would break non-Relay filters: a consumer filtering `Book.shelf` by ID against a non-Relay `ShelfType` would have to pass a GlobalID-encoded string even though the exposed GraphQL type uses an integer ID. `graphene-django`'s filter-connection defaults are unconditional because that path is Relay-shaped by construction; the package's default is non-Relay (`Meta.interfaces = (relay.Node,)` is opt-in), so the conditional shape matches the GraphQL surface the consumer sees.

**Name-collision note:** `graphene_django/filter/utils.py::get_filterset_class` and `django_graphene_filters/filterset_factories.py::get_filterset_class` are different upstream functions with the same name — the cookbook's is a `BaseFilterSet`-aware get-or-create helper, graphene-django's an explicit-vs-dynamic dispatcher pinned to connection-field declaration. The package ships neither: every filtered surface reads an explicit `Meta.filterset_class`.

Rationale companion — this Decision's justification and its two rejected alternatives: [Decision 4][rationale-d4].

### Decision 5 — `django-filter` as the foundation

The package's `FilterSet` **subclasses `django_filters.filterset.BaseFilterSet`** and `django-filter` is a **hard dependency** at [`pyproject.toml #"django-filter>=25.2"`][pyproject]. The cookbook's `AdvancedFilterSet` is built on `django_filters.filterset.BaseFilterSet` and reuses its load-bearing machinery (`declared_filters`, `base_filters`, `.filters`, `.form`, `.qs`, `get_filters()`, `Filter.method`, form cleaning, lookup generation); porting it without that inheritance would mean re-implementing all of those layers.

Pinned import shape (`django_filters.BaseFilterSet` does NOT exist at the top-level import path; the class lives at `django_filters.filterset.BaseFilterSet`):

```python
from django_filters import filterset

class FilterSetMetaclass(filterset.FilterSetMetaclass):
    ...

class FilterSet(..., filterset.BaseFilterSet, metaclass=FilterSetMetaclass):
    ...
```

An implementer who reaches for `from django_filters import BaseFilterSet` gets an `ImportError` at module import — the cookbook's `from django_filters import filterset` + `filterset.BaseFilterSet` shape is the one that resolves. `FilterSet`'s other bases are the shared set-family mixins (`ClassBasedTypeNameMixin`, `ActiveInputPermissionMixin`).

Consumer migration shape: a consumer who has `class MyFilter(django_filters.FilterSet)` writes `class MyFilter(FilterSet)` and inherits the package's `RelatedFilter` / lazy-resolution surface. The dependency is hard, so no `ImportWarning` branch exists on the filter path.

Rationale companion — this Decision's justification and its three rejected alternatives: [Decision 5][rationale-d5].

### Decision 6 — Finalizer phase-2.5 binding seam + materialize-before-`Schema` ordering

The filter subsystem's lazy-resolution pipeline runs inside [`django_strawberry_framework/types/finalizer.py::finalize_django_types`][finalizer]'s phase 2.5, after `apply_interfaces` / `install_relay_node_resolvers` and before phase 3's `strawberry.type` decoration. [`types/finalizer.py::_bind_filtersets`][finalizer] and the order side's `_bind_ordersets` both configure one shared driver, `_bind_sidecar_sets`, through a `_SidecarBindingSpec`, so the subpass order is single-sited across the two families.

**Ordered subpasses.** A single per-`DjangoType` loop that binds an owner and then calls `get_filters()` is order-dependent: if `BookFilter.get_filters()` expands `RelatedFilter("GenreFilter")` before the loop reaches `GenreType`, `GenreFilter._owner_definition` is still unset and owner-aware work in that expansion falls back to the registry. The pass therefore separates owner binding from expansion, and each subpass completes across ALL wired `DjangoType`s (definitions not yet finalized) before the next begins:

**Subpass 1 — Collect and bind every owner.** For every `definition` whose `definition.filterset_class is not None`:

1. Check the owner's model: `definition.model` must BE the filterset's `Meta.model` or derive from it, otherwise [`ConfigurationError`][glossary-configurationerror] names the owner type, owner model, filterset and filterset model.
2. **Bind the owner.** Set `filterset_class._owner_definition = definition`. If `filterset_class._owner_definition` is already set to a different definition, apply the strict multi-owner check from [Decision 4](#decision-4--upstream-primitives-parity-floor) (own-PK Relay identity, custom `get_queryset`, declared `RelatedFilter` targets); a mismatch raises [`ConfigurationError`][glossary-configurationerror] naming both owners. The owner slot keeps the FIRST binding; re-binding the same pair is idempotent.

No `get_filters()` call happens in subpass 1.

**Subpass 2 — Expand every filterset.** For every filterset bound in subpass 1, call `filterset_cls.get_filters()` to trigger Layer-4 expansion. With every reachable `_owner_definition` bound, `filter_for_field` / `filter_for_lookup` consult the owner-scoped lookup regardless of expansion order. An `ImportError` from an unresolved lazy target rewraps as [`ConfigurationError`][glossary-configurationerror] naming the filterset (the `ImportError` on `__cause__`); any other non-`ConfigurationError` exception rewraps the same way with `repr(exc)` in the message.

**Subpass 2.5 — Filter-only audits.** [`types/finalizer.py::_audit_filterset_subpass_2_5`][finalizer] runs two audits over the wired filtersets, in this order:

1. **Registered-`RelatedFilter`-target audit** (`_audit_unregistered_related_filter_targets`). Every reachable `RelatedFilter` target must resolve to a registered `DjangoType`. A related branch's visibility scoping runs the target type's `get_queryset` (step 3 of [Decision 8](#decision-8--relation-permission-cascade--get_queryset-cooperation)), so an unregistered target makes the branch unfulfillable even though its input field would be materialized. The walk is transitive with a visited set — cyclic cross-references (`BookFilter` <-> `ShelfFilter`) are legal — and raises [`ConfigurationError`][glossary-configurationerror] naming the filterset and the field. The runtime sibling of this error lives in `FilterSet._branch_visibility_seed`, the one resolution an active nested branch and every flat leaf walking the branch share.
2. **Encode-only-GlobalID-target rejection** (`_audit_globalid_filter_strategies`). Every `GlobalIDFilter` / `GlobalIDMultipleChoiceFilter` on a bound filterset resolves the target definition it validates against — the owner itself for the own-PK branch, the relation target otherwise — through the same resolver the runtime path uses. When that target's effective GlobalID strategy is `callable` or `custom`, the strategy is **encode-only**: there is no decode path, so a typed filter input could never validly consume the IDs the target emits, and the audit raises [`ConfigurationError`][glossary-configurationerror] naming the filterset and the field.

The related-target audit runs first: an unregistered relation target makes the relation head unresolvable, so ordering it first keeps the GlobalID audit operating on a validated relation graph. Both are filter-family audits with no order-family twin.

**Subpass 3 — Orphan helper-reference validation.** Compare `_helper_referenced_filtersets` (every `FilterSet` passed to `FilterInput[...]` / `filter_input_type(...)` per [Decision 11](#decision-11--filter_input_typefilterset-consumer-helper)) against the filtersets bound in subpass 1. One orphan raises [`ConfigurationError`][glossary-configurationerror] with the message `"FilterSet '<Name>' is referenced via FilterInput[...] / filter_input_type(...) but never assigned to a DjangoType via Meta.filterset_class. Add 'filterset_class = <Name>' to the relevant DjangoType's Meta."`; several orphans are reported in one message, sorted by qualified class name.

**Subpass 4 — Materialize input classes.** For every wired filterset, read `FilterArgumentsFactory(filterset_cls).arguments` to trigger the Layer-5 BFS, then call `materialize_input_class(name, cls)` for every class in the factory's `input_object_types` ledger, which sets the class as a module global of [`django_strawberry_framework.filters.inputs`][filters] and records `name → input class` in `_materialized_names` (per [Decision 9](#decision-9--input-class-namespace-vs-typeregistry-and-lifecycle)). `.arguments` is read for its side effect: it returns the **root** filterset's own input class ([`utils/inputs.py::GeneratedInputArgumentsFactory.arguments`][utils-inputs]), while the loop iterates the whole ledger, so every class built for a reachable `RelatedFilter` target is materialized too — and a sibling root's factory sees those builds through the class-level cache.

**Subpass 3 runs BEFORE subpass 4, and that order is load-bearing.** Orphan validation can only fail; materialization writes module globals and ledger rows. Validating first means an orphan failure leaves no partial state in `_materialized_names` or the factory's built-class ledger, so a re-run after fixing the orphan does not meet stale entries.

By phase 3, every referenced filter input class is a module global of `django_strawberry_framework.filters.inputs`, so by `strawberry.Schema(...)` time every `filter:` annotation on a root resolver resolves through `LazyType.resolve_type`.

Materialization MUST land before `strawberry.Schema(...)` runs. Injecting a `filter:` argument into an already-decorated `@strawberry.field` resolver is not a real path: Strawberry collects field arguments at `@strawberry.type` decoration time, before `finalize_django_types()` runs. The ordering is: resolvers annotate `filter:` with the helper (a string forward reference) at module-load time → `@strawberry.type` collects the lazy annotation → `finalize_django_types()` materializes the input class → `strawberry.Schema(query=Query, ...)` resolves the lazy reference → schema build succeeds. [`docs/README.md`][docs-readme]'s schema setup section pins `finalize_django_types()` before `strawberry.Schema(...)`.

Rationale companion — this Decision's justification and its four rejected alternatives: [Decision 6][rationale-d6].

### Decision 8 — Relation-permission cascade + `get_queryset` cooperation

A `FilterSet`'s `check_<field>_permission(request)` gates compose with the target type's [`get_queryset`][glossary-get_queryset-visibility-hook] hook and with `FilterSet._apply_related_constraints` (which applies the explicit `queryset=` parameter on a related filter — a **scope boundary** that nested filters, and flat filters walking the branch, can narrow but cannot escape; it is not a visibility gate, because it constrains parent rows only while a predicate through the branch is active, so hiding rows is the job of `get_queryset`). The composition flows through the resolver-facing classmethods `FilterSet.apply_sync(input_value, queryset, info)` and `FilterSet.apply_async(input_value, queryset, info)`. Resolvers pick the variant matching their own sync/async shape. `FilterSet.apply(...)` is a thin dispatcher that runs `apply_sync` and translates the typed [`SyncMisuseError`][querysets] — raised when a target's `get_queryset` turns out to be async-only — into a `RuntimeError` that tells the consumer to use `apply_async`.

**`GraphQLError` import path.** Every `GraphQLError` raised in this Decision and in [Decision 11](#decision-11--filter_input_typefilterset-consumer-helper) is `from graphql import GraphQLError` (the class Strawberry's response builder honors for the `extensions` payload), NOT `strawberry.exceptions.StrawberryGraphQLError`.

**Internal decomposition.** `apply_sync` / `apply_async` decompose into named helpers so each seam is testable:

- `_derive_related_visibility_querysets_sync(input_value, info, *, parent_db=None)` / `_derive_related_visibility_querysets_async(...)` — for every ACTIVE `RelatedFilter` branch, derive the target type's visibility-scoped queryset through [`django_strawberry_framework/utils/querysets.py::apply_type_visibility_sync`][querysets] / [`::apply_type_visibility_async`][querysets], the package-wide visibility-hook dispatch. The parent queryset's database alias is threaded through so each child hook sees the parent's shard.
- `_derive_flat_hop_visibility_async(input_value, info, into, *, parent_db)` — the flat-leaf twin of the async derivation: for every SUPPLIED flat leaf of one input level (read through `filters/inputs.py::filter_lookup_table`, the one input-leaf to filter mapping), awaits the target visibility of every hop the leaf walks into the request-wide hop map `into`: a declared hop keyed by `(id(<RelatedFilter declaration>), <database alias>)`, an undeclared hop and each intermediate model of a multi-relation declaration (`FilterSet._branch_via_types`, for the leaf's hops and for every active nested branch of the level) keyed by `(<scoping DjangoType>, <database alias>)` (`FilterSet._await_scoped_rows`).
- `_normalize_input(input_value) -> dict` — Strawberry input dataclass → `django-filter` form-data dict; reads each lookup's form key from `filters/inputs.py::filter_lookup_table` and converts each value through `normalize_input_value(filter_instance, raw_value, field_name)` per [Decision 4](#decision-4--upstream-primitives-parity-floor).
- `_branch_visibility_seed(field_name, related_filter, parent_db)` — the one resolution of a declared branch's target type (`FilterSet._target_type_for_related_filter`), child filterset and unscoped base rows (`utils/querysets.py::base_queryset(child_model, using=parent_db)`), shared by the nested branch (`_iter_visibility_steps`) and every flat leaf walking the branch (`_hop_visible_rows`); a target that does not resolve raises [`ConfigurationError`][glossary-configurationerror] naming the branch as "active in the filter input (nested, or walked by a flat leaf)".
- `_apply_related_constraints(input_value, parent_qs, child_qs_by_branch) -> QuerySet` — applies explicit `RelatedFilter(queryset=...)` constraints under active-branch scoping, intersected with the visibility-scoped child querysets, through `filters/sets.py::_restrict_through_branch`: `filters/sets.py::_admitted_rows` intersects the branch's child rows with its explicit `queryset=`, and `filters/sets.py::_restrict_to_related` keeps the parents reaching one of them through `optimizer/predicates.py::related_rows_exist`, the one correlated `EXISTS` every declared branch restricts through (a flat leaf walking the branch reaches the same two helpers through `filters/sets.py::FilterSet._reaches_hop`). **This helper runs BEFORE the FilterSet is instantiated** so the constrained queryset becomes the instance's stored `self.queryset` and propagates to `.qs`; `django-filter`'s `.qs` reads `self.queryset`, not any local the caller might mutate afterwards.
- `_run_permission_checks(input_value, request)` — runs the per-field `check_<field>_permission(request)` gates ONLY for fields present in the input; recurses through active `RelatedFilter` branches and the `and` / `or` / `not` arms into child filtersets.
- `_validate_form_or_raise(filterset)` — explicit `filterset.form.is_valid()` plus the `GraphQLError` raise.

`_apply_common_prelude` (normalize, request, constraints) and `_apply_common_finalize` (build, permission pass, form validation, lazy `.qs`) are the two halves both colors share.

**The pipeline**, as both `apply_sync` and `apply_async` run it (they differ only in the sync vs async dispatch of step 3 and in `apply_async` running step 7 onward in one worker thread):

1. **The consumer resolver calls `<OwnerType>.get_queryset(queryset, info)` first** on the consumer-shaped root queryset — visibility scoping happens BEFORE any filter clause runs: `queryset = BranchType.get_queryset(models.Branch.objects.order_by("id"), info)` THEN `queryset = BranchFilter.apply_sync(filter, queryset, info)` (or `await BranchFilter.apply_async(...)` from an async resolver). Skipping the `get_queryset` call lets the filter clause see through the visibility gate to hidden rows.
2. The consumer resolver then calls `FilterSet.apply_sync(input_value, queryset, info)` or `await FilterSet.apply_async(input_value, queryset, info)`.
3. **Nested `RelatedFilter` visibility scoping.** For each ACTIVE `RelatedFilter` branch (its key is present in the input), the pipeline derives the child visibility queryset by calling the **target type's `get_queryset(child_model._default_manager.all(), info)`**, where the target type is the child filterset's bound owner (`FilterSet._target_type_for_related_filter`; `registry.get(child_model)` when unbound). It runs first, before normalization, so the recursion-depth cap is checked at the earliest point. The child visibility queryset is what the parent's related constraint uses as its right-hand side, so a nested filter cannot use a hidden related row to make the parent match: without this step, `{ branches(filter: { shelves: { code: { exact: "secret-code" } } }) { id } }` would match `Branch` rows owning a `Shelf` that `ShelfType.get_queryset` hides. **A flat leaf walking a declared branch is scoped the same way.** A flat leaf whose ORM `field_name` walks one or more declared `RelatedFilter` hops (`FilterSet._flat_leaf_walk`), into a target column or onto the last hop's own key, answers as Django's ORM answers the same lookup in a world where every row a hop's target type hides, and every row a hop's explicit `queryset=` excludes, does not exist. A positive lookup keeps a parent with a visible chain whose terminal matches, which is its nested twin's answer: `shelvesCode` as `shelves: { code }`, `bookShelfTopic` as `book: { shelf: { topic } }`. The hops are `utils/permissions.py::walk_declared_relation_path`'s, the one reading of which declared branches a flat path walks, which the flat-path permission gates fire along too: each hop is the declaration whose `field_name` matches the next path segments (the longest multi-segment match wins), and the declared walk stops at the first segment no declaration claims or after a hop whose target does not resolve. The filter reads the walk with `undeclared=True`: past the last declared hop every further relation segment is an undeclared hop (`utils/permissions.py::RelationHop` with no declaration), whose rows answer for `utils/querysets.py::relation_target_type` of its model (the type the walking set is bound to when the path re-enters that set's model, `registry.get` otherwise) and are scoped by that type's `get_queryset` when it declares one of its own (`RelationHop.scope`); the undeclared hops are `utils/relations.py::leading_relation_hops`'s, `classify_path`'s hops over the longest leading part of the rest of the path, so each reaches the model Django's join reaches (a `pk` segment on a model keyed by a one-to-one or a parent link is that relation), and the unconsumed segments are evaluated on the deepest target. A `RelatedFilter` whose `field_name` is not a path of relations (a column such as `title__shelf`, a missing name, a `GenericForeignKey`) raises [`ConfigurationError`][glossary-configurationerror] when its filter set's expansion builds (`filters/sets.py::_require_relation_path`, reading the parent model only, so a lazily resolved target is never looked up). So `altShelves` (`BranchFilter` declares no branch over `alt_shelves`), `branchAltShelves` / `branch: { altShelves }` on shelves and `itemsName` on categories answer over the shelves, and items, their types let the viewer see. A leaf none of whose hops is declared or scoped (every relation reaches an unregistered model or a type keeping the identity hook) is not walked: it compiles as Django's raw relation, routed where it qualifies. An undeclared hop has no branch gate: the gates stay `relation_path_gates`'s, the last declared target's gate covering the whole remainder. At every hop the target type's `get_queryset` over `base_queryset(<target model>, using=<parent alias>)` (`FilterSet._hop_visible_rows`; an unscoped undeclared hop reads every row through the model's `_base_manager`, as Django's join does) and a declared hop's explicit `queryset=` apply, and a declared hop whose `field_name` spans several relations (`CardFilter.milestone` over `target_version__milestone`) passes only through the visible rows of each intermediate model (`FilterSet._via_rows`, the `via` rows of `related_rows_exist`), nested and flat alike; the leaf runs over the last hop's visible rows as a copy with `field_name` rebased onto the target model and the target filter set as its `parent` (for an undeclared last hop, `filters/sets.py::_UndeclaredHopSet`, which carries the hop's model, the target type's definition a `GlobalID` value validates against, and the request), and each hop folds outward through `FilterSet._reaches_hop` (the hop's `_admitted_rows`, then `optimizer/predicates.py::related_rows_exist`) onto the previous hop's visible rows, then onto the parent (`FilterSet._apply_active_leaf`): one correlated `EXISTS` per hop, built from the visible rows, never re-reading the parent table or embedding another leaf's restriction, with no framework `DISTINCT`. An `isnull=True` lookup also keeps a parent with no visible related row at some hop (Django's `LEFT JOIN` null extension over the visible rows: a `NULL` key, an absent row and a hidden row alike), where the nested twin stays existential (`shelf: { topic: { isNull: true } }` needs a visible shelf with no topic); `isnull=False` stays positive. A declared `exclude=True` filter keeps the parents its positive twin (the same filter with `exclude` off) does not keep, negated at the outermost parent, as a `not:` arm around the positive twin does, including through an expansion or a projection (`GenreFilter.without_book_titled`, projected as `genresWithoutBookTitled` on books and `bookGenresWithoutBookTitled` on loans, matches a book with no visible genre); the negation is `NOT EXISTS`, which a `NULL` link column cannot empty the way it empties a `NOT IN`. A consumer `method=` filter stays positive whatever its flags. Flat and nested twins therefore agree on every lookup except `isnull=True` and `exclude=True`. A relation-key leaf (nothing after the last declared relation: a `Meta.fields` key over a relation a renamed declaration claims, such as `shelves` beside `visible_shelves = RelatedFilter(ShelfFilter, field_name="shelves")`, or a declared model-choice filter over a declared relation, such as `ShelfFilter.home_branch` over `branch`) walks that last hop too: `isnull` tests whether a visible target row exists, a primary-key, `GlobalID` or model-choice value naming a hidden row matches nothing, a forward key keeps comparing the stored key and also requires it to reach a visible row (a book on a hidden shelf reads as having no shelf), and a to-many key compares the visible target rows' own key column (`filters/sets.py::FilterSet._leaf_chain`). Coverage is decided by path, not by how the leaf was generated: an expanded copy of a child filter, an owner-bound `ProjectedChildFilter` (its child filter runs over the hop's visible rows inside the child filter set), and a plain `Meta.fields` traversal under a declared root (`LoanFilter`'s `book__loans__patron__email` walks `book`, `loans` and `patron`) all count. A relation-key leaf over an undeclared relation reads the same way (`altShelves: { exact: [<pk of a secret shelf>] }` matches nothing, like a pk no row carries). Two leaf shapes are not walked: a leaf whose relations no declaration claims and no type scopes (above), and a consumer `method=` filter declared on the parent, whose Python receives the parent queryset and owns its own scoping ([`GOAL.md`][goal] "Trust boundary"). A leaf that returns its input BY IDENTITY over rows no visibility touched (django-filter's empty-value skip; `FilterSet._leaf_applies`) is inactive: it constrains nothing and runs no `get_queryset`. Hop visibility is one request-wide map, `FilterSet._flat_hop_visibility`, keyed by `(id(<RelatedFilter declaration>), <database alias>)` for a declared hop and by `(<scoping DjangoType>, <database alias>)` for an undeclared hop or intermediate model (`FilterSet._scoped_rows`), created by `apply_sync` / `apply_async` before the related constraints read it and shared with every logical-arm sibling and projection child instance, so a hop's `get_queryset` runs once per request however many leaves and arms walk it. An active hop whose target has no registered `DjangoType`, or whose target filter set does not resolve, raises the nested branch's [`ConfigurationError`][glossary-configurationerror] (`_branch_visibility_seed`).
4. The pipeline normalizes the Strawberry input dataclass into the form-data dict (walking nested `RelatedFilter` input objects, mapping `and_` / `or_` / `not_` back to the logical-operator keys, mapping per-lookup Python attrs through `LOOKUP_NAME_MAP`, converting values through `normalize_input_value`) and resolves the Django request through `_request_from_info(info)` ([`utils/permissions.py::request_from_info`][utils-permissions]: `info.context.request`, a bare `HttpRequest` context, a mapping context whose `"request"` is an `HttpRequest`, or Strawberry's Channels context; any other shape raises [`ConfigurationError`][glossary-configurationerror]).
4a. **Apply related constraints to the queryset BEFORE constructing the FilterSet instance.** `_apply_related_constraints(input_value, queryset, child_qs_by_branch)` runs `filters/sets.py::_restrict_through_branch` once per active branch: it AND-intersects the branch's explicit `RelatedFilter(queryset=...)` constraint with its visibility-scoped child queryset, then keeps the parent rows reaching a row of the intersected queryset through one correlated `EXISTS` built from those rows (`optimizer/predicates.py::related_rows_exist`, correlated on the relation's own link columns). `django_filters.filterset.BaseFilterSet.qs` derives from the instance's *stored* `self.queryset`, so constraining BEFORE construction is what carries the constraints through to `.qs`. The pipeline then instantiates `cls(data=normalized_data, queryset=constrained_queryset, request=request)`.
5. The pipeline calls `cls._run_permission_checks(input_value, request)` — denial gates raise `GraphQLError(...)` before any filter clause touches the queryset. The per-field gate runs **only for fields present in the input** (active-input-only), NOT for every declared field. This diverges from the cookbook's `AdvancedFilterSet.check_permissions(request)`, which walks every declared filter: permissions gate USE of the filter, not its declaration. The check recurses through `RelatedFilter`s into child filtersets' gates for active branches only, each gate firing at most once per class. A nested child filterset's own `apply_*` (run during step 3's derivation) passes `run_permissions=False`, so nested gates fire once, from this top-level pass.
6. **The pipeline explicitly calls `filterset.form.is_valid()`** and raises `GraphQLError("Invalid filter input", extensions={"code": "FILTER_INVALID", "errors": <serialized filterset.errors>})` when validation fails. `django_filters.filterset.BaseFilterSet.qs` only consults `self.errors` and falls through to `filter_queryset` regardless, so without the explicit raise invalid input would degrade into a partially-filtered or unfiltered queryset. The `extensions.errors` payload is `filterset.errors.get_json_data()`, giving `{<field_name>: [{"message": <str>, "code": <str>}, ...], ...}`.
7. **Active-branch related-queryset scoping — applied in step 4a.** The constraint applies ONLY when the related branch is present in the input; an empty `filter: {}` or `filter: { name: { iContains: "..." } }` (no `shelves` branch) leaves the parent queryset unconstrained; `filter: { shelves: { code: { iContains: "..." } } }` activates it, and an active flat leaf walking the branch (`shelvesCode`) applies it inside step 8. The cookbook's `_apply_related_queryset_constraints` applies all declared constraints unconditionally; the package narrows that to active branches so an empty filter never pre-excludes parent rows.
8. The instance's `.qs` property runs `filter_queryset(queryset)` (the tree-form override: flat leaves, then the `and` / `or` / `not` composition) and the pipeline returns `filterset.qs` to the resolver. A flat leaf walking a declared hop (step 3) applies its branch restriction inside this read (`_apply_flat_leaves` → `_apply_relation_leaf`), deriving each hop's visibility on first use on the sync path, and is never routed through the correlated `EXISTS` adapter: routing ([`FilterSet`][glossary-filterset] "Row-preserving to-many predicates") covers only framework-generated leaves the step-3 scoping does not walk. A walking leaf is row-preserving too, since each hop it walks is a correlated `EXISTS`.
9. The optimizer ([`DjangoOptimizerExtension`][glossary-djangooptimizerextension]) walks the selection tree on the post-filter queryset; [Queryset diffing][glossary-queryset-diffing] cooperates with any consumer `select_related` / `prefetch_related` work already present.

<a id="sync-async-api-split"></a>**Sync / async API split.** A single `FilterSet.apply(input_value, queryset, info)` cannot serve step 3: a target `DjangoType.get_queryset(...)` can be async-only (returns a coroutine), and a sync resolver cannot synchronously await it. The shape (matching `apply_type_visibility_sync` / `apply_type_visibility_async` in [`utils/querysets.py`][querysets]):

- `FilterSet.apply_sync(input_value, queryset, info) -> QuerySet` — the sync-resolver entry point. Dispatches step 3 through [`apply_type_visibility_sync`][querysets], as does a flat leaf's first-use hop derivation inside the step-8 `.qs` read; if a target's `get_queryset` returns a coroutine, it raises [`SyncMisuseError`][querysets] — a typed marker subclassing BOTH [`ConfigurationError`][glossary-configurationerror] and `RuntimeError`, so a consumer catching either still matches.
- `async def FilterSet.apply_async(input_value, queryset, info) -> QuerySet` — the async-resolver entry point. Dispatches step 3 through `_derive_related_visibility_querysets_async` (and `_collect_nested_visibility_querysets_async` for the `and` / `or` / `not` arms), awaiting the target's `get_queryset` regardless of shape. It also awaits, through `_derive_flat_hop_visibility_async`, every declared hop a supplied flat leaf walks, at the top level and in every `and` / `or` / `not` arm (`_collect_nested_visibility_querysets_async(..., flat_hop_visibility=...)`), into the request-wide hop map the sync `.qs` read then finds pre-filled, so an async-only `get_queryset` never runs inside the sync boundary. The pre-pass runs before any form exists: a supplied value the filter then skips (an empty string) costs one awaited `get_queryset` and constrains nothing, as a present-but-empty nested branch does; an unsupplied leaf costs nothing. It then runs `filters/sets.py::FilterSet._apply_common_finalize` — the filterset build, the permission pass, form validation and the lazy `.qs` read — in ONE `utils/querysets.py::run_in_one_sync_boundary` worker, so a consumer's filterset constructor, `check_<field>_permission` hook, custom `method=` filter body or leaf-clause ORM evaluation never blocks the event loop.
- `FilterSet.apply(input_value, queryset, info)` — a thin dispatcher that calls `apply_sync(...)` inside `try / except SyncMisuseError as exc:` and re-raises `RuntimeError("FilterSet.apply called against async get_queryset; use apply_async instead.") from exc`. The dispatch is **class-based, never a substring match**; the message carries no interpolated target type because `from exc` already puts the original [`SyncMisuseError`][querysets] on `__cause__`. Any other `RuntimeError` or `ConfigurationError` propagates unchanged. **Partial side-effect semantics:** for a nested branch the `SyncMisuseError` fires inside step 3, before normalization, request resolution, the related constraints, filterset construction, the permission pass, or form validation; for a hop a flat leaf walks it fires at the step-8 `.qs` read, after the permission pass and form validation. Either way `apply_sync` mutates no module globals or input-class namespace, and any visibility querysets derived before the misuse are pure reads, discarded when the error propagates.

Consumer pattern: sync resolvers call `BranchType.get_queryset(qs, info)` and `BranchFilter.apply_sync(filter, qs, info)`. Async resolvers `await` the same hook through [`apply_type_visibility_async`][querysets] (a `DjangoType.get_queryset` may be declared `async def`; there is no separate `aget_queryset` name) and then `await BranchFilter.apply_async(filter, qs, info)`. Every fakeshop library type uses a sync `get_queryset`, so the hand-written library resolvers call `apply_sync`; the async color is pinned live by `examples/fakeshop/test_query/test_library_api.py::test_genres_connection_filter_applies_async` on `/graphql-async/`, and an async-only `get_queryset` target is exercised in [`tests/filters/test_sets.py`][test-filters] (see [Test plan](#test-plan)).

<a id="related-queryset-boundary-scope"></a>**`_apply_related_constraints` scope.** The cookbook ancestor (`AdvancedFilterSet._apply_related_queryset_constraints`) filters the parent queryset by the related constraint; it does NOT filter the nested relation resolver's output. A `Branch` with one shelf inside the constraint AND one outside passes the parent filter and still surfaces BOTH shelves through `BranchType.shelves`. The contract is: "branches without any matching constrained shelf are excluded from the parent result; nested filter clauses, and flat leaves walking the branch (`shelvesTopic`), cannot use shelves outside the constraint to make a branch match." It is **not** "shelves outside the constraint never appear in the response." Output-shape scoping at the nested-relation level is out of scope. The active-branch refinement further narrows the contract: the constraint applies ONLY when a predicate through the branch is active, nested or flat.

Composition: [`apply_cascade_permissions`][glossary-apply_cascade_permissions] runs inside step 1 (the `get_queryset` hook); [Per-field permission hooks][glossary-per-field-permission-hooks], when they ship, slot into the field-resolver layer that runs after step 8.

### Decision 9 — Input-class namespace vs `TypeRegistry` and lifecycle

**The input-class namespace is the [`django_strawberry_framework.filters.inputs`][filters] module's own global namespace**, separate from the model-to-`DjangoType` registry at [`django_strawberry_framework.registry.registry`][registry] (which powers [`Meta.primary`][glossary-metaprimary]).

Every generated filter input class is a real module global of `django_strawberry_framework.filters.inputs`, set at finalize time. The class names are stable and class-derived (`f"{FilterSet.__name__}InputType"` → `"GalaxyFilterInputType"`). The "registry" IS the module's `__dict__` — there is no separate private dict registry, because Strawberry's `LazyType.resolve_type` reads `module.__dict__` directly and cannot traverse a sidecar dict. A lifecycle ledger (`django_strawberry_framework.filters.inputs._materialized_names`, a private `dict[str, type]`) maps `class_name → input_class` — each value the materialized Strawberry input class — so re-materialization is idempotent and clears cleanly. Source-class collision detection (two filtersets claiming one name before materialization) is the factory's separate `_type_filterset_registry`.

The two namespaces (model-to-`DjangoType` registry and input-class module globals) are disjoint by key type (Django model class vs string class name).

Lifecycle contract:

- **Registration is idempotent for the same `(name, input_class)` pair.** Calling `materialize_input_class("GalaxyFilterInputType", input_a)` twice with the same `input_a` is a no-op: the check is `is` identity against the class the ledger already holds under that name.
- **Registration raises [`ConfigurationError`][glossary-configurationerror] when the same name is claimed by a DIFFERENT input class**, with both input classes' qualified names in the message and rename advice naming the filterset. Because each name derives from the owning `FilterSet`'s `__name__`, this catches two same-named `FilterSet`s in different modules.
- **`registry.clear()` resets the filter input lifecycle ledger and every piece of generated-build state hanging off it.** `clear_filter_input_namespace()` is the family wrapper over the shared heavy clear at [`utils/inputs.py::clear_generated_input_namespace`][utils-inputs]: it empties `_materialized_names` and `_field_specs`, clears the `FilterArgumentsFactory` class-level caches (`input_object_types` plus the `_type_filterset_registry` collision map), and drops every `FilterSet` subclass's phase-2.5 binding state — `_owner_definition`, `_expanded_filters`, `_is_expanding_filters`, and the candidate-metadata snapshot published alongside the expansion cache, read off the family's lifecycle descriptor at `django_strawberry_framework/sets_mixins.py::SetLifecycleAttrs.binding_attrs`. Each attribute is dropped only where the subclass set it directly, so an inherited default is restored rather than masked. Both submodule lookups the clear needs are best-effort: an unimportable `filters.factories` or `filters.sets` skips only its own dependent reset.
- **Materialized class objects stay parked in the `django_strawberry_framework.filters.inputs` module `__dict__`; no clear path strips them.** `materialize_input_class` overwrites the module global on the next finalize, and it is the ledger reset that drives the rebuild. Stripping a global with `delattr` would break any `strawberry.lazy(...)` LazyType held by a consumer module whose reload fixture did not also reload the holder; leaving the class parked lets that LazyType keep resolving until the next finalize replaces it.
- **Import-cycle-safe integration via subsystem registration.** [`django_strawberry_framework/registry.py`][registry] is a low-level module imported by `types/`, `optimizer/`, and the package's `__init__.py`, so it imports nothing from the filter subsystem. The owning module announces its own teardown at import time, and `TypeRegistry.clear()` replays whatever announced itself:

  ```python
  # django_strawberry_framework/filters/__init__.py
  register_subsystem_clear(_clear_helper_referenced_filtersets, owner="filters.helper_references")

  # django_strawberry_framework/filters/inputs.py
  register_subsystem_clear(
      clear_filter_input_namespace,
      owner="filters.input_namespace",
      before_bind=True,
  )

  # django_strawberry_framework/registry.py
  class TypeRegistry:
      def clear(self) -> None:
          ...  # the registry's own state
          for clear in iter_subsystem_clears():
              clear()
  ```

  **Laziness is preserved**: only an imported owner can register, so a consumer who never imports `filters` has nothing to clear and no `except ImportError` branch exists. **A rename cannot rot silently**: registration resolves the function object at the owner's import. **`owner` is a stable logical identity, not an import path**, so `importlib.reload` replaces the old callback instead of accumulating duplicates. `before_bind=True` marks the input-namespace reset as generated state the finalizer re-runs before rebuilding generated types; the helper-reference ledger is a full-clear-only callback. `tests/filters/test_finalizer.py::test_registry_clear_works_without_filters_imported` pins that `registry.clear()` runs cleanly with no filter callback registered.
- **Partial-finalize recovery.** If `finalize_django_types()` raises mid-phase-2.5 (e.g., an unresolved `RelatedFilter`), the ledger and the module globals keep whatever was materialized before the raise; a subsequent `finalize_django_types()` re-runs the binding pass, and the idempotent `(name, input_class)` check lets already-materialized classes pass through.
- **Public `clear_filter_input_namespace()` helper.** Exposed from `django_strawberry_framework.filters.inputs` so tests can clear the filter namespace WITHOUT clearing the full `TypeRegistry`; `registry.clear()` reaches it through its registered row.

### Decision 11 — `filter_input_type(FilterSet)` consumer helper

The package ships a public helper at [`django_strawberry_framework.filters.filter_input_type`][filters], in two spellings that evaluate to one annotation: the call `filter_input_type(MyFilter)` and the type-checkable generic `FilterInput[MyFilter]`:

```python
# django_strawberry_framework/filters/__init__.py (shape; the module is authoritative)
def _filter_input_annotation(filterset_class: object, *, helper_spelling: str) -> object:
    return build_lazy_input_annotation(
        filterset_class,
        expected_base=FilterSet,
        helper_spelling=helper_spelling,
        expected_label="a FilterSet",
        ledger=_helper_referenced_filtersets,
        input_type_name_for=_input_type_name_for,
        module_path=INPUTS_MODULE_PATH,
    )


def filter_input_type(filterset_class: type[FilterSet]) -> object:
    return _filter_input_annotation(filterset_class, helper_spelling="filter_input_type()")


class FilterInput(Generic[_FilterSetT]):  # _FilterSetT is bound to FilterSet
    def __class_getitem__(cls, filterset_class: object) -> object:
        return _filter_input_annotation(filterset_class, helper_spelling="FilterInput[...]")
```

Both spellings return `Annotated["<Name>FilterInputType", strawberry.lazy("django_strawberry_framework.filters.inputs")]`. The body is single-sited with the order twin at `django_strawberry_framework/utils/inputs.py::build_lazy_input_annotation`: it validates eagerly (a non-`FilterSet` raises `TypeError` worded with the spelling the consumer wrote, `filter_input_type() requires a FilterSet subclass; got ...` or `FilterInput[...] requires ...`), records the class in `_helper_referenced_filtersets` for the finalize-time orphan check, and passes the runtime-computed name as the first `Annotated[...]` argument so it is wrapped as a `typing.ForwardRef` — the form Strawberry's `LazyType.resolve_type` resolves against `module.__dict__` at schema build (pinned by `test_filter_input_type_returns_forwardref_in_annotation_args`). A call is not a valid type expression, so a type checker rejects `filter_input_type(MyFilter)` in an annotation and accepts `FilterInput[MyFilter]`, rejecting `FilterInput[NotAFilterSet]` statically through the `FilterSet` bound. `FilterInput` is never instantiated: the resolver receives the generated Strawberry input object, an opaque handle whose one use is `MyFilter.apply_sync(filter, queryset, info)` / `apply_async`.

Consumers use it as a normal Python type annotation in a resolver signature:

```python
@strawberry.field
def all_galaxies(
    self,
    info: strawberry.Info,
    filter: FilterInput[GalaxyFilter] | None = None,
) -> list[GalaxyType]:
    ...
```

The annotation evaluates **when Strawberry evaluates it during schema declaration / collection**; the exact moment depends on the consumer's import style:

- **With normal annotations** it evaluates at module-load time; the `Annotated[...]` shape is stored on the resolver's `__annotations__`.
- **With `from __future__ import annotations`** (PEP 563), Python stores the annotation as a string and Strawberry evaluates it in the resolver's `__globals__` at type-collection time. Two implications: (a) `GalaxyFilter` MUST be importable from the resolver module's globals at type-processing time; (b) Strawberry may evaluate the annotation more than once, so **the helper is safe to call repeatedly with the same `FilterSet`** — the ledger is a `set`, and each call returns an equivalent `Annotated[...]`.

Either way, the `"GalaxyFilterInputType"` forward reference stays unresolved until `strawberry.Schema(...)` time, by which point `finalize_django_types()` has materialized the class per [Decision 6](#decision-6--finalizer-phase-25-binding-seam--materialize-before-schema-ordering).

**Orphan `FilterSet` validation.** A `FilterSet` referenced via the helper but never wired via `Meta.filterset_class = MyFilter` on any `DjangoType` would not be materialized, and `LazyType.resolve_type` would fail for `MyFilterInputType` at `strawberry.Schema(...)` time. The package fails loud at finalize:

- The helper records every `FilterSet` it is called with into the module-level `_helper_referenced_filtersets: set[type[FilterSet]]` in [`django_strawberry_framework.filters`][filters].
- Finalizer phase 2.5 subpass 3 compares the helper-referenced set against the wired filtersets and raises [`ConfigurationError`][glossary-configurationerror] for the orphans with the message quoted under [Decision 6](#decision-6--finalizer-phase-25-binding-seam--materialize-before-schema-ordering) (it names both helper spellings, since the ledger does not record which one the consumer wrote).
- `registry.clear()` replays the `filters.helper_references` teardown callback, so the orphan check is consistent across test-fixture reloads.
- `test_orphan_filter_input_type_reference_raises_at_finalize` pins this.

Rationale companion — this Decision's justification and its four rejected alternatives: [Decision 11][rationale-d11].

### Decision 12 — Live HTTP coverage strategy

Package coverage is earned through fakeshop live `/graphql/` HTTP flows wherever a real query reaches the line, per [`AGENTS.md`][agents] #"any line reachable via a real GraphQL query against fakeshop".

Live HTTP tests land in [`examples/fakeshop/test_query/test_library_api.py`][fakeshop-test-library] and cover: scalar-field filter clauses, choice-enum filter clauses, forward-FK filter clauses, reverse-FK filter clauses, M2M filter clauses, logical-and / logical-or / logical-not combinations, optimizer cooperation (`assertNumQueries(N)` against a filtered queryset with nested selection), the explicit `queryset=` **scope boundary** (the live tests pin that nested and flat predicates through the branch answer only from the rows it admits; it scopes the parent filter, not the nested resolver's output), and flat relation leaves answering like their nested twins under the target types' `get_queryset`, `isNull: true` and `exclude=True` answering over the visible rows.

Package-internal tests land in `tests/filters/`: an `__init__.py` shell, a `fixtures/` sub-package for the cross-module `RelatedFilter` fixtures, four modules mirroring the four `filters/` source modules (`test_base.py`, `test_sets.py`, `test_factories.py`, `test_inputs.py`), and `test_finalizer.py` for the phase-2.5 binding pass, which lives in [`types/finalizer.py`][finalizer]. They cover what a live query cannot easily reach: the Layer-4 re-entry guard, `LazyRelatedClassMixin.resolve_lazy_class` failure paths, `FILTER_DEFAULTS` Relay-vs-scalar branch selection, the `LOOKUP_PREFIXES` map for `construct_search`, error surfaces, and cache behavior.

## Edge cases and constraints

- **Same-module `RelatedFilter` references** (e.g., `GalaxyFilter` and `CelestialBodyFilter` in one `filters.py` with `RelatedFilter("CelestialBodyFilter")` and `RelatedFilter(GalaxyFilter)`). Layer 2 handles this: the absolute-path lookup fails and the `bound_class.__module__` retry succeeds.
- **Cross-module `RelatedFilter` references via absolute path** (e.g., `RelatedFilter("apps.products.filters.CategoryFilter")`). The absolute-path lookup succeeds; the retry is never reached.
- **Circular `RelatedFilter` cycles** (`A → B → A`, or a self-reference). The Layer-4 `_is_expanding_filters` re-entry guard returns the unexpanded filters on re-entry, so expansion terminates without raising and without caching a half-built result; the cache writes only when no string `_filterset` remains. The apply-time recursion over related and logical branches is capped at `FilterSet._MAX_LOGIC_DEPTH` with a typed [`ConfigurationError`][glossary-configurationerror].
- **`Meta.fields = "__all__"`** (the top-level shorthand). Expands to the scalar and forward-relation columns plus the primary key under the conditional `FILTER_DEFAULTS` per [Decision 4](#decision-4--upstream-primitives-parity-floor), and **excludes** M2M; relations become nested branches only through an explicit `RelatedFilter(...)`. `FilterSet.get_fields` carries the two deltas against `django_filters.utils.get_all_model_fields` (PK added, M2M removed) per [Decision 3](#decision-3--six-layer-lazy-resolution-pipeline); tests pin both. A dict-form per-field `"__all__"` (`{"name": "__all__"}`) expands to that field's concrete lookups, restricted to `exact` / `in` / `isnull` for a Relay owner's own PK.
- **`Meta.fields = {"galaxy__name": ["exact"]}`** (the double-underscore lookup-path shorthand). **Renders as a flat field named `galaxyName` with a nested lookup input** (`filter: { galaxyName: { exact: "..." } }`) — NOT as `filter: { galaxy: { name: { exact: "..." } } }`. `_build_input_fields` groups entries by their top-level GraphQL field name, so the consumer sees a flat surface that does not collide with an explicit `RelatedFilter(GalaxyFilter)` on the same filterset. Beside a declared `galaxy = RelatedFilter(...)` the path walks that branch, so `galaxyName` answers as `galaxy: { name }` does, inside the target type's `get_queryset` and the branch's explicit `queryset=` ([Decision 8](#decision-8--relation-permission-cascade--get_queryset-cooperation) step 3); with no declared root it is a plain traversal of the parent model. Consumers wanting the nested surface declare `RelatedFilter(GalaxyFilter)` — or set `HIDE_FLAT_FILTERS` (per [Decision 3](#decision-3--six-layer-lazy-resolution-pipeline)) to drop the flat rendering of relation-traversing paths schema-wide while keeping the nested branch.
- **`Meta.fields = {"created": ["date", "year", "year__gt"]}`** (transform lookups). Single-segment transforms (`date`, `year`, ...) are lookups in the field's operator bag via `LOOKUP_NAME_MAP`. A multi-segment chain (`year__gt`) is not nested: the grouping renders it as its own flat field named from the full path (`createdYearGt`) with its own bag. The cookbook's recursive `filterset_to_trees` / `try_add_sequence` / `sequence_to_tree` tree-form, which would nest such chains, is not ported.
- **`Meta.filterset_class = AdminGalaxyFilter` on a secondary `Meta.primary = False` `DjangoType`**. The secondary type is registered and reverse-discoverable; the filter binding runs on its definition exactly as on the primary's. The input-type namespace is name-keyed, so two `DjangoType`s on one model with different `filterset_class`es generate two distinct input types.
- **`Meta.filterset_class` on a `DjangoType` that also declares `Meta.interfaces = (relay.Node,)`**. The filter binding runs at phase 2.5 after the Relay-Node injection; the owner's own PK becomes a GlobalID filter typed to the owner.
- **Filter on a field that is NOT in the `DjangoType`'s `Meta.fields`** (e.g., the type exposes `name` but the filterset declares `description`). The filter clause still applies; the consumer can filter on columns they cannot select. This matches the cookbook and is intentional.
- **Filter that raises a Django ORM error at queryset-translation time** (e.g., a JSON-field lookup the backend does not support). The Django `FieldError` / `NotImplementedError` propagates as a `GraphQLError`; the framework does not pre-validate the backend's supported lookups.
- **`construct_search` lookup-prefix handling**. `construct_search` maps a `^` / `=` / `@` / `$`-prefixed filter name to `istartswith` / `iexact` / `search` (PostgreSQL full-text only) / `iregex`, the map ported verbatim from `django_graphene_filters`; no consumer surface reads it until [`Meta.search_fields`][glossary-metasearch_fields] ships.
- **`Meta.fields` with no lookups** (e.g., `{"name": []}`). `django-filter` generates no filter for the field, so the generated input has no `name` entry; no error is raised.
- **Filter input position empty** (`filter: {}`). The pipeline applies no clause and returns the queryset unfiltered. The optimizer's [Queryset diffing][glossary-queryset-diffing] cooperation is unaffected.
- **Async resolver returning a filtered queryset**. Strawberry's async path awaits the resolver; the queryset's filter clauses apply normally.
- **`Meta.fields` referencing a model property (not a field)**. Rejected by `django-filter` at `FilterSet` class creation (`TypeError("'Meta.fields' must not contain non-model field names: ...")`). Filtering on a property requires a custom `Filter` declaration with an explicit `method=`.
- **Filter against a queryset that's already been `.values(...)`-projected**. Filters apply; the projection persists. The framework does not pre-validate.
- **Two `<TypeName>FilterInputType`s of the same string name**. Rejected by the per-module namespace's name-uniqueness check (per [Decision 9](#decision-9--input-class-namespace-vs-typeregistry-and-lifecycle)): the same `(name, input_class)` pair is idempotent; the same name claimed by a different input class raises [`ConfigurationError`][glossary-configurationerror] naming both and the filterset to rename.
- **`RangeFilter` sub-input class names across two filtersets that share a `field_name`** (e.g., two filtersets each declaring a `RangeFilter` on `lifetime_fines_cents`). The nested range class is named per owning filterset (`f"{filterset_cls.__name__}{PascalCase(field_name)}RangeInputType"`) and cached on the filter instance by owning filterset, Django field path and inner scalar. These nested classes are embedded in the annotation, not materialized through [Decision 9](#decision-9--input-class-namespace-vs-typeregistry-and-lifecycle)'s ledger, and Strawberry would silently keep the first of two same-named classes, which is why the name is owner-qualified.
- **Python keywords `and` / `or` / `not` in dataclass field positions**. Strawberry input types are dataclass-backed and cannot carry fields named `and`, `or`, or `not`. The package uses `and_`, `or_`, `not_` and pins the GraphQL names via `strawberry.field(name="and")` / `name="or"` / `name="not"`.
- **A head both declared and generated** (`name = CharFilter(lookup_expr="iexact")` beside `Meta.fields = {"name": ["icontains"]}`). One `name` operator bag carries both lookups; each binds its own form key (`iExact` → `name`, `iContains` → `name__icontains`), so supplying both ANDs two predicates. A declared head over another column (`name = CharFilter(field_name="city")`) keeps its lookup on the declared filter the same way.
- **Two filters on one `(head, lookup)` slot** (a declared `name = CharFilter(field_name="description", lookup_expr="icontains")` beside the generated `name__icontains`). One would be unreachable from the generated input, so `filter_lookup_table` raises [`ConfigurationError`][glossary-configurationerror] naming the filter set, both form keys, the lookup and the head, at input build or at the first hand-built mapping. Two `__` heads that flatten to one input attr (`a__b_c`, `a_b__c`) raise the same way; a head spelled exactly like another head's flattened attr keeps that attr.
- **Flat expansions of a child's declared filters.** `BookFilter`'s `shelf = RelatedFilter(ShelfFilter)` exposes `ShelfFilter.home_branch` (`ModelChoiceFilter(field_name="branch")`) flat as `shelfHomeBranch`, bound to the expanded copy `shelf__home_branch`, so the copy's own queryset validates the value (a pk outside it answers "Select a valid choice") exactly as the nested `shelf: { homeBranch: ... }` form does. An expanded declared child named like a lookup (`name__exact`) is its own head beside the generated `name`.
- **Flat expansions of owner-bound child filters.** `LoanFilter`'s `patron = RelatedFilter(PatronFilter)` exposes `PatronFilter.email_must_have_at_sign` (`CharFilter(field_name="email", method=...)`, its validator appended in `PatronFilter.__init__`) flat as `patronEmailMustHaveAtSign`. A `method=` resolves on the owning filter set and a child `__init__` runs only for the child's instances, so the copy is a `filters/sets.py::ProjectedChildFilter` ([Decision 3](#decision-3--six-layer-lazy-resolution-pipeline) Layer 4): it validates with the field a `PatronFilter` instance builds (a value without `@` answers `missing_at_sign` under `patron__email_must_have_at_sign`), runs the method inside that instance over the `Patron` rows `PatronType.get_queryset` lets the request see, and keeps the loans whose `patron` is among them. The same holds for every flat leaf of a child that overrides `__init__`, and for a projected copy expanded again at the next hop. An `exclude=True` child filter projects as the complement of its positive twin, negated at the outermost parent (a parent with no visible child row matches it); a `method=` child filter stays positive whatever its `exclude` flag.
- **Flat leaves walking declared branches** ([Decision 8](#decision-8--relation-permission-cascade--get_queryset-cooperation) step 3). Anonymous `allLibraryBooks(filter: { shelfTopic: { exact: "secret" } })` returns the same nothing `shelf: { topic: { exact: "secret" } }` returns, because `ShelfType.get_queryset` hides the `secret` shelf from both; `shelvesTopic` on `allLibraryBranches` answers only from the shelves `BranchFilter.shelves`'s explicit `queryset=` admits, for staff too. A walked leaf answers over the visible rows as Django answers the flat path, so two lookups part from the existential nested twin: `bookShelfTopic: { isNull: true }` on loans also matches a loan whose book, or whose book's shelf, is hidden, absent or unset, while `book: { shelf: { topic: { isNull: true } } }` needs a visible shelf with no topic; and the declared `exclude=True` `GenreFilter.without_book_titled` (`withoutBookTitled`) matches what `not: { books: { title: ... } }` matches, as do its expansions `genresWithoutBookTitled` on books (a book with no visible genre matches) and `bookGenresWithoutBookTitled` on loans, never "has a visible related row the exclusion keeps". A leaf on the key of a declared hop's rows reads only the visible ones: an item whose every entry `EntryType.get_queryset` hides answers `entriesId: { isNull: true }` like an item with no entries, an entry whose property `EntryFilter.property`'s explicit `queryset=` excludes answers `propertyId: { isNull: true }`, and a key naming a hidden row matches nothing. A relation no `RelatedFilter` declares reads its target type the same way: anonymous `allLibraryBranches(filter: { altShelves: { exact: [<pk of a secret shelf>] } })` returns nothing, as for a pk no row carries, and `allCategories(filter: { itemsName: ... })` never matches through a private item; staff, who see those rows, match them.
- **A field or lookup the lookup table does not hold** in a hand-built mapping (`{"nope": ...}`, `{"name": {"gt": ...}}` on a head without `gt`, or a bare value on a head with several lookups and no `exact`) raises [`ConfigurationError`][glossary-configurationerror] instead of being written as a form key `django-filter` ignores. A bare value is shorthand for the head's `exact` lookup, or for its only lookup. A wire input cannot reach these: the generated input types it.
- **Lookup names + Python keyword `in`.** Strawberry's auto-camel-case only fires on underscored identifiers, so per [Decision 3](#decision-3--six-layer-lazy-resolution-pipeline)'s `LOOKUP_NAME_MAP` the package generates `i_contains` as the Python attr AND pins `iContains` as the GraphQL name. Same shape for every initial-`i` case (`iExact`, `iStartsWith`, `iEndsWith`, `iRegex`), for `isNull`, and for `in` (Python attr `in_`, GraphQL name `in`). The normalizer writes an `in_` value under the `in` filter's own form key when building the form-data dict.
- **Multi-`DjangoType`-per-model filterset binding.** When a model is exposed by several `DjangoType`s (per [`Meta.primary`][glossary-metaprimary]) and one `FilterSet` is wired onto two of them, the strict multi-owner check of [Decision 4](#decision-4--upstream-primitives-parity-floor) runs at phase-2.5 subpass 1: a divergence on own-PK Relay identity, a custom `get_queryset` on either owner, or a diverging declared `RelatedFilter` target raises [`ConfigurationError`][glossary-configurationerror] naming both owners. Consumers wanting separate surfaces declare two `FilterSet` subclasses (`PublicBookFilter` / `AdminBookFilter`).
- **Partial-finalize recovery for the input-class namespace.** If `finalize_django_types()` raises mid-phase-2.5, already-materialized classes stay in the module's `__dict__` and the ledger keeps them; a subsequent `finalize_django_types()` resumes, and the idempotent `(name, input_class)` check lets them pass through.
- **Fakeshop schema-reload pattern with already-materialized filter inputs.** `registry.clear()` resets both the model-to-`DjangoType` registry AND the filter-input lifecycle state in one call; the reload then re-runs `finalize_django_types()`, which re-materializes the input classes and overwrites the parked module globals in place. No stale ledger entry, field spec, factory cache entry, or binding attribute survives into the next run.
- **Forward relation whose link targets non-pk columns** (`PatronProfile.favorite_genre`, a `ForeignKey(to_field="name")`; a `ForeignObject` off the target pk). The generated identity filter compiles against `<relation>__pk`, because the stored column is not the primary key a GlobalID or raw-pk value carries; a `RelatedFilter` expansion of the leaf keeps the qualification ([Decision 4](#decision-4--upstream-primitives-parity-floor)).
- **Helper validation**. `filter_input_type` / `FilterInput[...]` validate eagerly (`TypeError` for a non-`FilterSet`) even though the returned annotation is lazy, so misuse fails at the resolver-declaration site.

## Risks and open questions

- **Layer 5's forward-reference shape against Strawberry releases.** The idiom is `Annotated["{Name}FilterInputType", strawberry.lazy("django_strawberry_framework.filters.inputs")]` resolved via `LazyType.resolve_type` reading `module.__dict__`. The package's `strawberry-graphql` floor in [`pyproject.toml`][pyproject] supports it, and every schema the suite builds resolves these references (each generated input carries the self-referential `and` / `or` / `not` fields), so a Strawberry regression fails CI. If Strawberry ever drops the module-globals path, the namespace design is revisited.
- **`Annotated["NotYetMaterialized", strawberry.lazy(...)]` resolution timing.** The materialize-before-`Schema` ordering ([Decision 6](#decision-6--finalizer-phase-25-binding-seam--materialize-before-schema-ordering)) depends on consumers calling `finalize_django_types()` BEFORE `strawberry.Schema(...)`, the order [`docs/README.md`][docs-readme] pins. A consumer who constructs the schema first gets a `LazyType.resolve_type` failure naming the missing class, which surfaces the ordering bug at schema build.
- **Input-type namespace under per-`Meta.primary` secondary `DjangoType`s.** The namespace is name-keyed, so two `DjangoType`s on one model with two `filterset_class`es generate two distinct input types. No aliasing key exists for two filtersets that should share one input type.
- **`Meta.filterset_class` accepting a plain `django_filters.FilterSet`.** The validator rejects it; consumers migrate by parent-class swap ([`GOAL.md #"migrates with a one-line parent-class swap"`][goal-migration-shape]). No adapter for un-reparented `django-filter` classes exists.
- **Filter applied to a relation that has a custom `get_queryset`.** Step 3 of [Decision 8](#decision-8--relation-permission-cascade--get_queryset-cooperation) derives the child visibility queryset from the target type's `get_queryset` for every ACTIVE `RelatedFilter` branch BEFORE the parent's related constraint runs, so a nested filter cannot match a parent through a hidden child, and neither can a flat leaf walking the same declared branch. The optimizer's `Prefetch` downgrade ([Queryset diffing][glossary-queryset-diffing]) covers OUTPUT planning, which runs after the parent queryset is WHERE-filtered; it does not scope parent-row filtering.
- **Logical-and / logical-or input shape.** The cookbook's flat shape (`filter: { and: [...] }`) ports verbatim; `and` / `or` / `not` sit on every `<TypeName>FilterInputType` (including nested `RelatedFilter` branch inputs) but never inside a per-field lookup bag.
- **`Meta.fields = "__all__"` performance AND schema-size growth.** The BFS runs once at finalize and is cached, so per-request cost is unaffected. The produced input type's SDL grows with `field_count × lookup_count`; wide models inflate introspection responses and client codegen. The workaround is an explicit `Meta.fields` dict with narrower lookup sets.
- **`Meta.search_fields` planned** while `LOOKUP_PREFIXES` / `construct_search` already ship in `filters/inputs.py`, so the planned card consumes them without retrofit; no consumer surface reads them today.
- **Glossary entry parity.** `LazyRelatedClassMixin`, `FilterArgumentsFactory`, `FILTER_DEFAULTS`, and `LOOKUP_PREFIXES` are internal symbols not in [`docs/GLOSSARY.md`][glossary]; they are documented here and in module docstrings. A future card that surfaces one publicly lands its glossary entry.

[`docs/SPECS/spec-027-filters-0_0_8.md`][spec-027] (this document) is at the canonical structured filename per [Decision 1](#decision-1--spec-filename-and-canonical-naming), with companion [`docs/SPECS/appx/spec-027-filters-0_0_8-terms.csv`][spec-027-terms] anchoring every project-specific term to its [`docs/GLOSSARY.md`][glossary] heading; [`uv run python scripts/check_spec_glossary.py --spec docs/SPECS/spec-027-filters-0_0_8.md`][check-spec-glossary] passes.
2. [`django_strawberry_framework/filters/`][filters] is a subpackage with `__init__.py`, `base.py`, `sets.py`, `factories.py`, `inputs.py` per [Decision 2](#decision-2--subpackage-layout-and-public-export-surface); `__init__.py` re-exports `FilterSet`, `RelatedFilter`, `FilterInput`, `filter_input_type` and the primitives; the top-level package's `__all__` does not carry them.
3. `base.py` ships the parity-floor primitives per [Decision 4](#decision-4--upstream-primitives-parity-floor): `TypedFilter`, `ArrayFilter`, `ArrayFilterMethod`, `RangeFilter`, `RangeField`, `validate_range`, `ListFilter`, `ListFilterMethod`, `GlobalIDFilter`, `GlobalIDMultipleChoiceFilter`, the raw-key pair `RelationPkFilter` / `RelationPkMultipleFilter`, and `RelatedFilter`. `Filter` (`django_filters.Filter` itself) and `LazyRelatedClassMixin` (from [`django_strawberry_framework/sets_mixins.py`][sets-mixins]) are re-exports.
4. `sets.py` ships `FilterSetMetaclass` and `FilterSet` per Layers 3 + 4 of [Decision 3](#decision-3--six-layer-lazy-resolution-pipeline). `FilterSet` subclasses `django_filters.filterset.BaseFilterSet` per [Decision 5](#decision-5--django-filter-as-the-foundation) and carries: (a) the `FILTER_DEFAULTS` class attribute + `filter_for_field` / `filter_for_lookup` overrides applying the Relay-vs-scalar conditional per [Decision 4](#decision-4--upstream-primitives-parity-floor), so runtime filter instances and Strawberry input shape stay aligned, and marking a forward relation whose link targets non-pk columns to compile against `<relation>__pk`; (b) the `_owner_definition: DjangoTypeDefinition | None` slot bound at finalizer phase 2.5; (c) **the resolver-facing classmethod pair `apply_sync(input_value, queryset, info) -> QuerySet` and `async def apply_async(input_value, queryset, info) -> QuerySet`** running the [Decision 8](#decision-8--relation-permission-cascade--get_queryset-cooperation) pipeline (related visibility derivation, nested and per flat-leaf hop, normalization through the `filter_lookup_table` form keys, request resolution, active-branch related constraints applied before construction, active-input-only permission pass, explicit `form.is_valid()` raising `GraphQLError("Invalid filter input", extensions={"code": "FILTER_INVALID", "errors": filterset.errors.get_json_data()})`, and `filterset.qs`); (c.1) the thin `apply(...)` dispatcher that runs `apply_sync(...)` inside `try / except SyncMisuseError` and re-raises a `RuntimeError` naming `apply_async`; (c.2) the named helpers (`_normalize_input`, `_derive_related_visibility_querysets_sync` / `_async`, `_run_permission_checks` — inherited from [`sets_mixins.py::ActiveInputPermissionMixin`][sets-mixins] — `_validate_form_or_raise`, `_apply_related_constraints`, `_branch_visibility_seed`, `_derive_flat_hop_visibility_async`); (d) `filter_queryset(self, queryset)` — the `django-filter` instance-method override for tree-form logic, distinct from `apply_sync` / `apply_async`; (e) the `get_fields` override pinning the `Meta.fields = "__all__"` deltas (PK included, M2M excluded) and the per-field `"__all__"` expansion; (f) `Meta.model`, `Meta.fields`, `get_filters`, `check_permissions` on top of the upstream `declared_filters` / `base_filters` / `.filters` / `.form` / `.qs` / `Filter.method` machinery.
5. `factories.py` ships `FilterArgumentsFactory` (Layer 5 BFS on the shared `GeneratedInputArgumentsFactory`, deriving input field types from the resolved filter instances through `convert_filter_to_input_annotation`, NOT from a parallel `FILTER_DEFAULTS` lookup); it builds but does not materialize. Logical-operator fields use `list[Annotated["Name", strawberry.lazy(...)]] | None` for `and_` / `or_` and `Annotated["Name", strawberry.lazy(...)] | None` for `not_`.
6. `inputs.py` IS the input-class namespace per [Decision 9](#decision-9--input-class-namespace-vs-typeregistry-and-lifecycle): filter input classes are materialized as real module globals of `django_strawberry_framework.filters.inputs` via `materialize_input_class(name, cls)` (idempotent for `(name, input_class)` pairs by `is` identity; [`ConfigurationError`][glossary-configurationerror] on a name claimed by a different input class). The module ships `materialize_input_class`, `clear_filter_input_namespace`, `_materialized_names`, `_build_logic_fields`, `_build_input_fields`, `construct_search`, `LOOKUP_PREFIXES`, `LOOKUP_NAME_MAP`, `filter_lookup_table` (the per-class `FilterLookupTable` holding each operator-bag lookup's form key, read by `_build_input_fields` and `FilterSet._normalize_input`; a second filter on one `(head, lookup)` slot raises [`ConfigurationError`][glossary-configurationerror]), `convert_filter_to_input_annotation`, and `normalize_input_value(filter_instance, raw_value, field_name=None)`; `FieldSpec`, `build_input_class` and `_input_type_name_for` are aliases for the shared generated-input substrate at [`django_strawberry_framework/utils/inputs.py`][utils-inputs].
7. `filters/__init__.py` exports the helper in both spellings per [Decision 11](#decision-11--filter_input_typefilterset-consumer-helper): `FilterInput[BranchFilter]` / `filter_input_type(BranchFilter)` return `Annotated["BranchFilterInputType", strawberry.lazy("django_strawberry_framework.filters.inputs")]`, validate eagerly (`TypeError` for a non-`FilterSet`), and record the filterset into `_helper_referenced_filtersets` for the finalizer's orphan check.
8. [`django_strawberry_framework/types/definition.py::DjangoTypeDefinition`][definition] carries the `filterset_class` slot, populated from `Meta.filterset_class`, and `related_target_for(field_name)` — `(target_definition, model_field)` for relation fields, `None` otherwise — the lookup [Decision 4](#decision-4--upstream-primitives-parity-floor)'s FK/PK conditional consults.
9. [`django_strawberry_framework/types/base.py::DEFERRED_META_KEYS`][base] does not contain `"filterset_class"`; [`ALLOWED_META_KEYS`][base] does; `_validate_filterset_class` raises [`ConfigurationError`][glossary-configurationerror] for a non-`FilterSet`.
10. [`django_strawberry_framework/types/finalizer.py::finalize_django_types`][finalizer] runs the phase-2.5 filter-binding pass per [Decision 6](#decision-6--finalizer-phase-25-binding-seam--materialize-before-schema-ordering): bind every owner (model check + strict multi-owner check), expand every filterset, run `_audit_filterset_subpass_2_5`'s two audits, orphan-validate `_helper_referenced_filtersets`, and only then materialize every built input class. The filter subsystem registers `clear_filter_input_namespace` (owner `filters.input_namespace`, `before_bind=True`) and `_clear_helper_referenced_filtersets` (owner `filters.helper_references`) through `registry.py::register_subsystem_clear` at import time, and `registry.clear()` replays every registered callback.
11. `tests/filters/` carries the `__init__.py` shell, the `fixtures/` sub-package, the four source-mirroring modules (`test_base.py`, `test_sets.py`, `test_factories.py`, `test_inputs.py`), and `test_finalizer.py`, per the [Test plan](#test-plan).
12. [`tests/types/test_base.py`][test-types] and [`tests/types/test_definition_order.py`][test-types] carry the `Meta.filterset_class` promotion and cross-module tests; [`tests/types/test_definition_relations.py`][test-types] covers `DjangoTypeDefinition.related_target_for`.
13. [`examples/fakeshop/apps/library/`][fakeshop-library] ships `filters.py` (with `BranchFilter`, `ShelfFilter`, `BookFilter`, `LoanFilter`, `PatronFilter` and same-module `RelatedFilter("...")` references) AND `filters_genre.py` (`GenreFilter`, the cross-module fixture for the Layer-2 absolute-import-path branch).
14. [`examples/fakeshop/apps/library/schema.py`][fakeshop-library-schema] wires `Meta.filterset_class` on the corresponding `DjangoType` classes; root resolvers annotate `filter:` as `FilterInput[filters.<Name>Filter] | None` per [Decision 11](#decision-11--filter_input_typefilterset-consumer-helper) and call `apply_sync(filter, queryset, info)` AFTER `<OwnerType>.get_queryset(queryset, info)`.
15. [`examples/fakeshop/test_query/test_library_api.py`][fakeshop-test-library] carries the live filter contracts listed in the [Test plan](#test-plan); the Relay-vs-scalar pair pins [Decision 4](#decision-4--upstream-primitives-parity-floor)'s conditional end-to-end and the nested-visibility test and the flat-twin rows pin [Decision 8](#decision-8--relation-permission-cascade--get_queryset-cooperation)'s step 3 for both spellings.
16. [`docs/GLOSSARY.md`][glossary] carries the [`FilterSet`][glossary-filterset], [`RelatedFilter`][glossary-relatedfilter], [`Meta.filterset_class`][glossary-metafilterset_class] and [`filter_input_type`][glossary-filter_input_type] entries, under the Filtering category; the [Public exports][glossary-public-exports] section does not list them.
