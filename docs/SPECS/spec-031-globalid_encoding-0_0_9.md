## Key glossary references

Skim these [`docs/GLOSSARY.md`][glossary] entries first — they anchor the vocabulary used throughout the spec:

- [Relay Node integration][glossary-relay-node-integration] — the shipped `0.0.5` foundation this card extends: `Meta.interfaces = (relay.Node,)` declares a Relay-Node-shaped type with `id: GlobalID!` and the four injected `resolve_*` defaults wired through `cls.get_queryset`. The `GlobalID` payload is what this card re-roots from the GraphQL type name onto the Django model label.
- [`DjangoType`][glossary-djangotype] — the type whose rows emit the `GlobalID`; the net-new [`Meta.globalid_strategy`][glossary-metaglobalid_strategy] key declares the per-type encoding strategy, and the schema-wide [`RELAY_GLOBALID_STRATEGY`][glossary-relay-globalid-strategy] setting is its project-wide default. The new key is validated and stored on the definition exactly as [`Meta.connection`][glossary-metaconnection] was in [`spec-030`][spec-030].
- [`Meta.interfaces`][glossary-metainterfaces] — the key that declares `relay.Node`; [Decision 6](#decision-6--metaglobalid_strategy-is-a-net-new-allowed_meta_keys-key-stored-on-the-definition) gates `Meta.globalid_strategy` to a Relay-Node-shaped type via the canonical `_is_relay_shaped(cls, interfaces)` predicate (the same one [`Meta.connection`][glossary-metaconnection] uses), accepting both `relay.Node` in `Meta.interfaces` and direct `relay.Node` inheritance.
- [`Meta.name`][glossary-metaname] — overrides the GraphQL type name; under the `type` strategy the `GlobalID` payload's type-name slot tracks `Meta.name` (the GraphQL surface name), which is exactly the refactor-fragility the `model` default avoids ([Decision 4](#decision-4--four-strategies-model-type-typemodel-callable-and-an-unchanged-node_id-portion)).
- [`Meta.model`][glossary-metamodel] — the Django model whose `model._meta.label_lower` (`"app_label.modelname"`, e.g. `products.item`) is the `model`-strategy payload; the decode side resolves that label back to the model via Django's app registry ([Decision 8](#decision-8--decode-routes-through-djangos-app-registry-then-the-framework-registry-to-the-primary-type)).
- [`Meta.primary`][glossary-metaprimary] — the multi-`DjangoType`-per-model rule; a decoded model-label ID routes through `registry.get(model)` (the primary, or the lone registered type), unless the consumer opts into type-scoped IDs via the `type` strategy for disjoint auth / cache scopes.
- [`ConfigurationError`][glossary-configurationerror] — raised at type-creation time for an unknown / malformed `Meta.globalid_strategy` value or the key on a non-Relay-Node type, and at finalization for an unknown `RELAY_GLOBALID_STRATEGY` setting value (the card DoD: "validation reject unknown strategy names loudly with `ConfigurationError`").
- [`finalize_django_types`][glossary-finalize_django_types] — the single-threaded schema-setup synchronization point whose Phase 2.5 already injects the four Relay `resolve_*` defaults; the strategy-parameterized `resolve_typename` injection lands in the same phase ([Decision 10](#decision-10--resolve_typename-injection-via-the-__func__-identity-test-at-phase-25)).
- [Definition-order independence][glossary-definition-order-independence] — the collection-then-finalize split the `resolve_typename` injection rides on; the effective strategy is resolved once per type at finalization, so the encoding is a stable schema-build-time contract.
- [`get_queryset` visibility hook][glossary-get_queryset-visibility-hook] — the decode dispatch routes through the resolved type's `resolve_node`, which honors `get_queryset`; a decoded ID for a row the requesting user cannot see resolves to `null`, never an error (the contract [`DONE-032-0.0.9`][kanban] consumes).
- [`SyncMisuseError`][glossary-syncmisuseerror] — the typed marker the Relay-foundation `resolve_node` / `resolve_nodes` raise on the sync branch when `get_queryset` returns a coroutine; the decode helper inherits this contract unchanged.
- [`DjangoConnectionField`][glossary-djangoconnectionfield] / [`DjangoConnection`][glossary-djangoconnection] — the [`DONE-030-0.0.9`][kanban] connection surface; its `edges { node { id } }` emit `GlobalID`s through the same per-node `resolve_typename` seam this card re-roots, so the connection field picks up the model-label payload with no `connection.py` change.
- [`DjangoNodeField`][glossary-djangonodefield] — the planned root single-node lookup field; **not** this card (it lands with the [Full Relay story][kanban], [`DONE-032-0.0.9`][kanban]); cited because it is the first consumer of the [decode helper](#decision-8--decode-routes-through-djangos-app-registry-then-the-framework-registry-to-the-primary-type) this card ships.
- [`Relation handling`][glossary-relation-handling] — relation `id`-only selections; [FK-id elision][glossary-fk-id-elision] reads the FK column off the parent and stringifies it into the `node_id` slot, so the model-label re-root touches only the type-name slot, never the relation's `id` round-trip.
- [FK-id elision][glossary-fk-id-elision] — the optimizer reads a forward-FK's `id` off the parent row; its [Multi-database cooperation][glossary-multi-database-cooperation] `router.db_for_read` stub-routing is the multi-DB analogue of this card's model-label-to-model routing — both resolve a Django model from a payload without a second query.
- [Scalar field conversion][glossary-scalar-field-conversion] — the converter table that maps an auto-pk to the Relay `GlobalID` when `Meta.interfaces = (relay.Node,)` is declared; this card changes the `GlobalID`'s payload, not the converter row that selects it.
- [Schema introspection management command][glossary-schema-introspection-management-command] — `manage.py inspect_django_type` reports the interface-supplied `GlobalID!` row for a Relay-Node pk; the row label is unaffected by the payload change (the command reports the GraphQL type / nullability, not the wire payload).
- [`DjangoOptimizerExtension`][glossary-djangooptimizerextension] — the optimizer projects the Django pk as a connector column for `resolve_id`; the model-label re-root needs the same pk projection unchanged ([Current state](#current-state)).
- [`strawberry_config`][glossary-strawberry_config] — the scalar-map factory every example schema in this spec passes to `strawberry.Schema(...)` alongside the singleton-factory [`DjangoOptimizerExtension`][glossary-djangooptimizerextension].
- [Cross-subsystem invariants][glossary-cross-subsystem-invariants] — the `1.0.0` rule that example-project schemas reference only shipped features; the breaking default flip ([Decision 9](#decision-9--changing-the-default-to-model-is-a-breaking-wire-format-change-acceptable-pre-100)) is timed before that freeze so the durable identity format is settled at `1.0.0`.

Dependency and forward-composition surfaces a reader will hit:

- [`DjangoNodeField`][glossary-djangonodefield] / the [Full Relay story][kanban] (`0.0.9`, [`DONE-032-0.0.9`][kanban]) — the first consumer of the decode dispatch; root `node(id:)` / `nodes(ids:)` are out of scope here.
- [Connection-aware optimizer planning][glossary-connection-aware-optimizer-planning] (`0.0.9`, [`DONE-033-0.0.9`][kanban]) — orthogonal; the GlobalID payload does not change the connection-walker work.
- [`BigInt` scalar][glossary-bigint-scalar] — a `BigAutoField` / `BigIntegerField` pk stringifies into the `node_id` slot via `str(...)`, same as today; the payload change is on the type-name slot only.
- [`apply_cascade_permissions`][glossary-apply_cascade_permissions] (`0.0.10`) — the decode dispatch respects [`get_queryset`][glossary-get_queryset-visibility-hook] immediately and gains declared-permission integration when the permissions subsystem lands.

  - [ ] [`django_strawberry_framework/types/base.py::ALLOWED_META_KEYS`][base] grows `"globalid_strategy"` (net-new public key — NOT a [`DEFERRED_META_KEYS`][base] promotion, mirroring [`spec-030`][spec-030] [Decision 8][spec-030] and [`spec-029`][spec-029] [Decision 6][spec-029]). A `_validate_globalid_strategy` helper (called from [`_validate_meta`][base], structurally modeled on `_validate_connection`) accepts `"model"` / `"type"` / `"type+model"` or a callable; an unknown string or wrong type raises [`ConfigurationError`][glossary-configurationerror]; a callable is **validated for arity and sync-ness** via `inspect.signature` (must accept the three positional `_GLOBALID_CALLABLE_PARAMS`, `(type_cls, model, root)`) and the shared [`utils/typing.py::is_async_callable`][relay-utils-typing] guard (via `_validate_globalid_callable`; must be sync), so a wrong-arity or `async def` encoder fails at type creation rather than as a raw `TypeError` / coroutine per request, and a callable the inspection itself cannot read (a `__signature__` or `__call__` descriptor that raises) is contained into the same [`ConfigurationError`][glossary-configurationerror] rather than leaking the descriptor's exception; the key is gated to a Relay-Node-shaped type via the precomputed `relay_shaped` bool (`_is_relay_shaped(cls, interfaces)`). The valid string vocabulary and the package default are the named constants [`STRING_GLOBALID_STRATEGIES`][base] / [`DEFAULT_GLOBALID_STRATEGY`][base] in [`types/base.py`][base] — the single source the validator's typo-guard text, the precedence resolver, the encoder, and the decode-shape enforcement all read.
  - [ ] The normalized value is **stored on [`DjangoTypeDefinition`][definition]** (a new `globalid_strategy` slot, populated in [`__init_subclass__`][base] like the `connection` / `filterset_class` / `orderset_class` slots) so the Phase-2.5 injection reads the per-type opt-in from the definition, not by re-parsing `Meta`.
  - [ ] `_validated_globalid_setting()` reads the schema-wide setting through [`conf.py::relay_globalid_strategy_setting()`][conf] (a `getattr(settings, "RELAY_GLOBALID_STRATEGY", None)` helper delivering "absent → package default", NOT a bare `conf.settings.RELAY_GLOBALID_STRATEGY` access, which raises `AttributeError` on the missing key) and validates it through the **same** `_validate_globalid_strategy(None, value, relay_shaped=True, source="setting")` rule the `Meta` path uses (unknown string, wrong-arity callable, or `async def` callable → [`ConfigurationError`][glossary-configurationerror] naming `RELAY_GLOBALID_STRATEGY`), since [`conf.py`][conf] is a thin reader that does not validate domain values. The finalizer snapshots the validated result on `registry._globalid_setting_snapshot` **unconditionally before the Relay loop** (so an invalid setting raises even with zero Relay types / all-override) and passes it into `install_globalid_typename_resolver`; the slot starts at the [`registry.py::GLOBALID_SETTING_UNSET`][registry] sentinel so "not yet computed" is distinguishable from a computed `None` (the absent-setting result), which is what makes the retry comparison exact; a mid-lifecycle setting change on a finalization retry raises [`ConfigurationError`][glossary-configurationerror] naming `registry.clear()` (which resets the slot to the sentinel). The pure two-arg `_resolve_globalid_strategy(definition, globalid_setting)` then applies the precedence — `definition.globalid_strategy` (the `Meta` override) → the passed-in `globalid_setting` snapshot → the `"model"` package default — reading no setting and validating nothing.

The **finalization-scoped** setting assertions — the unconditional unknown-setting `ConfigurationError` and the mid-lifecycle-change retry rejection — need a real `finalize_django_types()` run and therefore live beside the install step in [`tests/types/test_relay_interfaces.py`][test-relay-interfaces].
- [ ] Slice 2: the encode seam — strategy-parameterized `resolve_typename` injection + the four encoders + the default flip to `model` (per [Decision 3](#decision-3--the-encode-seam-a-strategy-parameterized-resolve_typename-default) / [Decision 4](#decision-4--four-strategies-model-type-typemodel-callable-and-an-unchanged-node_id-portion) / [Decision 9](#decision-9--changing-the-default-to-model-is-a-breaking-wire-format-change-acceptable-pre-100) / [Decision 10](#decision-10--resolve_typename-injection-via-the-__func__-identity-test-at-phase-25))

## Problem statement

`django-strawberry-framework`'s `0.0.5` [Relay Node integration][glossary-relay-node-integration] gave every `Meta.interfaces = (relay.Node,)` type an `id: GlobalID!` field. The `GlobalID` is Strawberry's standard `to_base64(type_name, node_id)` payload, and the `type_name` slot is the **GraphQL type name** — Strawberry's `relay.types.Node._id` field resolver computes it via `resolve_typename(root, info)`, whose default returns `info.path.typename`. So a `CategoryType` row's `GlobalID` decodes to `CategoryType:42`.

That is the standard Relay convention both upstreams ship (`graphene-django`'s `Node.to_global_id` base64-encodes `<GraphQL type name>:<id>`; `strawberry.relay.GlobalID` encodes `to_base64(type_name, node_id)`), and GlobalID parity proper was met at `DONE-015-0.0.5`. **But the GraphQL type name is the wrong durability anchor for a Django app.** In Django, the *model* is the durable thing — `products.Item` rarely moves — while the GraphQL type name (`ItemType`, `AdminItemType`, anything [`Meta.name`][glossary-metaname] sets) is a refactor-friendly facade a schema author renames freely. Baking the GraphQL type name into durable object identity means a type rename invalidates every cached `GlobalID` a client holds: a `useRefetchableFragment`, a persisted URL, a bookmarked node, an Apollo cache entry.

This card re-roots the default `GlobalID` payload onto the Django model label (`products.item:42`), so a schema author can rename `ItemType` → `ProductType` without breaking a single durable ID. It does this **before** the [Full Relay story][kanban] ([`DONE-032-0.0.9`][kanban]) mints root `node(id:)` / `nodes(ids:)` refetch fields into the public surface — because once those ship, the encoding format is a public durability contract, and changing it afterward becomes migration work instead of a config default. The card's own "Why it matters" is exactly this: "Getting this right before `1.0.0` lets consumers rename GraphQL types without invalidating every cached GlobalID. Waiting until after Full Relay ships turns the same decision into migration work."

The change is not all-or-nothing. Some consumers genuinely want type-scoped identity (disjoint auth or cache scopes per GraphQL type, or strict standard-Relay interop), so the card ships four strategies — `model` (new default), `type` (the opt-in legacy/standard convention), `type+model` (a transitional decode mode that accepts old type-anchored IDs while emitting model-anchored ones), and `callable` (fully custom) — selectable per type via `Meta.globalid_strategy` or schema-wide via the `RELAY_GLOBALID_STRATEGY` setting, with `Meta` override → setting → default precedence.

## Current state

A true description of the repo as of this writing (the plan is written against it), verified against the locked Strawberry `0.316.0`:

- The `GlobalID` payload is type-anchored. The one shipped surface the flip is **not** transparent to is `GlobalID` **filtering**: make [`filters/base.py`][filters-base]'s `type_name` validation **strategy-aware** so an emitted model-label ID round-trips through the own-PK / [`RelatedFilter`][glossary-relatedfilter] / `GlobalIDMultipleChoiceFilter` paths instead of being rejected against the old GraphQL type name (Slice 2 co-landing with the flip, [Decision 13](#decision-13--globalid-filter-validation-is-strategy-aware); [Current state](#current-state) / [Edge cases and constraints](#edge-cases-and-constraints)).
5. Earn package coverage through a live fakeshop HTTP round-trip proving emitted IDs use the model-label payload and that `GlobalID` filtering round-trips, per [`docs/TREE.md`][tree]'s coverage-priority rule (Slice 4).
6. Keep package version state command-gated and owned by the joint `0.0.9` cut: no slice edits `pyproject.toml`, [`__version__`][package-init], [`tests/base/test_init.py::test_version`][test-base-init], or `uv.lock` (Slice 5, [Decision 12](#decision-12--version-bumps-are-owned-by-the-joint-009-cut)).

- **Public `testing/relay.py` `global_id_for(type_cls, id)` / `decode_global_id(gid)` test helpers.** Those public helpers are named in [`DONE-032-0.0.9`][kanban]'s Files-likely-touched list; this card ships the internal encode / decode and validates them through package tests, no public export ([Decision 11](#decision-11--module-location-encodedecode-in-typesrelaypy-no-public-export-in-009)).
- **First-class type-rename / model-rename GlobalID migration history** (decoding old-format IDs across a rename through a recorded alias map). That is `BACKLOG.md` item 39's "type-rename GlobalID migrations"; this card's `type+model` transitional mode is the lighter-weight bridge ([Edge cases and constraints](#edge-cases-and-constraints)).
- **Connection-aware optimizer planning** ([`DONE-033-0.0.9`][kanban]) and **the connection field** ([`DONE-030-0.0.9`][kanban], shipped) — orthogonal; the connection field picks up the model-label payload through the same per-node `resolve_typename` seam with no change.

## Borrowing posture

Per the [`START.md`][start] "do both libraries provide it? → foundational" test, the `GlobalID` *primitive* is foundational and already shipped (`DONE-015-0.0.5`). What this card adds — a model-anchored payload default, the per-type / project-wide strategy override, and the transitional decode mode — is a **beyond-parity differentiator** neither upstream offers. The card's own upstream verification tags it `parity-adjacent, not required` for both upstreams: GlobalID parity proper was met at `0.0.5`, and the type-anchored convention stays available as the opt-in `type` strategy.

### Reference-package parity checkpoint

| Upstream | `django-strawberry-framework` | Status |
| --- | --- | --- |
| `graphene` `Node.to_global_id` → base64 `<GraphQL type name>:<id>` | `GlobalID` `type` strategy (opt-in) | parity met at `DONE-015-0.0.5` |
| `strawberry.relay.GlobalID` → `to_base64(type_name, node_id)` (type-name slot) | the `GlobalID` encode mechanism (reused wholesale) | parity met at `DONE-015-0.0.5` |
| (no model-anchored option upstream) | **`model` strategy default (`app_label.modelname:id`)** | **this card (`0.0.9`) — beyond parity** |
| (no per-type/project encoding override upstream) | **[`Meta.globalid_strategy`][glossary-djangotype] / `RELAY_GLOBALID_STRATEGY` / `type+model` / callable** | **this card (`0.0.9`) — beyond parity** |

### From Strawberry — borrow the encode/decode mechanism, re-root only the payload

Strawberry owns `GlobalID`, `to_base64` / `from_base64`, the `id: GlobalID!` field, and the `resolve_typename` seam. This card injects a `resolve_typename` default and supplies a `decode_global_id` dispatch — it does **not** hand-roll a base64 scheme or a parallel `GlobalID` type ([Decision 3](#decision-3--the-encode-seam-a-strategy-parameterized-resolve_typename-default)). The package's value is *what goes in the type-name slot* and *how a model label routes back to a type*, not the cursor/base64 plumbing. This mirrors the `0.0.5` foundation's posture of injecting `resolve_*` defaults rather than re-implementing the `Node` interface.

### From `graphene-django` / `strawberry-graphql-django` — borrow nothing new on the format

Both are type-anchored. The `type` strategy preserves that convention verbatim for consumers who want standard-Relay interop or type-scoped identity; nothing else is borrowed.

### Explicitly do not borrow

- **A hand-rolled GlobalID scheme.** `to_base64` / `from_base64` and the `GlobalID` type come from Strawberry.
- **Strawberry's native `GlobalID.resolve_type` for model-label decode.** It is hardcoded to a GraphQL-type-name schema lookup; the package supplies its own `decode_global_id` for the model-label shape ([Decision 8](#decision-8--decode-routes-through-djangos-app-registry-then-the-framework-registry-to-the-primary-type)).
- **Recorded rename-history migration.** `BACKLOG.md` item 39; this card stops at the `type+model` transitional bridge.

## User-facing API

### Declaring a per-type strategy

```python
import strawberry
from strawberry import relay

from django_strawberry_framework import DjangoType, finalize_django_types

from . import models


class ItemType(DjangoType):
    class Meta:
        model = models.Item
        fields = ("id", "name", "category")
        interfaces = (relay.Node,)            # required — a strategy is only meaningful on a Node type
        primary = True                        # two DjangoTypes share this model, so one must declare it
        # globalid_strategy omitted -> resolves to RELAY_GLOBALID_STRATEGY, then the "model" default


class LegacyItemType(DjangoType):
    class Meta:
        model = models.Item
        fields = ("id", "name")
        interfaces = (relay.Node,)
        primary = False                       # a secondary type ...
        globalid_strategy = "type"            # ... that keeps type-scoped identity for disjoint cache scopes


finalize_django_types()
```

`ItemType`'s `id` now decodes to `products.item:42` (the `model._meta.label_lower` payload); `LegacyItemType`'s `id` decodes to `LegacyItemType:42` (the GraphQL-type-name payload). The arrangement satisfies the [model-label-routing invariant](#decision-8--decode-routes-through-djangos-app-registry-then-the-framework-registry-to-the-primary-type) — the only model-label emitter is the primary, which accepts model-label decode — and raises no secondary-collapse warning, because the secondary is on `type` and stays self-routing.

### Schema-wide default via the setting

```python
# settings.py
DJANGO_STRAWBERRY_FRAMEWORK = {
    "RELAY_GLOBALID_STRATEGY": "type+model",   # transitional: emit model-anchored, accept both on decode
}
```

The setting is the schema-wide fallback for any type that does not declare `Meta.globalid_strategy`. Precedence is `Meta.globalid_strategy` → `RELAY_GLOBALID_STRATEGY` → the `"model"` package default ([Decision 5](#decision-5--precedence-metaglobalid_strategy--relay_globalid_strategy--package-default-model)).

### The four strategies

| Strategy | Type-name slot (encode) | Decode accepts | Use case |
| --- | --- | --- | --- |
| `"model"` (default) | `app_label.modelname` (`products.item`) | model-label | durable, rename-proof Django-idiomatic identity |
| `"type"` | GraphQL type name ([`Meta.name`][glossary-metaname] or class name) | type-name | standard-Relay interop; type-scoped auth / cache scopes |
| `"type+model"` | `app_label.modelname` | **both** model-label and type-name | migrating a deployed schema off type-anchored IDs |
| callable | `callable(type_cls, model, root) -> str` (sync; never sees `node_id` or `info` — must be pure over row identity) | n/a — **encode-only in `0.0.9`** (consumer-owned decode) | fully custom encodings |

The **`node_id` slot is unchanged across every strategy** — it is `resolve_id`'s `str(pk)` (or a custom [`resolve_id_attr`][glossary-relay-node-integration] slug), so a strategy switch never changes the `node_id` a `GlobalID` filter extracts or the relation `id` round-trip. (Switching a filter-**targeted** type to `callable` / `custom` is the one filter-visible effect: it fails the schema build, because those encode-only strategies have no framework decode path — [Decision 13](#decision-13--globalid-filter-validation-is-strategy-aware).) The callable strategy is **encode-only** in `0.0.9` (its `decode` is consumer-owned — [Decision 4](#decision-4--four-strategies-model-type-typemodel-callable-and-an-unchanged-node_id-portion) / [Decision 8](#decision-8--decode-routes-through-djangos-app-registry-then-the-framework-registry-to-the-primary-type)); the other three round-trip.

### Decode dispatch (consumed by `node(id:)` in `0.0.9`'s sibling card)

```python
# internal, in types/relay.py; the public testing/relay helper lands with DONE-032-0.0.9.
# `gid` is a relay.GlobalID instance (or its base64 string) — NOT a raw "app_label.model:pk" payload.
target_type, node_id = decode_global_id(gid)
#  GlobalID("products.item", "42") -> apps.get_model("products","item") -> registry.get(Item) -> ItemType, "42"
#  GlobalID("Item", "42")          -> registry.definition_for_graphql_name("Item")  (honors Meta.name) -> ItemType, "42"
#  Step 2 then checks the resolved type's strategy permits the payload shape;
#  a callable-strategy type has no decode path (encode-only in 0.0.9).
```

### Error shapes

- `Meta.globalid_strategy = "modle"` (typo) or any non-`{"model","type","type+model"}` string that is not callable → [`ConfigurationError`][glossary-configurationerror] at type creation.
- `Meta.globalid_strategy` on a non-Relay-Node type (no `relay.Node` in `Meta.interfaces` and no direct inheritance) → [`ConfigurationError`][glossary-configurationerror] at type creation.
- A `callable`-strategy encoder with the wrong arity (not `(type_cls, model, root)`) or declared `async def` → [`ConfigurationError`][glossary-configurationerror] at type creation (the `inspect.signature` arity bind + the shared [`utils/typing.py::is_async_callable`][relay-utils-typing] guard, [Decision 6](#decision-6--metaglobalid_strategy-is-a-net-new-allowed_meta_keys-key-stored-on-the-definition)) — not a raw `TypeError` / coroutine at request time.
- A `callable`-strategy encoder the validator cannot inspect at all — a `__signature__` property or a `__call__` descriptor that raises — → [`ConfigurationError`][glossary-configurationerror] at type creation naming the expected `(type_cls, model, root) -> str` shape, never the descriptor's own exception ([Decision 6](#decision-6--metaglobalid_strategy-is-a-net-new-allowed_meta_keys-key-stored-on-the-definition)).
- `RELAY_GLOBALID_STRATEGY = "bogus"` → [`ConfigurationError`][glossary-configurationerror] naming the setting, raised at the **unconditional finalization-time validation** (`_validated_globalid_setting()`, before the Relay loop — it fires even when no type consumes the setting, i.e. zero Relay types or every type overriding), since [`conf.py`][conf] does no domain validation.
- A `GlobalID` filter (`GlobalIDFilter` / `GlobalIDMultipleChoiceFilter` / [`RelatedFilter`][glossary-relatedfilter] child) bound against a target whose `effective_globalid_strategy` is `callable` / `custom` (encode-only) → [`ConfigurationError`][glossary-configurationerror] at schema build from the Phase-2.5 filterset-binding audit [`types/finalizer.py::_audit_globalid_filter_strategies`][finalizer], which keys on those two names only. A target whose recorded strategy is a **known `None`** is not a build-time error; it is rejected at request time by the runtime backstop below.
- A hand-built filterset that bypasses the Phase-2.5 audit and decodes a `GlobalID` for a `callable` / `custom` (or known-`None`-strategy) target at request time → `GraphQLError` with `extensions.code = "GLOBALID_UNVALIDATABLE"` from [`filters/base.py::_decode_and_validate_global_id`][filters-base] (the runtime backstop; the `None`-strategy case is a lifecycle defect surfaced here).
- `RELAY_GLOBALID_STRATEGY` changed mid-registry-lifecycle (the live value no longer matching an already-computed `registry._globalid_setting_snapshot` — i.e. the slot is no longer the [`GLOBALID_SETTING_UNSET`][registry] sentinel — on a finalization retry) → [`ConfigurationError`][glossary-configurationerror] naming `registry.clear()` (which resets the slot to the sentinel) as the required reset before re-finalizing.
- A type that declares **both** a `resolve_typename` override **and** an explicit `Meta.globalid_strategy` → [`ConfigurationError`][glossary-configurationerror] at finalization (contradictory type-name-slot sources, [Decision 10](#decision-10--resolve_typename-injection-via-the-__func__-identity-test-at-phase-25)).
- A `callable`-strategy encoder that returns a non-string (or empty) value → [`ConfigurationError`][glossary-configurationerror] from the installed closure, rather than Strawberry's opaque `Node._id` `AssertionError` ([Decision 10](#decision-10--resolve_typename-injection-via-the-__func__-identity-test-at-phase-25)).
- A model whose registered types emit model-label IDs but whose **primary** does not accept model-label decode → [`ConfigurationError`][glossary-configurationerror] at finalization (the model-label-routing invariant, [Decision 8](#decision-8--decode-routes-through-djangos-app-registry-then-the-framework-registry-to-the-primary-type)).
- A `decode_global_id` argument that is **not a `str` or `relay.GlobalID`** (`None`, an `int`, a lazy object, …) → [`ConfigurationError`][glossary-configurationerror] from the runtime input-type gate, before any parse ([Decision 8](#decision-8--decode-routes-through-djangos-app-registry-then-the-framework-registry-to-the-primary-type)).
- A `decode_global_id` input that passes the type gate as a **subclass** — a `str` subclass with a hostile `__str__` / `__repr__` / `__format__`, or a [`relay.GlobalID`][glossary-relay-node-integration] subclass whose `type_name` / `node_id` access raises or yields a non-`str` — → [`ConfigurationError`][glossary-configurationerror], never the hostile object's own exception: the raw input and both parsed slots are re-read through the base `str.__str__` descriptor, the slot reads sit inside a `BaseException` guard, a non-`str` slot is rejected before the truthiness check, and the diagnostics render through `exceptions.py::_safe_type_name` / `_safe_arg_repr` ([Decision 8](#decision-8--decode-routes-through-djangos-app-registry-then-the-framework-registry-to-the-primary-type)).
- A `decode_global_id` input that is malformed base64, does not parse to a `"<type_name>:<node_id>"` shape, or parses to an **empty `type_name` or empty `node_id`** → [`ConfigurationError`][glossary-configurationerror] (Strawberry's `relay.GlobalID.from_id` raises `GlobalIDValueError ⊂ ValueError`, caught and re-raised; the empty-slot checks are package-added, [Decision 8](#decision-8--decode-routes-through-djangos-app-registry-then-the-framework-registry-to-the-primary-type)).
- A `decode_global_id` payload that resolves to no installed app / model, to a model or GraphQL name with no registered Relay-Node [`DjangoType`][glossary-djangotype], to an ambiguous `graphql_type_name`, or to a candidate whose `effective_globalid_strategy` is **absent (`None`)** — e.g. a non-Relay-Node `DjangoType` — → [`ConfigurationError`][glossary-configurationerror] naming the resolution attempt (the absent-strategy rejection that keeps the uniform-error contract intact for `032`'s arbitrary client input, [Decision 8](#decision-8--decode-routes-through-djangos-app-registry-then-the-framework-registry-to-the-primary-type)).
- A `decode_global_id` payload whose shape the **resolved candidate's** strategy does not permit (a type-name payload for a `model`-strategy type, a model-label payload for a `type`-strategy type, or any payload for a `callable`- or `custom`-strategy type, which are encode-only) → [`ConfigurationError`][glossary-configurationerror] (the Step-2 enforcement of [Decision 8](#decision-8--decode-routes-through-djangos-app-registry-then-the-framework-registry-to-the-primary-type)).

Rationale companion — this Decision's justification and its one rejected alternative: [Decision 2][rationale-d2].

### Decision 3 — The encode seam: a strategy-parameterized `resolve_typename` default

Strawberry's `relay.types.Node._id` field resolver computes the `GlobalID`'s `type_name` slot via `resolve_typename(root, info)` (source-verified against the locked `0.316.0`). The default `Node.resolve_typename` returns `info.path.typename` (the GraphQL type name). **The encode seam is therefore `resolve_typename`** — inject a package default that returns the model label (or the strategy-appropriate value) and every emitted `GlobalID` re-roots, with zero change to Strawberry's `GlobalID` construction, `to_base64`, or the `node_id` slot.

The injection rides the existing Phase-2.5 mechanism: `install_relay_node_resolvers` already installs the four `resolve_*` defaults UNLESS the consumer overrode them (the `existing.__func__ is relay.Node.<attr>.__func__` identity test). The `resolve_typename` injection uses the same identity test against `relay.Node.resolve_typename.__func__`, so a consumer who declares their own `resolve_typename` keeps it ([Decision 10](#decision-10--resolve_typename-injection-via-the-__func__-identity-test-at-phase-25)).

Both branches of Strawberry's `_id` read `resolve_typename` off the `DjangoType` class — the `isinstance(root, Node)` branch via `root.__class__.resolve_typename`, the integration branch (raw model instance) via `origin.resolve_typename` resolved from the schema's type def. Installing the classmethod on the `DjangoType` class covers both.

Rationale companion — this Decision's justification and its three rejected alternatives: [Decision 3][rationale-d3].

### Decision 4 — Four strategies (`model`, `type`, `type+model`, callable) and an unchanged `node_id` portion

The card pre-pins the four strategies; this Decision pins their exact encode/decode semantics:

- **`model` (new default)** — type-name slot = `definition.model._meta.label_lower` (`"app_label.modelname"`, lowercased — Django's canonical model label, e.g. `products.item`). Decode resolves the label via `django.apps.apps.get_model(...)`.
- **`type` (opt-in legacy / standard Relay)** — type-name slot = the GraphQL type name ([`definition.graphql_type_name`][definition] = `Meta.name` or the class name), identical to Strawberry's `info.path.typename` default. The package leaves Strawberry's default `resolve_typename` in place for this strategy (installs nothing), so the payload is byte-identical to the pre-`0.0.9` output. This is the documented opt-out for type-scoped auth / cache scopes and standard-Relay interop.
- **`type+model` (transitional)** — **emits** the model-label payload (so new IDs are already rename-proof) but **decodes both** model-label and type-name payloads (so old type-anchored IDs minted before the migration still resolve). The bridge for a deployed schema turning on the `model` default without orphaning cached client IDs.
- **callable (encode-only in `0.0.9`)** — `Meta.globalid_strategy = my_encoder` where `my_encoder(type_cls, model, root) -> str` returns the type-name slot for fully custom encodings. **The signature is derived from the `resolve_typename(root, info)` seam, NOT `resolve_id`** — it receives the resolving `type_cls`, its Django `model`, and the model instance `root`, and it must synchronously return `str`. It does **not** receive `info`: the type-name slot is a durable identity component, so the encoder must be a pure function of the row's identity, and withholding `info` makes that purity a documented consumer obligation rather than an opening to fold request-scoped state into a durable ID. It deliberately does **not** receive `node_id` either: the seam computes the type-name slot before the node-id slot, so a node-id-dependent type-name would force a premature (and, for async / custom `resolve_id`, doubled) `resolve_id` call — incompatible with the `resolve_typename` seam without a fuller custom-`id`-resolver design that is out of scope here. Custom encodings whose type-name slot genuinely depends on the node id are therefore not expressible via this strategy in `0.0.9`. The framework's installed closure **validates the callable returns a non-empty `str`** and raises [`ConfigurationError`][glossary-configurationerror] on a non-string return rather than letting Strawberry's `Node._id` `assert isinstance(type_name, str)` fire as an opaque `AssertionError` ([Decision 10](#decision-10--resolve_typename-injection-via-the-__func__-identity-test-at-phase-25)). A `str` **subclass** return passes the `isinstance` check but can override `__str__` / `__format__` and escape the validated value later in Strawberry's base64 encoder, so the closure re-reads the return through the base `str.__str__` descriptor and emits that exact `str`; the emptiness check runs on the normalized value, so a subclass normalizing to `""` is rejected like a bare empty return. `callable` is **encode-only**: decode of a callable-encoded ID is the consumer's responsibility (or lands with the root-Node decode in [`DONE-032-0.0.9`][kanban]), so the `decode_global_id` dispatch has no callable branch ([Decision 8](#decision-8--decode-routes-through-djangos-app-registry-then-the-framework-registry-to-the-primary-type)).

A consumer-declared `resolve_typename` override is the **fifth effective strategy, `custom`** — a sibling of `callable`: the framework leaves the override in place and treats the type as encode-only for decode ([Decision 10](#decision-10--resolve_typename-injection-via-the-__func__-identity-test-at-phase-25)). Declaring both an override and `Meta.globalid_strategy` raises.

Across every strategy the `node_id` slot is `resolve_id`'s `str(pk)` (or a custom `resolve_id_attr` value). Only the type-name slot varies, and it is computed synchronously by `resolve_typename` for every strategy.

Rationale companion — this Decision's justification and its three rejected alternatives: [Decision 4][rationale-d4].

### Decision 5 — Precedence: `Meta.globalid_strategy` → `RELAY_GLOBALID_STRATEGY` → package default (`model`)

The precedence has two halves. First, the schema-wide setting is read and validated **exactly once per finalization, unconditionally, before the Relay loop**: `_validated_globalid_setting()` (in [`types/relay.py`][relay]) reads it through [`conf.py::relay_globalid_strategy_setting()`][conf] (the `getattr(settings, "RELAY_GLOBALID_STRATEGY", None)` helper — "absent → default"; a bare `conf.settings.RELAY_GLOBALID_STRATEGY` access would raise `AttributeError` on the missing key) and validates it through the shared `_validate_globalid_strategy(None, value, relay_shaped=True, source="setting")`. The finalizer snapshots the validated result on `registry._globalid_setting_snapshot` and passes it into `install_globalid_typename_resolver`. The slot's initial (and post-`registry.clear()`) value is the [`registry.py::GLOBALID_SETTING_UNSET`][registry] sentinel, **not** `None`: an absent setting validates to `None`, so only a distinct sentinel can say "no snapshot has been taken yet" without colliding with a legitimately computed `None`. The finalizer therefore stamps the snapshot when the slot is the sentinel and compares against it otherwise. Because the read is unconditional, an invalid `RELAY_GLOBALID_STRATEGY` raises even when **zero Relay-Node types are registered or every type overrides**. A mid-lifecycle setting change detected on a finalization retry (the live value no longer matching an already-stamped snapshot) raises [`ConfigurationError`][glossary-configurationerror] directing the consumer to `registry.clear()` (which resets the slot to the sentinel) before re-finalizing. Second, the per-type resolver `_resolve_globalid_strategy(definition, globalid_setting)` is a **pure two-arg precedence function that reads no setting and validates nothing**: the per-type `definition.globalid_strategy` (`Meta` override) if set; else the passed-in validated `globalid_setting` snapshot if configured; else the [`DEFAULT_GLOBALID_STRATEGY`][base] (`"model"`) package default. The install step ([Decision 10](#decision-10--resolve_typename-injection-via-the-__func__-identity-test-at-phase-25)) layers the consumer-`resolve_typename`-override classification on top — a preserved override forces the **`custom`** effective strategy regardless of this precedence, and declaring both an override and an explicit `Meta.globalid_strategy` raises — then **records the resolved effective strategy** (`model` / `type` / `type+model` / `callable` / `custom`) on the definition so decode reads a stored value. The resolved strategy is frozen at schema-build time — the encoding is a stable schema contract, not request-scoped state.

Rationale companion — this Decision's justification and its two rejected alternatives: [Decision 5][rationale-d5].

### Decision 6 — `Meta.globalid_strategy` is a net-new `ALLOWED_META_KEYS` key, stored on the definition

`Meta.globalid_strategy` lands **directly** in [`ALLOWED_META_KEYS`][base] (NOT a [`DEFERRED_META_KEYS`][base] promotion), the same net-new-key rule [`spec-030`][spec-030] [Decision 8][spec-030] and [`spec-029`][spec-029] [Decision 6][spec-029] set — its feature ships in the same card that adds the key, so it was never reserved-but-nonfunctional. A `_validate_globalid_strategy(meta, value, relay_shaped, *, source="meta")` helper (called from [`_validate_meta`][base], modeled on `_validate_connection`; the keyword-only `source` selects the error framing — `"meta"` names the offending type and enforces the Relay-Node-shape gate, `"setting"` names `RELAY_GLOBALID_STRATEGY` and skips the gate with `meta=None` / `relay_shaped=True` — and its callable arity / sync-ness checks are delegated to `_validate_globalid_callable`):

- `None` (absent) → returns `None` (resolves to the setting/default later);
- a string not in [`STRING_GLOBALID_STRATEGIES`][base] (`{"model", "type", "type+model"}`) and not callable → [`ConfigurationError`][glossary-configurationerror] naming the offending value and listing the valid strategies (typo guard). The vocabulary and the `"model"` package default are the named [`types/base.py`][base] constants [`STRING_GLOBALID_STRATEGIES`][base] / [`DEFAULT_GLOBALID_STRATEGY`][base], the single source this validator's typo-guard text, `_resolve_globalid_strategy`, the encoder, and the decode-shape enforcement all read rather than re-typing the literals. The offending value is rendered through the shared `exceptions.py::_safe_arg_repr` containment, so a hostile `__repr__` cannot escape while the error message is being assembled;
- a callable → **validated for the seam's arity and sync-ness**, the arity/sync checks delegated to `_validate_globalid_callable`: `inspect.signature(callable)` must accept the three positional parameters `(type_cls, model, root)`, and the shared [`utils/typing.py::is_async_callable`][relay-utils-typing] guard (partial- and instance-aware, so it catches `functools.partial` wrappers and `async def __call__` instances a lone `inspect.iscoroutinefunction` misses) must report sync; a wrong-arity callable (e.g. `(type_cls, model)`, or the superseded four-arg `(type_cls, model, root, info)` shape [Decision 4](#decision-4--four-strategies-model-type-typemodel-callable-and-an-unchanged-node_id-portion) dropped `info` from) or an `async def` callable raises [`ConfigurationError`][glossary-configurationerror] **at type creation**, naming the type and the expected `(type_cls, model, root) -> str` shape — rather than deferring a raw `TypeError` (wrong arity) or coroutine return to per-row request time. **The inspection itself is contained**: both the sync-ness probe and the `inspect.signature(...).bind(...)` probe are wrapped so a callable whose `__signature__` property or `__call__` descriptor raises becomes the same [`ConfigurationError`][glossary-configurationerror] ("could not be inspected", naming the expected shape) instead of leaking that descriptor's exception out of type creation. Un-inspectable is rejected, never waved through — a validator that cannot read a value has not validated it. This moves the whole class of callable misconfiguration to build time, matching the fail-loud-at-finalization posture for every other strategy error; the *return-value* (non-empty `str`) check is the one piece that can only run per call, in the installed closure ([Decision 10](#decision-10--resolve_typename-injection-via-the-__func__-identity-test-at-phase-25)). **The same callable arity/sync validation is reused for a callable `RELAY_GLOBALID_STRATEGY` setting value** ([Decision 7](#decision-7--the-relay_globalid_strategy-setting-and-the-settings-key-discipline)) — one validator, two sources, source-specific error text (type creation naming the type / finalization naming the setting);
- the key on a non-Relay-Node type — i.e. when the precomputed `relay_shaped` bool (`_is_relay_shaped(cls, interfaces)`, threaded in from `_validate_meta`, the same predicate `_validate_connection` uses) is False → [`ConfigurationError`][glossary-configurationerror] ("`<Model>.Meta.globalid_strategy` requires a Relay-Node-shaped type; add `relay.Node` to `Meta.interfaces` or inherit `relay.Node` directly."). The message is composed from the `_RELAY_NODE_GATE_LEAD` / `_RELAY_NODE_GATE_INHERIT_TAIL` constants [`types/base.py`][base] shares with the [`Meta.connection`][glossary-metaconnection] gate and `testing/relay.py::global_id_for`, so all three gates state the remediation identically.

The normalized value is **stored on [`DjangoTypeDefinition`][definition]** (a new `globalid_strategy` slot, populated in [`__init_subclass__`][base] like the `connection` / `filterset_class` / `orderset_class` slots), so the Phase-2.5 `resolve_typename` injection reads the per-type opt-in from the canonical definition record, not by re-parsing `Meta` (which is normalized away after validation).

### Decision 7 — The `RELAY_GLOBALID_STRATEGY` setting and the settings-key discipline

The `RELAY_GLOBALID_STRATEGY` key is added to the `DJANGO_STRAWBERRY_FRAMEWORK` settings surface **now** — as the named [`conf.py::RELAY_GLOBALID_STRATEGY_KEY`][conf] constant, which is both the `getattr` key the reader uses and the literal subject the setting-path validation error names, so the key cannot drift between the read site and the message — because this card is the feature that needs it ([`START.md`][start]'s rule, born from the documented past mistake of pre-populating `conf.py` with future-feature settings #"Don't preemptively populate `conf.py` with future-feature settings"). [`conf.py`][conf] stays a thin reader — it does **not** validate the value; `_validated_globalid_setting()` (in [`types/relay.py`][relay]) reads and validates it once per finalization, and the finalizer snapshots the result on `registry._globalid_setting_snapshot` before the Relay loop (the validation is unconditional, so it fires even with zero Relay types or all-override). **The setting value runs through the same validator as `Meta.globalid_strategy`** ([Decision 6](#decision-6--metaglobalid_strategy-is-a-net-new-allowed_meta_keys-key-stored-on-the-definition)) via `_validate_globalid_strategy(None, value, relay_shaped=True, source="setting")`, factored so both sources share one rule with source-specific error text: an unknown string, **a wrong-arity callable, or an `async def` callable** all raise [`ConfigurationError`][glossary-configurationerror] — the `Meta` path raises at type creation naming the type, the setting path raises at finalization naming the setting. A well-formed `(type_cls, model, root)` callable setting value is accepted (project-wide custom encoder). Without this, a wrong-arity / `async def` callable supplied through settings would survive finalization and fail later from the installed `resolve_typename` closure — the exact deferred-opaque-failure mode [Decision 6](#decision-6--metaglobalid_strategy-is-a-net-new-allowed_meta_keys-key-stored-on-the-definition) closes for the `Meta` path.

### Decision 8 — Decode routes through Django's app registry then the framework registry to the primary type

`decode_global_id(gid: relay.GlobalID | str)` opens with a **runtime input-type gate**: because every caller feeds it arbitrary client input, a value outside the annotation (`None`, an `int`, a lazy object, any non-`str` / non-`relay.GlobalID`) is rejected up front — `if not isinstance(gid, (relay.GlobalID, str)): raise ConfigurationError(...)` — so those paths cannot leak an `AttributeError` / `TypeError` past the uniform-error contract. A [`relay.GlobalID`][glossary-relay-node-integration] instance is read directly (`.type_name` / `.node_id`); a `str` is parsed via Strawberry's **`relay.GlobalID.from_id(value)`** (`strawberry/relay/types.py::GlobalID.from_id`) — there is no `GlobalID.from_base64` classmethod; the module-level `from_base64` returns a raw tuple, while `from_id` is the `str → GlobalID` parser for this branch. It never accepts a raw, un-encoded `"app_label.modelname:pk"` payload. A malformed base64 string or one that does not split into a `"<type_name>:<node_id>"` shape raises Strawberry's `GlobalIDValueError`, a **subclass of `ValueError`** (`strawberry/relay/types.py::GlobalIDValueError`) — so the helper catches `ValueError` (the superset spelling) and re-raises [`ConfigurationError`][glossary-configurationerror]. After parsing, an **empty `type_name`** (the encoder never emits one — the callable closure already rejects an empty type-name slot) **or an empty `node_id`** (the safer root-node contract; the package does not support blank-string primary keys) is likewise rejected as [`ConfigurationError`][glossary-configurationerror]. **Hostile input is contained at the same boundary**, because `isinstance` deliberately admits `str` and [`relay.GlobalID`][glossary-relay-node-integration] **subclasses**: such a value passes the gate and can then raise from — or substitute a different payload through — an overridden `__str__` / `__repr__` / `__format__` or an attribute descriptor. So the helper re-reads a `str` input through the base `str.__str__` descriptor before parsing, reads `.type_name` / `.node_id` inside a `BaseException` guard, rejects a non-`str` slot **before** the truthiness check rather than after it, and re-reads both surviving slots through `str.__str__`, so the value that reaches the dot test, the split, the registry lookups, and the error text is the inert one; every diagnostic renders the offending value through the shared `exceptions.py::_safe_type_name` / `_safe_arg_repr` containment. The rule is the decode-side sibling of the encoder's normalized-return contract ([Decision 4](#decision-4--four-strategies-model-type-typemodel-callable-and-an-unchanged-node_id-portion)): a value must be inert by the time it leaves the input boundary, not merely well-typed at the moment it is inspected. Every `decode_global_id` failure (non-`str`/`GlobalID` input, malformed string, unreadable or non-`str` `GlobalID` slots, empty `type_name` / `node_id`, unresolvable label, absent-strategy candidate, strategy-forbidden shape) thus presents the one uniform decode-failure exception type rather than leaking Strawberry's or Python's internal classes. It then runs a **two-step resolve-then-enforce** dispatch on the `(type_name, node_id)`.

**Step 1 — resolve a candidate type from the type-name slot's shape:**

- A **model-label** slot (contains a dot, `"app_label.modelname"`) → `django.apps.apps.get_model(app_label, model_name)` → [`registry.get(model)`][registry] (which returns the primary, or the lone registered type) → candidate `target_type`.
- A **GraphQL-type-name** slot (no dot) → a `graphql_type_name` registry lookup, **NOT** a `type_cls.__name__` lookup: the `type` strategy emits [`definition.graphql_type_name`][definition], which honors [`Meta.name`][glossary-metaname], so a class `ItemType` with `Meta.name = "Item"` emits `Item:<pk>` and can only decode by inverting the same function. The lookup is a new `registry.definition_for_graphql_name(name)` helper that scans [`registry.iter_definitions()`][registry] for a unique **Relay-Node-shaped** `graphql_type_name` match (it ignores non-Node definitions, since a non-Node type can never be the target of a `GlobalID`) → candidate `target_type`.

**Step 2 — enforce the candidate's effective strategy permits the payload shape**. Read the candidate's **recorded `effective_globalid_strategy`** (stamped on the [`DjangoTypeDefinition`][definition] at finalization, [Decision 10](#decision-10--resolve_typename-injection-via-the-__func__-identity-test-at-phase-25)) and reject a shape the strategy does not emit. The two shape memberships are the named [`types/relay.py`][relay] frozensets `MODEL_LABEL_STRATEGIES` (`{"model", "type+model"}`) and `TYPE_NAME_STRATEGIES` (`{"type", "type+model"}`), read through the `_accepts_model_label_decode` / `_accepts_type_name_decode` predicates — the single source shared with the model-label-routing audit's emit half (`_emits_model_label`) and with [`filters/base.py::_accepted_globalid_type_names`][filters-base], so the decodable-shape vocabulary is stated once instead of re-typed at each site:

- **absent (`None`)** → **`ConfigurationError`**. Every caller feeds `decode_global_id` **arbitrary client-controlled input** (root `node(id:)`, the write-side typed-id primitive, and the public test helper — all shipped by [`DONE-032-0.0.9`][kanban]), so a crafted/stale `to_base64("SomePlainType", "1")` can resolve (via `apps.get_model` → `registry.get`, or the type-name lookup) to a type whose `effective_globalid_strategy` was never stamped: a **non-Relay-Node** `DjangoType` (the install step runs for Relay types only) or a Relay type left mid-state. A `None` recorded strategy means "not a framework-decodable Relay-Node type" and is rejected — without this the `None` case would `KeyError` / leak a non-`ConfigurationError`, or worse return `(target_type, node_id)` for a type that cannot be a Node. This is belt-and-suspenders with the Relay-only scan in Step 1.
- `model` → a model-label payload only; a type-name payload for a `model`-strategy type raises [`ConfigurationError`][glossary-configurationerror].
- `type` → a type-name payload only; a model-label payload for a `type`-strategy type raises.
- `type+model` → **both** shapes (the transitional bridge — old type-anchored IDs and new model-anchored IDs both resolve).
- `callable` / `custom` → **no decode path in `0.0.9`** (both encode-only — `callable` per [Decision 4](#decision-4--four-strategies-model-type-typemodel-callable-and-an-unchanged-node_id-portion), `custom` = a consumer `resolve_typename` override per [Decision 10](#decision-10--resolve_typename-injection-via-the-__func__-identity-test-at-phase-25)); a payload whose candidate resolves to such a type raises [`ConfigurationError`][glossary-configurationerror] directing the consumer to own the decode (or await the root-Node decode in [`DONE-032-0.0.9`][kanban]).

On success returns `(target_type, node_id)`. An unresolvable label (no installed app/model, a model or GraphQL name with no registered Relay-Node [`DjangoType`][glossary-djangotype], or an ambiguous name), a candidate with no recorded strategy, or a shape the candidate's strategy forbids, raises [`ConfigurationError`][glossary-configurationerror] naming the resolution attempt — the same fail-loud shape [`RelatedFilter`][glossary-relation-handling] uses for unqualified names. The Step-2 enforcement is what makes `type+model` distinguishable from a permissive "accept anything resolvable" decoder, stops a `model`-strategy type from silently accepting stale type-anchored IDs, preserves the type-scoped-identity guarantee of the `type` strategy, and guarantees the uniform-`ConfigurationError` contract holds for the arbitrary client input `032` will feed it.

Multiple [`DjangoType`][glossary-djangotype]s for one model route asymmetrically: a **model-label** ID resolves through the **primary** ([`registry.get`][registry] honors [`Meta.primary`][glossary-metaprimary] as its first return state), while a **type-name** ID resolves to the specific type by `graphql_type_name`. That asymmetry creates a finalization invariant:

> **Model-label-routing invariant.** For any **multi-type** model (two or more registered Relay-Node `DjangoType`s), if *any* registered type's effective strategy emits model-label IDs (`model` or `type+model`), the model's **primary** type's effective strategy must also accept model-label decode (`model` or `type+model`).

A Phase-2.5 audit (parallel to the existing `_audit_primary_ambiguity`, run after every type's effective strategy is recorded, [Decision 10](#decision-10--resolve_typename-injection-via-the-__func__-identity-test-at-phase-25)) raises [`ConfigurationError`][glossary-configurationerror] naming the model, the model-label-emitting type, and the primary's strategy when the invariant is violated. **The audit is scoped to [`registry.models_with_multiple_types()`][registry]**: a single-type model trivially satisfies the invariant (the lone type both emits and decodes) and has no declared primary (`registry.primary_for(model)` is `None`; `registry.get(model)` returns the lone type), so iterating *all* models and calling `primary_for` would mis-handle the single-type case. For multi-type models the Phase-1 `_audit_primary_ambiguity` has already guaranteed a declared primary exists, so reading `primary_for(model)` is safe. Without it the now-default `model` strategy on any secondary omitted from a strategy audit would mint model-label IDs that route to a `type` / `callable` / `custom` primary and get rejected. A consumer who genuinely needs disjoint per-type identity keeps the secondaries on the `type` strategy (type-name IDs route type-scoped and never hit the primary), so the invariant constrains only the model-label emitters. The resolved type's `resolve_node` (the `0.0.5` default) then honors [`get_queryset`][glossary-get_queryset-visibility-hook], returning `null` for a hidden row.

`decode_global_id` is the framework's single decode entry point, and no package path routes a model-label payload through Strawberry's native `GlobalID.resolve_type`, which resolves a GraphQL type name only. This card ships the helper and its direct Slice-3 coverage; the consumers ship with [`DONE-032-0.0.9`][kanban] and are what feed it arbitrary client input — root `node(id:)` / `nodes(ids:)` via [`relay.py::_decode_or_graphql_error`][package-relay], which converts the uniform [`ConfigurationError`][glossary-configurationerror] into a `GLOBALID_INVALID` `GraphQLError`; the write-side typed-id primitive [`relay.py::decode_model_global_id`][package-relay] that the mutation flavors and the relation `<field>_id` decode share; and the public [`testing/relay.py`][testing-relay] re-export. `GlobalID` **filtering** never calls it: it reads the `node_id` slot and runs its own strategy-aware `type_name` validation ([Decision 13](#decision-13--globalid-filter-validation-is-strategy-aware)).

Rationale companion — this Decision's justification and its six rejected alternatives: [Decision 8][rationale-d8].

### Decision 9 — Changing the default to `model` is a breaking wire-format change, acceptable pre-`1.0.0`

`GlobalID` shipped type-anchored at `DONE-015-0.0.5`. Flipping the default to `model` changes **every** emitted `GlobalID` for a Relay-Node type that does not opt out — a breaking wire-format change. It is acceptable now because:

- The package is alpha (`README.md`: "alpha-quality … not production"; the public *names* are stable, "correctness and edge-case behavior are still hardening"), `GlobalID` is recent (`0.0.5`), and `1.0.0` is the API-freeze boundary ([Cross-subsystem invariants][glossary-cross-subsystem-invariants]).
- The card's entire rationale is to settle the durable format *before* `1.0.0` so a rename does not invalidate cached IDs; deferring the flip past `1.0.0` turns it into migration work.
- There is a clean opt-out: the `type` strategy reproduces the exact pre-`0.0.9` payload per type or project-wide, and `type+model` bridges a deployed schema.

The flip is documented as a breaking change in `CHANGELOG.md` (`### Changed`), [`TODAY.md`][today], and [`docs/GLOSSARY.md`][glossary] — parallel to the `PositiveBigIntegerField → BigInt` `0.0.6` breaking-wire-format precedent ([`BigInt` scalar][glossary-bigint-scalar]).

**Prescribed upgrade sequence (a Slice 5 doc deliverable).** The migration-safe strategy is *not* the default, and in `0.0.9` nothing decodes yet, so the breakage is **latent** — a consumer who upgrades without acting sees nothing wrong until [`DONE-032-0.0.9`][kanban]'s root `node(id:)` ships, at which point every old client-cached type-anchored ID is undecodable. The Slice 5 `CHANGELOG.md` / [`TODAY.md`][today] breaking-change note **must** spell out the ordered sequence rather than leave it implicit in the strategy table:

1. Deploy `RELAY_GLOBALID_STRATEGY = "type+model"` **while the old GraphQL type names still exist** — new IDs are model-anchored, old type-anchored IDs still decode.
2. Let clients receive model-label IDs and age out the old type-name IDs.
3. **Only then** rename GraphQL type names (or [`Meta.name`][glossary-metaname]) — or flip to `model`.

The ordering of step 3 is load-bearing and the prose must not overpromise: `type+model` decodes an old type-anchored ID **only while its old GraphQL type name still resolves through [`registry.definition_for_graphql_name`][registry]**. Renaming `ItemType` / `Meta.name` *during* the window still orphans cached old-type-name IDs — `type+model` is a strategy bridge, **not** a rename-history alias map (that is the `BACKLOG.md` item 39 non-goal). A consumer who must rename mid-window owns a consumer alias / callable migration until item 39 exists. The doc work in Slice 5 is contracted to produce this exact sequence and the rename caveat, not just name the strategies.

Rationale companion — this Decision's justification and its two rejected alternatives: [Decision 9][rationale-d9].

### Decision 10 — `resolve_typename` injection via the `__func__` identity test, at Phase 2.5

An `install_globalid_typename_resolver(type_cls, definition, globalid_setting)` step runs in [`finalize_django_types`][glossary-finalize_django_types] Phase 2.5, alongside `install_relay_node_resolvers`, for every Relay-Node-shaped type; the `globalid_setting` argument is the validated setting snapshot the finalizer computes once via `_validated_globalid_setting()` and stores on `registry._globalid_setting_snapshot` before the Relay loop. The resolved effective strategy is stored on the [`DjangoTypeDefinition`][definition] in a finalization-set field named **`effective_globalid_strategy: str | None = None`** (appended among the dataclass's defaulted fields with an explicit `None` default — distinct from the raw class-creation-time [`globalid_strategy`][definition] slot of [Decision 6](#decision-6--metaglobalid_strategy-is-a-net-new-allowed_meta_keys-key-stored-on-the-definition); a raw callable value and the resolved `custom` classification are different things). The step runs, in order:

0. **Re-entrancy guard (idempotency).** If `definition.effective_globalid_strategy is not None`, this type was already processed in a prior (possibly partial) finalize run — **skip** override-detection, recording, and install, leaving the recorded classification and any installed closure intact. This is load-bearing: [`finalize_django_types`][glossary-finalize_django_types] is documented to be re-run after a mid-Phase-2.5 raise (the per-entry `finalized` guards flip only in Phase 3, so a Phase-2.5 raise — *including the model-label-routing audit below* — leaves every type `finalized = False`, and a re-run re-enters this loop from the top). Without the guard, a re-run would re-run the `__func__` test on a type whose `resolve_typename` is **now the framework closure**, misclassify it `custom`, and overwrite the recorded strategy — a silent decode-breakage on exactly the recoverable path the finalizer promises to support. A genuine config fix rebuilds the definition (re-import / `registry.clear()` → a fresh definition with `effective_globalid_strategy = None`), so it is reprocessed; a bare retry on unchanged definitions leaves correct classifications untouched and re-raises the audit if the config is still bad.
1. **Detect a consumer `resolve_typename` override** via the `existing.__func__ is relay.Node.resolve_typename.__func__` identity test (MRO-aware, the same discriminator the four `resolve_*` defaults use), **with the framework-closure exclusion**: every framework-installed closure is stamped with the `_FRAMEWORK_CLOSURE_MARKER` sentinel attribute (set on the plain function before `classmethod(...)` wrapping, so it survives `classmethod.__func__` retrieval), and a marked function — typically inherited through the MRO from a **concrete Relay parent** that was processed earlier in the same finalize — is **not** a consumer override. Without the exclusion, a concrete Relay child of a concrete Relay parent would see the parent's installed closure fail the bare identity test and be misclassified `custom` (silently encode-only, audit-blind, and spuriously both-declared when the child carries its own `Meta.globalid_strategy`). The step-0 re-entrancy guard protects the *same* definition across finalize re-runs; only the marker protects a *different* definition inheriting the installed closure. A consumer override inherited from an abstract base lacks the marker, so it still classifies `custom` — the intended semantics. If the consumer overrode `resolve_typename`:
   - and the type **also** declares an explicit [`Meta.globalid_strategy`][glossary-djangotype] → **[`ConfigurationError`][glossary-configurationerror]** — two contradictory sources of truth for the type-name slot ("declare a `resolve_typename` override OR `Meta.globalid_strategy`, not both"). The schema-wide `RELAY_GLOBALID_STRATEGY` *setting* is **not** a conflict — it is a default an override legitimately supersedes; only an explicit per-type `Meta.globalid_strategy` collides.
   - otherwise the type's **effective strategy is `custom`**: the framework installs **nothing** (the override owns the type-name slot) and [`decode_global_id`][relay] treats the type as **encode-only** ([Decision 8](#decision-8--decode-routes-through-djangos-app-registry-then-the-framework-registry-to-the-primary-type)). An override can emit any label the framework decoder does not understand, so classifying it `custom`/encode-only closes the self-inconsistency in which a preserved override emits a label the type's own (`model`-default) decoder then rejects.
2. **Otherwise** (no override) resolve the effective strategy via the pure two-arg `_resolve_globalid_strategy(definition, globalid_setting)` ([Decision 5](#decision-5--precedence-metaglobalid_strategy--relay_globalid_strategy--package-default-model); it consumes the passed-in validated snapshot and reads no setting itself) and install: the package `resolve_typename` closure for `model` / `type+model` / `callable`; **nothing** for `type` (Strawberry's default `resolve_typename` returns `info.path.typename`, byte-identical to pre-`0.0.9`) — **unless** the MRO-resolved attribute is a marked framework closure inherited from a concrete Relay parent (`_inherits_framework_closure`), in which case `type` installs its **own** closure too (the **shadow-install**): the inherited closure captured the *parent's* `definition` and would otherwise keep shadowing Strawberry's default, emitting the parent's payload. The shadow-install is the only way a `type`-strategy type carries a framework `resolve_typename` closure, so it is the only path reaching `encode_typename`'s `type` branch (`definition.graphql_type_name`) during `id` resolution; the public `testing/relay.py::global_id_for` helper ([`DONE-032-0.0.9`][kanban]) calls `encode_typename` directly with the recorded strategy and reaches that branch without an installed closure. The `callable` closure **validates the consumer callable returns a non-empty `str`** and raises [`ConfigurationError`][glossary-configurationerror] on a non-string return, rather than letting Strawberry's `Node._id` `assert isinstance(type_name, str)` fire as an opaque `AssertionError`. (The callable's *arity and sync-ness* are validated earlier, at type creation — [Decision 6](#decision-6--metaglobalid_strategy-is-a-net-new-allowed_meta_keys-key-stored-on-the-definition).)
3. **Record the resolved effective strategy** (`model` / `type` / `type+model` / `callable` / `custom`) in `definition.effective_globalid_strategy` so [`decode_global_id`][relay] reads a stored value (`None` ⇒ "not a framework-decodable type" — decode rejects it, [Decision 8](#decision-8--decode-routes-through-djangos-app-registry-then-the-framework-registry-to-the-primary-type)). The post-install `resolve_typename.__func__` can no longer distinguish a consumer override from the framework closure, which is why the classification (step 1) and the re-entrancy guard (step 0) both key on this recorded field rather than re-deriving from the live method.

`resolve_typename` is **not** added to the static `_RELAY_RESOLVER_DEFAULTS` table, because that table maps a name to a single static default; the typename default is strategy-parameterized per type, so it needs its own injection site that reads the resolved strategy.

A sibling **model-label-routing audit** runs after every type's effective strategy is recorded, scoped to [`registry.models_with_multiple_types()`][registry] — single-type models trivially satisfy the invariant (the lone type both emits and decodes) and have no `primary_for(model)` (it returns `None`; only `registry.get(model)` returns the lone type). For multi-type models, Phase-1 `_audit_primary_ambiguity` has already guaranteed a declared primary exists, so `primary_for(model)` is safe to read. Its error message branches on the primary's recorded strategy: a primary carrying a string strategy is told to re-declare it to `model` / `type+model`, while a primary whose strategy is `None` is **not** Relay-Node-shaped and cannot legally declare [`Meta.globalid_strategy`][glossary-djangotype] at all, so that branch prescribes making the primary Relay-Node-shaped instead; both branches also offer moving the emitting type(s) onto `type`. Immediately after the audit, over the same materialized model tuple, [`types/finalizer.py::_warn_model_label_secondary_collapse`][finalizer] **warns** (never raises) on the legal-but-lossy arrangement the audit permits: a NON-primary registered type that also emits model-label IDs. A model-label payload always decodes through `registry.get(model)` to the primary, so such a secondary's `GlobalID`s refetch AS the primary and its distinct identity and `get_queryset` visibility scope silently collapse into the primary's — legal by [Decision 8](#decision-8--decode-routes-through-djangos-app-registry-then-the-framework-registry-to-the-primary-type) (a model-anchored ID cannot distinguish secondaries), and the most likely accidental configuration now that `model` is the default. The warning names the model, the offending secondary, the primary it collapses onto, and the per-type `type` opt-out that restores disjoint identity. See [Decision 8](#decision-8--decode-routes-through-djangos-app-registry-then-the-framework-registry-to-the-primary-type).

### Decision 13 — `GlobalID` filter validation is strategy-aware

The default flip is **not** transparent to the shipped filter surface. [`filters/base.py::_decode_and_validate_global_id`][filters-base] today validates the **whole** `type_name` slot: it raises `GraphQLError("GlobalID type mismatch: filter expects <expected> but received <actual>")` when `decoded.type_name != _expected_global_id_type_name(filter_instance)`, where the expected name is the owning [`DjangoType`][glossary-djangotype]'s `graphql_type_name` (own-PK branch) or the [`RelatedFilter`][glossary-relatedfilter] target's `graphql_type_name` (relation branch). So once `ItemType.id` emits `products.item:<pk>`, feeding that emitted ID back to `filter: { id: { exact: … } }` would be rejected against the expected `ItemType` — regressing the card's headline emitted-ID workflow. `GlobalIDFilter`, `GlobalIDMultipleChoiceFilter`, and every `RelatedFilter`-expanded child filter share this one code path.

**Fix:** replace the single expected-GraphQL-type-name check with **strategy-aware target validation** keyed on the resolved owner/target definition's recorded `effective_globalid_strategy` ([Decision 10](#decision-10--resolve_typename-injection-via-the-__func__-identity-test-at-phase-25)) — the same field decode reads, so encode, decode, and filter validation all agree on one contract. The accepted `type_name` payload(s) per strategy:

- `model` → the target model's label (`definition.model._meta.label_lower`); a bare GraphQL type name is now rejected.
- `type` → the target's `graphql_type_name` (the pre-`0.0.9` behavior, unchanged).
- `type+model` → **either** the model label or the `graphql_type_name` (the migration window — old type-anchored and new model-anchored IDs both filter).
- `callable` / `custom` → **fail closed**. An encode-only strategy has no framework decode path, so a `GlobalID` input that is *required to decode* can never be validly consumed against such a target; silently matching on `node_id` accepted arbitrary payloads. A `GlobalID` filter bound against a `callable` / `custom`-strategy target is therefore rejected at schema build by the Phase-2.5 filterset-binding audit [`types/finalizer.py::_audit_globalid_filter_strategies`][finalizer] (run inside `_bind_filtersets`), raising [`ConfigurationError`][glossary-configurationerror]; the audit resolves each bound filter's target through the same [`filters/base.py::resolve_globalid_target_definition`][filters-base] the runtime path uses, so build time and request time can never disagree about which definition is being validated against. For a hand-built filterset that bypasses the audit, [`filters/base.py::_decode_and_validate_global_id`][filters-base] raises a runtime `GraphQLError` with `extensions.code = "GLOBALID_UNVALIDATABLE"` as the backstop. A resolved target definition whose recorded `effective_globalid_strategy` is a known `None` (a non-framework-decodable candidate — a lifecycle defect) is rejected by that **runtime** backstop and only there: the build-time audit keys on the two encode-only names, so a known-`None` target finalizes and fails on the first request that reaches the input. The **only** node-id-only fallback that survives is the pre-existing no-resolvable-definition case (an **unbound owner / unresolvable target**, where no definition — and thus no strategy — is available at all; in the shipped code, [`filters/base.py::_accepted_globalid_type_names`][filters-base] returns `None` for a `None` target definition); that one is retained.

A wrong-model / wrong-type ID is still rejected for the three framework strategies (the guard is preserved, not dropped). Because the validation reads the **recorded** `effective_globalid_strategy`, the filter change **must co-land with the flip in Slice 2** (the field is stamped during Slice 2's finalization install); shipping the flip without it would regress the live products filter suite.

## Edge cases and constraints

- **Proxy models** — the model-label payload uses the [`DjangoType`][glossary-djangotype]'s *declared* [`Meta.model`][glossary-metamodel] `label_lower`, so a proxy-backed type encodes the proxy's label and a concrete-backed type encodes the concrete label; both decode through `apps.get_model`, which resolves proxy labels. The `node_id` slot keys on `root.__class__._meta.pk.attname` (the existing `_resolve_id_default` proxy-safe behavior), unchanged.
- **Multi-table inheritance (MTI)** — a child model has its own label and its own pk; `apps.get_model(app, child)` resolves it and the child pk fills the `node_id` slot. A `DjangoType` over the parent encodes the parent label. No special handling beyond using the declared model's label.
- **Slug / custom `resolve_id_attr`** — the `node_id` slot is `resolve_id`'s value (a slug, a UUID, whatever `resolve_id_attr` selects), independent of the type-name strategy; a slug-keyed type gets `app_label.modelname:<slug>` under `model`. The two slots are orthogonal.
- **Composite primary key** — already rejected at finalization for Relay-Node types ([composite-pk rejection][glossary-relay-node-integration]); a model-label `GlobalID` still needs a single-column `node_id`, so this card inherits the existing `ConfigurationError` unchanged.
- **Model / app rename** — Django's `apps.get_model` does **not** follow historical renames; renaming `products.Item` → `catalog.Product` changes the label and invalidates old `model`-anchored IDs. This is the model-anchored analogue of the type-rename fragility the card mitigates (model renames are far rarer than GraphQL-type renames). Mitigations: the `type+model` transitional mode plus a callable strategy with a consumer alias map; first-class recorded rename-history decoding is `BACKLOG.md` item 39 ("type-rename GlobalID migrations"). Flagged in [Risks and open questions](#risks-and-open-questions).
- **`Meta.name` interaction under `type`** — the `type` strategy's payload tracks [`Meta.name`][glossary-metaname] (the GraphQL surface name), so renaming via `Meta.name` under `type` still invalidates IDs — which is exactly the fragility `model` avoids; documented so a consumer choosing `type` understands the trade.
- **Multiple `DjangoType`s per model, mixed strategies** — a `model`-strategy ID for a multi-type model decodes to the [`Meta.primary`][glossary-metaprimary] type (model-label IDs route to the primary); a sibling can opt into `type` for disjoint identity (type-name IDs route type-scoped by `graphql_type_name`, never to the primary). A model-anchored ID cannot distinguish secondaries (by design — they share the model). The **model-label-routing invariant** ([Decision 8](#decision-8--decode-routes-through-djangos-app-registry-then-the-framework-registry-to-the-primary-type)) makes the dangerous case a finalization error: if any registered type emits model-label IDs (`model` / `type+model`) the primary must accept model-label decode, so a `type`-strategy primary with a `model`-default secondary is rejected at finalization rather than minting undecodable IDs.
- **Consumer `resolve_typename` override** — a type that declares its own `resolve_typename` keeps it (the framework installs nothing) and is classified `custom` / **encode-only** for framework decode ([Decision 10](#decision-10--resolve_typename-injection-via-the-__func__-identity-test-at-phase-25)) — `decode_global_id` raises a clear [`ConfigurationError`][glossary-configurationerror] for such a type rather than mis-routing a label it cannot interpret. Declaring both an override and an explicit [`Meta.globalid_strategy`][glossary-djangotype] raises at finalization (contradictory type-name-slot sources); the schema-wide setting is not a conflict.
- **`GlobalID` filtering** — the `node_id` extraction is unchanged, but the `type_name` **validation becomes strategy-aware** ([Decision 13](#decision-13--globalid-filter-validation-is-strategy-aware)): a `model`-strategy filter accepts the model-label payload (and rejects the old bare GraphQL type name), `type` accepts the GraphQL type name, `type+model` accepts both, and a `callable` / `custom` filter target **fails closed** — rejected at schema build by the Phase-2.5 [`_audit_globalid_filter_strategies`][finalizer] audit, with the runtime `GLOBALID_UNVALIDATABLE` `GraphQLError` in [`_decode_and_validate_global_id`][filters-base] backstopping hand-built filtersets and additionally rejecting a known-`None`-effective-strategy target, the one fail-closed case the build-time audit does not cover; only an unbound-owner / unresolvable target keeps the node-id-only path. A consumer filtering by an emitted ID therefore uses the same payload shape the type emits; a wrong-model ID is still rejected for the three framework strategies.
- **The connection field** ([`DONE-030-0.0.9`][kanban]) and any [`DjangoListField`][glossary-djangolistfield] emitting nodes — `edges { node { id } }` / `list[T]` `{ id }` pick up the model-label payload through the same per-node `resolve_typename`, no field change.
- **Async `resolve_id`** — Strawberry's `_id` computes the type-name slot via `resolve_typename(root, info)` **first**, then handles an awaitable `node_id` (the `resolve_awaitable` branch) by constructing the `GlobalID` after the await. `resolve_typename` is sync for all four strategies — including the callable strategy, whose signature is `(type_cls, model, root) -> str` and which never touches `node_id` ([Decision 4](#decision-4--four-strategies-model-type-typemodel-callable-and-an-unchanged-node_id-portion)) — so the awaitable-`node_id` branch is unaffected and no strategy forces a premature or doubled `resolve_id`.

The resolved effective strategy (`model` / `type` / `type+model` / `callable` / `custom`) is recorded in the named field **`effective_globalid_strategy: str | None = None`** on the [`DjangoTypeDefinition`][definition]; a Phase-2.5 model-label-routing audit, scoped to [`registry.models_with_multiple_types()`][registry], raises [`ConfigurationError`][glossary-configurationerror] when a multi-type model emits model-label IDs but its primary cannot decode them, and its `_warn_model_label_secondary_collapse` sibling warns (never raises) when a non-primary type also emits them ([Decision 3](#decision-3--the-encode-seam-a-strategy-parameterized-resolve_typename-default) / [Decision 8](#decision-8--decode-routes-through-djangos-app-registry-then-the-framework-registry-to-the-primary-type) / [Decision 10](#decision-10--resolve_typename-injection-via-the-__func__-identity-test-at-phase-25)). The package default is flipped to `model` ([Decision 9](#decision-9--changing-the-default-to-model-is-a-breaking-wire-format-change-acceptable-pre-100)). **Co-landing with the flip, [`filters/base.py::_decode_and_validate_global_id`][filters-base] is made strategy-aware** ([Decision 13](#decision-13--globalid-filter-validation-is-strategy-aware)): it reads the resolved owner/target's recorded `effective_globalid_strategy` and accepts the model label (`model`), the `graphql_type_name` (`type`), or both (`type+model`); a `callable` / `custom` target **fails closed** — rejected at schema build by the Phase-2.5 [`types/finalizer.py::_audit_globalid_filter_strategies`][finalizer] audit (run in `_bind_filtersets`) with a runtime `GLOBALID_UNVALIDATABLE` `GraphQLError` backstop in [`_decode_and_validate_global_id`][filters-base] for hand-built filtersets, which also rejects a known-`None`-effective-strategy target, only the unbound-owner / unresolvable-target case keeping node-id-only — so an emitted model-label ID round-trips through `GlobalIDFilter` / `GlobalIDMultipleChoiceFilter` / [`RelatedFilter`][glossary-relatedfilter]. The callable arity/sync validation is shared between the `Meta.globalid_strategy` and `RELAY_GLOBALID_STRATEGY` paths ([Decision 7](#decision-7--the-relay_globalid_strategy-setting-and-the-settings-key-discipline)). [`tests/types/test_relay_interfaces.py`][test-relay-interfaces] covers each strategy's payload, override→`custom` recording, the both-declared / non-`str`-callable / model-label-routing `ConfigurationError`s, the finalize-re-run re-entrancy, and the default flip; [`tests/filters/test_base.py`][test-filters-base] covers the strategy-aware filter validation (own-PK / relation / multi-value per strategy, wrong-model rejection, callable/custom fail-closed reject, retained unbound-owner node-id-only) and [`tests/filters/test_finalizer.py`][test-filters-finalizer] covers the Phase-2.5 audit rejections.

**Slice 3 — decode**

5. [`django_strawberry_framework/types/relay.py`][relay] ships `decode_global_id(gid: relay.GlobalID | str)` (accepts an encoded [`relay.GlobalID`][glossary-relay-node-integration] / its base64 string, never a raw payload) implementing the **resolve-then-enforce** dispatch of [Decision 8](#decision-8--decode-routes-through-djangos-app-registry-then-the-framework-registry-to-the-primary-type): Step 1 resolves a candidate (model-label via `django.apps.apps.get_model` → [`registry.get`][registry] to the primary [`DjangoType`][glossary-djangotype] honoring [`Meta.primary`][glossary-metaprimary]; GraphQL-type-name via the new `registry.definition_for_graphql_name` helper keyed on [`definition.graphql_type_name`][definition] over **Relay-Node definitions only**, NOT `type_cls.__name__`); Step 2 reads the candidate's recorded `effective_globalid_strategy` and rejects a payload shape it does not permit (`model` model-label only / `type` type-name only / `type+model` both / `callable` + `custom` no decode — encode-only / **absent `None` → reject**). Malformed input (Strawberry's `relay.GlobalID.from_id` raising `GlobalIDValueError ⊂ ValueError`), an unresolvable label, an absent-strategy (non-Relay-Node) candidate, or a strategy-forbidden shape all raise [`ConfigurationError`][glossary-configurationerror] (one uniform decode-failure type — guaranteeing the contract for `032`'s arbitrary client input). The same boundary **contains subclasses**: the raw `str` and both parsed slots are re-read through the base `str.__str__` descriptor, the slot reads sit inside a `BaseException` guard, a non-`str` slot is rejected before the truthiness check, and diagnostics render through `exceptions.py::_safe_type_name` / `_safe_arg_repr`. Step 2's shape memberships are the named [`types/relay.py`][relay] `MODEL_LABEL_STRATEGIES` / `TYPE_NAME_STRATEGIES` frozensets, read through `_accepts_model_label_decode` / `_accepts_type_name_decode` and shared with the model-label-routing audit and the strategy-aware filter. Tests pin the three-decodable-strategy round-trip symmetry, the `Meta.name` `type`-strategy round-trip, the transitional accept-old-ID path, both Step-2 rejection directions, the `callable`/`custom`-no-decode and non-Node-`None` rejections (in both the type-name and model-label arrivals), the malformed-input and input-containment errors, primary-routing, the unresolvable-label and unregistered-model errors, and [`registry.definition_for_graphql_name`][registry]'s match / [`Meta.name`][glossary-metaname] / Relay-only-scan / miss / ambiguity behavior in [`tests/test_registry.py`][test-registry].

**Slice 4 — live HTTP coverage**

6. Live HTTP tests in [`examples/fakeshop/test_query/test_products_api.py`][fakeshop-test-products] prove an emitted `GlobalID` is model-anchored (`::test_emitted_globalid_is_model_anchored`), that **feeding that emitted model-label ID back into `filter: { id: { exact: … } }` round-trips through the real products API** (`::test_globalid_filter_round_trip` — the headline workflow, proving the strategy-aware filter accepts the emitted payload it just produced, [Decision 13](#decision-13--globalid-filter-validation-is-strategy-aware); the filter value is the emitted string verbatim, never reconstructed), and that the `type` strategy reproduces the GraphQL-type-name payload (`::test_type_strategy_opt_out_reproduces_type_name`) via `override_settings` wrapped around the `project_schema_override` reload fixture, so the override is in force when the schema re-finalizes. Every pre-`0.0.9` emitted-ID **and filter-input** `GlobalID` assertion is updated for the model-label default flip across all three affected live suites and the one affected package-tier suite (per the [Test plan](#test-plan)), and no type-anchored `GlobalID` payload survives in the live tier apart from the `type`-opt-out test's deliberate `"ItemType"`.
