## Key glossary references

Skim these [`docs/GLOSSARY.md`][glossary] entries first — they anchor the vocabulary used throughout the spec:

- [Relay Node integration][glossary-relay-node-integration] — the shipped `0.0.5` foundation: `Meta.interfaces = (relay.Node,)` declares a Relay-Node-shaped type with `id: GlobalID!` and the four injected `resolve_*` defaults wired through `cls.get_queryset`. This card's root fields dispatch to those defaults; the one per-type change is inside `install_is_type_of`'s closure, which honors the root fields' concrete-type routing stamp before its isinstance fallback ([Decision 4](#decision-4--djangonodefield--djangonodesfield-a-bare-interface-form-and-a-typed-form)).
- [`DjangoNodeField`][glossary-djangonodefield] — the planned root single-node lookup field this card ships: `genre: GenreType | None = DjangoNodeField(GenreType)` (typed) and `node: relay.Node | None = DjangoNodeField()` (the Relay-spec interface form). The first consumer of [`DONE-031-0.0.9`][kanban]'s decode dispatch.
- [`DjangoConnectionField`][glossary-djangoconnectionfield] / [`DjangoConnection`][glossary-djangoconnection] — the shipped [`DONE-030-0.0.9`][kanban] connection surface whose factory pipeline (per-target connection classes, synthesized sidecar arguments, visibility→filter→order→default-order→optimizer→slice composition) the relation-as-Connection upgrade reuses with a relation-manager-seeded source.
- [`Meta.connection`][glossary-metaconnection] — the type-level `{"total_count": bool}` opt-in; a synthesized relation connection resolves through the same per-target connection class, so `totalCount` availability follows the **target** type's declaration (type-level, one stable connection shape per node type).
- [`Meta.interfaces`][glossary-metainterfaces] — the key whose validation this card's Slice 1 extends with named rejections for the six `strawberry.relay` non-interface helpers ([Decision 8](#decision-8--the-six-schema-validation-diagnostics)).
- [`Meta.globalid_strategy`][glossary-metaglobalid_strategy] / [`RELAY_GLOBALID_STRATEGY`][glossary-relay-globalid-strategy] — the shipped (`0.0.9`, [`DONE-031-0.0.9`][kanban]) encoding-strategy system; the root fields decode whatever payload the strategy system emits, and [`testing.relay.global_id_for`](#decision-10--public-testingrelaypy-helpers-and-the-export-gate) computes the strategy-appropriate encoded id for a `(type, pk)` pair.
- [`Meta.primary`][glossary-metaprimary] — a decoded model-label id routes to the model's primary [`DjangoType`][glossary-djangotype]; the typed `DjangoNodeField(Target)` form layers a declared-target check on top ([Decision 4](#decision-4--djangonodefield--djangonodesfield-a-bare-interface-form-and-a-typed-form)).
- [`Meta.name`][glossary-metaname] — type-name-anchored ids decode through `registry.definition_for_graphql_name`, which honors `Meta.name`; the root fields inherit that contract unchanged.
- [`get_queryset` visibility hook][glossary-get_queryset-visibility-hook] — the load-bearing permission surface: the shipped `resolve_node` / `resolve_nodes` defaults run it, so a decoded id for a hidden row resolves to `null`, never an error ([Decision 5](#decision-5--null-for-invisible-rows-graphqlerror-for-malformed-ids)).
- [`ConfigurationError`][glossary-configurationerror] — raised at type-creation time for a malformed [`Meta.relation_shapes`][glossary-metarelation_shapes] declaration and at finalization for the no-Node-types and non-Node-target diagnostics; the decode helper's uniform failure type, converted to `GraphQLError` at the root-field boundary.
- [`finalize_django_types`][glossary-finalize_django_types] — Phase 2.5 already injects interfaces, the Relay `resolve_*` defaults, and the `GlobalID` typename resolver; the relation-as-Connection synthesis and the no-Node-types check land in the same phase ([Decision 6](#decision-6--relation-as-connection-synthesis-at-finalization-phase-25)).
- [Definition-order independence][glossary-definition-order-independence] — the collection-then-finalize split the connection synthesis rides on: relation targets are resolved (Phase 1) before the upgrade runs (Phase 2.5), so the target-is-Node-shaped gate reads settled definitions.
- [`SyncMisuseError`][glossary-syncmisuseerror] — the typed marker the `resolve_node` / `resolve_nodes` defaults raise on the sync branch when `get_queryset` returns a coroutine; the synthesized relation connections inherit that contract unchanged, and the root fields additionally raise it themselves when a **consumer** `resolve_node` / `resolve_nodes` override returns an awaitable under `schema.execute_sync()` ([Error shapes](#error-shapes)).
- [Connection-aware optimizer planning][glossary-connection-aware-optimizer-planning] — the sibling [`DONE-033-0.0.9`][kanban] card, which owns every connection's optimizer plan, root or nested; the sequencing constraint [Decision 12](#decision-12--sequencing-against-the-connection-aware-optimizer-and-the-library-first-activation) builds around.
- [Strictness mode][glossary-strictness-mode] — the synthesized nested connections reuse [`connection.py`][connection]'s pipeline, and the strictness-mode interaction with that pipeline is [`DONE-033-0.0.9`][kanban]'s scope (see [Non-goals](#non-goals)); the live tests this card adds assert behavior, not SQL shape.
- [`DjangoOptimizerExtension`][glossary-djangooptimizerextension] — root-gated optimization is untouched; the connection field owns its own cooperation seam ([`spec-030`][spec-030] Decision 11) and the synthesized relation connections reuse it.
- [`FilterSet`][glossary-filterset] / [`OrderSet`][glossary-orderset] / [`Meta.filterset_class`][glossary-metafilterset_class] / [`Meta.orderset_class`][glossary-metaorderset_class] — the sidecars whose `filter:` / `orderBy:` arguments the synthesized relation connections carry, exactly as the shipped root connection field does ([`filter_input_type`][glossary-filter_input_type] / [`order_input_type`][glossary-order_input_type] drive the lazy annotations).
- [`DjangoListField`][glossary-djangolistfield] — the annotation-driven factory-function precedent (`list[T]` vs `list[T] | None` drives outer nullability) the root node fields follow for the **rendered SDL type only**; their resolution is nullable-by-contract (`required=False` unconditionally — [Decision 5](#decision-5--null-for-invisible-rows-graphqlerror-for-malformed-ids)).
- [Relation handling][glossary-relation-handling] — the shipped list-shaped relation conversion the connection counterparts **replace**: under the `"connection"` default an eligible relation's generated `list[T]` field is removed and only `<field>Connection` reaches the SDL. The raw many-side list returns solely through an explicit [`Meta.relation_shapes`][glossary-metarelation_shapes] `"both"` entry, and the list it restores is row-bounded by the request policy ([`resource_policy.py::bounded_rows`][resource-policy]).
- [`apply_cascade_permissions`][glossary-apply_cascade_permissions] / [Per-field permission hooks][glossary-per-field-permission-hooks] — the `0.0.10` permissions subsystem ([`DONE-034-0.0.10`][kanban]); the root fields respect `get_queryset`, and declared-permission integration is that card's scope.
- [`Meta.search_fields`][glossary-metasearch_fields] — the `search:` argument stays absent from every connection until `0.1.2` ([`TODO-BETA-056-0.1.2`][kanban]); reaffirmed for the synthesized relation connections.
- [`strawberry_config`][glossary-strawberry_config] — the scalar-map factory every example schema in this spec passes to `strawberry.Schema(...)`; its `relay_max_results` passthrough is the schema-side knob over connection page sizes, and it is no longer the only bound — the request's [`resource_policy.py::ResourcePolicy.max_page_size`][resource-policy] is a **ceiling** over whatever value it resolves ([Edge cases and constraints](#edge-cases-and-constraints)).
- [`TestClient`][glossary-testclient] / [`GraphQLTestCase`][glossary-graphqltestcase] — the `0.0.12` consumer test clients; `testing/relay.py` is this card's narrower test-helper surface and shares the `testing/` subpackage with them.
- [Cross-subsystem invariants][glossary-cross-subsystem-invariants] — the `1.0.0` rule that example-project schemas reference only shipped features; the library activation slice references only surfaces this card and its predecessors ship.

## Problem statement

`django-strawberry-framework` has every Relay ingredient on disk but no assembled Relay story. The `0.0.5` [Relay Node integration][glossary-relay-node-integration] gave Relay-Node-shaped types `id: GlobalID!` and `get_queryset`-aware `resolve_node` / `resolve_nodes` defaults. [`DONE-030-0.0.9`][kanban] shipped [`DjangoConnectionField`][glossary-djangoconnectionfield] — cursor pagination with sidecar-derived `filter:` / `orderBy:` arguments and opt-in `totalCount`. [`DONE-031-0.0.9`][kanban] settled the durable identity format (the model-anchored `GlobalID` default) and shipped the internal `decode_global_id` resolve-then-enforce dispatch. But a consumer still **cannot refetch a node by id** — there is no root `node(id:)` field, no `nodes(ids:)` batch field, no way to expose a relation as a connection, and no public helper to mint or decode a `GlobalID` in a test. The Relay contract that makes client frameworks (Relay Compiler, Apollo with the Node pattern) "just work" — *any* object with an `id` is refetchable through one canonical root field — is unmet, and both upstreams meet it: graphene-django's `DjangoObjectType.get_node` runs `cls.get_queryset(model.objects, info).get(pk=id)` behind its root Node field, and strawberry-graphql-django's `resolve_model_node(s)` run the type's `get_queryset` behind Strawberry's `relay.node()`. The card's parity tags are **Required** for both upstreams.

The assembly is not a thin wrapper over Strawberry's native root field. Strawberry's `relay.node()` dispatches via `GlobalID.resolve_type(info)` → `info.schema.get_type_by_name(type_name)` — a **GraphQL-type-name** schema lookup. Under the `0.0.9` model-anchored default, an emitted id carries `library.genre`, not `GenreType`; the native dispatch cannot decode it ([`spec-031`][spec-031] flagged exactly this and deferred the consumer to this card). The package must own the root-field dispatch through its own [`decode_global_id`][types-relay], which also enforces the per-type strategy contract and never trusts the client's claim of which type an id belongs to ([Decision 3](#decision-3--root-fields-dispatch-through-the-package-decode-not-strawberrys-native-node-field)).

The card also closes the relation gap: a Relay-shaped schema exposes collections as connections, but the package's generated relation fields are `list[T]`-only. The implicit relation-as-Connection upgrade converts every Relay-Node-shaped type's eligible many-side relations to a `<field>Connection` (with `Meta.relation_shapes` narrowing per relation), so the cookbook-shaped nested-connection queries the [`GOAL.md`][goal] astronomy showcase promises become expressible. Finally, the card hardens the configuration surface (six named schema-validation diagnostics) and ships the public `testing.relay` helpers that make the new durable ids testable by consumers.

## Borrowing posture

Per the [`START.md`][start] "do both libraries provide it? → foundational" test, the root Node field and relation connections are **foundational** — both upstreams ship them, and the card tags both parities Required. The package's additions on top (the model-label-aware dispatch, `Meta.relation_shapes`, the named diagnostics) are consequences of decisions already shipped, not new differentiation.

### Reference-package parity checkpoint

| Upstream | `django-strawberry-framework` | Status |
| --- | --- | --- |
| graphene-django `relay.Node.Field()` root field; `DjangoObjectType.get_node` runs `cls.get_queryset(...).get(pk=id)` | `DjangoNodeField` dispatching to the `get_queryset`-aware `resolve_node` default | **this card (`0.0.9`) — required parity** |
| strawberry-graphql-django: Strawberry `relay.node()` + `resolve_model_node(s)` running the type's `get_queryset` | `DjangoNodeField` / `DjangoNodesField` over the shipped `resolve_node` / `resolve_nodes` defaults | **this card (`0.0.9`) — required parity** |
| Both upstreams: relations exposable as connections (graphene-django `DjangoFilterConnectionField` on relations; strawberry-django `@strawberry_django.connection()` fields) | implicit relation-as-Connection upgrade + `Meta.relation_shapes` | **this card (`0.0.9`)** — the *implicit* default is package-shaped (declarative Meta, not per-field decorators) |
| (no model-anchored decode upstream) | root dispatch through `decode_global_id` (model-label + type-name + strategy enforcement) | this card — consequence of [`DONE-031-0.0.9`][kanban]'s beyond-parity encoding |

### From `graphene-django` — borrow the user-facing shape and the null contract

The one-line root field (`node = relay.Node.Field()` → `node: relay.Node | None = DjangoNodeField()`) and the visibility contract (`get_node` filters through `get_queryset`; an invisible row is `None`, not an error). The typed form's expected-type check mirrors graphene's `Node.Field(only_type)` posture of failing loud on a wrong-type id ([Decision 4](#decision-4--djangonodefield--djangonodesfield-a-bare-interface-form-and-a-typed-form) keeps the error but moves nothing else).

### From `strawberry-graphql-django` — borrow the runtime mechanism

The per-type-batched, order-preserving `nodes` resolution (group ids by resolved type, one `resolve_nodes` call per type, reassemble in input order with `null` holes) is Strawberry's own `NodeExtension.get_node_list_resolver` shape, which strawberry-django rides as-is; the package's `_order_nodes` already ports the order-preserving half. The relation-as-Connection runtime reuses the [`spec-030`][spec-030] machinery that was itself borrowed from Strawberry's `ListConnection`.

### Explicitly do not borrow

- **Strawberry's native `NodeExtension` dispatch.** `id.resolve_type(info)` is a GraphQL-type-name schema lookup; it cannot decode the model-label payload the package now emits by default, and it trusts the client-supplied type-name slot. The package owns the dispatch through `decode_global_id` ([Decision 3](#decision-3--root-fields-dispatch-through-the-package-decode-not-strawberrys-native-node-field)).
- **strawberry-django's decorator-per-field connection surface.** Connections on relations arrive declaratively (the implicit upgrade + `Meta.relation_shapes`), not as per-field `@strawberry_django.connection()` decorations — the package's reason to exist ([`START.md`][start] "Meta classes everywhere on consumer surfaces").
- **graphene-django's connection-on-list auto-wrapping internals.** The cursor/connection mechanics stay Strawberry's (`ListConnection`), per [`spec-030`][spec-030] Decision 9.

## User-facing API

### Root refetch fields

```python
import strawberry
from strawberry import relay

from django_strawberry_framework import DjangoNodeField, DjangoNodesField, finalize_django_types

from apps.library.schema import GenreType


@strawberry.type
class Query:
    # The Relay-spec canonical fields (interface-shaped):
    node: relay.Node | None = DjangoNodeField()
    nodes: list[relay.Node | None] = DjangoNodesField()

    # The typed single-node convenience (the GOAL.md astronomy shape):
    genre: GenreType | None = DjangoNodeField(GenreType)


finalize_django_types()
```

`node(id:)` decodes the `GlobalID` **server-side** (model-label `library.genre:42` or type-name `GenreType:42`, per the target's recorded strategy), dispatches to the resolved type's `resolve_node` — which runs [`get_queryset`][glossary-get_queryset-visibility-hook] — and returns `null` for a row the requesting user cannot see or that does not exist. `nodes(ids:)` resolves per-type batched and returns results in input order with `null` entries for missing / hidden ids. The root fields are **nullable by contract** ([Decision 5](#decision-5--null-for-invisible-rows-graphqlerror-for-malformed-ids)): the synthesized resolvers always dispatch `resolve_node` / `resolve_nodes` with `required=False`, so the documented annotation spelling is the optional one — `relay.Node | None` renders `node: Node`, `list[relay.Node | None]` renders `[Node]!`. The consumer's class-attribute annotation still drives the rendered SDL nullability (the [`DjangoListField`][glossary-djangolistfield] annotation mechanism), but a non-optional spelling does **not** switch the resolver onto a raising path — a missing or hidden row then surfaces as Strawberry's generic non-null violation, so the optional spelling is the supported shape.

### Relation-as-Connection upgrade

```python
class BookType(DjangoType):
    class Meta:
        model = models.Book
        fields = ("id", "title", "shelf", "genres", "loans")
        interfaces = (relay.Node,)
        primary = True


class GenreType(DjangoType):
    class Meta:
        model = models.Genre
        fields = ("id", "name", "books")
        interfaces = (relay.Node,)
        connection = {"total_count": True}
        # "connection" is the default for every eligible relation; "both" is the
        # explicit opt-in that keeps the raw list beside it:
        relation_shapes = {"books": "both"}   # or "connection" (the default) or "list" (drop the connection)
```

Because `GenreType` declares `"both"` for `books`, it exposes `books: [BookType!]!` **and** `booksConnection: BookTypeConnection!`; drop that entry and the default `"connection"` shape removes `books` from the SDL entirely, leaving `booksConnection` as the only way to reach a genre's books. The connection carries `first` / `after` / `last` / `before`, the target's sidecar-derived `filter:` / `orderBy:` arguments, and `totalCount` when the **target** declares [`Meta.connection`][glossary-metaconnection]` = {"total_count": True}`. Eligibility: the declaring type is Relay-Node-shaped, the relation is many-side (reverse FK, forward / reverse M2M), and the relation **target**'s type is Relay-Node-shaped. An eligible relation defaults to `"connection"`; a non-Node-target relation silently stays list-only under the default but raises [`ConfigurationError`][glossary-configurationerror] when `relation_shapes` explicitly requests `"connection"` / `"both"` for it.

### Error shapes

- `relay.GlobalID` (or `relay.NodeID`, `relay.Connection`, `relay.ListConnection`, `relay.Edge`, `relay.PageInfo`) in [`Meta.interfaces`][glossary-metainterfaces] → [`ConfigurationError`][glossary-configurationerror] at type creation **naming the helper** and what it actually is ([Decision 8](#decision-8--the-six-schema-validation-diagnostics)).
- A non-Strawberry-interface class in `Meta.interfaces` → [`ConfigurationError`][glossary-configurationerror] naming the class (shipped; re-affirmed).
- [`Meta.connection`][glossary-metaconnection] on a non-Relay-Node type → [`ConfigurationError`][glossary-configurationerror] with the add-`relay.Node`-or-inherit-it-directly remediation (shipped; re-affirmed).
- A `DjangoNodeField()` / `DjangoNodesField()` declaration on a schema with **no** registered Relay-Node-shaped [`DjangoType`][glossary-djangotype]s → [`ConfigurationError`][glossary-configurationerror] at finalization: `"node lookup configured but no Node types registered."`.
- [`Meta.relation_shapes`][glossary-metarelation_shapes] that is not a `dict[str, str]`, carries a value outside `{"list", "connection", "both"}`, names an unknown / non-relation / single-valued field, names a **consumer-authored** relation (overrides own the field's shape), is declared on a non-Relay-Node type, or explicitly requests a connection over a non-Node-shaped target → [`ConfigurationError`][glossary-configurationerror] (shape, key-name, and consumer-authored failures at type creation; target-shape failures at finalization, where relation targets are settled).
- A generated `<field>_connection` name colliding with a model field or consumer-declared attribute → [`ConfigurationError`][glossary-configurationerror] at finalization naming the collision and the `relation_shapes = {"<field>": "list"}` opt-out.
- A malformed / undecodable / strategy-forbidden `GlobalID` fed to `node(id:)` / `nodes(ids:)` → `GraphQLError("Invalid GlobalID: ...", extensions={"code": "GLOBALID_INVALID"})` (the internal [`ConfigurationError`][glossary-configurationerror] is caught and converted at the field boundary — reachable only because the argument is `strawberry.ID`, not `relay.GlobalID`, so malformed base64 reaches the package instead of Strawberry's upstream `convert_argument`; [Decision 4](#decision-4--djangonodefield--djangonodesfield-a-bare-interface-form-and-a-typed-form) / [Decision 5](#decision-5--null-for-invisible-rows-graphqlerror-for-malformed-ids)). In a `nodes(ids:)` batch, a malformed id **anywhere** fails the whole field (the `[Node]!` non-null nulls the enclosing `data`); positional `null` is reserved for well-formed-but-invisible/missing ids ([Decision 5](#decision-5--null-for-invisible-rows-graphqlerror-for-malformed-ids)).
- A **well-formed** id whose `node_id` cannot coerce to the type of the target's id slot (e.g. `library.genre:abc`) → `null` (single) / a positional `null` hole (batch), via the id-slot pre-coercion in `relay.py` — the concrete field behind the target's `resolve_id_attr()`, not `model._meta.pk` unconditionally; no query is issued and no Django `ValueError` or backend `OverflowError` leaks ([Decision 5](#decision-5--null-for-invisible-rows-graphqlerror-for-malformed-ids)). This is an *existence* outcome (the literal identifies no row), not a malformed-id error.
- A typed `DjangoNodeField(GenreType)` receiving an id that decodes to a different type → `GraphQLError` naming the expected and received types; the typed `DjangoNodesField(GenreType)` batch fails the whole field the same way on any wrong-type id ([Decision 4](#decision-4--djangonodefield--djangonodesfield-a-bare-interface-form-and-a-typed-form)).
- `first` + `last` together on any connection → the shipped `GraphQLError` (re-affirmed by the conformance suite).
- An async [`get_queryset`][glossary-get_queryset-visibility-hook] reached from a sync execution context → [`SyncMisuseError`][glossary-syncmisuseerror], raised by the `resolve_node` / `resolve_nodes` defaults and passed through the root fields unchanged.
- A **consumer** `resolve_node` / `resolve_nodes` override returning an awaitable under `schema.execute_sync()` → [`SyncMisuseError`][glossary-syncmisuseerror] raised by the root field itself, naming the type and method and carrying the recourse `"DjangoNodeField and DjangoNodesField execute resolve_node(s) synchronously under schema.execute_sync(); make the consumer override synchronous or run the schema asynchronously."` The orphaned coroutine is closed rather than treated as a result ([Decision 5](#decision-5--null-for-invisible-rows-graphqlerror-for-malformed-ids)).
- A consumer `resolve_nodes` override returning a list that is not positionally 1:1 with the `node_ids` it received → [`ConfigurationError`][glossary-configurationerror] naming the type, the row count returned, and the id count requested. A generator / iterator return is materialized before the check, so it reaches the check rather than dying on a bare `len()` ([Decision 4](#decision-4--djangonodefield--djangonodesfield-a-bare-interface-form-and-a-typed-form)).
- A `nodes(ids:)` list longer than the request's resource policy allows, or an operation whose cooperative execution deadline has already passed → the policy's own rejection error ([Edge cases and constraints](#edge-cases-and-constraints)).

### Decision 3 — Root fields dispatch through the package decode, not Strawberry's native node field

`DjangoNodeField` / `DjangoNodesField` synthesize their own resolvers that call [`types/relay.py::decode_global_id`][types-relay] and then dispatch to the resolved type's `resolve_node` / `resolve_nodes` classmethods. They do **not** wrap Strawberry's `relay.node()` field.

Both fields call the cooperative execution-deadline check before handing work to the database, and the **placement is the contract**: `DjangoNodeField` checks before the decode, because the decode is the step that makes a visibility-scoped query inevitable; `DjangoNodesField` checks *after* its empty-list short circuit — so a request asking for nothing is never rejected for the deadline — and before the batch decode that leads to one query per decoded type ([Edge cases and constraints](#edge-cases-and-constraints)).

Rationale companion — this Decision's justification and its three rejected alternatives: [Decision 3][rationale-d3].

### Decision 4 — `DjangoNodeField` / `DjangoNodesField`: a bare interface form and a typed form

Both factories accept an **optional** target type:

- **Bare form** — `node: relay.Node | None = DjangoNodeField()` / `nodes: list[relay.Node | None] = DjangoNodesField()`: the Relay-spec canonical fields. The decoded id may resolve to *any* registered Relay-Node-shaped [`DjangoType`][glossary-djangotype]; the consumer's class-attribute annotation (the `relay.Node` interface) drives the GraphQL field type, mirroring [`DjangoListField`][glossary-djangolistfield]'s annotation-driven contract. Concrete-type routing is **not** left to the shipped isinstance-based `is_type_of` injection alone: for a model carrying two registered Relay types, `isinstance(obj, (type_cls, model))` answers `True` on both candidates, so candidate iteration order — not the id — would pick the `__typename`. The root fields therefore **stamp** the decode-resolved [`DjangoType`][glossary-djangotype] on each fetched instance, and `install_is_type_of`'s closure honors that stamp before its isinstance fallback, so `__typename` follows the type the `GlobalID` named. Model instances are shallow-copied before stamping, so a consumer reusing the same ORM object in another field or request never retains a stale routing hint; `None` (hidden / missing / uncoercible → `null`) passes through untouched; and the stamp is best-effort on a non-model or `__slots__` object a consumer override may return, which falls back to the isinstance behavior. Unstamped instances — relation resolvers, consumer resolvers — are unaffected.
- **Typed form** — `genre: GenreType | None = DjangoNodeField(GenreType)`: the [`GOAL.md`][goal] astronomy showcase shape. Note the showcase currently spells it **non-optional** (`galaxy: GalaxyNode = DjangoNodeField(GalaxyNode)`, and the same for `celestial_body`), which is the shape [Decision 5](#decision-5--null-for-invisible-rows-graphqlerror-for-malformed-ids) declares *unsupported* — a missing/hidden row under a non-optional annotation surfaces Strawberry's generic non-null violation rather than the Relay `null`. Slice 7 flips both `GOAL.md` showcase fields to `… | None` so the `1.0.0` showcase models the supported nullable-by-contract spelling ([Doc updates](#doc-updates)). Construction-time validation reuses the shared [`list_field.py::_validate_djangotype_target`][list-field] guards plus the connection-style fifth guard (the target must be Relay-Node-shaped, via the canonical `_is_relay_shaped` predicate). At request time, an id that decodes to a **different** type raises `GraphQLError` naming the expected and received types; a matching id dispatches to the target's `resolve_node` as usual. `DjangoNodesField(GenreType)` is the typed batch sibling with the same per-id check — a wrong-type id anywhere in the batch fails the **whole field** with that `GraphQLError` (the `[Node]!` non-null nulls the enclosing `data`), not a per-position `null`, since the mismatch is a client bug detected before any query (consistent with the single typed field, and parallel to the malformed-id whole-field failure in [Decision 5](#decision-5--null-for-invisible-rows-graphqlerror-for-malformed-ids)).
- **Argument spelling** — both factories declare their id argument as `strawberry.ID` (`id: strawberry.ID` / `ids: list[strawberry.ID]`), **not** `relay.GlobalID`. Strawberry special-cases a `relay.GlobalID`-annotated argument in `strawberry/types/arguments.py::convert_argument` (`if type_ is GlobalID: return GlobalID.from_id(value)`) during argument conversion — *before* the resolver runs — so a malformed base64 / non-`type:id` payload would raise Strawberry's engine-owned `GlobalIDValueError` upstream of the package, bypassing the [Decision 5](#decision-5--null-for-invisible-rows-graphqlerror-for-malformed-ids) `GLOBALID_INVALID` contract entirely. Declaring `strawberry.ID` hands the resolver the raw string, which [`decode_global_id`][types-relay] (typed `relay.GlobalID | str`) parses, so the package owns *every* failure shape uniformly. The rendered SDL is byte-identical: under Strawberry's modern `relay_use_legacy_global_id = False` default (`strawberry/schema/config.py`) the `GlobalID` scalar already renders as `ID`, so `node(id: ID!)` is exactly what either annotation produces — and is the Relay spec's literal signature.
- **`nodes` semantics** — `ids: [ID!]!`; results in input order; missing / hidden ids become `null` entries (so the return annotation is `list[relay.Node | None]`, rendering `[Node]!`); duplicate ids are resolved per position (each occurrence gets its row); resolution is **batched per distinct type** — ids are grouped by their decoded type and each type's `resolve_nodes` runs once (the shipped order-preserving `_order_nodes` reassembly), mirroring Strawberry's `get_node_list_resolver` grouping. In async context the synthesized `nodes` resolver returns a single gathering coroutine over the per-type `resolve_nodes` calls (per-call `in_async_context()` dispatch — [Edge cases and constraints](#edge-cases-and-constraints)), not a pass-through of the defaults' values. The per-type call is the `resolve_nodes` **classmethod**, so a consumer override is preserved — and the reassembly indexes each result by its within-group position, which makes the override's return shape a **contract**: it must be input-ordered and 1:1 with the `node_ids` it received, `None` for missing. The obvious `get_queryset().filter(pk__in=node_ids)` spelling violates it (unordered, shrunk for missing ids, `IndexError` on duplicates), so a wrong-length return is rejected with a [`ConfigurationError`][glossary-configurationerror] naming the type rather than silently producing wrong rows; a generator / iterator return is materialized first so it reaches that check. Ordering itself is the documented override obligation, not re-validated.

Rationale companion — this Decision's justification and its three rejected alternatives: [Decision 4][rationale-d4].

### Decision 5 — Null for invisible rows, GraphQLError for malformed ids

Two failure families with two contracts:

- **Visibility / existence failures → `null`.** A well-formed id whose row is hidden by [`get_queryset`][glossary-get_queryset-visibility-hook] or absent from the database resolves to `null` (bare and typed forms; a `null` list entry for `nodes`). Hidden and missing rows traverse the **same** code path — the filtered queryset's `qs.first()` (`required=False`) — so neither error shape nor timing distinguishes "exists but hidden" from "does not exist" (the card: "never reveal *existence* of hidden rows through error timing or status codes"). The dispatch is `required=False` **unconditionally**: field nullability never routes the resolver onto the raising `qs.get()` / `DoesNotExist` path, so the root fields are nullable by contract and the optional annotation spelling is the supported one.
- **Uncoercible-pk failures → `null` (existence family).** [`decode_global_id`][types-relay] validates payload **shape**, not id-literal validity: `library.genre:abc` decodes cleanly to `(GenreType, "abc")`, but `abc` is not a valid integer pk. The shipped [`types/relay.py::_coerce_node_id`][types-relay] only unwraps a `relay.GlobalID` wrapper — it does **not** coerce the literal to the target's Python type — so a raw `qs.filter(pk="abc")` would raise Django's `ValueError: Field 'id' expected a number but got 'abc'`, leaking ORM internals on a path no caller could reach before this card wired the first consumer. `relay.py` therefore **pre-coerces** the decoded `node_id` and treats a coercion failure as "identifies no row" → `null` (single) / a positional `null` hole (batch, coerced per id so one garbage entry does not poison the whole `pk__in`). Two properties of that pre-coercion are load-bearing:
  - **Which field it coerces against is the id slot, not `model._meta.pk`.** The coercion field is the concrete field behind `resolved_type.resolve_id_attr()` — the same one the dispatch then filters on (`"pk"` maps to `model._meta.pk`; any other value resolves through `model._meta.get_field`; a `relay.NodeID` over a non-concrete attr has no column, skips coercion, and passes the raw literal through). They coincide for the default and diverge for a consumer `id: relay.NodeID[...]` annotation, which is also the documented composite-pk escape hatch where `_meta.pk` is a `CompositePrimaryKey` with no single-column `to_python`. Coercing against `_meta.pk` there would **mis-type** the value — `"007"` becomes `7`, which then filters `code=7` and not `code="007"` — or spuriously reject a literal an existing row carries. A builder who reads only "pre-coerce to the pk type" writes exactly that bug.
  - **The coercion is `to_python` *then* `run_validators`.** `to_python` is a pure type cast and does not range-check, so a syntactically valid but out-of-range literal would otherwise reach the query and raise a raw backend `OverflowError`; running the field's own validators rejects it here, before any query. The mechanics are the shared [`utils/querysets.py::coerce_field_value_or_none`][querysets] primitive, so the node field, the raw relation-pk coercion, and the `__in` filter member coercion cannot drift apart; picking *which* field to coerce against stays at each call site.

  No query is issued for an uncoercible id, so the no-existence-oracle property is unaffected — its equal-query-count pin concerns *coercible* ids, which all reach the one shared queryset path. This matches graphene-django, whose node resolver swallows resolution exceptions to `None`.
- **Format / decode failures → `GraphQLError`.** A malformed base64 string, a non-`type:id` payload, an unresolvable model label / type name, a payload shape the resolved type's strategy forbids, or a candidate with no recorded strategy — every [`ConfigurationError`][glossary-configurationerror] from [`decode_global_id`][types-relay] — is caught at the field boundary and re-raised as `GraphQLError("Invalid GlobalID: <reason>", extensions={"code": "GLOBALID_INVALID"})`. Decode runs entirely on payload data (no database access), so the error reveals nothing about any row. **This contract is reachable only because the argument is declared `strawberry.ID`** (the raw string), not `relay.GlobalID` ([Decision 4](#decision-4--djangonodefield--djangonodesfield-a-bare-interface-form-and-a-typed-form) Argument-spelling): a `relay.GlobalID` argument is parsed by Strawberry's `convert_argument` *before* the resolver, so malformed base64 / bad-shape payloads would raise the engine's `GlobalIDValueError` upstream with no `GLOBALID_INVALID` code and `decode_global_id`'s string-parsing branch would be dead code. **Catch scope is narrow:** the `try` / `except ConfigurationError` → convert wraps the `decode_global_id` call **only**; the subsequent `resolve_node` / `resolve_nodes` dispatch (and the id-slot pre-coercion above) run *outside* it. This matters because [`SyncMisuseError`][glossary-syncmisuseerror] subclasses [`ConfigurationError`][glossary-configurationerror] (`class SyncMisuseError(ConfigurationError, RuntimeError)`): an async [`get_queryset`][glossary-get_queryset-visibility-hook] met from a sync context is a *server misconfiguration*, must surface as `SyncMisuseError` (DoD item 3's pass-through), and must **never** be mislabeled `GLOBALID_INVALID` — a blanket try/except around the whole resolver body would silently break that, so the boundary scopes the decode call alone.
- **An awaitable in a sync context → `SyncMisuseError`, from either of two sources.** The first is inherited and unchanged: the `resolve_node` / `resolve_nodes` defaults raise [`SyncMisuseError`][glossary-syncmisuseerror] when a consumer's `get_queryset` is async and the sync branch reaches it. The second is the root field's own — a **consumer** `resolve_node` / `resolve_nodes` override that returns an awaitable while `in_async_context()` is false. The whole ORM pipeline runs synchronously there, so the coroutine can never be awaited; treating a truthy coroutine as a resolved row would return a nonsense value for every id, so the field rejects it, closes the orphaned coroutine, and names the type, the method, and the recourse (`"DjangoNodeField and DjangoNodesField execute resolve_node(s) synchronously under schema.execute_sync(); make the consumer override synchronous or run the schema asynchronously."`). Both sources sit **outside** the decode catch-convert boundary above, so neither is ever mislabeled `GLOBALID_INVALID`.
- **Batch decode failures fail the whole field.** A malformed / undecodable id **anywhere** in a `nodes(ids:)` batch raises `GLOBALID_INVALID` for the **whole field** — decode runs over every id before any query, and the `[Node]!` non-null return propagates the error to null the enclosing `data` rather than producing a per-position malformed hole. Positional `null` is reserved exclusively for well-formed ids that are hidden or missing (a visibility/existence outcome); a malformed id is a *request* error and is never silently absorbed into a `null` slot. The typed batch form's wrong-type id ([Decision 4](#decision-4--djangonodefield--djangonodesfield-a-bare-interface-form-and-a-typed-form)) fails the whole field the same way.

Rationale companion — this Decision's justification and its five rejected alternatives: [Decision 5][rationale-d5].

### Decision 6 — Relation-as-Connection synthesis at finalization Phase 2.5

A new finalizer step (after `install_globalid_typename_resolver`, before Phase 3 decoration) synthesizes the relation connections: for each Relay-Node-shaped type, walk the selected many-side relations (reverse FK, forward / reverse M2M — the [Relation handling][glossary-relation-handling] many-side set); for each whose resolved **target** type is Relay-Node-shaped, apply the resolved shape (`Meta.relation_shapes` entry, else `"connection"`):

- `"connection"` — **the default.** Add `<field>_connection` (camel-cased to `<field>Connection` by Strawberry); remove the generated `list[T]` annotation and the Phase-2 list resolver for the relation, before Phase 3 freezes the annotation set, so the SDL never carries the list form.
- `"both"` — add `<field>_connection` **and** keep the generated `list[T]` field. An explicit opt-in, not a shape a schema receives.
- `"list"` — synthesize nothing.

**Why the default suppresses the list rather than adding beside it.** A raw many-side list has no cursor and therefore no page of its own, so a `list[T]` emitted *beside* a bounded connection is a way around that connection's cap — a client selects the sibling instead. Connection-only is therefore the shape a Relay-Node-shaped type gets by default, and the raw list is what `"both"` opts back in; the list `"both"` produces is row-bounded by the request policy ([`resource_policy.py::bounded_rows`][resource-policy]) rather than unbounded. A builder who implements this step as "add a connection beside the list" reintroduces the bypass while every test about the connection still passes.

The synthesized field is `relay.connection(_connection_type_for(target_type), resolver=<relation resolver>)` — the [`spec-030`][spec-030] factory pieces verbatim, with one difference: the resolver body seeds the pipeline from the **parent's relation manager** (`getattr(root, <accessor>).all()`) instead of `model._default_manager.all()`, then runs the same tail (target [`get_queryset`][glossary-get_queryset-visibility-hook] → `filter` → `orderBy` → deterministic pk-order → optimizer seam → cursor slice). The synthesized signature carries the **target**'s sidecar-derived `filter:` / `order_by:` arguments (the shipped `_synthesized_signature`), and `totalCount` follows the target's [`Meta.connection`][glossary-metaconnection] (type-level, one stable connection shape per node type — the `_connection_type_for` cache is reused as-is). Name collisions (`<field>_connection` already a model field, a consumer-declared attribute, or another synthesized name) raise [`ConfigurationError`][glossary-configurationerror] naming the collision and the `"list"` opt-out — and the guard checks the **GraphQL surface, not only Python attributes**: the generated name and every existing field name are compared both as Python attributes and as their camel-cased GraphQL names under Strawberry's default `NameConverter` / `auto_camel_case=True` rule, so a consumer-authored `booksConnection` attribute collides with a generated `books_connection` even though the Python names differ. The schema's actual `StrawberryConfig` does not exist at finalization time (`strawberry.Schema(...)` is constructed *after* [`finalize_django_types`][glossary-finalize_django_types]), so a non-default `name_converter` / `auto_camel_case=False` configuration is outside the guard's reach — such a collision falls through to Strawberry's own schema-build duplicate-field error, documented as a known constraint ([Edge cases and constraints](#edge-cases-and-constraints)).

**The resolver is built from three arguments, and each one is load-bearing.** `_build_relation_connection_resolver(target_type, accessor_name, relation_field_name, declaring_type)`:

- the **accessor** ([`utils/relations.py::instance_accessor`][relations]) is what rows are read through on the instance. For a reverse relation declared without `related_name` it DIVERGES from the relation field name — Django's `ForeignObjectRel.name` is the related *query* name (`book`) while the instance attribute is `get_accessor_name()` (`book_set`) — so `getattr(root, field.name)` raises `AttributeError` there. Every fakeshop fixture sets `related_name`, which is exactly why the split stays invisible until a consumer omits one.
- the **relation field name** stays the GraphQL vocabulary: it names the generated field, feeds the collision guard, and is the key the [`DONE-033-0.0.9`][kanban] walker builds its window `to_attr` from. Probing the accessor instead would silently never hit the windowed page.
- the **declaring type** is the iterated `type_cls`, deliberately **not** `registry.get(model)`. It is the `parent_type` the walker keyed the planned connection's strictness/plan key under, so passing the type that actually declared the relation keeps a divergent secondary type's key honest rather than aliasing it onto the primary's.

**The step is re-entrant, and that is a contract, not an implementation detail** — [`finalize_django_types`][glossary-finalize_django_types] documents a re-call as the recovery path after a partial failure, so Phase 2.5 must survive running twice over the same class:

- Every synthesized field object carries a package-private marker attribute. A rerun recognizes its own prior attachment through it and skips rather than misreading the field as a name collision — and, for a `"connection"` shape, re-removes the list form that the rerun's Phase 2 re-attached, since leaving a re-attached, now-unannotated relation resolver in place breaks Phase 3.
- The `generated -> relation field name` mapping is recorded on the declaring [`DjangoTypeDefinition`][definition] (a `relation_connections` slot) so the [`DONE-033-0.0.9`][kanban] walker can recognize and window-plan the nested connection. It is written on first attach **and re-written on the re-entrant path**, because a fresh partial-finalize pass may have lost the slot; suppressed shapes (`"list"`, non-Node target, consumer-authored) record nothing, which is what makes the slot's presence meaningful.
- Each attachment registers an **identity-safe teardown** with the registry, so `registry.clear()` removes the synthesized field and restores the pre-synthesis annotations and the suppressed list resolver. Identity-safe means it recognizes only the two framework-owned objects it created (the `StrawberryField` and the resolver function `strawberry.type` replaces it with) and restores a suppressed value only into a slot still vacant — a consumer replacement made after finalization is never clobbered. This is class hygiene for the fresh-registry lifecycle, not a general unfinalizer.

### Decision 7 — `Meta.relation_shapes` is a net-new `ALLOWED_META_KEYS` key, stored on the definition

`Meta.relation_shapes` lands **directly** in [`ALLOWED_META_KEYS`][base] (NOT a `DEFERRED_META_KEYS` promotion) — the net-new-key rule of [`spec-031`][spec-031] Decision 6 / [`spec-030`][spec-030] Decision 8: the key ships functional in the same card that adds it. A `_validate_relation_shapes(meta, value, relay_shaped)` helper (called from [`_validate_meta`][base], structurally modeled on `_validate_connection`) owns the shape checks and the Relay-Node gate; the field-level name checks (the fourth and fifth bullets below) run in a stage-2 `_validate_relation_shape_targets` helper called from `__init_subclass__` after `_select_fields` / `consumer_authored_fields` exist — the [`spec-029`][spec-029] `nullable_overrides` two-stage precedent, since the selected-field set and the consumer-override union do not exist at `_validate_meta` time. The combined contract:

- `None` (absent) → `None` (every eligible relation defaults to `"connection"` at synthesis time);
- a non-`dict`, non-`str` keys, or values outside `{"list", "connection", "both"}` → [`ConfigurationError`][glossary-configurationerror] naming the offending entry and listing the valid shapes (typo guard);
- the key on a non-Relay-Node type (the precomputed `relay_shaped` bool, the same predicate `Meta.connection` uses) → [`ConfigurationError`][glossary-configurationerror] ("`Meta.relation_shapes` requires a Relay-Node-shaped type; add `relay.Node` to `Meta.interfaces` or remove the key");
- key names referencing unknown model fields, non-relation fields, single-valued relations (forward FK / OneToOne — there is nothing to paginate), or fields excluded from the selected set → [`ConfigurationError`][glossary-configurationerror] naming the field and the reason. Name-existence checks run at type creation (mirroring the [`Meta.optimizer_hints`][glossary-metaoptimizer_hints] typo guard); the target-is-Node-shaped check runs at finalization (targets resolve there — [Decision 6](#decision-6--relation-as-connection-synthesis-at-finalization-phase-25));
- a key naming a **consumer-authored** relation (an annotation or `strawberry.field` override in the `consumer_authored_fields` set, computed in the same `__init_subclass__` pass) → [`ConfigurationError`][glossary-configurationerror] at type creation explaining that consumer overrides own the field's shape. Without this rule an explicit `relation_shapes = {"books": "connection"}` over a consumer-authored `books` would be accepted and then silently skipped by the synthesis — neither adding `booksConnection` nor suppressing the list — violating the explicit-request fail-loud posture the non-Node-target and collision rules already follow. The **implicit** default continues to silently skip consumer-authored relations, whatever that default is (the shipped override contract outranks the upgrade; only an explicit request fails loud).

The normalized dict is stored on [`DjangoTypeDefinition`][definition] (a new `relation_shapes` slot, populated in `__init_subclass__` like the `connection` / `filterset_class` / `orderset_class` / `globalid_strategy` slots), so the Phase-2.5 synthesis reads the per-type declaration from the canonical definition record.

### Decision 8 — The six schema-validation diagnostics

The card's DoD requires "six schema-validation diagnostics … with the documented messages." This spec pins the enumeration — the six are the six `strawberry.relay` **non-interface helpers**, each rejected by name when found in [`Meta.interfaces`][glossary-metainterfaces]:

1. `relay.GlobalID` — "a scalar-like id wrapper, not an interface; Relay-Node-shaped types get `id: GlobalID!` automatically from `relay.Node`."
2. `relay.NodeID` — "an annotation helper for custom id fields (`id: relay.NodeID[int]`), not an interface."
3. `relay.Connection` — "a generic output type; declare [`Meta.connection`][glossary-metaconnection] / use [`DjangoConnectionField`][glossary-djangoconnectionfield] for connection shapes."
4. `relay.ListConnection` — same remediation as `Connection`.
5. `relay.Edge` — "a generic output type the connection machinery instantiates; not consumer-declarable."
6. `relay.PageInfo` — "a generated pagination type; not an interface."

All six already *fail* today through `_validate_interfaces` — five through the generic "is not a Strawberry interface" branch (none carries `is_interface=True`), `NodeID` through the earlier non-class branch because it is a `typing.Annotated` alias, not a class ([Current state](#current-state)); Slice 1 adds a named branch that fires **first** (before the non-class branch, so `NodeID` is named too), so the message tells the consumer what the helper is and what they probably meant (`relay.Node`). Two further diagnostics the card body lists are **already shipped** and get re-affirmation pins, not new code: the non-Strawberry-interface-class rejection naming the offending class, and the `Meta.connection`-on-non-Node rejection with the documented remediation. One is **net-new in Slice 2**: a declared `DjangoNodeField()` / `DjangoNodesField()` on a registry with no Relay-Node-shaped types raises at finalization with the card's exact message — `"node lookup configured but no Node types registered."` — backed by a module-level ledger both factories append to (`registry.clear()` co-clears it; the `_helper_referenced_filtersets` / `_helper_referenced_ordersets` precedent).

### Decision 9 — Cursor mechanics stay delegated to Strawberry; this card pins the conformance contract

No new cursor code ships. The cursor remains Strawberry's `ListConnection` opaque payload — `to_base64("arrayconnection", <offset>)` — documented as **opaque** (clients must not parse it), with `relay_max_results` (via [`strawberry_config`][glossary-strawberry_config] passthrough, default 100) capping page sizes under the request policy's [`max_page_size`][resource-policy] ceiling ([Edge cases and constraints](#edge-cases-and-constraints)). What this card adds is the **conformance suite**: tests pinning the Relay-spec edge cases the card enumerates, against both a root [`DjangoConnectionField`][glossary-djangoconnectionfield] and a synthesized relation connection:

- `first: 0` → empty `edges` + well-formed `pageInfo`.
- `first: N` where N exceeds the remainder → the actual remainder, `hasNextPage: false`.
- An `after` cursor whose row was deleted → the query does **not** error. That no-error property is the **only** guarantee pinned: the locked Strawberry `SliceMetadata.from_arguments` decodes `after` to a numeric offset (`start = int(after) + 1`) — the cursor encodes a *position*, not a row identity — so inserts/deletes before that position can skip or duplicate rows between page requests. [`spec-030`][spec-030] carries the same corrected contract ([its rationale companion][spec-030-rationale-revisions]); the suite must not assert "falls through to the next existing row" or any other keyset-cursor property the implementation deliberately defers to `Meta.cursor_field`.
- `first` + `last` together → the shipped `GraphQLError`. (Re-affirmed for `totalCount`-opted connection types; the Slice-4 build discovered the guard was **schema-bypassed for bare connection types** — when `_connection_type_for` returned the bare `DjangoConnection[T]` generic alias, Strawberry's schema-build generic specialization copies the connection type into a plain specialized class whose `resolve_connection` is `ListConnection`'s, dropping the package override, so `first` + `last` resolved silently. Probe-verified at the root `DjangoConnectionField` level against the locked Strawberry `0.316.0`. Slice 4 ships the root-cause fix: `_connection_type_for` **always** returns a generated concrete `<TypeName>Connection` subclass of `DjangoConnection[T]` — concrete classes are used as-is by the schema build, so the override always survives — with the bare variant carrying no `totalCount` member and preserving the inherited `"A connection to a list of items."` SDL description for byte-identical SDL versus the shipped bare-alias surface.)
- `pageInfo` four-field correctness (`hasNextPage`, `hasPreviousPage`, `startCursor`, `endCursor`), **including** that `hasNextPage` is computed correctly on a `pageInfo`-only query — one that does **not** request `edges`. (A GraphQL response omits unrequested fields, so "unrequested `hasNextPage`" is unobservable; the real, non-trivial edge is the inverse selection. Strawberry's `ListConnection.resolve_connection` consults the selection set via `strawberry/relay/utils.py::should_resolve_list_connection_edges`, whose skip-resolution path fires only when **both** `edges` and `pageInfo` are absent from the selection — so a `pageInfo`-only query still walks the pagination window, exactly where a lazy implementation could miscompute `hasNextPage`.)
- Backward pagination (`last` / `before`) honoring the Relay spec.

The card's `b64("offset:N")` wording is read as the *conceptual* cursor shape; the byte-exact payload is Strawberry's `arrayconnection:N`. Both are opaque base64 offset cursors; the spec records the discrepancy rather than changing the shipped format ([Risks and open questions](#risks-and-open-questions)). **`Meta.cursor_field` (stable column-keyed cursors) is outside this card's scope** — the card puts it on [`BACKLOG.md`][backlog] item 39 sub-feature 3 and this Decision ships no cursor code of any kind. The scope statement is about the card and stays true; the backlog placement did not: the keyset surface has since shipped ([`keyset.py`][keyset]), so a connection whose target type declares [`Meta.cursor_field`][base] slices through the package's keyset seam rather than the offset payload this Decision delegates. Nothing here changed to accommodate it — the delegation is what made the later opt-in additive.

Rationale companion — this Decision's justification and its one rejected alternative: [Decision 9][rationale-d9].

### Decision 10 — Public `testing/relay.py` helpers and the export gate

A new [`django_strawberry_framework/testing/relay.py`][testing-init] ships exactly the two helpers the card's DoD names:

- **`global_id_for(type_cls, id) -> str`** — the encoded `GlobalID` string a finalized Relay-Node-shaped type emits for a pk: reads the definition's recorded `effective_globalid_strategy` and computes the strategy-appropriate payload (`model` / `type+model` → `model._meta.label_lower`; `type` → `graphql_type_name`), then base64-encodes via Strawberry's own `GlobalID`. For a `callable` / `custom` strategy it raises [`ConfigurationError`][glossary-configurationerror] — those encoders run on a live `root` instance the helper does not have, so it cannot promise the emitted payload (the encoder signature is `(type_cls, model, root) -> str` and never receives `info`). Non-finalized / non-Relay-Node inputs raise [`ConfigurationError`][glossary-configurationerror] with cause-discriminated remediations: an **unfinalized** type gets the finalize-first remediation (call `finalize_django_types()` / build the schema — the strategy is stamped at finalization), while a **finalized non-Relay-Node** type gets the Relay-gate remediation (add `relay.Node` to `Meta.interfaces`) — the two spec-named tests pin the two causes separately.
- **`decode_global_id(gid) -> tuple[type, str]`** — the public re-export of [`types/relay.py::decode_global_id`][types-relay] (same uniform-[`ConfigurationError`][glossary-configurationerror] contract; the internal helper's signature is already consumer-shaped).
- **The pair is intentionally asymmetric for secondary model-label emitters**. `global_id_for` answers "what does this type emit" — so for a **secondary** [`Meta.primary`][glossary-metaprimary]`= False` type under `model` / `type+model` it emits the same `app_label.modelname:<pk>` payload the live type emits — while `decode_global_id` of a model-label payload resolves through `registry.get(model)` to the **primary** type (the shipped [`DONE-031-0.0.9`][kanban] dispatch; the model-label-routing audit guarantees the primary can decode it). `decode_global_id(global_id_for(T, pk)) == (T, str(pk))` therefore holds **only** when `T` is the lone/primary type of its model (model-label strategies) or when `T` is on the `type` strategy (type-name payloads decode by `graphql_type_name` back to `T` itself). A secondary model-label emitter round-trips to `(primary_type, str(pk))` — the documented contract, not a bug, and exactly the routing a live `node(id:)` performs on the same id.

This satisfies the package's tested-usage promotion discipline ([`spec-031`][spec-031] [Decision 11][spec-031-rationale-d11] withheld the public export because "no shipped `0.0.9` consumer" existed): this card ships the consumer (the root fields) and the live fakeshop usage, so the public surface is earned. The helpers live under `testing/` (not the package root) because their audience is consumer *test suites* — the card's own DoD places them at `django_strawberry_framework.testing.relay`.

### Decision 11 — Module and test-file locations

- **Source:** `DjangoNodeField` / `DjangoNodesField` and the root-resolver synthesis land in a **new top-level [`django_strawberry_framework/relay.py`][relay-toplevel]** — the card's Files-likely-touched location, the home [`spec-031`][spec-031] [Decision 11][spec-031-rationale-d11] explicitly reserved for this card, and the sibling of the same-shaped `connection.py` / `list_field.py` flat factory modules. The encode/decode internals **stay** in [`types/relay.py`][types-relay] (shipped there by `031`); the new module imports them. The module is the home of the **whole typed-`GlobalID` consumption contract**, not only the root fields: alongside the two factories it holds `decode_model_global_id` and its `DecodeResult` / `GlobalIDDecode` result types — the non-raising decode + expected-model check + id coercion the mutation, form, and serializer flavors all consume — and `_resolve_real_pk`. That split lives here because READ and WRITE need different things from one decode: the READ node field filters `{id_attr: value}` and works off the row, so it never needs a primary key, while every WRITE consumer uses the result as an actual pk (`get(pk=...)`, a relation `pk__in` visibility query, an FK / M2M assignment), so a consumer `id: relay.NodeID[...]` over a non-pk column must be resolved to the real pk first. Keeping both in one module is what lets the two share `_node_id_slot` and `_coerce_pk_or_none` rather than growing divergent copies of the id-slot rule. `testing/relay.py` is the public-helper home per [Decision 10](#decision-10--public-testingrelaypy-helpers-and-the-export-gate). The finalizer synthesis step and the `Meta.relation_shapes` validation land in [`types/finalizer.py`][finalizer] / [`types/base.py`][base] respectively (the card's list).

A strict [`docs/TREE.md`][tree] mirror would instead demand a single `tests/test_relay.py` for the one new flat module. Relation-shapes *key validation* tests sit with the other `Meta` validation in [`tests/types/test_base.py`][test-types-base].

### Decision 12 — Sequencing against the connection-aware optimizer and the library-first activation

Two sequencing constraints shape Slices 3–6:

- **Connection-aware planning and the strictness-mode interaction are [`DONE-033-0.0.9`][kanban]'s, not this card's** ([Non-goals](#non-goals)). Consequences pinned here: (a) this card's live nested-connection tests assert **behavior** (right rows, right pagination, right `totalCount`), never SQL shape — the SQL-shape assertions are `033`'s deliverable; (b) no shipped example converts an *optimizer-dogfooding* surface to connections in this card (the products conversion is deferred out of this card's diff); (c) the synthesized relation resolver seeds from the relation manager precisely so `033`'s window-pagination planning has a cooperation seam.

  **This posture is a statement about this card's scope, and it stands. What it deferred *to* has since been discharged, and by a different route than the deferral named.** `DONE-033-0.0.9` shipped in the same joint `0.0.9` cut, so every one of the three consequences above has an owner that closed it: the deferred SQL-shape assertions over the nested `booksConnection` / `genresConnection` landed in `033`'s live library slice; strictness now flags an unplanned, unserved nested-connection access through the union-published sentinels (`033`'s strictness-wiring slice), retiring this card's strictness-blind posture; and the products connections-only conversion landed **with `033`**, not at [`TODO-BETA-062-0.1.5`][kanban] — [`examples/fakeshop/apps/products/schema.py`][fakeshop-products-schema]'s `Query` is four `DjangoConnectionField`s today, because the gate this card named (a `0.0.9` connection deriving an empty plan) is exactly what `033` removed, so the conversion became `033`'s to make rather than a later card's. `TODO-BETA-062-0.1.5` was re-scoped accordingly and now covers the products `node` / `nodes` entry points and the `totalCount` opt-in. Read every "deferred to `062`" sentence in this spec against this paragraph: the deferral out of **this card** is true, the destination is not.
- **Library-first activation, via the `BookType` promotion.** The card's live-coverage DoD (refetch, paginated connection, cursor round-trip, `totalCount`) is satisfiable with the existing `GenreType` alone — but a *live* relation-as-Connection proof needs a Relay-shaped parent whose many-side target is also Relay-shaped, and the library has none today. Slice 6 promotes **`BookType`** to Relay-Node shape (`interfaces = (relay.Node,)`), making `GenreType.books` eligible and giving `nodes(ids:)` a second concrete type to batch across. The promotion changes `BookType.id` to `GlobalID!` (existing library assertions on integer book ids move to encoded model-label payloads — bounded test churn, the [`spec-031`][spec-031] Slice-4 precedent). The promotion also adds a **`BookType.get_queryset`** hiding `circulation_status="repair"` books from non-staff requests (mirroring the shipped [`ShelfType.get_queryset`][fakeshop-library-schema] `topic="secret"` pattern, staff-bypass included): no fakeshop type is currently both Relay-Node-shaped **and** `get_queryset`-filtered, so without this edit the live hidden-row `null` test (Goal 1 / [Decision 5](#decision-5--null-for-invisible-rows-graphqlerror-for-malformed-ids) headline contract) has no eligible type — `node(id:)` only refetches Relay-shaped types, and every Relay-shaped type would otherwise be visibility-unfiltered. The filter additionally makes the target's `get_queryset` observable inside the live `booksConnection` (the nested-connection visibility proof). `BookType` is the [`Meta.primary`][glossary-metaprimary] type for `library.Book`; its non-Relay `NullabilityOverrideBookType` secondary is unaffected (the model-label-routing audit constrains only model-label *emitters*, and the primary now both emits and decodes).

## Edge cases and constraints

- **`first: 0`** — empty `edges`, well-formed `pageInfo` (`hasNextPage` true iff rows exist past the empty window). Pinned by the conformance suite.
- **Stale `after` cursor** — the query does not error, but offset cursors encode a position, not row identity: a delete before the position shifts the sequence (rows can be skipped), an insert can duplicate them across pages. Positional stability under concurrent mutation is **not guaranteed** and not asserted ([`spec-030`][spec-030]'s contract). That is a property of the **offset** cursor, not of the package: stable column-keyed cursors ship as the [`Meta.cursor_field`][base] keyset opt-in ([`keyset.py`][keyset]), which a connection over an opted-in type uses instead, and which this card neither ships nor exercises.
- **`relay_max_results`, under the policy's `max_page_size` ceiling** — Strawberry caps any single page (default 100) for root and synthesized connections alike, and a consumer raises that schema-side cap via [`strawberry_config`][glossary-strawberry_config]`(relay_max_results=...)`. A raise is only effective up to the request's [`resource_policy.py::ResourcePolicy.max_page_size`][resource-policy] (default `100`), which is a **ceiling** over the resolved value, not a replacement for it: a connection may be narrower than the policy and can never be wider. The clamp is resolved once at the connection's entry seam, before any window or slicing path reads it, and the same clamped integer feeds plan time and resolve time so the two windows agree by construction. The conformance suite pins the over-cap error shape at the schema-side cap.
- **Duplicate ids in `nodes(ids:)`** — each position resolves independently (the same row may appear twice); the per-type batch still issues one query per distinct type. Strawberry's own index-map collapses duplicate `GlobalID` keys, which is one reason the package owns the batch resolver rather than borrowing the native one wholesale.
- **`nodes(ids: [])`** — returns `[]` without touching the database, and without checking the execution deadline: the short circuit runs first, so a request asking for nothing is never rejected for a budget it cannot spend.
- **A `GlobalID` for a non-Node `DjangoType`** — `decode_global_id` rejects it (absent recorded strategy); the root field surfaces `GLOBALID_INVALID`. No database access occurs, so no existence signal leaks.
- **Well-formed id, uncoercible id literal** — `library.genre:abc` decodes to `(GenreType, "abc")` (shape-valid), but `abc` is not a valid integer pk. `relay.py` pre-coerces the literal against the **concrete field behind the target's `resolve_id_attr()`** — `"pk"` maps to `model._meta.pk`, any other value resolves through `model._meta.get_field`, and a `relay.NodeID` over a non-concrete attr skips coercion and passes the raw literal — running `to_python` then `run_validators`, and returns `null` (single) / a positional `null` hole (batch — coerced per id so one garbage entry does not poison the `pk__in`), issuing no query. That prevents both the raw Django `ValueError: Field 'id' expected a number` that `qs.filter(pk="abc")` would leak and the backend `OverflowError` an in-range-looking but out-of-range literal would raise from a `pk__in` ([Decision 5](#decision-5--null-for-invisible-rows-graphqlerror-for-malformed-ids)). The shipped `_coerce_node_id` only unwraps a `relay.GlobalID` wrapper, so this coercion is the root field's responsibility, not the `resolve_node` default's.
- **`nodes(ids:)` is bounded by the resource policy, not by `relay_max_results`** — `relay_max_results` caps connection *pages* (itself under the policy's own `max_page_size` ceiling, above) and says nothing about a refetch batch. The two policy fields are deliberately independent, so raising the page size never raises the batch size. The batch bound is its own policy field, [`resource_policy.py::ResourcePolicy.max_node_ids`][resource-policy] (default `200`): the resource-policy extension charges the width of any `[ID!]` list argument named `ids` in a query operation against it and rejects an over-cap request. The charge runs on **coerced-shape input**, so an over-cap list is refused before a single `GlobalID` is decoded and before any queryset is built — a variable-carried 10,000-id payload never reaches the field. Duplicate ids are charged positionally, because the field reassembles every position.
- **Cooperative execution deadline** — when the request's resource policy sets `execution_deadline_seconds`, both root fields consult it before handing work to the database, and the placement is the contract: `DjangoNodeField` checks **before the decode** (the decode is what makes a visibility-scoped query inevitable), `DjangoNodesField` checks **after the empty-list short circuit and before the batch decode**. The check is cooperative, not preemptive — nothing in-process interrupts a query already handed to the driver, so what it buys is that the request starts no more work.
- **Multi-type models at the root fields** — a model-label id routes to the [`Meta.primary`][glossary-metaprimary] type; a type-name id routes to the named type. The `031` model-label-routing audit already guarantees the primary can decode whatever its secondaries emit; the root fields inherit that invariant without new checks.
- **Typed field + secondary type** — `DjangoNodeField(SecondaryType)` is legal (the four target guards accept any registered Relay-shaped type); a model-label id then decodes to the *primary* and fails the typed match. Documented: typed fields over secondaries pair naturally with the `type` strategy (type-scoped ids), the same pairing `031` documented for disjoint identity scopes.
- **Bare `node` field with no other root fields** — Strawberry only registers schema types it can reach; a schema whose *only* root field is interface-typed `node` must pass its concrete types via `strawberry.Schema(types=[...])` or expose them through other fields. Documented in the root-field docstring; not package-fixable (engine behavior).
- **The default shape removes the generated list field** — under `"connection"` the synthesized connection replaces the relation's annotation and Phase-2 list resolver *before* Phase-3 decoration, so the SDL never carries the list form. An eligible many-side relation on a Relay-Node-shaped type is therefore reachable **only** through `<field>Connection` unless the type asks for `"both"`. Consumer overrides of the relation field (annotation or `strawberry.field`) are `consumer_authored_fields` and the synthesis **skips overridden relations under the implicit default** (the shipped override contract outranks the upgrade — the consumer owns that field's shape). An **explicit** `relation_shapes` entry naming a consumer-authored relation raises at type creation instead of being silently ignored ([Decision 7](#decision-7--metarelation_shapes-is-a-net-new-allowed_meta_keys-key-stored-on-the-definition)).
- **Re-entering Phase 2.5 after a partial finalize** — [`finalize_django_types`][glossary-finalize_django_types] is re-callable after a mid-iteration failure, so the synthesis runs again over classes it already touched. A synthesized field is recognized by its marker (never mistaken for a collision), a `"connection"` relation's list form is re-removed because the rerun's Phase 2 re-attached it, and the walker-readable `relation_connections` slot is re-recorded because the failed pass may have dropped it ([Decision 6](#decision-6--relation-as-connection-synthesis-at-finalization-phase-25)).
- **Collision detection under custom naming configs** — the Phase-2.5 collision guard compares Python attribute names AND default-camel-cased GraphQL names ([Decision 6](#decision-6--relation-as-connection-synthesis-at-finalization-phase-25)), because the schema's `StrawberryConfig` — and any custom `name_converter` / `auto_camel_case=False` — is not constructed until after finalization. A collision visible only under a non-default converter surfaces as Strawberry's schema-build duplicate-field error rather than the package's named [`ConfigurationError`][glossary-configurationerror]; the guard is best-effort at the only phase the package controls.
- **Self-referential M2M / reverse-FK cycles** — the synthesis is per-relation and non-recursive (it adds fields, never walks into the target), so cycles terminate trivially; nested query depth is the consumer's choice and the pre-`033` N+1 caveat applies per level.
- **Async end-to-end** — the bare/typed **single-node** resolver passes the `resolve_node` default's value straight through: a coroutine in async context that Strawberry's executor awaits as a plain-field return. The **`nodes`** resolver cannot pass values through — it calls `resolve_nodes` once per distinct decoded type, and in async context each call returns a coroutine ([`types/relay.py::_resolve_nodes_default`][types-relay] dispatches per-call via [`in_async_context()`][types-relay]), so the synthesized `nodes` resolver itself detects the async context (the same per-call `in_async_context()` check) and returns a **single gathering coroutine** that awaits the per-type results and interleaves them into input order with `null` holes. This per-call detection is deliberately the *other* mechanism from [`connection.py`][connection]'s commit-sync/async-at-construction split ([`spec-030`][spec-030] Decision 10): the synthesized relation connections reuse that committed-at-construction shape (they wrap a known consumer resolver), but the root fields have no consumer resolver to inspect at construction, so they dispatch per call. An async [`get_queryset`][glossary-get_queryset-visibility-hook] met from a sync context raises [`SyncMisuseError`][glossary-syncmisuseerror], unchanged — and so does a **consumer** `resolve_node` / `resolve_nodes` override that returns an awaitable while the field is running synchronously, which the field rejects itself rather than passing an unawaitable coroutine down the sync path ([Decision 5](#decision-5--null-for-invisible-rows-graphqlerror-for-malformed-ids)).
- **No existence oracle** — hidden and missing rows share one queryset path and one `null` result; the typed-mismatch and decode errors run before any query. The conformance suite asserts the error-paths-never-query property with a query-count assertion.

## Test plan

Tests live across the package-internal `tests/` tree and the `examples/fakeshop/test_query/` tree, per [`docs/TREE.md`][tree], [`AGENTS.md`][agents], and the coverage rule in [`examples/fakeshop/test_query/README.md`][fakeshop-test-query-readme]: **any package coverage line reachable by a real GraphQL query against the fakeshop schema MUST be earned in `test_query/`, the first place to add a test** — fall back to the package tree only when the path is genuinely unreachable from a live `/graphql/` request, and mock behavior, never the class. Concretely for this card:

- **Live-first (Slices 4 and 6).** The cursor-conformance matrix runs live against the already-shipped `allLibraryGenresConnection` (Slice 4 — no activation dependency), and Slice 6's activation suite is the mandated coverage home for every live-reachable root-field and relation-connection path: bare + typed `node`, `nodes` batch (order / `null` holes / duplicates / empty list), the malformed-id `GLOBALID_INVALID` error, hidden-row `null`, and the synthesized relation connections including sidecar arguments and `totalCount`.
- **Package-only where live is genuinely unreachable**, with the reason pinned per family: type-creation / finalization [`ConfigurationError`][glossary-configurationerror]s (an invalid config cannot appear in the example schema — [Cross-subsystem invariants][glossary-cross-subsystem-invariants]); registry lifecycle / ledger resets via `registry.clear()`; public-export import assertions; [`SyncMisuseError`][glossary-syncmisuseerror] (requires a deliberately async-`get_queryset` type); async execution contexts (the `django.test.Client` WSGI path executes sync); the `relay_max_results` cap (requires a non-default `StrawberryConfig` the fakeshop project schema does not set); and synthesized-relation shape variants beyond the fakeshop graph (the `"connection"` / `"list"` narrowings and the reverse-FK relation-connection variant, exercised on cardinality fixtures).
- **Package twins that keep the per-slice gate green.** Slices 2–4 land before the Slice-6 schema activation, so they carry package-internal tests covering the new lines in the interim; the live suite remains the canonical coverage surface once Slice 6 lands (the README rule is satisfied at card close, and CI's `fail_under = 100` is satisfied at every slice boundary).

Every live HTTP test follows the `_reload_project_schema_for_acceptance_tests` fixture pattern from [`test_library_api.py`][fakeshop-test-library] (clear the global registry, reload `apps.<app>.schema`, reload `config.schema`, reload `config.urls` and clear URL caches), per the [`test_query/README.md`][fakeshop-test-query-readme] requirement. File placement per [Decision 11](#decision-11--module-and-test-file-locations).

**Strategy is finalize-frozen, so strategy-varying tests must reload.** Each type's `GlobalID` strategy is stamped **once** at finalization onto `definition.effective_globalid_strategy` (`install_globalid_typename_resolver` → `_resolve_globalid_strategy`, the only `RELAY_GLOBALID_STRATEGY` read site) — it is not re-read per query, so the root fields add no per-request settings access or shared mutable state (the only request-time addition is the typed-form identity check, one `is` comparison). The observable consequence: an `@override_settings(RELAY_GLOBALID_STRATEGY=...)` applied *after* a type finalizes changes nothing for that type — a test exercising a non-default strategy must clear the registry and reload the schema (exactly what `_reload_project_schema_for_acceptance_tests` already does) so the type re-finalizes under the override. Corollary worth stating as a feature: [`testing.relay.global_id_for`](#decision-10--public-testingrelaypy-helpers-and-the-export-gate) reads the **stamped** strategy, so the helper is consistent-by-construction with live emission and can never disagree with the schema the way a fresh settings read could.
