## Key glossary references

Skim these [`docs/GLOSSARY.md`][glossary] entries first — they anchor the vocabulary used throughout the spec:

- [Connection-aware optimizer planning][glossary-connection-aware-optimizer-planning] — this card. The entry's "nested connections fall back to per-row queries" sentence is the problem statement; Slice 7 flips the status and rewrites the body to describe the shipped mechanism.
- [`DjangoConnectionField`][glossary-djangoconnectionfield] / [`DjangoConnection`][glossary-djangoconnection] — the shipped [`DONE-030-0.0.9`][kanban] connection surface. Its entry's "in `0.0.9` the derived plan is **empty**" caveat is already stale for *root* connections ([Current state](#current-state)) and goes away entirely with this card.
- [`Meta.relation_shapes`][glossary-metarelation_shapes] — the [`DONE-032-0.0.9`][kanban] key whose synthesized `<field>Connection` siblings are this card's planning target; the entry's `SyncMisuseError`-until-`033` caveat survives (the async connection pipeline stays out of scope, [Non-goals](#non-goals)).
- [`DjangoOptimizerExtension`][glossary-djangooptimizerextension] — the schema extension whose `apply_to` seam, plan cache, and strictness constructor this card extends; no constructor or public-surface change.
- [Plan cache][glossary-plan-cache] — the B1 cache whose key gains the nested-pagination-variable component ([Decision 7](#decision-7--plan-cache-key-hygiene-nested-pagination-variables-hash-root-pagination-arguments-do-not)); the entry's "variable filtering" property is refined, not broken — variables that do not affect the plan stay out of the key.
- [Strictness mode][glossary-strictness-mode] — the B3 contract this card wires into the connection pipeline; today `_check_n1` fires only from the generated list-relation resolvers ([`types/resolvers.py::_check_n1`][resolvers]).
- [Queryset diffing][glossary-queryset-diffing] — the B8 reconciliation that must not regress (card DoD); the windowed prefetch rides `append_prefetch_unique` / `diff_plan_for_queryset` like every generated `Prefetch`.
- [FK-id elision][glossary-fk-id-elision] / [`only()` projection][glossary-only-projection] — shipped plan vocabulary the windowed child plans reuse unchanged; the window adds *annotations*, which compose with `.only()`.
- [`OptimizerHint`][glossary-optimizerhint] / [`Meta.optimizer_hints`][glossary-metaoptimizer_hints] — the per-relation override surface; `SKIP` suppresses window planning for the relation's connection sibling, `strategy(...)` selects the fetch backend for one connection field, and a `prefetch(Prefetch(..., to_attr=...))` on a generated relation is refused outright ([Decision 6](#decision-6--refusal-arms-divergent-aliases-hints-and-scalar-only-connections)).
- [`Meta.connection`][glossary-metaconnection] — the target-type `total_count` opt-in; a windowed nested connection serves `totalCount` from the `_dst_total_count` annotation, which is present exactly when the page's selection can observe a count, and `first: 0` / overshot `after:` pages are served from a retained partition marker row rather than a per-parent fallback ([Decision 4](#decision-4--windowed-prefetch-planning-under-a-package-reserved-to_attr) / [Decision 5](#decision-5--connection-class-fast-path-with-annotation-presence-detection-and-a-per-parent-fallback)).
- [`get_queryset` visibility hook][glossary-get_queryset-visibility-hook] — baked into windowed child querysets exactly as into every generated `Prefetch` child queryset (and with the same consequence: the plan goes `cacheable = False`).
- [`FilterSet`][glossary-filterset] / [`OrderSet`][glossary-orderset] / [`Meta.filterset_class`][glossary-metafilterset_class] / [`Meta.orderset_class`][glossary-metaorderset_class] — the sidecars whose `filter:` / `orderBy:` arguments a nested connection may carry; a nested connection with sidecar input is **not** window-planned in `0.0.9` and falls back per-parent ([Decision 6](#decision-6--refusal-arms-divergent-aliases-hints-and-scalar-only-connections)).
- [`filter_input_type`][glossary-filter_input_type] / [`order_input_type`][glossary-order_input_type] — the helpers behind the products root resolvers' current `filter:` / `orderBy:` arguments; the conversion replaces those hand-written signatures with [`DjangoConnectionField`][glossary-djangoconnectionfield]'s synthesized equivalents.
- [`DjangoType`][glossary-djangotype] / [Relay Node integration][glossary-relay-node-integration] / [`Meta.interfaces`][glossary-metainterfaces] — all four products types are already Relay-Node-shaped, which is why their relations already synthesize connection siblings today.
- [Definition-order independence][glossary-definition-order-independence] / [`finalize_django_types`][glossary-finalize_django_types] — the synthesis metadata this card's walker reads is recorded at finalization Phase 2.5, after relation targets settle.
- [Relation handling][glossary-relation-handling] — the shipped list-shaped relation planning is untouched; the windowed prefetch is an *additional* plan entry under a `to_attr`, never a replacement for the list field's accessor-keyed prefetch.
- [`DjangoListField`][glossary-djangolistfield] — root-gated list planning is untouched; the products conversion removes the products *resolvers*, not any `DjangoListField` usage (products never used it).
- [`SyncMisuseError`][glossary-syncmisuseerror] — the async-`get_queryset`-through-a-synthesized-connection contract is unchanged ([Non-goals](#non-goals)).
- [Multi-database cooperation][glossary-multi-database-cooperation] — windowed child querysets follow the shipped generated-`Prefetch` alias rules (they do NOT inherit the root alias); the window adds annotations only.
- [Schema audit][glossary-schema-audit] — unchanged; the audit walks relation fields, and synthesized connection siblings resolve through the same targets.
- [`Meta.search_fields`][glossary-metasearch_fields] — the `search:` argument stays absent from every connection until `0.1.2` ([`TODO-BETA-056-0.1.2`][kanban]); reaffirmed.
- [`ConfigurationError`][glossary-configurationerror] — no new validation surface; this card adds no `Meta` key and no public symbol.
- [`strawberry_config`][glossary-strawberry_config] — its `relay_max_results` passthrough is the page-size cap the plan-time window math must honor ([Decision 4](#decision-4--windowed-prefetch-planning-under-a-package-reserved-to_attr)).

  - [ ] [`optimizer/walker.py::_merge_aliased_selections`][walker] becomes argument-aware for synthesized connection siblings before `_plan_connection_relation(...)` runs: either connection selections stay unmerged until pagination classification, or the merged selection preserves per-response-key argument payloads.   - [ ] [`optimizer/walker.py::_walk_selections`][walker] gains a branch before the `django_field is None → continue` guard: when the shared selection-name resolver matches a `relation_connections` key (exact reverse lookup first, authoritative forward name-converter match when reversal is lossy), dispatch to a new `_plan_connection_relation(...)` that (a) unwraps the selection's `edges { node { ... } }` children via the consolidated helpers when present and otherwise recognizes scalar-only `pageInfo` / `totalCount` selections, (b) builds the child plan over the relation target exactly as `_build_prefetch_child_queryset` does (visibility hook baked when the target overrides [`get_queryset`][glossary-get_queryset-visibility-hook], flipping `cacheable = False`; connector columns ensured; child-plan metadata merged) — and if the base child queryset is unwindowable — `sliced` / `select_for_update` / `combined` / `distinct` / `values`, classified by [`optimizer/nested_fetch.py::unwindowable_child_queryset_reason`][nested-fetch] before the child plan is applied — leaves the relation unplanned to fall back per-parent, since the window's `Count(1) OVER` would over-count pre-dedup rows and the other four shapes cannot carry a window at all ([Decision 4](#decision-4--windowed-prefetch-planning-under-a-package-reserved-to_attr)), (c) appends the deterministic total order (the [`spec-030`][spec-030] pipeline rule: pk appended unless the effective ordering already ends in a unique column — the shared helper is hoisted per [Decision 11](#decision-11--module-and-test-file-locations)), (d) preserves the existing guard ordering for `first`+`last` before computing the slice window from the selection's resolved `first` / `last` / `before` / `after` argument values (converted selections resolve variable references through `info.variable_values` — source-verified against the locked Strawberry `0.316.0`, `strawberry/types/nodes.py` #"info.variable_values.get(name)") mirroring `SliceMetadata.from_arguments` with `relay_max_results` read from the schema config, (e) catches `SliceMetadata` `ValueError` / malformed-cursor `TypeError` and emits **no** window prefetch — but still records the connection's resolver identities in `plan.planned_resolver_keys` so strictness ([Decision 8](#decision-8--strictness-mode-wiring-for-connection-paths)) treats the field as accounted-for and the shipped nested field path raises its OWN pagination/cursor error rather than a spurious `OptimizerError("Unplanned N+1")`, (f) applies the window via the new `plans.py` helper, and (g) appends `Prefetch(<accessor>, queryset=<windowed child qs>, to_attr="_dst_<field>_connection")` plus the connection field's resolver identities to `plan.planned_resolver_keys`.

  - [ ] [`connection.py::_build_relation_connection_resolver`][connection] gains two parameters: a **relation-field-name** parameter — the precomputed `_dst_<field>_connection` probe, threaded from [`types/finalizer.py::_synthesize_relation_connections`][finalizer] (which passes `field.name`) so the probe is correct when the accessor diverges from `field.name` for a reverse relation without `related_name` — and a **declaring-type** parameter, which is the `parent_type` component of the resolver key without which the resolve-time key cannot match the walker's emission ([Decision 8](#decision-8--strictness-mode-wiring-for-connection-paths)); the call site passes the iterated type rather than the model's primary type, so a divergent secondary type's connection stays correctly flagged. It does **not** return a prebuilt connection instance; Strawberry's `ConnectionExtension` still calls the generated connection class's `resolve_connection`. If sidecar kwargs are present, the `to_attr` is ignored and the shipped pipeline runs so a future planner/argument desync cannot serve unfiltered wrong data.

## Problem statement

The `0.0.9` Relay cohort shipped a complete, correct, and **partially unoptimized** connection surface. Root connections are now planned — the post-`032` hardening pass landed `edges { node }` extraction for the root seam, so a root `DjangoConnectionField`'s pre-slice queryset receives `select_related` / `prefetch_related` / `only()` like any list resolver. But the **nested** half is untouched: every `<field>Connection` sibling that [`DONE-032-0.0.9`][kanban]'s relation-as-Connection upgrade synthesizes resolves through a per-parent pipeline — `getattr(root, accessor).all()` per parent row, then visibility, ordering, optimizer, and cursor slice per parent row. A cookbook-shaped two-level query (`{ allObjects { edges { node { values { edges { node { value } } } } } } }`, the `django-graphene-filters` recipes shape the card names) issues one query per parent: the textbook N+1, shipped knowingly under [`spec-032`][spec-032] Decision 12's joint-cut sequencing argument — *both cards ship in the same `0.0.9` cut, so no released version carries the gap*. This card is the second half of that argument.

The gap is wider than latency. The parent's selection walker skips nested connection selections entirely (`books_connection` matches no model field; the unknown-name guard `continue`s), so the plan never records them — which means [Strictness mode][glossary-strictness-mode] cannot flag them either: `"raise"` runs sail silently past a per-parent access pattern that the same query expressed as a plain list relation would have failed loudly. And the [Plan cache][glossary-plan-cache] has a latent correctness boundary: once pagination *values* are baked into prefetch querysets, two requests differing only in a variable-supplied `first:` must not share a cached plan — a key-hygiene rule the current `@skip` / `@include`-only variable collection cannot express.

The upstream proof that the mechanism works at scale is direct: `strawberry-graphql-django` detects a connection on a nested field inside its prefetch builder, computes the slice window via Strawberry's own `SliceMetadata.from_arguments`, and pushes the window into the prefetch as `RowNumber()` / `Count(1)` window functions partitioned by the key Django uses to attach prefetched children back to each parent (`/Users/riordenweber/projects/strawberry-django-main/strawberry_django/optimizer.py::_optimize_prefetch_queryset`, `pagination.py::apply_window_pagination`); its connection class then resolves edges, `pageInfo`, and `totalCount` straight from the prefetched rows' annotations (`relay/list_connection.py::DjangoListConnection.resolve_connection` #"resolve_optimized_connection_by_prefetch"). Each parent's page costs one window-function query for the whole batch, and `totalCount` rides the same query. graphene-django ships no native equivalent — the card's parity claim is correctly `strawberry-graphql-django`-only and **Required**.

Finally, the card unblocks the dogfooding surface that was deliberately fenced off: the products connections-only conversion. The products live optimizer tests (`test_products_optimizer_*`) pin the package's SQL shapes through real HTTP queries; converting the products Query to connections before nested planning existed would have regressed exactly those pins, so [`DONE-032-0.0.9`][kanban] and the card both sequenced the conversion behind this card — "Land the products list->connection replacement together with this card."

## Goals

1. **Plan nested connections.** The walker recognizes synthesized relation-connection selections through definition metadata and plans a windowed `Prefetch` for each — child plan over the target (visibility, projections, nested relations, deeper nested connections recursively), deterministic total order matching the pipeline's rule, relation-kind-correct partition key, slice window from the selection's resolved pagination arguments capped by `relay_max_results`, landed under a package-reserved `to_attr` so the list sibling's accessor-keyed prefetch and the window never collide (Slice 1, [Decision 3](#decision-3--walker-recognition-is-definition-metadata-driven-not-name-pattern-guessing) / [Decision 4](#decision-4--windowed-prefetch-planning-under-a-package-reserved-to_attr)).
2. **Consume the window.** The synthesized relation connection resolver returns annotated rows through an internal wrapper, and the generated connection class serves `edges` (offset cursors from `_dst_row_number`), `pageInfo`, and `totalCount` (from `_dst_total_count`, when the target opted in and the page's selection can observe a count) directly from that wrapper — `first: 0` and overshot `after:` pages included, served from the window's retained partition marker row — one window query per relation per request, zero per-parent queries on the fast path, falling back to the shipped per-parent pipeline whenever the window is absent or unsafe to consume (Slice 2, [Decision 5](#decision-5--connection-class-fast-path-with-annotation-presence-detection-and-a-per-parent-fallback)).
3. **Keep the plan cache honest.** Variables feeding **nested** pagination arguments are hashed into the plan-cache key (their values are baked into plans); variables feeding **root** pagination arguments stay out (their values never affect plan content) — the card's "skip pagination args that do not affect selection shape, hash the ones that do" (Slice 3, [Decision 7](#decision-7--plan-cache-key-hygiene-nested-pagination-variables-hash-root-pagination-arguments-do-not)).
4. **Wire strictness into connections.** An unplanned, unserved nested-connection access fires the [Strictness mode][glossary-strictness-mode] contract (`warn` / `raise`) through the same resolver-key vocabulary list relations use, closing the silent-N+1 hole [`spec-032`][spec-032] documented (Slice 4, [Decision 8](#decision-8--strictness-mode-wiring-for-connection-paths)).
5. **Prove it live, then dogfood it.** The library suite gains the deferred fixed-query-count SQL-shape assertions for the cookbook-equivalent nested-connection shape; the products Query converts to connections-only (the cookbook mirror) with the `test_products_optimizer_*` SQL-shape dogfooding re-pinned through `edges { node }` (Slices 5–6, [Decision 10](#decision-10--the-products-connections-only-conversion-lands-with-this-card)).
6. **No B1–B8 regression.** The plan cache, queryset diffing, FK-id elision, `only()` projection, hints, multi-DB rules, and the root-connection planning that already shipped all keep their existing coverage green (card DoD).
7. **Keep package version state command-gated and owned by the joint `0.0.9` cut**: no slice edits `__version__`, [`tests/base/test_init.py::test_version`][test-base-init], or `uv.lock` (Slice 7, [Decision 12](#decision-12--version-bumps-are-owned-by-the-joint-009-cut)).

## Non-goals

- **Async connection pipeline.** A Relay target whose `get_queryset` is `async def` still raises [`SyncMisuseError`][glossary-syncmisuseerror] through its synthesized `<field>Connection` (the [`Meta.relation_shapes`][glossary-metarelation_shapes] `"list"` narrowing remains the recourse). The window planning below is sync-pipeline planning; the async story is untouched.
- **Windowed planning for sidecar-filtered nested connections.** A nested connection carrying `filter:` / `orderBy:` input falls back to per-parent resolution in `0.0.9` ([Decision 6](#decision-6--refusal-arms-divergent-aliases-hints-and-scalar-only-connections)) — baking [`FilterSet`][glossary-filterset] / [`OrderSet`][glossary-orderset] application into plan-time child querysets needs request-scoped input threading through the walker, a follow-up with its own design surface.
- **Root `totalCount` window folding.** The shipped root contract — selection-gated `.count()` / `.acount()` on the pre-slice queryset — stays. One `COUNT` per root connection is not an N+1; folding it into the main query via a partition-less window (upstream's `DjangoListConnection.resolve_connection` annotation) is a micro-optimization that would churn a shipped, tested contract mid-cohort. Recorded as a possible follow-up in [Risks and open questions](#risks-and-open-questions).
- **Keyset / column-anchored cursors — out of scope for this card, and since shipped.** The window math this card describes inherits Strawberry's offset-cursor semantics verbatim. `Meta.cursor_field` value-encoded cursors were [`BACKLOG.md`][backlog] item 39 at authoring time and landed afterwards, forking this card's mechanism at five sites in [`connection.py`][connection]: keyset mode is resolved off the generated class per connection; `_consume_window` derives its bounds through `derive_keyset_window_bounds` instead of `derive_connection_window_bounds`, because a value cursor cannot pass through `SliceMetadata`; the fast path builds keyset edges directly with `encode_keyset_cursor` rather than through `resolve_edge`, the one exception to [Decision 5](#decision-5--connection-class-fast-path-with-annotation-presence-detection-and-a-per-parent-fallback)'s "the cursor prefix stays owned by Strawberry's edge type"; a counted keyset-seek page carries its own `_dst_keyset_seek_count` annotation and drift guard; and a non-window keyset source routes to the keyset resolver rather than to `ListConnection`. A keyset target's declared cursor field also wins over the pk-append rule in the shared deterministic-order helper, and a nested `orderBy:` sidecar on such a target deliberately leaves that response key unplanned rather than overriding the cursor order.
- **The G1–G3 robustness guards** (evaluated-queryset guard, operation-type `only()` gating, fragment `type_condition` narrowing) — [`DONE-035-0.0.10`][kanban], which deliberately sequenced itself *after* this card to avoid concurrent walker churn (its own dependency note).

## Borrowing posture

Per the [`START.md`][start] "do both libraries provide it? → foundational" test, connection-aware planning is a **one-upstream Required parity**: `strawberry-graphql-django` plans nested connection selections natively; graphene-django has only rudimentary connection-aware optimization (the card tags it ⚛️ parity-adjacent). The behavioral mechanism is borrowed from the strawberry side wholesale — exactly the [`START.md`][start] rule ("behaviorally we copy strawberry-graphql-django's good ideas") — while the consumer surface stays the package's own: nothing new to declare, no decorators, no per-field opt-ins; the optimization applies to the `Meta`-declared relation connections automatically.

### From `strawberry-graphql-django` — borrow the runtime mechanism

The window-pagination prefetch is ported at the mechanism level: `RowNumber()` and `Count(1)` window functions partitioned by the parent attach key, row-number range filters for the slice, reversed row-number for backward (`last`-only) pagination, and prefetch-cache connection resolution reading the annotations (`/Users/riordenweber/projects/strawberry-django-main/strawberry_django/pagination.py::apply_window_pagination`, itself based on Django's own approach in <https://github.com/django/django/pull/15957>; `relay/list_connection.py` #"resolve_optimized_connection_by_prefetch"). The slice arithmetic reuses the engine: Strawberry's `strawberry/relay/utils.py::SliceMetadata.from_arguments` is the same helper upstream calls. Upstream's **DISTINCT guard** is adopted too: upstream's `get_total_count` falls back to a plain `.count()` when `queryset.query.distinct` is set, because SQL evaluates window functions *before* `DISTINCT` dedup and `Count(1) OVER` would over-count — the package resolves the same hazard at plan time by leaving a distinct-target relation **unplanned** so it falls back per-parent ([Decision 4](#decision-4--windowed-prefetch-planning-under-a-package-reserved-to_attr) / [Decision 6](#decision-6--refusal-arms-divergent-aliases-hints-and-scalar-only-connections)).

### Explicitly do not borrow

- **The queryset-config marker system.** Upstream threads an `is_optimized_by_prefetching` flag through a `QuerySet`-attached config and monkeypatches `QuerySet._clone` to carry it. The package detects the window by **annotation presence on the prefetched rows** (upstream's own fallback probe) plus the package-reserved `to_attr` — no global state, no monkeypatching, the same posture that rejected the `resolve_type` patch in the `031` cycle.
- **Plan-time `field_kwargs` application.** Upstream applies the nested field's *full* argument set (filters included) inside the prefetch builder. The package's plan cache makes request-scoped values in plans a correctness hazard, so `0.0.9` windows only the argument family whose values it can hash into the key (pagination), and falls back per-parent for sidecar input ([Decision 6](#decision-6--refusal-arms-divergent-aliases-hints-and-scalar-only-connections)).
- **The `_strawberry_*` annotation names.** The package namespaces its annotations `_dst_*` (matching the `DST_*` context keys and the `_dst_` marker convention) so a consumer running both libraries in one process can never collide.
- **Upstream's per-field-node `Info` reconstruction.** The walker reads resolved argument values off converted selections (the engine resolves variables during conversion); no synthesized `Info` objects.

## User-facing API

**This card adds no public symbol, no `Meta` key, and no constructor argument.** The consumer-visible changes are behavioral:

```graphql
{
  allLibraryGenresConnection(
    first: 10
  ) {
    edges {
      node {
        name
        booksConnection(
          first: 3
        ) {
          edges {
            node {
              title
            }
          }
          totalCount
          pageInfo {
            hasNextPage
            endCursor
          }
        }
      }
    }
  }
}
```

- **Before this card**: 1 query for the genres page, then *per genre* one query for its books page (plus one `COUNT` per genre when `totalCount` is selected and the target opted in).
- **After this card**: 1 query for the genres page + **1 window-function query** covering every genre's books page and every `totalCount` — a fixed count regardless of how many genres the first page returns. Wire results are byte-identical.
- [Strictness mode][glossary-strictness-mode] `"raise"` now flags a nested-connection access the plan does not cover (previously silent), with the same planned-key exemption semantics as list relations.

The products example reshapes to the cookbook mirror (Slice 6):

```python
from django_strawberry_framework import DjangoConnection, DjangoConnectionField


@strawberry.type
class Query:
    all_categories: DjangoConnection[CategoryType] = DjangoConnectionField(CategoryType)
    all_items: DjangoConnection[ItemType] = DjangoConnectionField(ItemType)
    all_properties: DjangoConnection[PropertyType] = DjangoConnectionField(PropertyType)
    all_entries: DjangoConnection[EntryType] = DjangoConnectionField(EntryType)
```

The hand-written resolvers (and their `filter_input_type(...)` / `order_input_type(...)` parameter declarations) disappear; the synthesized signatures expose the same `filter:` / `orderBy:` arguments from the same [`Meta.filterset_class`][glossary-metafilterset_class] / [`Meta.orderset_class`][glossary-metaorderset_class] sidecars, and the pipeline applies the same visibility → filter → order → deterministic-order → optimizer composition the resolvers spelled by hand.

### Error shapes

- The inherited guards are unchanged on both the fast path and the fallback: the `first` + `last` guard, the sidecar-input-over-non-queryset guard, the `totalCount`-over-non-queryset guard, and the [`SyncMisuseError`][glossary-syncmisuseerror] contract.
- The window machinery does add error surface of its own, all of it fail-closed:
  - `connection.py::_consume_window` converts a malformed-pagination `ValueError` / `TypeError` (and `AttributeError` / `KeyError` / `IndexError`) into a `GraphQLError` rather than letting the raw exception surface as the field's own error.
  - [`utils/connections.py::window_range_plan`][utils-connections] raises `OptimizerError` on a negative window offset or limit rather than clamping it — silently treating a negative direct-call limit as unbounded would produce wrong rows in both renderers.
  - [`utils/connections.py::assert_window_fetch_mode`][utils-connections] raises `OptimizerError` when a probe window would also annotate the count. It is deliberately not a `ValueError` / `TypeError`, so the walker's leave-unplanned pagination handler cannot swallow it.
  - [`optimizer/walker.py`][walker] raises [`ConfigurationError`][glossary-configurationerror] at plan time for an `OptimizerHint.prefetch(Prefetch(..., to_attr=...))` on a generated relation ([Decision 6](#decision-6--refusal-arms-divergent-aliases-hints-and-scalar-only-connections)).
  - `resolve_connection` also runs the request policy's `max_page_size` ceiling and the execution deadline check before any window work, so either can raise before the fast path is reached.
- [Strictness mode][glossary-strictness-mode] `"raise"` surfaces `OptimizerError(f"Unplanned N+1: <field>")` for an unplanned, unserved nested-connection access — where `<field>` is the underlying **relation** field name (`books`), the same exception class and vocabulary list relations use and the same name the planner's `resolver_key` is built from, NOT the generated `<field>_connection` attribute ([Decision 8](#decision-8--strictness-mode-wiring-for-connection-paths)).

### Decision 4 — Windowed-prefetch planning under a package-reserved `to_attr`

`_plan_connection_relation` plans each recognized nested connection as `Prefetch(<accessor>, queryset=<windowed child queryset>, to_attr="_dst_<field>_connection")`.

**The window is one fetch strategy's rendering of the plan, not the only one.** [`optimizer/nested_fetch.py`][nested-fetch] owns the strategy seam: `"windowed"` (the default, the `RowNumber()` / `Count(1)` prefetch described below), `"lateral"` (a Postgres `CROSS JOIN LATERAL` backend in [`optimizer/lateral_fetch.py`][lateral-fetch]), and `"auto"` (one cache-stable lateral-capable plan whose fetch-time decision follows the nested queryset's effective database alias). A runtime single-parent fast path ([`optimizer/single_parent_fetch.py`][single-parent-fetch]) serves a one-parent batch as a plain bounded query and synthesizes `_dst_row_number` in Python. The backend is selected per extension instance through the `nested_connection_strategy=` constructor argument or the `NESTED_CONNECTION_STRATEGY` setting, and per field through [`OptimizerHint`][glossary-optimizerhint]`.strategy(name)`. Every backend lands its rows under the same `to_attr` and is consumed by the same resolver probe, so everything below about the `to_attr` grammar, the deterministic order, the partition key, and the annotation vocabulary is strategy-independent; only the SQL that produces the rows differs.

- **Child queryset**: built exactly like every generated prefetch child — `related_model._default_manager.all()`, target [`get_queryset`][glossary-get_queryset-visibility-hook] applied when overridden (flipping `plan.cacheable = False`, the shipped request-scope rule), the nested `edges { node { ... } }` child plan applied (projections, `select_related`, deeper prefetches — **including deeper windowed connections recursively**), connector columns ensured so Django can attach rows and the window can partition.
- **Deterministic order (a cursor-parity invariant, not a tidiness refactor)**: the window's `ORDER BY` MUST be produced by the *same* helper the resolve-time pipeline uses — the effective ordering (queryset, else model `Meta.ordering`) with the pk appended unless it already ends in a unique column — hoisted to [`plans.py`][plans] ([Decision 11](#decision-11--module-and-test-file-locations)). The entire fast-path↔fallback wire-parity promise depends on it: if the plan-time window order and the resolve-time order ever diverge (someone "improves" one rule and not the other), the window's row numbers stop agreeing with the pipeline's offset cursors and a fast-path `endCursor` no longer round-trips to an optimizer-less `after:` — a silent, data-dependent failure. This invariant is named here (not buried in the module-location decision) precisely because the hoist is a *correctness* prerequisite; `tests/optimizer/test_plans.py::TestDeterministicOrderHoistParity` (Slice 1) and `test_fast_path_cursor_round_trips_to_fallback_after` (Slice 2) are the named guards.
- **Partition key**: [`optimizer/plans.py`][plans] owns `window_partition_for_prefetch(field)`, which returns the parent-side expression Django's prefetch attach uses, not a vague "related connector" and not the existing child-pk connector helper used for `.only()` safety. Reverse FK partitions by the child table FK attname (`parent_field.field.attname`). Reverse M2M prefetches partition through the child's forward M2M field name, letting Django resolve it onto the through join (`Genre.books` → `Book.genres` → through `genre_id`). Forward M2M prefetches partition through the target model's reverse query name, which is not always the accessor when `related_name` is absent. `GenericRelation` is windowable too. [`optimizer/join_taxonomy.py::classify_relation_join`][join-taxonomy] is the one classifier on the planning path and **never raises**: an unsupported relation kind, or any relation whose partition expression cannot be derived, comes back with `windowable=False` and the relation is left unplanned rather than guessed at. `window_partition_for_prefetch` keeps the raising contract for direct callers.
- **The partition helper takes the raw Django relation field, not a `FieldMeta`**: the forward-M2M reverse query name lives only on `field.remote_field`, which `FieldMeta` does not carry, so [`optimizer/walker.py::_plan_connection_relation`][walker] resolves the live field via `model._meta.get_field(...)` (`_raw_relation_field`) and passes it. The partition-key bullet above already presupposes that raw descriptor, so this is an accepted implementation detail, not a divergence — recorded so a later reader does not re-flag it.
- **Window**: `_dst_row_number = RowNumber() OVER (PARTITION BY <parent key> ORDER BY <deterministic order>)`, with filters for the requested row-number range — the `plans.py` helper ported from upstream's `apply_window_pagination`, including the reversed-row-number branch for `last`-only backward pagination. `_dst_total_count = Count(1) OVER (PARTITION BY <parent key>)` is annotated **only when the page's own selection can observe a count** — a selected `totalCount`, a `pageInfo.hasNextPage` the window shape cannot answer otherwise, or a window shape that needs the count to classify its rows. A plain `first: N` edges-only page therefore carries no partition `COUNT` at all: it pays an n+1 sentinel overfetch and answers `hasNextPage` from whether the sentinel row arrived. The observability decision is one [`utils/connections.py::FetchMode`][utils-connections] value per window (`COUNTED` / `PROBED` / the count-free constant shapes), derived at plan time and consumed unchanged at resolve time, so plan and resolver cannot disagree about which annotations exist.
- **Unwindowable child querysets are classified before the window is built**: [`optimizer/nested_fetch.py::unwindowable_child_queryset_reason`][nested-fetch] runs on the base child queryset and names five reasons — `sliced`, `select_for_update`, `combined`, `distinct`, `values`. Any of them leaves the relation **unplanned** to fall back per-parent ([Decision 6](#decision-6--refusal-arms-divergent-aliases-hints-and-scalar-only-connections)). `distinct` is the correctness-critical reason and the package's analogue of upstream's `get_total_count` `if queryset.query.distinct: … return queryset.count()` guard: SQL evaluates window functions *before* `DISTINCT` dedup, so `Count(1) OVER (PARTITION BY …)` counts pre-dedup rows and `_dst_total_count` would over-count whenever the child queryset de-duplicates — a visibility/permission [`get_queryset`][glossary-get_queryset-visibility-hook] that joins and de-duplicates is a normal shape, and `.distinct()` already appears across the fakeshop apps. Resolving it toward the conservative fallback beats a per-parent re-count, which would reintroduce the N+1 the window exists to kill. Because the classification is made on the base queryset it is one strategy-independent gate rather than a per-backend re-check. Pinned by `test_distinct_child_queryset_left_unplanned_for_correct_total_count` (Slice 1).
- **Scalar-only connections**: `pageInfo`-only and `totalCount`-only nested selections still window-plan (the load-bearing contract: **planned, not a fallback**, so strictness `"raise"` does not turn harmless scalar connection metadata into an avoidable per-parent error). When `edges { node }` is absent there are no node-child scalar columns to select, so `_plan_connection_relation` seeds a minimal **pk / connector / deterministic-order** projection for the windowed child queryset (`_project_scalar_only_window`) rather than loading the target's full columns: the target pk (Relay edge identity), the relation connector column (Django's prefetch attach), and the concrete local columns the deterministic order references (related-span and unresolvable-expression order entries are skipped — the window's `OVER (ORDER BY …)` and the queryset `ORDER BY` reference them in SQL regardless of the projection). The `_dst_*` row-number / total-count annotations compose with `.only()` (annotations, not deferred columns). An edge-bearing selection's projection still follows its node child plan exactly as before.
- **Slice arithmetic**: Strawberry's `SliceMetadata.from_arguments` over the selection's **resolved** argument values (literals and variables alike — converted selections resolve variables), `max_results` read from the schema config's `relay_max_results` (default 100) and then lowered, if the request policy declares a smaller `max_page_size`, by the one shared [`utils/connections.py::resolve_relay_max_results`][utils-connections] — the request policy is a **ceiling over** whichever cap won, and both the plan-time and the resolve-time cap come from that same helper, so they are the same number by construction. `ValueError` from negative / over-max sizes and `TypeError` from malformed cursor values are caught by `_plan_connection_relation`, which emits **no** window prefetch (so the per-parent pipeline raises the cursor/cap error at the nested field's own error path, not at the root planner) but still records the connection's resolver identities in `plan.planned_resolver_keys`. Recording the key is the load-bearing distinction from the other [Decision 6](#decision-6--refusal-arms-divergent-aliases-hints-and-scalar-only-connections) fallbacks: it keeps strictness ([Decision 8](#decision-8--strictness-mode-wiring-for-connection-paths)) from preempting the real pagination error with a spurious `OptimizerError("Unplanned N+1")` under `"raise"` — error locality wins for a malformed slice, whereas the [Decision 6](#decision-6--refusal-arms-divergent-aliases-hints-and-scalar-only-connections) refusal arms stay unplanned so strictness CAN flag a whole-relation refusal as a genuine per-parent access.
- **`to_attr` isolation**: the window lands on a `_dst_`-namespaced attribute, never the relation accessor. The [`"both"`][glossary-metarelation_shapes] shape — an explicit opt-in that keeps the list sibling beside the connection — means both can be selected together; two `Prefetch`es on one accessor with different querysets is Django's "lookup already seen" error, and a windowed result would silently corrupt the list field's semantics. The `to_attr` gives the window its own slot; the list field's accessor-keyed prefetch (when its selection plans one) is untouched. The grammar has two forms, both owned by `optimizer/nested_planner.py::relation_connection_to_attr`: `_dst_<field>_connection` for a relation whose selections agree on their arguments, and `_dst_<field>$<response key>_connection` for each key of a divergent-alias selection, which plans one window per key. `$` is the separator because Django splits `prefetch_to` on `LOOKUP_SEP`, so a `__` in a `to_attr` would be read as a lookup path. The `_dst_` prefix is the package's reserved namespace (consistent with `_dst_optimizer_*` context keys and the `_dst_synthesized_relation_connection` marker).
- **Resolver keys**: the connection field's resolver identities (declaring type + **relation** field name + runtime paths, the same `resolver_key` vocabulary list relations use) are appended to `plan.planned_resolver_keys` so strictness ([Decision 8](#decision-8--strictness-mode-wiring-for-connection-paths)) sees the field as planned. The runtime path carries the connection's response key (`booksConnection`); the field-name component is the relation field (`books`), so the resolve-time `_check_n1` key matches by construction.

Rationale companion — this Decision's justification and its four rejected alternatives: [Decision 4][rationale-d4].

### Decision 5 — Connection-class fast path with annotation-presence detection and a per-parent fallback

`_build_relation_connection_resolver` does **not** construct a connection object. Strawberry's `ConnectionExtension.resolve` calls the field resolver for a node iterable and then invokes the generated connection class's `resolve_connection`; returning a prebuilt connection from the resolver would feed that connection object back through `resolve_connection` as if it were the node iterable. The resolver's fast-path responsibility is therefore limited to a handoff:

- probe the precomputed `to_attr` on `root`. The synthesized resolver is built once at finalization and is otherwise handed only the instance **accessor**, which diverges from the field name for a reverse relation without `related_name` (`field.name == "book"`, accessor `"book_set"`, generated `book_connection`, `to_attr` `_dst_book_connection`); deriving the probe from the accessor would compute the wrong attribute and the fast path would silently never fire for exactly the reverse-no-`related_name` shape the package special-cases everywhere else. `_build_relation_connection_resolver` therefore takes the relation field name (or the precomputed `_dst_<field>_connection` string) as an **explicit constructor parameter**, which `_synthesize_relation_connections` passes from `field.name` — the same key the slot, the generated attribute, and the `to_attr` are all built from — when it constructs the resolver. The probe is then `getattr(root, <precomputed to_attr>, None)`;
- the probe is per response key first, then shared: the resolver looks for `_dst_<field>$<info.path.key>_connection` (the divergent-alias form) before falling back to `_dst_<field>_connection`, and threads whichever attribute held rows into the strictness probe ([Decision 8](#decision-8--strictness-mode-wiring-for-connection-paths));
- when the value is a list whose rows carry `_dst_row_number`, and the resolver's own `filter` / `order_by` kwargs are absent, wrap it in an internal `_WindowedConnectionRows` marker. The probe reads the **row number only**; `_dst_total_count` is annotated conditionally ([Decision 4](#decision-4--windowed-prefetch-planning-under-a-package-reserved-to_attr)), so demanding it would refuse every count-free page and every strategy that synthesizes row numbers without a count. The marker carries exactly two things: the rows, and a zero-argument `fallback` callable that re-runs the per-parent pipeline. It deliberately carries **no** slice metadata — Strawberry's `ConnectionExtension.resolve` consumes `first` / `last` / `before` / `after` and forwards them only to `resolve_connection`, so the resolver cannot classify its own rows and every window classification happens in `resolve_connection`, which re-derives the bounds through the same [`utils/connections.py`][utils-connections] helper the walker planned with. That is the stronger cursor-parity guarantee: the resolve-time window is computed by the plan-time helper rather than trusted from a value the resolver stashed. The `fallback` callable exists because `resolve_connection` cannot rebuild the per-parent relation manager the resolver holds;
- when sidecar kwargs are present, ignore the window and run the pipeline; a future planner/argument desync must degrade to the correct filtered query, never to an unfiltered window;
- when the attribute is absent, or present without the annotations, run the shipped per-parent pipeline unchanged.

[`connection.py::DjangoConnection.resolve_connection`][connection] is the single override every generated connection class inherits; it detects `_WindowedConnectionRows` after the existing `first`+`last` guard and before delegating to Strawberry's list slicing. Whether the class also serves `totalCount` is a `ClassVar` the generated total-count class sets, not a second `resolve_connection` — so there is one dispatch site, and the count opt-in cannot drift away from the window handling. The fast path builds the Relay object there:

- edges are built through the generated edge class's `resolve_edge(..., cursor=<zero_based_offset>)`; the cursor prefix stays owned by Strawberry's edge type. The positional offset cursor is `_dst_row_number - 1` for **every** window, including the `last`-only reversed one: [Slice 1's `apply_window_pagination`](#decision-4--windowed-prefetch-planning-under-a-package-reserved-to_attr) keeps `_dst_row_number` as the **forward** row number for all windows (mirroring upstream `strawberry-django`, which keeps `_strawberry_row_number` forward and adds a separate `_strawberry_row_number_reversed` purely for the plan-time `__lte` filter) and never overwrites it with reversed numbering. So the rows of a `last: 2` page of five arrive in forward order numbered `4, 5`, and the forward absolute-offset cursor matches the pipeline's `ListConnection` cursors directly. Byte-parity is proven by `test_fast_path_wire_parity_last_only`.
- `pageInfo` is derived from the edge rows and the bounds `resolve_connection` re-derived. `has_previous_page` is true when the first row is past row 1, or when a keyset cursor was supplied. `has_next_page` follows the window's own [`FetchMode`][utils-connections], one of four answers: the count-free n+1 probe reports whether the sentinel row arrived; a counted keyset-seek page compares the row number against the seek count in the value domain; the shapes that are `False` by construction — an unbounded forward page, and the reversed `last`-only page — report `False` without consulting anything; and a counted offset page makes the forward comparison against `_dst_total_count`. Because the row numbers stay forward for every window, all four land on the pipeline's values, the reversed `last`-only window included.
- `totalCount` (when the target's [`Meta.connection`][glossary-metaconnection] opted in and the field is selected) is read from `_dst_total_count` on any annotated row. The window handling branches before `_guard_total_count_countable` / `.count()`, so the marker is treated as an annotated optimized source, not as an uncountable non-queryset iterable. A page whose selection needs a count-derived answer from a window that carries no count does not guess: it returns to the per-parent pipeline through the marker's `fallback`, and the check runs before any edge is built so the recovery discards no work.
- **`first: 0` and an overshot `after:` are served from the window, not fallen back.** These two shapes would otherwise be indistinguishable from a genuinely childless parent, so the plan keeps each partition's **row 1 as a marker row**: the range filter ORs it in, and the marker-only list carries the real count and page flags. `first: 0` then serves `edges: []` with `hasNextPage: true` and the true `totalCount`; an overshot `after:` serves `edges: []` with `hasPreviousPage: true`, and when the window is count-free the marker still proves `total <= offset`. One query, no per-parent fallback. Consequently an **empty** rows list now *proves* the parent has no related rows — a parent with children would have kept its marker row or its probe sentinel — and that parent is served `totalCount = 0`, no cursors, `has_next_page` `False`, and `has_previous_page = offset > 0`.
- SDL identity, the `first`+`last` guard, and the `totalCount` member shape remain identical because the generated connection class is the only layer constructing the connection instance.

When the wrapper is absent, the generated connection class delegates to the shipped path — correctness never depends on the plan having fired, **whenever** the window is absent or unsafe to consume. No optimizer installed, strictness off, any [Decision 6](#decision-6--refusal-arms-divergent-aliases-hints-and-scalar-only-connections) refusal arm, and a consumer's own prefetch are the common causes, and the list is deliberately open rather than exhaustive. An unwindowable child queryset needs no resolver-side branch of its own — because the relation is never window-planned, no `to_attr` is written, the probe misses, and the per-parent pipeline (which counts correctly) runs.

**`last: 0` is the one shape that always degrades, and does so on purpose.** Strawberry's `edges[-0:]` slices to the *whole* set rather than to nothing, so a `last: 0` page serves every edge. Rather than special-case that quirk inside the window, the planner leaves `last: 0` fully unplanned: no window prefetch is emitted, no resolver key is recorded, the per-parent pipeline reproduces the quirk byte-for-byte, and strictness sees the access like any other unplanned one. The resolver keeps a defensive `reverse and limit == 0` tail for direct callers.

Rationale companion — this Decision's justification and its four rejected alternatives: [Decision 5][rationale-d5].

### Decision 6 — Refusal arms, divergent aliases, hints, and scalar-only connections

Nine nested-connection shapes are **not** window-planned; each resolves per-parent through the shipped pipeline (and a whole-relation refusal is therefore visible to strictness as unplanned). Non-planning has two granularities: a **per-response-key** refusal leaves one alias unplanned while its siblings still plan, and a **whole-relation** refusal leaves the relation unplanned for every key. Source comments and test docstrings cite an arm **by its content** ("the unwindowable-child-queryset refusal arm"), never by ordinal and never by this Decision's heading text, so neither a renumbering nor a rename can silently falsify a citation. The refusal arms, with the site that decides each:

1. **Sidecar input** (`filter:` / `orderBy:` arguments on the nested selection) — *per key*, `optimizer/nested_planner.py::_divergent_key_windows #"sidecar arguments"`. Baking sidecar application into plan-time child querysets means request-scoped input values inside cached plans and `FilterSet.apply_sync`'s `info`-dependence at walk time — a real design surface (input normalization, permission gates, cache-key explosion) deferred whole. The fallback is functionally identical to the shipped behavior.
2. **A window Strawberry's slice arithmetic cannot express** — `after` combined with `last`, an inverted `after` / `before` interval, and every backward keyset shape — *per key*, raised as `UnwindowableConnection` by [`utils/connections.py::derive_connection_window_bounds`][utils-connections] (and its keyset twin `::derive_keyset_window_bounds`) and routed to a fallback rather than approximated.
3. **`last: 0`** — *per key*, `optimizer/nested_planner.py::_divergent_key_windows #"if reverse and limit == 0:"`. Upstream's `edges[-0:]` serves *every* edge for `last: 0`; reproducing that quirk from a window is not worth a special case, so the shape is left unplanned deliberately, the per-parent pipeline reproduces it byte-for-byte, and strictness sees the access.
4. **One response key carrying two conflicting argument payloads** — *whole relation*, `optimizer/nested_planner.py::plan_connection_relation #"if response_key_arguments_conflict(sel):"`. Two selections merging onto one response key with different arguments have no single correct window.
5. **[`OptimizerHint.SKIP`][glossary-optimizerhint] on the underlying relation** — *whole relation*. SKIP means "the optimizer leaves this relation alone"; that contract extends to the relation's connection sibling.
6. **An unwindowable child queryset** — *whole relation*, classified before the child plan is applied by [`optimizer/nested_fetch.py::unwindowable_child_queryset_reason`][nested-fetch], which names five reasons: `sliced`, `select_for_update`, `combined`, `distinct`, `values`. The `distinct` reason is the correctness-critical one: SQL evaluates window functions before `DISTINCT`, so the `_dst_total_count` `Count(1) OVER` annotation would over-count a de-duplicated child queryset (typically a visibility/permission [`get_queryset`][glossary-get_queryset-visibility-hook] that joins and de-duplicates), and shipping a silently wrong `totalCount` is worse than a per-parent count that is right. The classifier runs on the **base** child queryset, so one strategy-independent gate answers for every fetch backend and no post-build re-check is needed ([Decision 4](#decision-4--windowed-prefetch-planning-under-a-package-reserved-to_attr)).
7. **An unwindowable relation kind** — *whole relation*, `optimizer/nested_planner.py::plan_connection_relation` on a `join.windowable` of `False` from [`optimizer/join_taxonomy.py::classify_relation_join`][join-taxonomy]. The classifier never raises; an unsupported kind returns unplanned.
8. **A relation the field map cannot resolve** (no `field_map` entry, or `related_model is None`) — *whole relation*.
9. **A window the active fetch strategy refused for every response key** — *whole relation*, `optimizer/nested_planner.py::plan_connection_relation #"if not planned_keys:"`. The child plan is built against a throwaway `sub_plan` and absorbed into the parent only once at least one key planned, so a refusal leaks no resolver key, FK-id elision, or `cacheable` flip into the parent plan.

Two shapes that read like fallbacks and are **not**:

- **Aliased duplicates with divergent pagination arguments** (`a: booksConnection(first: 2)` + `b: booksConnection(first: 5)`) are window-planned, **one window per response key**, each under its own `_dst_<field>$<key>_connection` `to_attr` ([Decision 4](#decision-4--windowed-prefetch-planning-under-a-package-reserved-to_attr)). Django accepts several `Prefetch`es on one accessor as long as their `to_attr`s differ, so one `to_attr` per key is enough; both keys' resolver identities are recorded, and the shared `_dst_<field>_connection` attribute is not written for a divergent selection. Identical-argument aliases still merge into one window. The residual fallback is the case where *every* alias is itself one of the refusal arms above.
- **`pageInfo`-only and `totalCount`-only selections** are planned. They do not need a node child plan, but they do need the same per-parent row-number / count metadata and the same strictness silence as an edge-bearing connection. Planning them (rather than turning a harmless scalar metadata selection into a strictness error with no field-level remediation) is the load-bearing contract; with no node-child scalars to narrow to, the window is projected to the minimal pk / connector / deterministic-order columns rather than the full row (see [Decision 4](#decision-4--windowed-prefetch-planning-under-a-package-reserved-to_attr)'s scalar-only bullet).

**Hints shape the window as well as suppress it.** `select_related()` is invalid for a many-side relation anyway, and `prefetch_related()` applies to the list-shaped planning only. Two hint shapes do reach the window: [`OptimizerHint`][glossary-optimizerhint]`.strategy(name)` selects the nested-connection fetch backend for one connection field, overriding the extension instance's `nested_connection_strategy=` and the `NESTED_CONNECTION_STRATEGY` setting ([Decision 4](#decision-4--windowed-prefetch-planning-under-a-package-reserved-to_attr)); and an `OptimizerHint.prefetch(Prefetch(..., to_attr=...))` on a generated relation raises [`ConfigurationError`][glossary-configurationerror] at plan time rather than coexisting with the window — a consumer `to_attr` and the package's own can never collide, because the pairing is refused outright. A plain `OptimizerHint.prefetch(Prefetch(obj))` still targets the accessor and leaves the window alone.

Rationale companion — this Decision's justification and its two rejected alternatives: [Decision 6][rationale-d6].

### Decision 7 — Plan-cache key hygiene: nested pagination variables hash, root pagination arguments do not

[`_build_cache_key`][extension] gains pagination-variable collection: walk the operation (and reachable fragments) for `first` / `last` / `before` / `after` arguments whose value is a variable reference **on non-root field nodes**, and fold those variables' values into the existing `relevant_vars` frozenset. The directive-variable and pagination-variable name sets are memoized per operation identity in the same per-execution style as the printed-AST cache, so nested fallback connection pipelines do not re-walk the full AST per parent row.

- **Why nested values must key the cache**: Slice 1 bakes the resolved values into windowed prefetch querysets. Two requests sharing a printed AST (`booksConnection(first: $n)`) but differing in `$n` would otherwise share one cached plan — and serve one request's page size to the other. This is a correctness rule, not an optimization.
- **Why root values must not**: a root connection's pagination happens post-plan in `ConnectionExtension`; plan content is invariant in them. Hashing them would fragment B1's cache across every page of every consumer pagination loop — the card's "skip pagination args that do not affect selection shape".
- **Fragment traversal preserves response-path depth**: the collector tracks depth at the spread site, not raw fragment-definition nesting. A root connection selected inside a fragment on `Query` is still root and stays out; a nested connection selected inside a fragment on a parent node is still nested and keys the cache.
- **The collection is a syntactic superset by design**: any non-root field's pagination-named variable is collected, including on fields that are not connections (a custom resolver with a `first:` arg). Over-collection costs duplicate cache entries for identical plans (cheap, bounded by the LRU); under-collection serves wrong data. The same asymmetry argument the directive-variable collection already encodes.
- **The AST walk is shared and memoized**: Slice 3 must not add a second full-operation walk to a path that nested fallback connections call per parent. The implementation should derive directive and pagination variable name sets from one reachable-fragments traversal and store them on the extension's execution-local memo keyed by `id(operation)`.
- **Inline literals** already key the cache via the printed AST — for nested windows that is now load-bearing (two literal `first:` values genuinely need two plans); for root arguments it remains a pre-existing, harmless fragmentation, recorded in [Risks and open questions](#risks-and-open-questions).
- **Cacheable plans and visibility-bearing targets are disjoint**: a windowed plan caches only when **no** windowed target overrides [`get_queryset`][glossary-get_queryset-visibility-hook] — baking a request-scoped visibility queryset flips `plan.cacheable = False` (the shipped request-scope rule, untouched and inherited by [Decision 4](#decision-4--windowed-prefetch-planning-under-a-package-reserved-to_attr)). So the flagship library shape (`allLibraryGenresConnection { … booksConnection { … } }`, where `BookType.get_queryset` filters `circulation_status="repair"` for non-staff) is uncacheable for that orthogonal reason, and Slice 3's nested-pagination-variable correctness rule is exercised by **non-visibility synthetic targets**, not the cookbook shape. The Slice 5 fixed-query-count library pins and the Slice 3 cache pins therefore use **different fixtures** — stated here so a reviewer does not assume the library example covers both.

Rationale companion — this Decision's justification and its three rejected alternatives: [Decision 7][rationale-d7].

### Decision 8 — Strictness-mode wiring for connection paths

The synthesized relation connection resolver fires the B3 contract when **all three** hold:

1. **strictness is not `"off"` for this execution**, read from the per-execution `_active_strictness` [`ContextVar`][context] armed at `on_execute` entry, falling back to the `DST_OPTIMIZER_STRICTNESS` stash. The `ContextVar` is what makes the condition reachable at all: the stash is unavailable to an execution that runs without a `context_value`, and it is written at plan-publish time, so an operation whose root resolver returns something the walker cannot plan never publishes it. Reading only the stash leaves a configured N+1 guard silently disarmed in both shapes;
2. **the field's resolver key is not planned** — declaring type + **relation** field name + runtime path, the shared `resolver_key` vocabulary. "Planned" is satisfied by the `DST_OPTIMIZER_PLANNED` stash **or** by the per-execution scoped-relations set, which every execution publishes whether or not strictness is on;
3. **the fast-path `to_attr` is absent on `root`** (the access will actually query).

Then: `OptimizerError` under `"raise"`, logged warning under `"warn"` — by parameterizing [`types/resolvers.py::_check_n1`][resolvers] (explicit `kind="connection_to_attr"`, the `to_attr` probe, the relation field name, and an optional fallback reason) rather than duplicating its logic in `connection.py`. The resolver key (and therefore the flagged message) is keyed on the underlying relation field name (`books`), NOT the generated `books_connection` attribute, so it is byte-uniform with the list-relation message and with the key the walker emits — a consumer who selected `booksConnection` is pointed at the `books` relation that backs it.

Fallback nested connections still call the root connection pipeline per parent. [`optimizer/extension.py::_publish_plan_to_context`][extension] therefore unions `DST_OPTIMIZER_FK_ID_ELISIONS`, `DST_OPTIMIZER_PLANNED`, and `DST_OPTIMIZER_LOOKUP_PATHS` into any existing frozenset stash rather than overwriting. Branch-sensitive resolver keys embed runtime paths, so parent and child plans can coexist without false positives. `DST_OPTIMIZER_PLAN` remains last-wins introspection data; the correctness sentinels are the unioned sets.

Rationale companion — this Decision's justification and its two rejected alternatives: [Decision 8][rationale-d8].

### Decision 9 — The `edges { node }` selection helpers consolidate into one module both consumers import

## Edge cases and constraints

- **`"both"` shape with both siblings selected** — the list field's accessor-keyed prefetch, a consumer's existing plain accessor prefetch, and the connection's `to_attr` window coexist on one relation with no Django duplicate-lookup error; the list field returns the **full** related set, the connection returns the windowed page. Pinned at the plan-object level by a dedicated `diff_plan_for_queryset` test AND, for the consumer-visible behavior, LIVE over `/graphql/` by `test_list_relation_and_connection_sibling_coexist_live` (Slice 5 — list full set + connection page resolve together at a flat query count; round-3 live-coverage G1).
- **Identical-argument aliases merge into one window; divergent ones get one window each.** The walker preserves per-response-key argument payloads so resolved pagination and sidecar arguments can be compared before window planning. Divergent aliases plan one `Prefetch` per response key under the per-key `to_attr` grammar, record both keys' resolver identities, and leave the shared `_dst_<field>_connection` attribute unwritten; the tests assert the set of `to_attr`s and the resolver-key count, not merely that the query resolves. The residual fallback is the case where every alias is itself a refusal arm ([Decision 6](#decision-6--refusal-arms-divergent-aliases-hints-and-scalar-only-connections)).
- **M2M shared children** — two parents sharing the same child still get per-parent pages because the partition key is the through-table parent-side key, not child pk. Pinned for both forward and reverse M2M at the partition-expression level, and live over `/graphql/` by `test_nested_total_count_no_per_parent_count` (three books sharing four genres, each parent's page and `totalCount` correct).
- **Recursion terminates structurally.** A windowed child plan may itself contain a windowed prefetch (the two-level cookbook shape); depth is bounded by the validated query depth, the same bound the walker already rides.
- **`first: 0` and overshot `after:`** — a window that returned no rows for these shapes would be indistinguishable from a genuinely empty parent, so the plan retains each partition's row 1 as a **marker row**. Both shapes are served from the window in one query: `first: 0` returns empty edges with `hasNextPage: true`, an overshot `after:` returns empty edges with `hasPreviousPage: true`, and either carries the true `totalCount` when the window was counted (when it was not, the marker still proves `total <= offset`).
- **Parents with no related rows** — a physically empty rows list, which now *proves* the parent has no children, because a parent with children would have kept its marker row or its probe sentinel; `totalCount` is `0`, `hasNextPage` is `False`, `hasPreviousPage` is `offset > 0`, and no fallback is triggered.
- **`last: 0`** — the one shape that is always left fully unplanned, deliberately: Strawberry's `edges[-0:]` serves every edge rather than none, the per-parent pipeline reproduces that quirk byte-for-byte, and strictness sees the access ([Decision 5](#decision-5--connection-class-fast-path-with-annotation-presence-detection-and-a-per-parent-fallback) / [Decision 6](#decision-6--refusal-arms-divergent-aliases-hints-and-scalar-only-connections)).
- **`last`-only backward pagination** — the windowed prefetch's `reverse` branch filters the tail rows, but `_dst_row_number` stays **forward** (Slice 1 keeps it forward and uses `_dst_row_number_reversed` only for the plan-time `__lte` filter; see [Decision 5](#decision-5--connection-class-fast-path-with-annotation-presence-detection-and-a-per-parent-fallback)), so the resolver's positional cursor is the uniform `_dst_row_number - 1` and the flags land on the pipeline's values — `has_next_page` through the constant-`False` arm of the four-way fork rather than a comparison. The windows the slice arithmetic cannot express — `after` combined with `last`, an inverted `after` / `before` interval, and every backward keyset shape — are raised as `UnwindowableConnection` and fall back per key rather than being approximated. The exact supported set follows `SliceMetadata`'s arithmetic and is pinned by tests, not prose.
- **`relay_max_results` agreement** — the cap is resolved by one shared helper on both sides: the schema config's `relay_max_results` (available at request time; the walker runs per-request), lowered by the request policy's `max_page_size` when that is smaller. A window can therefore never be narrower or wider than the resolve-time cap; a consumer raising the cap via [`strawberry_config`][glossary-strawberry_config]`(relay_max_results=...)` affects both sides through the one config object, and a request policy tightens both together.
- **Visibility-filtered targets** — the windowed child queryset bakes the target's [`get_queryset`][glossary-get_queryset-visibility-hook] (plan `cacheable = False`, the shipped request-scope rule); row numbers and `_dst_total_count` are computed **post-visibility**, so a nested `totalCount` counts visible rows only — identical to the pipeline path's post-`get_queryset` count. The live Slice-5 test pins this through `BookType`'s `circulation_status="repair"` filter. Because the visibility queryset makes the plan uncacheable, Slice 3's plan-cache pins cannot use this shape — they use non-visibility synthetic targets, and the Slice 5 library pins (fixed query count) and the Slice 3 cache pins use different fixtures ([Decision 7](#decision-7--plan-cache-key-hygiene-nested-pagination-variables-hash-root-pagination-arguments-do-not)). If a target's `get_queryset` additionally `.distinct()`es, the relation is left unplanned entirely (next bullet).
- **Unwindowable child querysets are left unplanned** — `distinct` is one of five reasons the base-queryset classifier names, alongside `sliced`, `select_for_update`, `combined`, and `values`. For `distinct` the reason is correctness: SQL evaluates window functions before `DISTINCT`, so the `_dst_total_count` `Count(1) OVER` annotation would over-count a de-duplicated child queryset (from the target's `get_queryset` or a custom default manager), and falling back per-parent counts correctly ([Decision 4](#decision-4--windowed-prefetch-planning-under-a-package-reserved-to_attr) / [Decision 6](#decision-6--refusal-arms-divergent-aliases-hints-and-scalar-only-connections)). Pinned by `test_distinct_child_queryset_left_unplanned_for_correct_total_count`.
- **Secondary `DjangoType`s with divergent `relation_shapes`** — nested recognition reads the model's **primary** type's `relation_connections` slot ([Decision 3](#decision-3--walker-recognition-is-definition-metadata-driven-not-name-pattern-guessing)), inheriting `field_map`'s primary-resolution rule; a secondary `DjangoType` that shapes a relation differently from the primary is out of scope for windowed planning in `0.0.9` and falls back per-parent (visible to strictness). Pinned by `test_secondary_type_relation_shapes_nested_recognition`.
- **Consumer cooperation (B8)** — a consumer `Prefetch` on the relation accessor and the window's `to_attr` prefetch are distinct lookups; `diff_plan_for_queryset`'s exact-match and absorption rules see different keys and never merge them. The `"both"` relation test selects the list sibling, the connection sibling, and a consumer accessor prefetch together. A consumer who prefetches **the `to_attr` name itself** is writing into the package-reserved `_dst_` namespace — explicitly unsupported, documented, not guarded.
- **FK-id elision and `only()` inside windows** — child plans are ordinary plans: nested forward-FK `{ id }`-only selections elide, scalar projections apply, connector and ordering columns are force-included so the partition and `ORDER BY` never hit deferred-field refetches. Window annotations are annotations — they compose with `.only()`.
- **Multi-database** — the windowed child queryset follows the shipped generated-`Prefetch` alias rule (it does NOT inherit the root alias; [Multi-database cooperation][glossary-multi-database-cooperation] axis 3); window functions execute on whatever alias the child queryset resolves to.
- **Plan immutability** — the windowed `Prefetch` rides `append_prefetch_unique` and the finalize-to-tuple discipline; cached windowed plans are copied before diffing like every plan (B1 cache-immutability property, re-affirmed by the Slice-3 tests).
- **Backend floor** — window functions with `QuerySet.filter` against them require Django ≥ 4.2 and a window-capable backend; the package floor is `Django>=5.2` and every supported CPython bundles SQLite ≥ 3.25, so the windowed strategy ships with no conditional path. A consumer on an exotic backend without window support gets that backend's `NotSupportedError` — surfaced, not swallowed. The window-capability caveat is the **windowed** strategy's; the `"auto"` strategy resolves per effective database alias, using the Postgres lateral backend where the alias and query shape support it and the same bounded window everywhere else, so a backend choice changes performance rather than pagination correctness ([Decision 4](#decision-4--windowed-prefetch-planning-under-a-package-reserved-to_attr)).
- **The outer `totalCount` predicate stays direct-children-scoped** — a nested connection's `totalCount` must not fire the outer connection's count (`_total_count_requested` already checks direct children only; re-affirmed by a Slice-2 test now that nested `totalCount` is common).
- **No existence/behavior change for unplanned shapes** — every fallback resolves byte-identically to today's pipeline output; the fallback tests assert wire parity, not just non-error.
