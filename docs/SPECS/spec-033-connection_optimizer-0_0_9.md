# Spec: Connection-aware optimizer planning — windowed nested-connection prefetches, pagination-aware plan-cache keys, strictness wiring for connection paths, and the products connections-only conversion

Shipped in `0.0.9` (card [`DONE-033-0.0.9`][kanban]), the last member of the `0.0.9` Relay cohort. The optimizer plans the nested `<field>Connection` siblings that [`DONE-032-0.0.9`][kanban]'s relation-as-Connection upgrade synthesizes, beside the root-connection planning [`DjangoConnectionField`][glossary-djangoconnectionfield] ([`DONE-030-0.0.9`][kanban]) carries. The [Slice checklist](#slice-checklist) stays unticked because the `Status:` line is the completion source of truth (the shipped-spec convention); the [Current state](#current-state) section maps where the surface lives in the package.

Status: **SHIPPED (`0.0.9`)** — card [`DONE-033-0.0.9`][kanban], released under the [`CHANGELOG.md`][changelog] `## [0.0.9]` heading. Seven slices: Slice 1 (the **plan-side foundation** — the consolidated selection helpers, the synthesis-metadata slot on [`DjangoTypeDefinition`][definition], argument-aware alias classification, union-published optimizer sentinels, walker recognition of synthesized relation connections, and relation-kind-correct windowed-`Prefetch` planning under a package-reserved `to_attr` — [Decision 3](#decision-3--walker-recognition-is-definition-metadata-driven-not-name-pattern-guessing) / [Decision 4](#decision-4--windowed-prefetch-planning-under-a-package-reserved-to_attr) / [Decision 9](#decision-9--the-edges--node--selection-helpers-consolidate-into-one-module-both-consumers-import)), Slice 2 (the **connection-class fast path** — the synthesized relation connection resolver hands the `to_attr` rows to the generated connection class in an internal wrapper, and the class derives `edges` / cursors / `pageInfo` / `totalCount` from the annotations, falling back per parent whenever the window is absent or unsafe to consume — [Decision 5](#decision-5--connection-class-fast-path-with-annotation-presence-detection-and-a-per-parent-fallback)), Slice 3 (**plan-cache key hygiene** — nested-connection pagination *variables* key the plan cache; ## Key glossary references

Skim these [`docs/GLOSSARY.md`][glossary] entries first — they anchor the vocabulary used throughout the spec:

- [Connection-aware optimizer planning][glossary-connection-aware-optimizer-planning] — this card's entry.
- [`DjangoConnectionField`][glossary-djangoconnectionfield] / [`DjangoConnection`][glossary-djangoconnection] — the [`DONE-030-0.0.9`][kanban] connection surface. A root connection's pre-slice queryset plans through `apply_connection_optimization`; a nested relation connection plans through this card's windowed prefetch.
- [`Meta.relation_shapes`][glossary-metarelation_shapes] — the [`DONE-032-0.0.9`][kanban] key whose synthesized `<field>Connection` siblings are this card's planning target (`"connection"` is the default; `"both"` keeps the list sibling beside the connection). Its async-`get_queryset` `SyncMisuseError` caveat stands ([Non-goals](#non-goals)).
- [`DjangoOptimizerExtension`][glossary-djangooptimizerextension] — the schema extension whose `apply_to` seam, plan cache, `strictness`, and `nested_connection_strategy=` constructor argument this card's planning runs through.
- [Plan cache][glossary-plan-cache] — the B1 cache whose key carries the nested-pagination-variable component ([Decision 7](#decision-7--plan-cache-key-hygiene-nested-pagination-variables-hash-root-pagination-arguments-do-not)); variables that do not affect the plan stay out of the key.
- [Strictness mode][glossary-strictness-mode] — the B3 contract; [`types/resolvers.py::_check_n1`][resolvers] serves the generated list-relation resolvers and, with `kind="connection_to_attr"`, the synthesized relation connections.
- [Queryset diffing][glossary-queryset-diffing] — the B8 reconciliation; the windowed prefetch rides `append_prefetch_unique` / `diff_plan_for_queryset` like every generated `Prefetch`.
- [FK-id elision][glossary-fk-id-elision] / [`only()` projection][glossary-only-projection] — plan vocabulary the windowed child plans reuse unchanged; the window adds *annotations*, which compose with `.only()`.
- [`OptimizerHint`][glossary-optimizerhint] / [`Meta.optimizer_hints`][glossary-metaoptimizer_hints] — the per-relation override surface; `SKIP` leaves the relation's connection sibling unplanned, `strategy(...)` selects the fetch backend for one connection field, and a `prefetch(...)` hint never reaches the window ([Decision 6](#decision-6--refusal-arms-divergent-aliases-hints-and-scalar-only-connections)).
- [`Meta.connection`][glossary-metaconnection] — the target-type `total_count` opt-in; a windowed nested connection serves `totalCount` from the `_dst_total_count` annotation, and `first: 0` / overshot `after:` pages are served from a retained partition marker row rather than a per-parent fallback ([Decision 4](#decision-4--windowed-prefetch-planning-under-a-package-reserved-to_attr) / [Decision 5](#decision-5--connection-class-fast-path-with-annotation-presence-detection-and-a-per-parent-fallback)).
- [`get_queryset` visibility hook][glossary-get_queryset-visibility-hook] — baked into windowed child querysets exactly as into every generated `Prefetch` child queryset (and with the same consequence: the plan goes `cacheable = False`).
- [`FilterSet`][glossary-filterset] / [`OrderSet`][glossary-orderset] / [`Meta.filterset_class`][glossary-metafilterset_class] / [`Meta.orderset_class`][glossary-metaorderset_class] — the sidecars whose `filter:` / `orderBy:` arguments a nested connection may carry; a response key with sidecar input is **not** window-planned and resolves per parent ([Decision 6](#decision-6--refusal-arms-divergent-aliases-hints-and-scalar-only-connections)).
- [`filter_input_type`][glossary-filter_input_type] / [`order_input_type`][glossary-order_input_type] — the explicit-argument helpers for hand-written resolvers; the connections-only products `Query` uses neither, because [`DjangoConnectionField`][glossary-djangoconnectionfield] synthesizes the same arguments from the sidecars.
- [`DjangoType`][glossary-djangotype] / [Relay Node integration][glossary-relay-node-integration] / [`Meta.interfaces`][glossary-metainterfaces] — all four products types are Relay-Node-shaped, which is why their many-side relations synthesize connection siblings.
- [Definition-order independence][glossary-definition-order-independence] / [`finalize_django_types`][glossary-finalize_django_types] — the synthesis metadata the walker reads is recorded at finalization Phase 2.5, after relation targets settle.
- [Relation handling][glossary-relation-handling] — list-shaped relation planning is untouched; the windowed prefetch is an *additional* plan entry under a `to_attr`, never a replacement for the list field's accessor-keyed prefetch.
- [`DjangoListField`][glossary-djangolistfield] — root-gated list planning is untouched; the products `Query` uses none.
- [`SyncMisuseError`][glossary-syncmisuseerror] — the async-`get_queryset`-through-a-synthesized-connection contract ([Non-goals](#non-goals)).
- [Multi-database cooperation][glossary-multi-database-cooperation] — windowed child querysets follow the generated-`Prefetch` alias rules (they do NOT inherit the root alias); the window adds annotations only.
- [Schema audit][glossary-schema-audit] — the audit walks relation fields, and synthesized connection siblings resolve through the same targets.
- [`Meta.search_fields`][glossary-metasearch_fields] — planned for `0.1.2` ([`TODO-BETA-060-0.1.2`][kanban]); no connection generates a `search:` argument.
- [`ConfigurationError`][glossary-configurationerror] — this card adds no `Meta` key and no public symbol; the plan-time refusal of a `to_attr` prefetch hint is a `ConfigurationError` ([Error shapes](#error-shapes)).
- [`strawberry_config`][glossary-strawberry_config] — its `relay_max_results` passthrough is the page-size cap the plan-time window math honors ([Decision 4](#decision-4--windowed-prefetch-planning-under-a-package-reserved-to_attr)).
- [Cross-subsystem invariants][glossary-cross-subsystem-invariants] — "filters, orders, … and connection fields all compose with `DjangoOptimizerExtension`" is the `1.0.0` invariant this card completes for the connection half.

## Slice checklist

Each top-level item maps to one review unit: six functional slices (1→2, then 3 and 4 on 1–2, 5 on 2, 6 on 2–5) plus the doc + card-completion wrap (7).

- [ ] Slice 1: plan-side foundation — synthesis metadata, argument-aware alias handling, walker recognition, relation-kind-correct windowed-`Prefetch` planning (per [Decision 3](#decision-3--walker-recognition-is-definition-metadata-driven-not-name-pattern-guessing) / [Decision 4](#decision-4--windowed-prefetch-planning-under-a-package-reserved-to_attr) / [Decision 9](#decision-9--the-edges--node--selection-helpers-consolidate-into-one-module-both-consumers-import))
  - [ ] The `edges { node }` selection-unwrap helpers (`named_children`, `node_children_with_runtime_prefix`, `with_runtime_prefix`, `should_include`, `is_fragment`, `included_field_selections`, `response_key` / `response_keys`, `connection_node_children`) are public names in [`optimizer/selections.py`][selections]; [`optimizer/walker.py`][walker] and [`optimizer/extension.py`][extension] both import them from there, and neither imports them from the other ([Decision 9](#decision-9--the-edges--node--selection-helpers-consolidate-into-one-module-both-consumers-import)). `_connection_node_child_selections` stays in `extension.py` (the root-seam entry point) as a thin composition over `selections.connection_node_children`.
  - [ ] [`types/finalizer.py::_synthesize_relation_connections`][finalizer] records, on the declaring type's [`DjangoTypeDefinition`][definition], a `relation_connections: dict[str, str]` slot mapping each generated Python attribute name (`"books_connection"`) to its underlying relation field name (`"books"`). The walker reads this slot — never the `_dst_synthesized_relation_connection` marker on field objects, never `connection.py` internals — to recognize a nested connection selection (card DoD: "without reaching into `DjangoConnectionField` internals").
  - [ ] [`optimizer/walker.py::_merge_aliased_selections`][walker] keeps per-response-key argument payloads on a merged selection (`_record_response_key_arguments`), so a response key carrying conflicting payloads (`_response_key_arguments_conflict`) and aliases whose payloads diverge (`_aliased_arguments_diverge`) are classified before any `Prefetch` or `planned_resolver_keys` entry is emitted.
  - [ ] [`optimizer/extension.py::_publish_plan_to_context`][extension] unions `DST_OPTIMIZER_FK_ID_ELISIONS`, and under a non-`"off"` strictness `DST_OPTIMIZER_PLANNED` and `DST_OPTIMIZER_LOOKUP_PATHS`, into any existing frozenset stash instead of overwriting it, and publishes the planned resolver keys to the per-execution scoped-relations set on every execution. Resolver keys and FK-id elision keys are runtime-path-sensitive, so parent and nested connection plans coexist without collision; `DST_OPTIMIZER_PLAN` remains last-wins introspection data.
  - [ ] [`optimizer/walker.py::_walk_selections`][walker] resolves each selection through `_resolve_selection_target` (exact `snake_case` reversal against `relation_connections` first, then the forward name-converter maps, where a connection outranks a model field of the same GraphQL name) before the unknown-name guard; a connection match dispatches to `_plan_connection_relation`, a thin delegate to [`optimizer/nested_planner.py::plan_connection_relation`][nested-planner]. That planner (a) unwraps the selection's `edges { node { ... } }` children through the consolidated helpers, or plans a scalar-only `pageInfo` / `totalCount` selection with no node children; (b) builds the base child queryset over the relation target (visibility hook baked when the target overrides [`get_queryset`][glossary-get_queryset-visibility-hook], flipping `cacheable = False`) and leaves the relation unplanned when [`optimizer/nested_fetch.py::unwindowable_child_queryset_reason`][nested-fetch] names a reason (`sliced` / `select_for_update` / `combined` / `distinct` / `values`); (c) builds the child plan against a throwaway sub-plan, absorbed into the parent only once a window plans; (d) takes the deterministic total order from [`optimizer/plans.py::effective_connection_order`][plans], the helper the resolve-time pipeline uses ([Decision 11](#decision-11--module-and-test-file-locations)); (e) derives each window from the selection's resolved `first` / `last` / `before` / `after` values (variables resolve through `info.variable_values`, Strawberry `strawberry/types/nodes.py` #"info.variable_values.get(name)") through the shared [`utils/connections.py::derive_connection_window_bounds`][utils-connections], capped by `relay_max_results` and the request policy; (f) on a `ValueError` / `TypeError` from that derivation emits **no** window but records the connection's resolver identities in `plan.planned_resolver_keys`, so strictness ([Decision 8](#decision-8--strictness-mode-wiring-for-connection-paths)) treats the field as accounted-for and the per-parent field path raises its OWN pagination/cursor error rather than a spurious `OptimizerError("Unplanned N+1")`; (g) hands one `NestedConnectionRequest` per window to the active fetch strategy, which appends `Prefetch(<accessor>, queryset=<windowed child qs>, to_attr=<relation_connection_to_attr(...)>)`; and (h) on success records the connection field's resolver identities.
  - [ ] The relation-kind-specific parent partition expression is the `partition_expr` of [`optimizer/join_taxonomy.py::classify_relation_join`][join-taxonomy]'s descriptor, and [`optimizer/plans.py::apply_window_pagination`][plans]`(queryset, *, partition_by, order_by, offset, limit, reverse, with_total_count, next_page_probe, keyset_seek)` annotates `_dst_row_number` (`RowNumber()` partitioned by the parent key) and, when `with_total_count`, `_dst_total_count` (`Count(1)` partitioned the same way) before filtering to the requested window rows — the mechanism port of `/Users/riordenweber/projects/strawberry-django-main/strawberry_django/pagination.py::apply_window_pagination` (itself based on Django's own approach in <https://github.com/django/django/pull/15957>).
  - [ ] A reverse FK / reverse OneToOne link's columns come from one reader, `utils/relations.py::relation_link`: `partition_expr` is the lone child carrier column, a reverse `ForeignObject` with more than one carrier column comes back `windowable=False` and resolves per parent, `prefetch_attach_columns` names every carrier, `parent_link_field` is set only for a link passing `utils/relations.py::is_single_column_foreign_key`, and the parent `.only()` carries the non-pk source columns the link targets (`optimizer/field_meta.py::FieldMeta.source_link_attnames`; for an M2M, the through FK's `to_field` target) on the window and on every refusal arm but the `SKIP` hint and a relation missing from the field map, both decided before the append ([Decision 4](#decision-4--windowed-prefetch-planning-under-a-package-reserved-to_attr)).
  - [ ] Refusal arms per [Decision 6](#decision-6--refusal-arms-divergent-aliases-hints-and-scalar-only-connections): sidecar input and a window the slice arithmetic cannot express leave that response key unplanned; conflicting argument payloads for one response key, an [`OptimizerHint.SKIP`][glossary-optimizerhint] hint, an unwindowable base child queryset, an unwindowable relation kind, an unresolvable relation, and a strategy refusal of every key leave the whole relation unplanned — no window prefetch, no `planned_resolver_keys` entry — so Slice 4's strictness contract sees the per-parent access. Aliased duplicates with divergent pagination arguments are **planned**, one window per response key under a per-key `to_attr`; `pageInfo`-only and `totalCount`-only selections are planned too, with a pk/connector/order-only child projection, and `last: 0` is planned as the `first: 0` window.
  - [ ] Package coverage: [`tests/optimizer/test_walker.py`][test-opt-walker] + [`tests/optimizer/test_plans.py`][test-opt-plans] + `tests/optimizer/test_join_taxonomy.py` per the [Test plan](#test-plan).
- [ ] Slice 2: connection-class fast path (per [Decision 5](#decision-5--connection-class-fast-path-with-annotation-presence-detection-and-a-per-parent-fallback))
  - [ ] [`connection.py::_build_relation_connection_resolver`][connection]`(target_type, accessor_name, relation_field_name, declaring_type, definition)` takes the **relation field name** — passed by [`types/finalizer.py::_synthesize_relation_connections`][finalizer] from `field.name`, so the `to_attr` probe is correct when the accessor diverges from the field name for a reverse relation without `related_name` — and the **declaring type**, the `parent_type` component of the resolver key without which the resolve-time key cannot match the walker's emission ([Decision 8](#decision-8--strictness-mode-wiring-for-connection-paths)); the call site passes the iterated type rather than the model's primary type, so a divergent secondary type's connection stays correctly flagged. When `getattr(root, <per-key or shared to_attr>, None)` is a list whose members carry `_dst_row_number`, and the resolver's **own** call kwargs carry no `filter` / `order_by`, the resolver returns an internal `_WindowedConnectionRows` wrapper. It does **not** return a connection instance; Strawberry's `ConnectionExtension` still calls the generated connection class's `resolve_connection`. With sidecar kwargs present the `to_attr` is ignored and the per-parent pipeline runs, so a planner/argument desync cannot serve unfiltered wrong data.
  - [ ] [`connection.py::DjangoConnection.resolve_connection`][connection] — the single override every generated connection class inherits — detects the wrapper after the `first`+`last` guard (in `_consume_window`), re-derives the slice bounds through the shared [`utils/connections.py`][utils-connections] helper, and `_resolve_from_window` builds edges via the generated edge class's `resolve_edge(..., cursor=<zero_based_offset>)`, derives `pageInfo` from the rows and those bounds, attaches `totalCount` (when the target's [`Meta.connection`][glossary-metaconnection] opted in and the field is selected) from `_dst_total_count`, and skips the per-parent pipeline entirely. `first: 0` and an overshot `after:` are served from the window's retained partition **marker row**; an empty rows list proves the parent has no children. A selection needing a count-derived answer from a count-free window → the wrapper's `fallback` re-runs the per-parent pipeline for that parent, preserving byte-identical results and error paths.

- [ ] Slice 3: plan-cache key hygiene (per [Decision 7](#decision-7--plan-cache-key-hygiene-nested-pagination-variables-hash-root-pagination-arguments-do-not))
  - [ ] [`optimizer/extension.py::_build_cache_key`][extension] folds into its variable component, alongside the `@skip` / `@include` directive variables, the values of variables referenced in `first` / `last` / `before` / `after` arguments of **non-root** field nodes (`_collect_cache_relevant_var_names`). The root field's own pagination arguments never affect plan content — slicing happens post-plan in `ConnectionExtension`; nested pagination values are baked into windowed prefetches and therefore key the cache. Two requests differing only in a nested `first: $n` value get distinct cached plans; two requests differing only in a root `first: $n` value share one.
  - [ ] Fragment traversal preserves response-path depth: a root connection selected inside a fragment on `Query` is still root and its pagination variables stay out; a nested connection selected inside a fragment on a parent node is still nested and its pagination variables are included.

## Problem statement

A relation-as-Connection sibling resolves, unplanned, through a per-parent pipeline: `getattr(root, accessor).all()` per parent row, then visibility, ordering, optimizer, and cursor slice per parent row. A cookbook-shaped two-level query (`{ allObjects { edges { node { values { edges { node { value } } } } } } }`, the `django-graphene-filters` recipes shape the card names) then issues one query per parent: the textbook N+1. Root connections do not have the problem — a root `DjangoConnectionField`'s pre-slice queryset receives `select_related` / `prefetch_related` / `only()` through `apply_connection_optimization` like any list resolver — so the gap is the **nested** half.

The gap is wider than latency. A walker that skips nested connection selections (`books_connection` matches no model field) records nothing for them, so [Strictness mode][glossary-strictness-mode] cannot flag them either: `"raise"` would sail past a per-parent access that the same query expressed as a plain list relation fails loudly on. And the [Plan cache][glossary-plan-cache] has a correctness boundary: once pagination *values* are baked into prefetch querysets, two requests differing only in a variable-supplied `first:` must not share a cached plan — a key-hygiene rule an `@skip` / `@include`-only variable collection cannot express.

The upstream proof that the mechanism works at scale is direct: `strawberry-graphql-django` detects a connection on a nested field inside its prefetch builder, computes the slice window via Strawberry's own `SliceMetadata.from_arguments`, and pushes the window into the prefetch as `RowNumber()` / `Count(1)` window functions partitioned by the key Django uses to attach prefetched children back to each parent (`/Users/riordenweber/projects/strawberry-django-main/strawberry_django/optimizer.py::_optimize_prefetch_queryset`, `strawberry_django/pagination.py::apply_window_pagination`); its connection class then resolves edges, `pageInfo`, and `totalCount` straight from the prefetched rows' annotations (`strawberry_django/relay/list_connection.py::DjangoListConnection.resolve_connection` #"resolve_optimized_connection_by_prefetch"). Each parent's page costs one window-function query for the whole batch, and `totalCount` rides the same query. graphene-django ships no native equivalent — the card's parity claim is `strawberry-graphql-django`-only and **Required**.

Finally, the products live optimizer tests (`test_products_optimizer_*`) pin the package's SQL shapes through real HTTP queries; a connections-only products `Query` keeps those pins honest only once nested connections plan, which is why the products list→connection conversion lands with this card.

## Goals

1. **Plan nested connections.** The walker recognizes synthesized relation-connection selections through definition metadata and plans a windowed `Prefetch` for each — child plan over the target (visibility, projections, nested relations, deeper nested connections recursively), deterministic total order matching the pipeline's rule, relation-kind-correct partition key, slice window from the selection's resolved pagination arguments capped by `relay_max_results`, landed under a package-reserved `to_attr` so the list sibling's accessor-keyed prefetch and the window never collide (Slice 1, [Decision 3](#decision-3--walker-recognition-is-definition-metadata-driven-not-name-pattern-guessing) / [Decision 4](#decision-4--windowed-prefetch-planning-under-a-package-reserved-to_attr)).
2. **Consume the window.** The synthesized relation connection resolver returns annotated rows through an internal wrapper, and the generated connection class serves `edges` (offset cursors from `_dst_row_number`), `pageInfo`, and `totalCount` (from `_dst_total_count`, when the target opted in and the field is selected) directly from that wrapper — `first: 0` and overshot `after:` pages included, served from the window's retained partition marker row — one window query per relation per request, zero per-parent queries on the fast path, falling back to the per-parent pipeline whenever the window is absent or unsafe to consume (Slice 2, [Decision 5](#decision-5--connection-class-fast-path-with-annotation-presence-detection-and-a-per-parent-fallback)).
3. **Keep the plan cache honest.** Variables feeding **nested** pagination arguments key the plan cache (their values are baked into plans); variables feeding **root** pagination arguments stay out (their values never affect plan content) — the card's "skip pagination args that do not affect selection shape, hash the ones that do" (Slice 3, [Decision 7](#decision-7--plan-cache-key-hygiene-nested-pagination-variables-hash-root-pagination-arguments-do-not)).
4. **Wire strictness into connections.** An unplanned, unserved nested-connection access fires the [Strictness mode][glossary-strictness-mode] contract (`warn` / `raise`) through the same resolver-key vocabulary list relations use (Slice 4, [Decision 8](#decision-8--strictness-mode-wiring-for-connection-paths)).
5. **Prove it live, then dogfood it.** The library suite pins the fixed-query-count SQL shape of the cookbook-equivalent nested-connection query; the products Query is connections-only (the cookbook mirror) with the `test_products_optimizer_*` SQL-shape dogfooding pinned through `edges { node }` (Slices 5–6, [Decision 10](#decision-10--the-products-connections-only-conversion-lands-with-this-card)).
6. **No B1–B8 regression.** The plan cache, queryset diffing, FK-id elision, `only()` projection, hints, multi-DB rules, and root-connection planning keep their coverage green (card DoD).
7. **No version bump in a slice**: the surface ships in the `0.0.9` release ([Decision 12](#decision-12--version-bumps-are-owned-by-the-joint-009-cut)).

## Non-goals

- **Async connection pipeline.** A Relay target whose `get_queryset` is `async def` raises [`SyncMisuseError`][glossary-syncmisuseerror] through its synthesized `<field>Connection` (the [`Meta.relation_shapes`][glossary-metarelation_shapes] `"list"` narrowing is the recourse). Window planning is sync-pipeline planning.
- **Windowed planning for sidecar-filtered nested connections.** A nested connection response key carrying `filter:` / `orderBy:` input resolves per parent ([Decision 6](#decision-6--refusal-arms-divergent-aliases-hints-and-scalar-only-connections)) — baking [`FilterSet`][glossary-filterset] / [`OrderSet`][glossary-orderset] application into plan-time child querysets needs request-scoped input threading through the walker, a design surface of its own.
- **Root `totalCount` window folding.** The root contract — selection-gated `.count()` / `.acount()` on the pre-slice queryset — stays. One `COUNT` per root connection is not an N+1; folding it into the main query via a partition-less window (upstream's `DjangoListConnection.resolve_connection` annotation) is a micro-optimization over a tested contract.
- **Keyset cursors.** `Meta.cursor_field` value-encoded cursors ([`keyset.py`][keyset]) are out of scope for this card, and fork its mechanism at five sites in [`connection.py`][connection]: keyset mode is resolved off the generated class per connection (`_keyset_connection_context`); `_consume_window` derives its bounds through `derive_keyset_window_bounds` instead of `derive_connection_window_bounds`, because a value cursor cannot pass through `SliceMetadata`; the fast path builds keyset edges directly with `encode_keyset_cursor` rather than through `resolve_edge`, the one exception to [Decision 5](#decision-5--connection-class-fast-path-with-annotation-presence-detection-and-a-per-parent-fallback)'s "the cursor prefix stays owned by Strawberry's edge type"; a counted keyset-seek page carries its own `_dst_keyset_seek_count` annotation and drift guard; and a non-window keyset source routes to `_resolve_keyset_connection` rather than to `ListConnection`. A keyset target's declared cursor field also wins over the pk-append rule in `effective_connection_order`.
- **The G1–G3 robustness guards** (evaluated-queryset guard, operation-type `only()` gating, fragment `type_condition` narrowing) — [`DONE-035-0.0.10`][kanban].
- **The rest of the fakeshop products activation.** Root [`DjangoNodeField`][glossary-djangonodefield] / [`DjangoNodesField`][glossary-djangonodesfield] entry points on products and `Meta.connection` opt-ins are [`TODO-BETA-066-0.1.5`][kanban]'s; this card takes exactly the list→connection root-field replacement ([Decision 10](#decision-10--the-products-connections-only-conversion-lands-with-this-card)).
- **The permissions subsystem** — [`DONE-034-0.0.10`][kanban]; cascade visibility composes with connections through [`apply_cascade_permissions`][glossary-apply_cascade_permissions], which runs inside `get_queryset` — honored by both the pipeline and the windowed child queryset.
- **`search:` argument** — [`Meta.search_fields`][glossary-metasearch_fields] is planned for `0.1.2`.

## Borrowing posture

Per the [`START.md`][start] "do both libraries provide it? → foundational" test, connection-aware planning is a **one-upstream Required parity**: `strawberry-graphql-django` plans nested connection selections natively; graphene-django has only rudimentary connection-aware optimization (the card tags it ⚛️ parity-adjacent). The behavioral mechanism is borrowed from the strawberry side wholesale, while the consumer surface stays the package's own: nothing new to declare, no decorators, no per-field opt-ins; the optimization applies to the `Meta`-declared relation connections automatically.

### From `strawberry-graphql-django` — borrow the runtime mechanism

The window-pagination prefetch is ported at the mechanism level: `RowNumber()` and `Count(1)` window functions partitioned by the parent attach key, row-number range filters for the slice, reversed row-number for backward (`last`-only) pagination, and prefetch-cache connection resolution reading the annotations (`/Users/riordenweber/projects/strawberry-django-main/strawberry_django/pagination.py::apply_window_pagination`, itself based on Django's own approach in <https://github.com/django/django/pull/15957>; `relay/list_connection.py` #"resolve_optimized_connection_by_prefetch"). The slice arithmetic reuses the engine: Strawberry's `strawberry/relay/utils.py::SliceMetadata.from_arguments` is the same helper upstream calls. Upstream's **DISTINCT guard** is adopted too: upstream's `get_total_count` falls back to a plain `.count()` when `queryset.query.distinct` is set, because SQL evaluates window functions *before* `DISTINCT` dedup and `Count(1) OVER` would over-count — the package resolves the same hazard at plan time by leaving a distinct-target relation **unplanned** so it resolves per parent ([Decision 4](#decision-4--windowed-prefetch-planning-under-a-package-reserved-to_attr) / [Decision 6](#decision-6--refusal-arms-divergent-aliases-hints-and-scalar-only-connections)).

### Explicitly do not borrow

- **The queryset-config marker system.** Upstream threads an `is_optimized_by_prefetching` flag through a `QuerySet`-attached config and monkeypatches `QuerySet._clone` to carry it. The package detects the window by **annotation presence on the prefetched rows** (upstream's own fallback probe) plus the package-reserved `to_attr` — no global state, no monkeypatching.
- **Plan-time `field_kwargs` application.** Upstream applies the nested field's *full* argument set (filters included) inside the prefetch builder. The package's plan cache makes request-scoped values in plans a correctness hazard, so the window covers only the argument family whose values it can hash into the key (pagination), and a response key with sidecar input resolves per parent ([Decision 6](#decision-6--refusal-arms-divergent-aliases-hints-and-scalar-only-connections)).
- **The `_strawberry_*` annotation names.** The package namespaces its annotations `_dst_*` (matching the `DST_*` context keys and the `_dst_` marker convention) so a consumer running both libraries in one process can never collide.
- **Upstream's per-field-node `Info` reconstruction.** The walker reads resolved argument values off converted selections (the engine resolves variables during conversion); no synthesized `Info` objects.

## User-facing API

**This card adds no public symbol and no `Meta` key.** The consumer-visible changes are behavioral:

```graphql
{
  allLibraryGenresConnection(
    first: 10
  ) {
    edges {
      node {
        name
        booksConnection(
          first: 3
        ) {
          edges {
            node {
              title
            }
          }
          totalCount
          pageInfo {
            hasNextPage
            endCursor
          }
        }
      }
    }
  }
}
```

- **Unplanned**: 1 query for the genres page, then *per genre* one query for its books page (plus one `COUNT` per genre when `totalCount` is selected and the target opted in).
- **Planned**: 1 query for the genres page + **1 window-function query** covering every genre's books page and every `totalCount` — a fixed count regardless of how many genres the first page returns. Wire results are byte-identical.
- [Strictness mode][glossary-strictness-mode] `"raise"` flags a nested-connection access the plan does not cover, with the same planned-key exemption semantics as list relations.

The products example is the cookbook mirror (Slice 6):

```python
from django_strawberry_framework import DjangoConnection, DjangoConnectionField


@strawberry.type
class Query:
    all_categories: DjangoConnection[CategoryType] = DjangoConnectionField(CategoryType)
    all_items: DjangoConnection[ItemType] = DjangoConnectionField(ItemType)
    all_properties: DjangoConnection[PropertyType] = DjangoConnectionField(PropertyType)
    all_entries: DjangoConnection[EntryType] = DjangoConnectionField(EntryType)
```

The synthesized signatures expose the `filter:` / `orderBy:` arguments from the [`Meta.filterset_class`][glossary-metafilterset_class] / [`Meta.orderset_class`][glossary-metaorderset_class] sidecars, and the pipeline applies the visibility → filter → order → deterministic-order → optimizer composition.

### Error shapes

- The inherited guards hold on both the fast path and the fallback: the `first` + `last` guard, the sidecar-input-over-non-queryset guard, the `totalCount`-over-non-queryset guard, and the [`SyncMisuseError`][glossary-syncmisuseerror] contract.
- The window machinery adds error surface of its own, all of it fail-closed:
  - `connection.py::_consume_window` lets the window derivation's `PaginationArgumentError` (an invalid cursor, a negative or over-cap `first` / `last`, raised by `utils/connections.py::validate_offset_pagination` or, on the keyset fork, `::assert_relay_pagination_bound`) surface as the field's own error, and catches only `UnwindowableConnection`. It catches and re-raises nothing else as client-facing text: an exception that is not the package's own argument validation reaches the production error policy, which masks it.
  - [`utils/connections.py::window_range_plan`][utils-connections] raises `OptimizerError` on a negative window offset or limit rather than clamping it — silently treating a negative direct-call limit as unbounded would produce wrong rows in both renderers.
  - [`utils/connections.py::assert_window_fetch_mode`][utils-connections] raises `OptimizerError` when a probe window would also annotate the count. It is deliberately not a `ValueError` / `TypeError`, so the planner's leave-unplanned pagination handler cannot swallow it.
  - [`optimizer/walker.py::_apply_hint`][walker] raises [`ConfigurationError`][glossary-configurationerror] at plan time for an `OptimizerHint.prefetch(Prefetch(..., to_attr=...))` on a relation whose resolver the package generated ([Decision 6](#decision-6--refusal-arms-divergent-aliases-hints-and-scalar-only-connections)).
  - `resolve_connection` also applies the request policy's `max_page_size` ceiling and runs the execution deadline check before any window work, so either can raise before the fast path is reached.
- [Strictness mode][glossary-strictness-mode] `"raise"` surfaces `OptimizerError(f"Unplanned N+1: <field>")` (with the fallback reason appended) for an unplanned, unserved nested-connection access — where `<field>` is the underlying **relation** field name (`books`), the same exception class and vocabulary list relations use and the same name the planner's `resolver_key` is built from, NOT the generated `<field>_connection` attribute ([Decision 8](#decision-8--strictness-mode-wiring-for-connection-paths)).

### Decision 4 — Windowed-prefetch planning under a package-reserved `to_attr`

[`optimizer/nested_planner.py::plan_connection_relation`][nested-planner] plans each recognized nested connection as `Prefetch(<accessor>, queryset=<windowed child queryset>, to_attr="_dst_<field>_connection")`.

**The window is one fetch strategy's rendering of the plan, not the only one.** [`optimizer/nested_fetch.py`][nested-fetch] owns the strategy seam: `"windowed"` (the default, the `RowNumber()` / `Count(1)` prefetch described below), `"lateral"` (a Postgres `CROSS JOIN LATERAL` backend in [`optimizer/lateral_fetch.py`][lateral-fetch]), and `"auto"` (one cache-stable lateral-capable plan whose fetch-time decision follows the nested queryset's effective database alias). A runtime single-parent fast path ([`optimizer/single_parent_fetch.py`][single-parent-fetch]) serves a one-parent batch of the count-free plain `first: N` page over a direct-FK join as a plain bounded query and synthesizes `_dst_row_number` in Python. The backend is selected per extension instance through the `nested_connection_strategy=` constructor argument or the `NESTED_CONNECTION_STRATEGY` setting, and per field through [`OptimizerHint`][glossary-optimizerhint]`.strategy(name)`. Every backend lands its rows under the same `to_attr` and is consumed by the same resolver probe, so everything below about the `to_attr` grammar, the deterministic order, the partition key, and the annotation vocabulary is strategy-independent; only the SQL that produces the rows differs.

- **Child queryset**: built exactly like every generated prefetch child — `related_model._default_manager.all()`, target [`get_queryset`][glossary-get_queryset-visibility-hook] applied when overridden (flipping `plan.cacheable = False`, the request-scope rule), the nested `edges { node { ... } }` child plan applied (projections, `select_related`, deeper prefetches — **including deeper windowed connections recursively**), connector columns ensured so Django can attach rows and the window can partition.
- **Deterministic order (a cursor-parity invariant, not a tidiness refactor)**: the window's `ORDER BY` is produced by the *same* helper the resolve-time pipeline uses — [`optimizer/plans.py::effective_connection_order`][plans]: a keyset target's declared cursor field, else the effective ordering (queryset, else model `Meta.ordering`) with the pk appended unless it already ends in a unique column ([Decision 11](#decision-11--module-and-test-file-locations)). The fast-path↔fallback wire-parity promise depends on it: if the plan-time window order and the resolve-time order diverged, the window's row numbers would stop agreeing with the pipeline's offset cursors and a fast-path `endCursor` would no longer round-trip to an optimizer-less `after:` — a silent, data-dependent failure. `tests/optimizer/test_plans.py::TestDeterministicOrderHoistParity` and `test_fast_path_cursor_round_trips_to_fallback_after` are the named guards.
- **Partition key**: [`optimizer/join_taxonomy.py::classify_relation_join`][join-taxonomy] derives it as the descriptor's `partition_expr`, the parent-side expression Django's prefetch attach uses, not the child-pk connector used for `.only()` safety. A reverse FK / reverse OneToOne partitions by its link's lone child carrier column, read through `utils/relations.py::relation_link`: the child FK attname for a `ForeignKey` (`shelf_id`, whatever its `to_field`), the `from_fields` column for a one-column `ForeignObject`. A relation's `attname` is never the source: a plain `ForeignObject` has `attname == name` and no `column`. A reverse `ForeignObject` with more than one carrier column has no single partition expression, so it comes back `windowable=False`. The M2M partitions come from `optimizer/join_taxonomy.py::_partition_expr`: reverse M2M partitions through the child's forward M2M field name, letting Django resolve it onto the through join (`Genre.books` → `Book.genres` → through `genre_id`); forward M2M partitions through the target model's reverse query name, which is not always the accessor when `related_name` is absent. `GenericRelation` is windowable too. `classify_relation_join` is the one classifier on the planning path and **never raises**: an unsupported relation kind, or any relation whose partition expression cannot be derived, comes back with `windowable=False` and the relation is left unplanned rather than guessed at.
- **The partition is derived from the raw Django relation field, not a `FieldMeta`**: the forward-M2M reverse query name lives only on `field.remote_field`, which `FieldMeta` does not carry, so the planner resolves the live field via `model._meta.get_field(...)` (`optimizer/nested_planner.py::_raw_relation_field`) and hands it to `classify_relation_join` and to the strategy request.
- **Link columns load on both sides**: the child plan's `.only()` carries every column of the descriptor's `prefetch_attach_columns` (each carrier, plus a `GenericRelation`'s `content_type_id`), and the parent plan's `.only()` carries the non-pk source columns the link targets (`optimizer/field_meta.py::FieldMeta.source_link_attnames`: a reverse `ForeignKey(to_field=...)` target, a reverse `ForeignObject`'s `to_fields`, and for an M2M in either direction the `to_field` its through table's source-side FK targets), because Django's attach and the per-parent fallback read them off every row. `optimizer/nested_planner.py::plan_connection_relation` appends the parent columns before the `SKIP` hint and the first refusal arm, so the window, every refusal arm and a `SKIP`'s per-parent resolution find them loaded; only a relation missing from the field map leaves them unloaded. The append rides the same `.only()` gate as `optimizer/walker.py::_record_relation_carriers`. The correlated strategies (lateral, single-parent) join and cast on one link column, so the descriptor's `parent_link_field` is set only for a link passing `utils/relations.py::is_single_column_foreign_key`; a reverse `ForeignObject` of any width leaves it `None`, the lateral and single-parent paths refuse it, and the windowed body serves a one-column one.
- **Window**: `_dst_row_number = RowNumber() OVER (PARTITION BY <parent key> ORDER BY <deterministic order>)`, with filters for the requested row-number range — [`optimizer/plans.py::apply_window_pagination`][plans], ported from upstream's `apply_window_pagination`, including the reversed-row-number branch for `last`-only backward pagination. `_dst_total_count = Count(1) OVER (PARTITION BY <parent key>)` is annotated only when the window's [`utils/connections.py::FetchMode`][utils-connections] is `COUNTED`: `totalCount` is selected, or the page is `first: 0` (whose marker row carries the count). A page selecting `pageInfo.hasNextPage` without `totalCount` on a plain `first: N` or bounded forward offset shape is `PROBED`: it pays an n+1 sentinel overfetch and answers `hasNextPage` from whether the sentinel arrived. An unbounded forward page and a reversed `last`-only page are `CONSTANT_FALSE` (`hasNextPage` is `False` by construction), and a bounded edges-only page is `NONE`; neither carries a count. `WindowRangePlan.fetch_mode` decides the mode at plan time from the merged selection's observers (`connection_total_count_selected` / `connection_has_next_page_selected`); the resolver reads the window's physical shape back rather than re-deriving the mode per alias, and `assert_window_fetch_mode` keeps probe and count mutually exclusive.
- **Unwindowable child querysets are classified before the window is built**: [`optimizer/nested_fetch.py::unwindowable_child_queryset_reason`][nested-fetch] runs on the base child queryset and names five reasons — `sliced`, `select_for_update`, `combined`, `distinct`, `values`. Any of them leaves the relation **unplanned** to resolve per parent ([Decision 6](#decision-6--refusal-arms-divergent-aliases-hints-and-scalar-only-connections)). `distinct` is the correctness-critical reason and the package's analogue of upstream's `get_total_count` `if queryset.query.distinct: … return queryset.count()` guard: SQL evaluates window functions *before* `DISTINCT` dedup, so `Count(1) OVER (PARTITION BY …)` counts pre-dedup rows and `_dst_total_count` would over-count whenever the child queryset de-duplicates — a visibility/permission [`get_queryset`][glossary-get_queryset-visibility-hook] that joins and de-duplicates is a normal shape. Because the classification is made on the base queryset it is one strategy-independent gate rather than a per-backend re-check. Pinned by `test_distinct_child_queryset_left_unplanned_for_correct_total_count`.
- **Scalar-only connections**: `pageInfo`-only and `totalCount`-only nested selections still window-plan (**planned, not a fallback**, so strictness `"raise"` does not turn harmless scalar connection metadata into a per-parent error). With no `edges { node }` there are no node-child scalar columns to select, so the planner seeds a minimal **pk / connector / deterministic-order** projection for the windowed child queryset (`_project_scalar_only_window`) rather than loading the target's full columns: the target pk (Relay edge identity), the relation's connector columns (`prefetch_attach_columns`, every column Django's prefetch attach reads), and the concrete local columns the deterministic order references (related-span and unresolvable-expression order entries are skipped — the window's `OVER (ORDER BY …)` and the queryset `ORDER BY` reference them in SQL regardless of the projection). The `_dst_*` annotations compose with `.only()`. An edge-bearing selection's projection follows its node child plan.
- **Slice arithmetic**: Strawberry's `SliceMetadata.from_arguments` over the selection's **resolved** argument values (literals and variables alike — converted selections resolve variables; inline integer literals are coerced from their token strings), inside the shared [`utils/connections.py::derive_connection_window_bounds`][utils-connections]. `first` is set to the cap whenever neither `first` nor `last` is an integer, and `last: 0` is rewritten to `first: 0` (`utils/connections.py::page_arguments`, the same rewrite the per-parent fallback applies); cursor presence is read by the engine's own truthiness, so an empty-string `before` / `after` is no cursor. The cap is the schema config's `relay_max_results` (default 100) lowered, if the request policy declares a smaller `max_page_size`, by [`utils/connections.py::resolve_relay_max_results`][utils-connections] — the request policy is a **ceiling over** whichever cap won, and the plan-time and resolve-time caps both come from that helper, so they are the same number by construction. A `PaginationArgumentError` from a negative / over-max size or a malformed cursor (`utils/connections.py::validate_offset_pagination` runs before the engine; its `decode_offset_cursor` rejects anything but a minted `arrayconnection:<index>` with `0 <= index < sys.maxsize`) makes `_connection_window_slice_from_arguments` return no window, so the planner emits **no** window prefetch (the per-parent pipeline raises the cursor/cap error at the nested field's own error path, not at the root planner) but still records the connection's resolver identities in `plan.planned_resolver_keys`. Recording the key is the load-bearing distinction from the [Decision 6](#decision-6--refusal-arms-divergent-aliases-hints-and-scalar-only-connections) refusal arms: it keeps strictness ([Decision 8](#decision-8--strictness-mode-wiring-for-connection-paths)) from preempting the real pagination error with a spurious `OptimizerError("Unplanned N+1")` under `"raise"`, whereas the refusal arms stay unplanned so strictness CAN flag them as genuine per-parent accesses.
- **`to_attr` isolation**: the window lands on a `_dst_`-namespaced attribute, never the relation accessor. The [`"both"`][glossary-metarelation_shapes] shape — an explicit opt-in that keeps the list sibling beside the connection — means both can be selected together; two `Prefetch`es on one accessor with different querysets is Django's "lookup already seen" error, and a windowed result would silently corrupt the list field's semantics. The `to_attr` gives the window its own slot; the list field's accessor-keyed prefetch is untouched. The grammar has two forms, both owned by `optimizer/nested_planner.py::relation_connection_to_attr`: `_dst_<field>_connection` for a relation whose selections agree on their arguments, and `_dst_<field>$<response key>_connection` for each key of a divergent-alias selection, which plans one window per key. `$` is the separator because Django splits `prefetch_to` on `LOOKUP_SEP`, so a `__` in a `to_attr` would be read as a lookup path. The `_dst_` prefix is the package's reserved namespace (consistent with the `dst_optimizer_*` context keys and the `_dst_synthesized_relation_connection` marker).
- **Resolver keys**: the connection field's resolver identities (declaring type + **relation** field name + runtime paths, the same `resolver_key` vocabulary list relations use) are appended to `plan.planned_resolver_keys` so strictness ([Decision 8](#decision-8--strictness-mode-wiring-for-connection-paths)) sees the field as planned. The runtime path carries the connection's response key (`booksConnection`); the field-name component is the relation field (`books`), so the resolve-time `_check_n1` key matches by construction.

### Decision 5 — Connection-class fast path with annotation-presence detection and a per-parent fallback

`_build_relation_connection_resolver` does **not** construct a connection object. Strawberry's `ConnectionExtension.resolve` calls the field resolver for a node iterable and then invokes the generated connection class's `resolve_connection`; returning a prebuilt connection from the resolver would feed that connection object back through `resolve_connection` as if it were the node iterable. The resolver's fast-path responsibility is therefore limited to a handoff:

- probe the `to_attr` on `root`, derived from the relation **field name**. The synthesized resolver is built once at finalization and reads rows through the instance **accessor**, which diverges from the field name for a reverse relation without `related_name` (`field.name == "book"`, accessor `"book_set"`, generated `book_connection`, `to_attr` `_dst_book_connection`); deriving the probe from the accessor would compute the wrong attribute and the fast path would never fire for that shape. `_build_relation_connection_resolver` therefore takes `relation_field_name` as an explicit parameter, which `_synthesize_relation_connections` passes from `field.name` — the same key the slot, the generated attribute, and the `to_attr` are built from;
- the probe is per response key first, then shared: the resolver looks for `_dst_<field>$<info.path.key>_connection` (the divergent-alias form) before falling back to `_dst_<field>_connection`, and threads whichever attribute held rows into the strictness probe ([Decision 8](#decision-8--strictness-mode-wiring-for-connection-paths));
- when the value is a list whose rows carry `_dst_row_number` (`_window_rows_are_annotated`; an empty list qualifies, since a parent with children keeps its marker or sentinel row), and the resolver's own `filter` / `order_by` kwargs are absent, wrap it in an internal `_WindowedConnectionRows` marker. The probe reads the **row number only**; `_dst_total_count` is annotated conditionally ([Decision 4](#decision-4--windowed-prefetch-planning-under-a-package-reserved-to_attr)), so demanding it would refuse every count-free page and every strategy that synthesizes row numbers without a count. The marker carries exactly two things: the rows, and a zero-argument `fallback` callable that re-runs the per-parent pipeline. It carries **no** slice metadata — Strawberry's `ConnectionExtension.resolve` consumes `first` / `last` / `before` / `after` and forwards them only to `resolve_connection`, so the resolver cannot classify its own rows and every window classification happens in `resolve_connection`, which re-derives the bounds through the same [`utils/connections.py`][utils-connections] helper the planner used. The resolve-time window is computed by the plan-time helper rather than trusted from a value the resolver stashed. The `fallback` callable exists because `resolve_connection` cannot rebuild the per-parent relation manager the resolver holds;
- when sidecar kwargs are present, ignore the window and run the pipeline; a planner/argument desync degrades to the correct filtered query, never to an unfiltered window;
- when the attribute is absent, or present without the row-number annotation, run the per-parent pipeline.

[`connection.py::DjangoConnection.resolve_connection`][connection] is the single override every generated connection class inherits; its `_consume_window` step detects `_WindowedConnectionRows` after the `first`+`last` guard and before delegating to Strawberry's list slicing. Whether the class also serves `totalCount` is the `_resolves_total_count` `ClassVar` the generated total-count class sets, not a second `resolve_connection` — so there is one dispatch site, and the count opt-in cannot drift away from the window handling. `_resolve_from_window` builds the Relay object:

- edges are built through the generated edge class's `resolve_edge(..., cursor=<zero_based_offset>)`; the cursor prefix stays owned by Strawberry's edge type. The positional offset cursor is `_dst_row_number - 1` for **every** window, including the `last`-only reversed one: `apply_window_pagination` keeps `_dst_row_number` as the **forward** row number for all windows (mirroring upstream `strawberry-django`, which keeps `_strawberry_row_number` forward and adds a separate `_strawberry_row_number_reversed` purely for the plan-time `__lte` filter; the package's twin is `_dst_row_number_reversed`). So the rows of a `last: 2` page of five arrive in forward order numbered `4, 5`, and the forward absolute-offset cursor matches the pipeline's `ListConnection` cursors directly. Byte-parity is proven by `test_fast_path_wire_parity_last_only`.
- `pageInfo` is derived from the edge rows and the bounds `resolve_connection` re-derived. `has_previous_page` is true when the first row is past row 1, or when a keyset cursor was supplied. `has_next_page` follows the window's own [`FetchMode`][utils-connections]: the count-free n+1 probe reports whether the sentinel row arrived; a counted keyset-seek page compares the row number against the seek count in the value domain; the shapes that are `False` by construction — an unbounded forward page and the reversed `last`-only page — report `False`; and a counted offset page compares the last row number against `_dst_total_count`. Because the row numbers stay forward for every window, all of them land on the pipeline's values.
- `totalCount` (when the target's [`Meta.connection`][glossary-metaconnection] opted in and the field is selected) is read from `_dst_total_count` on an annotated row. The window handling branches before `_guard_total_count_countable` / `.count()`, so the marker is treated as an annotated optimized source, not as an uncountable non-queryset iterable. A page whose selection needs a count-derived answer from a window that carries no count does not guess: it returns to the per-parent pipeline through the marker's `fallback`, and the check runs before any edge is built so the recovery discards no work.
- **`first: 0` and an overshot `after:` are served from the window, not fallen back.** These two shapes would otherwise be indistinguishable from a genuinely childless parent, so the plan keeps each partition's **row 1 as a marker row**: the range filter ORs it in, and the marker-only list carries the page flags (and, for `first: 0`, the real count). `first: 0` serves `edges: []` with `hasNextPage: true` and the true `totalCount`; an overshot `after:` serves `edges: []` with `hasPreviousPage: true`, and when the window is count-free the marker still proves `total <= offset`. One query, no per-parent fallback. Consequently an **empty** rows list *proves* the parent has no related rows — a parent with children would have kept its marker row or its probe sentinel — and that parent is served `totalCount = 0`, no cursors, `has_next_page` `False`, and `has_previous_page = offset > 0`.
- SDL identity, the `first`+`last` guard, and the `totalCount` member shape are identical on both paths because the generated connection class is the only layer constructing the connection instance.

When the wrapper is absent, the generated connection class delegates to the per-parent path — correctness never depends on the plan having fired. No optimizer installed, any [Decision 6](#decision-6--refusal-arms-divergent-aliases-hints-and-scalar-only-connections) refusal arm, and a consumer's own prefetch are the common causes, and the list is deliberately open rather than exhaustive. An unwindowable child queryset needs no resolver-side branch of its own — because the relation is never window-planned, no `to_attr` is written, the probe misses, and the per-parent pipeline (which counts correctly) runs.

**`last: 0` is the `first: 0` page.** Strawberry's `edges[-0:]` slices to the *whole* set rather than to nothing, so a raw `last: 0` would serve every edge, past the page cap. [`utils/connections.py::page_arguments`][utils-connections] rewrites `last: 0` with no integer `first` to `first: 0` before anything slices, on the planned window and the per-parent pipeline, offset and keyset alike, so the planner windows it exactly as it windows `first: 0`.

Rationale companion — this Decision's justification and its rejected alternatives: [Decision 5][rationale-d5].

### Decision 6 — Refusal arms, divergent aliases, hints, and scalar-only connections

Eight nested-connection shapes are **not** window-planned; each resolves per parent through the pipeline and stays visible to strictness as unplanned. Non-planning has two granularities: a **per-response-key** refusal leaves one alias unplanned while its siblings still plan, and a **whole-relation** refusal leaves the relation unplanned for every key. Source comments and test docstrings cite an arm **by its content** ("the unwindowable-child-queryset refusal arm"), never by ordinal and never by this Decision's heading text. The refusal arms, with the site that decides each:

1. **Sidecar input** (`filter:` / `orderBy:` arguments on the nested selection) — *per key*, `optimizer/nested_planner.py::_divergent_key_windows #"sidecar arguments"`. Baking sidecar application into plan-time child querysets means request-scoped input values inside cached plans and `FilterSet.apply_sync`'s `info`-dependence at walk time — a design surface (input normalization, permission gates, cache-key explosion) of its own. The per-parent pipeline applies the sidecars.
2. **A window Strawberry's slice arithmetic cannot express** — `after` combined with `last`, an inverted `after` / `before` interval, and every backward keyset shape — *per key*, raised as `UnwindowableConnection` by [`utils/connections.py::derive_connection_window_bounds`][utils-connections] (and its keyset twin `::derive_keyset_window_bounds`) and routed to a fallback rather than approximated.
3. **One response key carrying two conflicting argument payloads** — *whole relation*, `optimizer/nested_planner.py::plan_connection_relation #"if response_key_arguments_conflict(sel):"`. Two selections merging onto one response key with different arguments have no single correct window.
4. **[`OptimizerHint.SKIP`][glossary-optimizerhint] on the underlying relation** — *whole relation*. SKIP means "the optimizer plans no fetch for this relation" (the parent row still loads its link columns); that contract extends to the relation's connection sibling.
5. **An unwindowable child queryset** — *whole relation*, classified on the base child queryset by [`optimizer/nested_fetch.py::unwindowable_child_queryset_reason`][nested-fetch], which names five reasons: `sliced`, `select_for_update`, `combined`, `distinct`, `values`. The `distinct` reason is the correctness-critical one: SQL evaluates window functions before `DISTINCT`, so the `_dst_total_count` `Count(1) OVER` annotation would over-count a de-duplicated child queryset (typically a visibility/permission [`get_queryset`][glossary-get_queryset-visibility-hook] that joins and de-duplicates), and a silently wrong `totalCount` is worse than a per-parent count that is right. The classifier runs on the **base** child queryset, so one strategy-independent gate answers for every fetch backend and no post-build re-check is needed ([Decision 4](#decision-4--windowed-prefetch-planning-under-a-package-reserved-to_attr)).
6. **An unwindowable relation kind or link** — *whole relation*, `optimizer/nested_planner.py::plan_connection_relation` on a `join.windowable` of `False` from [`optimizer/join_taxonomy.py::classify_relation_join`][join-taxonomy]. The classifier never raises; an unsupported kind, or a reverse `ForeignObject` whose link spans more than one carrier column (no single partition expression), returns unplanned.
7. **A relation the field map cannot resolve** (no `field_map` entry, or `related_model is None`) — *whole relation*.
8. **A window the active fetch strategy refused for every response key** — *whole relation*, `optimizer/nested_planner.py::plan_connection_relation #"if not planned_keys:"`. The child plan is built against a throwaway `sub_plan` and absorbed into the parent only once at least one key planned, so a refusal leaks no resolver key, FK-id elision, or `cacheable` flip into the parent plan.

Two shapes that read like fallbacks and are **not**:

- **Aliased duplicates with divergent pagination arguments** (`a: booksConnection(first: 2)` + `b: booksConnection(first: 5)`) are window-planned, **one window per response key**, each under its own `_dst_<field>$<key>_connection` `to_attr` ([Decision 4](#decision-4--windowed-prefetch-planning-under-a-package-reserved-to_attr)). Django accepts several `Prefetch`es on one accessor as long as their `to_attr`s differ; the planned keys' resolver identities are recorded, and the shared `_dst_<field>_connection` attribute is not written for a divergent selection. Identical-argument aliases merge into one window. The residual fallback is the case where *every* alias is itself one of the refusal arms above.
- **`pageInfo`-only and `totalCount`-only selections** are planned. They do not need a node child plan, but they do need the same per-parent row-number / count metadata and the same strictness silence as an edge-bearing connection; the window is projected to the minimal pk / connector / deterministic-order columns (see [Decision 4](#decision-4--windowed-prefetch-planning-under-a-package-reserved-to_attr)'s scalar-only bullet).

**Hints shape the window as well as suppress it.** `select_related()` is invalid for a many-side relation, and `prefetch_related()` / `prefetch(...)` hints apply to the list-shaped planning only — the window reads no prefetch hint. [`OptimizerHint`][glossary-optimizerhint]`.strategy(name)` selects the nested-connection fetch backend for one connection field, overriding the extension instance's `nested_connection_strategy=` and the `NESTED_CONNECTION_STRATEGY` setting ([Decision 4](#decision-4--windowed-prefetch-planning-under-a-package-reserved-to_attr)). An `OptimizerHint.prefetch(Prefetch(..., to_attr=...))` on a relation whose resolver the package generated raises [`ConfigurationError`][glossary-configurationerror] at plan time (`optimizer/walker.py::_apply_hint`): the generated resolver reads Django's prefetch cache, never a `to_attr`, so a consumer `to_attr` there would silently lazy-load behind a plan strictness trusts. A plain `OptimizerHint.prefetch(Prefetch(obj))` targets the accessor and leaves the window alone.

Rationale companion — this Decision's justification and its rejected alternatives: [Decision 6][rationale-d6].

### Decision 7 — Plan-cache key hygiene: nested pagination variables hash, root pagination arguments do not

[`_build_cache_key`][extension] folds pagination variables into its `relevant_vars` frozenset: one walk of the operation (and reachable fragments), `_collect_cache_relevant_var_names`, collects both the `@skip` / `@include` directive variables and the variables referenced in `first` / `last` / `before` / `after` arguments **on non-root field nodes**. The variable-name sets are document-derived, so they are memoized cross-request beside the rendered document key (`_doc_cache_entry`), and the resolved `(document key, variable values)` pair is memoized per execution on the execution frame keyed by `id(operation)` — nested fallback connection pipelines that call the key builder per parent row neither re-walk the AST nor rebuild the frozenset.

- **Why nested values must key the cache**: Slice 1 bakes the resolved values into windowed prefetch querysets. Two requests sharing a printed AST (`booksConnection(first: $n)`) but differing in `$n` would otherwise share one cached plan — and serve one request's page size to the other. This is a correctness rule, not an optimization.
- **Why root values must not**: a root connection's pagination happens post-plan in `ConnectionExtension`; plan content is invariant in them. Hashing them would fragment B1's cache across every page of every consumer pagination loop — the card's "skip pagination args that do not affect selection shape".
- **Fragment traversal preserves response-path depth**: the collector tracks depth at the spread site, not raw fragment-definition nesting, and its cycle guard keys on `(fragment name, spread-site depth)`. A root connection selected inside a fragment on `Query` is still root and stays out; a nested connection selected inside a fragment on a parent node is still nested and keys the cache.
- **The collection is a syntactic superset by design**: any non-root field's pagination-named variable is collected, including on fields that are not connections (a custom resolver with a `first:` arg). Over-collection costs duplicate cache entries for identical plans (cheap, bounded by the LRU); under-collection serves wrong data — the same asymmetry the directive-variable collection encodes. Every collected value is normalized to a hashable form at the cache boundary.
- **Inline literals** key the cache via the printed AST — for nested windows that is load-bearing (two literal `first:` values genuinely need two plans); for root arguments it is a harmless fragmentation.
- **Cacheable plans and visibility-bearing targets are disjoint**: a windowed plan caches only when **no** windowed target overrides [`get_queryset`][glossary-get_queryset-visibility-hook] — baking a request-scoped visibility queryset flips `plan.cacheable = False` (the request-scope rule, inherited by [Decision 4](#decision-4--windowed-prefetch-planning-under-a-package-reserved-to_attr)). So the flagship library shape (`allLibraryGenresConnection { … booksConnection { … } }`, where `BookType.get_queryset` hides `circulation_status="repair"` books from non-staff) is uncacheable for that orthogonal reason, and the nested-pagination-variable correctness rule is exercised by **non-visibility synthetic targets**, not the cookbook shape. The Slice 5 fixed-query-count library pins and the Slice 3 cache pins therefore use **different fixtures**.

Rationale companion — this Decision's justification and its rejected alternatives: [Decision 7][rationale-d7].

### Decision 8 — Strictness-mode wiring for connection paths

The synthesized relation connection resolver fires the B3 contract when **all three** hold:

1. **strictness is not `"off"` for this execution**, read from the per-execution frame armed at `on_execute` entry ([`optimizer/_context.py::active_strictness`][context]), falling back to the `DST_OPTIMIZER_STRICTNESS` stash. The frame is what makes the condition reachable at all: the stash is unavailable to an execution that runs without a `context_value`, and it is written at plan-publish time, so an operation whose root resolver returns something the walker cannot plan never publishes it;
2. **the field's resolver key is not planned** — declaring type + **relation** field name + runtime path, the shared `resolver_key` vocabulary. "Planned" is satisfied by the `DST_OPTIMIZER_PLANNED` stash **or** by the per-execution scoped-relations set, which every execution publishes whether or not strictness is on;
3. **the fast-path `to_attr` is absent on `root`** (the access will actually query).

Then: `OptimizerError` under `"raise"`, logged warning under `"warn"` — through [`types/resolvers.py::_check_n1`][resolvers] (`kind="connection_to_attr"`, the `to_attr` probe, the relation field name, and the fallback reason appended to the message) rather than duplicated logic in `connection.py`. The reason names a sidecar-bearing selection as such and gives every other fallback the generic per-parent reason. The resolver key (and therefore the flagged message) is keyed on the underlying relation field name (`books`), NOT the generated `books_connection` attribute, so it is byte-uniform with the list-relation message and with the key the planner emits — a consumer who selected `booksConnection` is pointed at the `books` relation that backs it.

Fallback nested connections still call the root connection pipeline per parent, which publishes its own plan. [`optimizer/extension.py::_publish_plan_to_context`][extension] therefore unions `DST_OPTIMIZER_FK_ID_ELISIONS`, `DST_OPTIMIZER_PLANNED`, and `DST_OPTIMIZER_LOOKUP_PATHS` into any existing frozenset stash rather than overwriting. Branch-sensitive resolver keys embed runtime paths, so parent and child plans coexist without false positives. `DST_OPTIMIZER_PLAN` remains last-wins introspection data; the correctness sentinels are the unioned sets.

### Decision 9 — The `edges { node }` selection helpers consolidate into one module both consumers import

## Edge cases and constraints

- **`"both"` shape with both siblings selected** — the list field's accessor-keyed prefetch, a consumer's plain accessor prefetch, and the connection's `to_attr` window coexist on one relation with no Django duplicate-lookup error; the list field returns the **full** related set, the connection returns the windowed page. Pinned at the plan-object level by `test_both_shape_connection_to_attr_coexists_with_list_and_consumer_prefetch` and, for the consumer-visible behavior, live over `/graphql/` by `test_list_relation_and_connection_sibling_coexist_live` (list full set + connection page resolve together at a flat query count).
- **Identical-argument aliases merge into one window; divergent ones get one window each.** The walker preserves per-response-key argument payloads so resolved pagination and sidecar arguments can be compared before window planning. Divergent aliases plan one `Prefetch` per response key under the per-key `to_attr` grammar, record the planned keys' resolver identities, and leave the shared `_dst_<field>_connection` attribute unwritten; the tests assert the set of `to_attr`s and the resolver-key count, not merely that the query resolves. The residual fallback is the case where every alias is itself a refusal arm ([Decision 6](#decision-6--refusal-arms-divergent-aliases-hints-and-scalar-only-connections)).
- **M2M shared children** — two parents sharing the same child get per-parent pages because the partition key is the through-table parent-side key, not child pk. Pinned for both forward and reverse M2M at the partition-expression level, and live over `/graphql/` by `test_nested_total_count_no_per_parent_count` (books sharing genres, each parent's page and `totalCount` correct).
- **Recursion terminates structurally.** A windowed child plan may itself contain a windowed prefetch (the two-level cookbook shape); depth is bounded by the validated query depth, the same bound the walker rides.
- **`first: 0` and overshot `after:`** — a window that returned no rows for these shapes would be indistinguishable from a genuinely empty parent, so the plan retains each partition's row 1 as a **marker row**. Both shapes are served from the window in one query: `first: 0` returns empty edges with `hasNextPage: true` and the true `totalCount`, an overshot `after:` returns empty edges with `hasPreviousPage: true` (when the window is count-free the marker still proves `total <= offset`).
- **Parents with no related rows** — a physically empty rows list *proves* the parent has no children, because a parent with children would have kept its marker row or its probe sentinel; `totalCount` is `0`, `hasNextPage` is `False`, `hasPreviousPage` is `offset > 0`, and no fallback is triggered.
- **`last: 0`** — the `first: 0` page on every connection, planned as the `first: 0` window and served from its marker row; never Strawberry's serve-all `edges[-0:]` ([Decision 5](#decision-5--connection-class-fast-path-with-annotation-presence-detection-and-a-per-parent-fallback)).
- **`last`-only backward pagination** — the windowed prefetch's `reverse` branch filters the tail rows on `_dst_row_number_reversed`, but `_dst_row_number` stays **forward** ([Decision 5](#decision-5--connection-class-fast-path-with-annotation-presence-detection-and-a-per-parent-fallback)), so the resolver's positional cursor is the uniform `_dst_row_number - 1` and the flags land on the pipeline's values — `has_next_page` through the constant-`False` arm rather than a comparison. The windows the slice arithmetic cannot express — `after` combined with `last`, an inverted `after` / `before` interval, and every backward keyset shape — are raised as `UnwindowableConnection` and fall back per key rather than being approximated. The exact supported set follows `SliceMetadata`'s arithmetic and is pinned by tests, not prose.
- **`relay_max_results` agreement** — the cap is resolved by one shared helper on both sides: the schema config's `relay_max_results` (available at request time; the walker runs per request), lowered by the request policy's `max_page_size` when that is smaller. A window can therefore never be narrower or wider than the resolve-time cap; a consumer raising the cap via [`strawberry_config`][glossary-strawberry_config]`(relay_max_results=...)` affects both sides through the one config object, and a request policy tightens both together.
- **Visibility-filtered targets** — the windowed child queryset bakes the target's [`get_queryset`][glossary-get_queryset-visibility-hook] (plan `cacheable = False`, the request-scope rule); row numbers and `_dst_total_count` are computed **post-visibility**, so a nested `totalCount` counts visible rows only — identical to the pipeline path's post-`get_queryset` count. The live Slice 5 test pins this through `BookType`'s `circulation_status="repair"` filter. Because the visibility queryset makes the plan uncacheable, the Slice 3 plan-cache pins use non-visibility synthetic targets ([Decision 7](#decision-7--plan-cache-key-hygiene-nested-pagination-variables-hash-root-pagination-arguments-do-not)). If a target's `get_queryset` additionally `.distinct()`es, the relation is left unplanned entirely (next bullet).
- **Unwindowable child querysets are left unplanned** — `distinct` is one of five reasons the base-queryset classifier names, alongside `sliced`, `select_for_update`, `combined`, and `values`. For `distinct` the reason is correctness: SQL evaluates window functions before `DISTINCT`, so the `_dst_total_count` `Count(1) OVER` annotation would over-count a de-duplicated child queryset (from the target's `get_queryset` or a custom default manager), and resolving per parent counts correctly ([Decision 4](#decision-4--windowed-prefetch-planning-under-a-package-reserved-to_attr) / [Decision 6](#decision-6--refusal-arms-divergent-aliases-hints-and-scalar-only-connections)). Pinned by `test_distinct_child_queryset_left_unplanned_for_correct_total_count`.
- **Secondary `DjangoType`s with divergent `relation_shapes`** — nested recognition reads the model's **primary** type's `relation_connections` slot ([Decision 3](#decision-3--walker-recognition-is-definition-metadata-driven-not-name-pattern-guessing)), inheriting `field_map`'s primary-resolution rule; a secondary `DjangoType` that shapes a relation differently from the primary is not window-planned and resolves per parent (visible to strictness). Pinned by `test_secondary_type_relation_shapes_nested_recognition`.
- **Consumer cooperation (B8)** — a consumer `Prefetch` on the relation accessor and the window's `to_attr` prefetch are distinct lookups; `diff_plan_for_queryset`'s exact-match and absorption rules see different keys and never merge them. A consumer who prefetches **the `to_attr` name itself** is writing into the package-reserved `_dst_` namespace — unsupported; the resolver consumes only rows carrying `_dst_row_number`, so an unannotated list there resolves through the pipeline.
- **FK-id elision and `only()` inside windows** — child plans are ordinary plans: nested forward-FK `{ id }`-only selections elide, scalar projections apply, connector and ordering columns are force-included so the partition and `ORDER BY` never hit deferred-field refetches. Window annotations are annotations — they compose with `.only()`.
- **Multi-database** — the windowed child queryset follows the generated-`Prefetch` alias rule (it does NOT inherit the root alias; [Multi-database cooperation][glossary-multi-database-cooperation] axis 3); window functions execute on whatever alias the child queryset resolves to.
- **Plan immutability** — the windowed `Prefetch` rides `append_prefetch_unique` and the finalize-to-tuple discipline; cached windowed plans are copied before diffing like every plan (the B1 cache-immutability property).
- **Backend floor** — window functions with `QuerySet.filter` against them require Django ≥ 4.2 and a window-capable backend; the package's `Django>=` floor is above 4.2 and SQLite gained window functions in 3.25, so the windowed strategy ships with no conditional path. A consumer on a backend without window support gets that backend's `NotSupportedError` — surfaced, not swallowed. The window-capability caveat is the **windowed** strategy's; the `"auto"` strategy resolves per effective database alias, using the Postgres lateral backend where the alias and query shape support it and the same bounded window everywhere else, so a backend choice changes performance rather than pagination correctness ([Decision 4](#decision-4--windowed-prefetch-planning-under-a-package-reserved-to_attr)).
- **The outer `totalCount` predicate stays direct-children-scoped** — a nested connection's `totalCount` must not fire the outer connection's count (`_total_count_requested` checks direct children only, recursing through fragment wrappers but never into `edges { node }`).
- **Reverse links other than a pk `ForeignKey`** — a reverse `ForeignObject` joined on two carrier columns has no partition expression: its nested connection resolves per parent (one page query per parent, exact rows) while its plain list prefetch attaches in one query with both carriers in the child `.only()`. A one-column reverse `ForeignObject` and a reverse `ForeignKey(to_field=...)` window on the lone carrier and attach without a per-row refetch. On every one of them the parent `.only()` carries the link's non-pk targets, so no parent refetches a deferred link column, including when the connection is refused for conflicting alias arguments and resolves per parent. An M2M whose through table's FKs target non-pk columns loads the source-side target on the source row, so a list or a window over it, in either direction, is one root query plus one batched query. A forward relation downgraded to a `Prefetch` loads its own carrier (a one-column `ForeignObject`'s `from_fields` column, never its `attname`) on the source row. Lateral and single-parent refuse a `ForeignObject` link (`parent_link_field` is `None`) and the windowed body serves a one-column one ([Decision 4](#decision-4--windowed-prefetch-planning-under-a-package-reserved-to_attr) / [Decision 6](#decision-6--refusal-arms-divergent-aliases-hints-and-scalar-only-connections)). Pinned by `tests/optimizer/test_relation_link_execution.py::test_two_column_link_connection_resolves_per_parent` and its sibling rows.
- **No behavior change for unplanned shapes** — every fallback resolves byte-identically to the per-parent pipeline; the fallback tests assert wire parity, not just non-error.

**Slice 1 — plan-side foundation**

2. The `edges { node }` selection helpers live in [`optimizer/selections.py`][selections] with [`optimizer/walker.py`][walker] and `extension.py` both importing them and neither importing them from the other ([Decision 9](#decision-9--the-edges--node--selection-helpers-consolidate-into-one-module-both-consumers-import)).

4. The planner plans every recognized nested connection as a windowed `Prefetch` under `_dst_<field>_connection` — child plan with visibility / projections / recursion, deterministic order shared with the pipeline via `effective_connection_order` (the cursor-parity invariant, [Decision 4](#decision-4--windowed-prefetch-planning-under-a-package-reserved-to_attr)), relation-kind-correct partition key (a reverse link's lone carrier column; a multi-carrier reverse `ForeignObject` left unplanned), link columns loaded on both sides, slice window from resolved arguments capped by `relay_max_results`, the `_dst_row_number` annotation plus `_dst_total_count` where the `FetchMode` is `COUNTED`, resolver keys recorded — plans divergent aliases as one window per response key under a per-key `to_attr`, leaves the [Decision 6](#decision-6--refusal-arms-divergent-aliases-hints-and-scalar-only-connections) refusal arms unplanned, and recognizes only the primary type's `relation_connections` slot ([Decision 3](#decision-3--walker-recognition-is-definition-metadata-driven-not-name-pattern-guessing)). Argument-aware alias handling, scalar-only connection planning, malformed-slice error locality, the DISTINCT-target and secondary-type fallbacks, shared-child M2M partitioning, subquery-wrap survival, union context publication, and `"both"` + consumer prefetch coexistence are pinned. [`tests/optimizer/test_walker.py`][test-opt-walker] / [`test_plans.py`][test-opt-plans] / [`test_extension.py`][test-opt-extension] cover the slice.

**Slice 2 — connection-class fast path**

5. The synthesized relation connection resolver returns an internal windowed-row wrapper, and the generated connection class serves edges / cursors / `pageInfo` / `totalCount` from the window annotations, with wire parity against the pipeline path, cursor cross-path compatibility, last-only parity, the fast path firing for a reverse relation without `related_name` (the resolver receives the field name, not the accessor, so its `_dst_<field>_connection` probe is correct), annotated `totalCount` bypassing the non-queryset count guard, through-schema proof under Strawberry's `ConnectionExtension`, sidecar kwargs refusing the window, `first: 0` and overshot `after:` served from the retained marker row, and `last: 0` served as the `first: 0` page ([Decision 5](#decision-5--connection-class-fast-path-with-annotation-presence-detection-and-a-per-parent-fallback)). One window query per relation per request; zero per-parent queries on the fast path. [`tests/test_relay_connection.py`][test-relay-connection] covers the slice.

[`tests/optimizer/test_extension.py`][test-opt-extension] covers the slice.
