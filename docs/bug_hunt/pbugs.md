# pbugs.md — suspected residual-bug locations

Items 1-10 are ranked by suspicion after auditing the 27 verified fixes of the `bug_hunt-0_0_14.md` run. Ranking signals: items still `pending` in the hunt, files whose neighbors had high defect density (the same bug class rarely stops at one file), and boundaries where several just-landed fixes now interact for the first time.

Items 11-20 are a second tranche, added after running the full GitHub matrix locally. They are not code locations the hunt ranked low — they are classes the hunt is *structurally unable to reach*, because every hunt item was probed on exactly one cell: Python 3.14 / Django 6.1 / SQLite / single-DB. `is_forward_concrete_relation` is the proof. It carried 100% coverage, sat inside a file the hunt closed as `no-bugs` after 39 adversarial probes, and was still wrong on a push/PR cell. Numbering continues rather than interleaving so existing references stay valid, but item 11 is the only entry in this file that is *demonstrated* rather than inferred, and on evidence it outranks most of the top 10.

## 0. Reading note on the second tranche
Each of 11-20 names a code surface plus the axis that hides it. When triaging, treat "passes on the coverage node" as carrying no information about that axis; the whole point of the tranche is that the green gate is measured somewhere the defect cannot appear.

## 1. `django_strawberry_framework/utils/write_transaction.py` (hunt: pending)
Owns alias pinning, `FOR UPDATE` locks, the phase alias guard, and the `conflict` envelope — the single highest-stakes shared substrate, and it already absorbed collateral edits from the mutations/rest_framework fixes without its own hunt item.
Scrutiny: the auth-alias read-only exception (transaction placed in backend read-only mode, restored on exit) under nested/pre-existing settings; the lexical write-shape allow-list on the pinned connection versus SQL reachable through `SELECT`-invoked functions; lock acquisition when the visibility queryset reduces to a pk subquery over a combined query.
Tests: two-session concurrency tests (delete-under-update with `select_for_update` opted out; SQLite lockless path returning `conflict` not silent success); a permission backend that issues writes on the auth alias and must be refused by the database, not the regex; a guard test that a leading SQL comment or `EXPLAIN ANALYZE UPDATE` on a non-pinned alias is still rejected; verify the read-only pragma/`SET TRANSACTION` value is restored when an enclosing barrier pre-set it.

## 2. `django_strawberry_framework/utils/querysets.py` (hunt: pending)
The sealed execution queryset (spec-045) is the package's central security boundary; its hunt item touched two lines, meaning the sealing logic itself has not been adversarially probed this run.
Scrutiny: `apply_type_visibility_sync` / `apply_type_visibility_async` against hostile returns the docs claim fail closed — consumer `QuerySet` subclasses with shadowed compiler-reachable methods, injected `_result_cache`, combined-query branches over a foreign table, `Prefetch` entries whose inner queryset re-routes, `Manager` returns whose `.all()` is overridden.
Tests: one hostile-object matrix per documented fail-closed clause (each must raise typed `ConfigurationError`, never execute consumer code); identity tests proving the returned queryset is framework-constructed even when the hook returns its input verbatim; recursive resealing of nested `prefetch_related` under a pinned non-default alias in the sharded fakeshop mode.

## 3. `django_strawberry_framework/views.py` (hunt: pending)
The body cap, UTF-8 wire contract, and `csrf_exempt`-outside / `csrf_protect`-inside ordering are all boundary code with off-by-one and ordering hazards, and the sibling `_request_body.py`/middleware items passed while this consumer of them is unhunted.
Scrutiny: measured-not-materialized counting at exactly `limit` and `limit + 1`; the multipart POST carve-out when `Content-Length` is absent, lies low, or the method is not POST; `request.encoding` mutated by upstream middleware before the view runs; the `413`/`400` bodies never triggering Django's own parse first.
Tests: live `/graphql/` byte-boundary tests (`limit`, `limit+1`, chunked with no length); multipart with over-limit declared length asserting no upload handler ran (instrument a recording handler); a UTF-16 and BOM'd body through both sync and async views; a CSRF-subclass project with and without `GraphQLRequestBodyBoundaryMiddleware`, asserting exactly one CSRF check runs in each arrangement.

## 4. Async parity: `django_strawberry_framework/types/resolvers.py` siblings and the connection pipelines
The `SynchronousOnlyOperation` class of bug was just fixed in three resolvers; the same lazy-ORM-touch-on-event-loop pattern plausibly survives in adjacent paths that were not the item's focus.
Scrutiny: `many_resolver` when `visibility_type` is set (the fixed branch was `visibility_type is None`); file/image field resolvers touching storage; `connection.py::_pipeline_async` steps that call sidecar `filter`/`orderBy` apply paths which may run sync ORM; mutation post-write re-fetch under the async pipeline.
Tests: live ASGI tests (not `schema.execute_sync`) with the optimizer disabled or strictness `off`, querying every relation cardinality unprefetched; an async serializer/form mutation whose payload selection walks relations; assert no `SynchronousOnlyOperation` and that strictness accounting still fires before the awaited fetch.

## 5. `django_strawberry_framework/utils/permissions.py` (hunt: pending)
Shared permission traversal plus Django/Channels request decoding; every neighbor that consumed it (`mutations/permissions.py`, auth) needed `is_authenticated`/bool-return hardening, so the shared layer likely holds the same shapes unguarded.
Scrutiny: scope/context decoding on hostile or minimal Channels scopes; permission traversal over `RelatedFilter`/`RelatedOrder` branch gates with denial mid-path; truthy-non-bool returns and coroutine returns reaching the shared executor rather than the flavor-level wrappers.
Tests: reuse the Mandatory Adversarial Probing Matrix directly on the shared helpers (scope without `user`, `SimpleLazyObject(lambda: None)`, actor without `is_authenticated`); an active-input-only scope test proving inactive branches never invoke their gates; a sync-context coroutine-returning gate must fail typed, not leak a never-awaited warning.

## 6. `django_strawberry_framework/utils/sessions.py` (hunt: pending)
The session-engine resolver and connection actor lease back both WebSocket revalidation checkpoints; `auth/sessions.py` passed clean but this substrate was probed only indirectly.
Scrutiny: the revalidation window boundary (`0.0` versus exactly-window-aged validations) at both checkpoints; lease behavior when the session store raises mid-revalidation (fail closed to `4403`, not an unhandled task exception inside the result loop); the `SignedCookieSessionStore` `issubclass` capability check against engines exposing `SessionStore` lazily.
Tests: a fake clock driving window-edge cases at admission and at frame emission; a store whose `load` raises on the Nth call while a subscription is mid-stream, asserting connection close code and one server-side log; engine matrix including a custom client-side store that does not subclass the signed-cookie class (documented to be treated server-side — pin it).

## 7. `django_strawberry_framework/utils/write_values.py` + `utils/inputs.py` (hunt: pending)
The neutral decode substrate under all three write flavors; the flavors each got shape-mismatch fixes wrapped *around* it, which is the classic sign the shared layer's own edges were never hit directly.
Scrutiny: UNSET versus explicit `None` versus missing-key for every value kind (scalar, FK id, M2M list, file, excluded); scalar-into-list and list-into-scalar at the substrate level rather than per flavor; generated-input lifecycle reset between schema rebuilds (`schema_reload.py` consumers).
Tests: parametrized substrate-level matrix mirroring the flavor-level tests that just landed, so a fourth flavor cannot re-import the bug; live mutations sending `null` for a non-nullable M2M and a scalar for a list input, asserting field-keyed `FieldError` not a 500; double schema rebuild asserting no cross-build input-class leakage.

## 8. Window math after the UNSET wave: `keyset.py` × `utils/connections.py` × `optimizer/single_parent_fetch.py`
Many independent UNSET/generator guards just landed across three cooperating layers; each is locally verified but their compositions (probe row + `list()` coercion, keyset seek + `last:`, fast-path eligibility) were not re-proven together.
Scrutiny: `split_window_rows` list coercion interacting with the sentinel `next_page_probe` overfetch and the single-parent fast path's synthesized row numbers; `derive_keyset_window_bounds` when one bound is UNSET and the other explicit `null`; `resolve_relay_max_results` narrowing when the policy cap and `max_results` are both unset.
Tests: a pagination property suite over `first`/`last`/`after`/`before` x offset/keyset x root/nested x fast-path-eligible/ineligible, asserting page contents and `pageInfo` against a brute-force slice of the ordered rows; explicit tests that a generator-backed rows source produces identical pages to a list-backed one.

## 9. `django_strawberry_framework/extensions/resource_policy.py` budget semantics after the narrowing
The `_charge_container` fix narrows family charging to typed `GraphQLList`; the audit confirmed width/depth/nodes/bytes still bound untyped arrays, but budget *parity* between spellings is now the risk surface.
Scrutiny: literal-versus-variable cost parity for every limit (an attacker picks the cheaper spelling); custom scalars carrying large nested arrays now charged only by the generic bounds — confirm those bounds alone keep worst-case work proportional; `memoryview`/`bytearray` length semantics versus encoded JSON size.
Tests: for each `ResourcePolicy` limit, a pair of tests sending the same payload inline and via variables asserting both are rejected at the same threshold; a JSON-scalar payload tuned to maximize nodes under the membership radar asserting `RESOURCE_LIMIT_EXCEEDED` before ORM work (assert zero queries).

## 10. Package integration: `__init__.py` exports, `utils/errors.py`, `utils/imports.py` (hunt: pending + final items)
The cross-boundary item has not run, and `utils/errors.py::_str_list` was already collaterally patched — error-envelope totality and the lazy/soft-dependency export machinery are the remaining system-level seams.
Scrutiny: every `FieldError` constructor total over hostile metadata (exceptions with exploding `__str__`, lazy translation proxies, bytes messages); PEP 562 lazy exports (`SerializerMutation`, `routers`, middleware leaves) under partially-installed soft dependencies including import-order permutations; `__all__` versus actually-importable symbols after the hunt's cross-file additions (`is_forward_concrete_relation` promotion and the optimizer `_context` `__all__` fix suggest drift elsewhere).
Tests: extend `tests/base/test_init.py` with an `__all__` round-trip plus a `dir()`/lazy-getattr consistency check; reuse `tests/_soft_dependency.py` to simulate each absent soft dependency and import the package root, asserting DRF/channels/toolbar-free import stays clean and leaf access raises the install-hint `ImportError`; a hostile-args sweep over every public exception and error constructor asserting str/repr/pickle never raise.

## 11. Django-metadata divergence across the supported 5.2 -> 6.1 range (demonstrated)
The package contains **zero** `django.VERSION` sniffing — verified across the whole of `django_strawberry_framework/` — so it assumes every Django internal it reads is uniform across three majors. That assumption is already false: `ManyToManyField` reports `column="genres"` / `concrete=True` on the 5.2 floor and `column=None` / `concrete=False` on 6.0+, which is exactly what made `utils/relations.py::is_forward_concrete_relation` answer two different ways across one supported matrix. Those two flags were audited and the remaining read sites cleared, but that was one pair found by one failing assertion, not a sweep.
Scrutiny: every attribute read off a field / rel / `Query` — `path_infos`, `target_field`, `attname`, `pk_fields`, `get_accessor_name`, and the *presence* of attributes on `ForeignObjectRel` (several predicates lean on absence rather than on a positive test, which is the same fragility in a different disguise); `Options.get_fields()` ordering; the optimizer's compiler touchpoints (`query.where`, `alias_map`, `resolve_expression`). Note `optimizer/field_meta.py::FieldMeta` persists `concrete` into a frozen slot, so a forward-M2M `FieldMeta` is **not equal across Django versions** — confirm nothing keys a cache, hash, or equality check on it.
Tests: assert the *derived predicate*, never the raw flag, across every relation shape, using doubles that carry BOTH versions' flag combinations so each shape is exercised twice on every cell. `tests/utils/test_relations.py::test_is_forward_concrete_relation_reads_cardinality_not_the_column_flag` is the pattern: the real `Book.genres` only ever pins whichever metadata the installed Django ships, and the old predicate passed that assertion on 6.x for the wrong reason.

## 12. Environment-conditional branches the single-cell coverage gate cannot see
`fail_under = 100` is enforced on exactly one node (latest / 3.14 / single-DB / SQLite). Coverage read 100.00% while the M2M predicate was wrong, because line execution on one interpreter, one vendor, and one DB layout says nothing about the others. Any branch that exists *for* a different environment is either dead on the coverage node or covered by a double that may not match that environment's reality.
Scrutiny: the sharpest instance is item 1's substrate — `select_for_update` is a **no-op on SQLite**, so the entire row-locking path in `utils/write_transaction.py` is line-covered by a vendor that does not implement it, and the "SQLite lockless path returns `conflict`" claim is asserted against the only vendor that cannot disprove it. Same question for every `except` arm and vendor fallback whose sole executing test is a stand-in.
Tests: combine the per-cell `.coverage` data files across the dispatch matrix and diff which lines execute on exactly one cell; treat any such line as a candidate environment-specific double. Cheaper interim gate: run the suite once under `FAKESHOP_PG_DSN` with `--cov` and diff the missing-line set against the SQLite run.

## 13. `django_strawberry_framework/optimizer/lateral_fetch.py` — Postgres-only SQL, line-covered on SQLite
427 statements whose own module docstring concedes that SQLite covers "the pure builder, the plan-time downgrades, the fetch-time extraction, and the scripted-cursor execution" and that "only a real Postgres server can prove the SQL itself". That proof is `tests/test_lateral_pg_parity.py`, which lives in the `workflow_dispatch`-only Postgres tier. So on every push and PR this file reaches 100% line coverage against a vendor that cannot execute a single statement it emits. It is also the package's deepest compiler surgery (`query.where.clone()`, `alias_map`, target `column` reads), which makes it maximally exposed to item 11.
Scrutiny: the plan-time downgrade predicates — a shape that *should* downgrade but does not produces invalid SQL only on Postgres, and nothing on the PR tier can notice; the `CROSS JOIN LATERAL` emission against Django 6.1's `Query` internals versus the 5.2 floor.
Tests: `postgres.yml` declares no `FAKESHOP_SHARDED` and every sharded cell in `django.yml` is SQLite, so **Postgres x multi-DB is a completely unexercised intersection** — and that intersection is precisely where alias pinning lives. Add a pg x sharded cell, extend the pg parity params to the shapes only the SQLite suite exercises, and run the pg tier at least once per release rather than ad hoc.

## 14. The three monkeypatch modules against a one-dimensional version matrix
`_strawberry_patches.py`, `_django_patches.py`, and `_cross_web_patches.py` patch private upstream API by definition. But `strawberry-graphql==0.316.0` is pinned *only* on the `Django 5.2.16 / Python 3.10` cells, so **floor-strawberry x Django 6.x** and **latest-strawberry x Django 5.2** are never built at all. `django.yml`'s own comment documents the live hazard: upstream renamed the WebSocket dispatch attribute (`subscribe` + `execute` -> `stream` in 0.319.0) *inside* the supported range, and an unwrapped rename is **silent** — the delegating wrapper forwards it and the protocol keeps working, minus the masking and the revocation stop.
Scrutiny: the severe failure mode is not an exception, it is a patch that silently no-ops when its target moves, leaving the package working with the *security* behavior quietly removed. Enumerate every attribute each patch module reaches for and check existence across 0.316 -> latest and Django 5.2 -> 6.1, not merely at the two points that happen to be installed.
Tests: one assertion per patch that the target exists AND that the patch actually took effect (observable behavior, not "import did not raise"), so a moved target fails loudly on whichever cell installs that version; add a matrix cell pinning the strawberry floor on Django 6.x.

## 15. Dynamic annotation synthesis across the PEP 649 boundary
Schema generation is built on synthesizing `__annotations__` and resolving them through `get_type_hints`, across eleven package modules (`utils/inputs.py`, `types/finalizer.py`, `types/base.py`, `connection.py`, `mutations/fields.py`, `mutations/inputs.py`, `auth/mutations.py`, `optimizer/hints.py`, `optimizer/nested_fetch.py`, `types/relations.py`, `management/commands/inspect_django_type.py`). Python **3.14 implements PEP 649**: annotations became lazily evaluated via `__annotate__`. The coverage node runs 3.14; the advertised floor is 3.10. That is the largest semantic gap anywhere in the matrix, and it sits directly under the package's core mechanism.
Scrutiny: forward-reference resolution inside the synthesized namespaces (`make_input_namespace` / `clear_generated_input_namespace`); any site that reads `__annotations__` directly, where 3.14 now triggers lazy evaluation at a different moment than 3.10 evaluated it eagerly; whether a dynamically built input class carries a stale `__annotate__` after a schema rebuild.
Tests: build every generated input / output class on both ends of the range and compare the *resolved* hint mapping, not the schema SDL, so a divergence that the printer happens to normalize is still caught. Secondary: `filterwarnings = error` turns any interpreter-specific `DeprecationWarning` into a single-cell failure, so warning-shape differences across 3.10 -> 3.14 are themselves a matrix hazard.

## 16. Fixture-shape gap: the exotic model shapes the package reasons about do not exist in fakeshop
AGENTS mandates testing through real usage in the example project, but an inventory of `examples/fakeshop/apps/*/models.py` finds **zero** occurrences of `CompositePrimaryKey`, `to_field=`, `parent_link`, `ForeignObject(`, and `db_column=`, and no multi-table inheritance at all (all four `abstract = True` bases are abstract, so no concrete parent link is ever generated). Yet the package reasons about every one of those shapes in load-bearing code: `utils/relations.py::has_composite_pk` and `FieldMeta.fk_id_elision_eligible` must fail closed on composite PKs; `relation_kind` documents a dedicated branch for "the concrete auto-created MTI parent link"; `FieldMeta.target_field_attname` claims to preserve "non-PK `to_field` connector rules"; `filters/base.py` reasons about "the composite `ForeignObject` (whose `target_field` would raise)". Every one of those branches is therefore pinned only by `SimpleNamespace` doubles encoding an author's belief about Django's metadata — which is exactly the double-versus-reality mismatch that produced the item 11 bug. `db_column=` is the sharpest omission: it is the only thing that makes `column != attname`, and the bug just fixed was about `column`.
Scrutiny: whether each documented branch is reachable from any real model anywhere in the repo, or only from a hand-built namespace; whether the doubles' flag combinations are actually producible by Django for that shape on both 5.2 and 6.x.
Tests: add the missing shapes to fakeshop (a composite-PK model, an MTI parent/child pair, a non-PK `to_field` FK, a `db_column`-renamed column) and drive them through live `/graphql/` queries and a write mutation, so the branches are exercised by Django's own metadata rather than by a transcription of it. Where a shape is genuinely unsupported, assert the typed refusal against a real model instead of a double.

## 17. Model/migration drift is ungated
`makemigrations --check` appears nowhere in `.github/workflows/` or in the pre-commit config. Because this package generates the GraphQL surface from `Model._meta` rather than from the database, a model field added without its migration produces a schema field whose column does not exist: type generation succeeds, the SDL looks correct, `--check`-style doc gates stay green, and the failure only materializes as an `OperationalError` the first time that field is selected. The suite builds its test DB from migrations, so the drift is invisible to any test that does not happen to query the new field.
Scrutiny: the six fakeshop apps' migration state versus their current models, especially `kanban` and `glossary`, which are written by the board tooling and change outside normal feature work; whether `scripts/build_kanban_*` render against a migrated copy whose schema can silently trail the models.
Tests: add `manage.py makemigrations --check --dry-run` to the lint job — it is a seconds-long gate that closes the whole class. Pair it with one live query per app that selects every generated field, so a column that exists in `_meta` but not in the DB fails at test time rather than in a consumer's deployment.

## 18. Local runs and CI runs use different settings modules
`pytest.ini` declares `DJANGO_SETTINGS_MODULE = config.test_settings`, but `.envrc` exports `DJANGO_SETTINGS_MODULE="config.settings"`, and pytest-django prefers the environment variable over the ini. With direnv active every maintainer run therefore uses `config.settings`, while CI — which has no direnv — uses `config.test_settings`. Every local matrix run recorded in this session was under `config.settings`. Today the delta is a single key (`test_settings.py` overrides only `PASSWORD_HASHERS` to MD5), so this is a latent hazard rather than a live defect — but it means "it passed locally" and "it passed in CI" are not the same statement, and any future divergence is untested in exactly one direction with no signal that a direction is missing.
Scrutiny: also note the default posture the whole suite inherits — `config.settings` sets `DEBUG = True`, so the permissive branch is the default for every test that does not explicitly opt out (63 `DEBUG=False` opt-ins exist, which is real coverage but leaves the live `test_query/` end-to-end tier running against the non-production posture); and CI's MD5 hasher changes any password-upgrade-on-login or hasher-sensitive path in the auth surface.
Tests: make the two modules agree or make the divergence explicit — either drop the `.envrc` export so both paths resolve through `pytest.ini`, or add a test asserting `settings.SETTINGS_MODULE == "config.test_settings"` under pytest so a silent override fails loudly. Add a live-tier pass under `DEBUG=False` so the production error/debug posture is exercised end to end, not only in unit-level overrides.

## 19. Global-state isolation depends on the scheduler, not on the code
`--dist loadscope` pins a module's tests to one worker, and registry / connection-cache isolation is opt-in per module (the autouse `_isolate_global_registry` shim). AGENTS requires that "test correctness must remain independent of module and function order", but nothing enforces it: a module that leaks global state is only caught when a victim happens to land on the same worker, and worker assignment shifts with test count — which changes on essentially every commit. The suite also carries process-lifetime `lru_cache`s keyed on model classes (`utils/relations.py::_classify_path_cached`, `_path_traverses_to_many_cached`) that no registry teardown invalidates, plus a generated-input namespace whose documented failure mode is cross-build leakage.
Scrutiny: which modules mutate the global registry, the connection cache, or the generated-input namespace without the isolation fixture; whether `clear_generated_input_namespace` is reached on every failure path, not just the happy one; whether the relation caches can serve a stale answer after a registry clear or a model swap under `override_settings`.
Tests: run the full suite with `-n0` and again with the module order shuffled, and require identical results — this is the direct enforcement of the AGENTS rule and currently nothing performs it. Additionally run each test module alone in a fresh process and diff against its in-suite result; a module that only passes with company is leaking or depending on a leak.

## 20. Vendor-divergent SQL semantics beyond LATERAL
Item 13 covers the code that is explicitly Postgres-only. The subtler exposure is code that is vendor-*agnostic by intent* but rides SQL whose semantics differ, validated on PR CI against SQLite alone. The classic instance is case-insensitive matching: SQLite's `LIKE` is already case-insensitive for ASCII, while Postgres requires `ILIKE`. A defect in which `icontains` / `istartswith` / `iexact` emits a plain `LIKE` would pass the entire filter suite on SQLite and fail only on Postgres — and `filters/` is one of the most heavily tested subsystems in the repo, all of it on the vendor that cannot expose this.
Scrutiny: `NULL` collation order (`NULLS FIRST` on SQLite versus `NULLS LAST` on Postgres for `DESC`), which silently reorders any nullable ordering key and any to-many order aggregate; `DISTINCT` combined with `ORDER BY` on a non-selected expression (Postgres rejects what SQLite accepts); `Decimal` and `datetime` adaptation, which matters for `keyset.py`'s encrypted cursors because the encoded bound must compare identically to what the driver returns; string collation in `orders/` for non-ASCII.
Tests: for every generated `i`-prefixed lookup, assert the emitted SQL operator rather than only the result set, so the assertion is vendor-independent; add a nullable ordering key to the pagination property suite in item 8 and require identical page contents on both vendors; run the keyset roundtrip matrix under `FAKESHOP_PG_DSN` and compare cursor bounds against the SQLite run.
