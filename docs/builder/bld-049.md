## The audit found real vulnerabilities before the lock was fixed

The open question ("pip-audit vs safety vs osv") was settled empirically as well as on the
marker-split argument in spec-049 Decision 5: the chosen tool was run against the tree
before Slice 1 finished, using the same pinned image the workflow uses.

```

  ghcr.io/google/osv-scanner-action:v2.3.8 --lockfile=uv.lock
```

**Before:** `Total 2 packages affected by 14 known vulnerabilities (0 Critical, 12 High,
2 Medium, 0 Low)`, exit 1.

## Decisions taken during the build (beyond the spec's numbered set)

1. **`pyyaml` into the dev group, not a hand-rolled parser.** No YAML parser was installed.
   A regex-only scanner cannot find job boundaries without modelling block structure, which
   is exactly where the assertions need to be right. Dev group only; `[project].dependencies`
   untouched.
2. **`--lockfile=uv.lock` rather than `-r ./`.** Upstream's own examples use recursive scan.
   The explicit lockfile target names the audited artifact in the workflow, so a reader
   knows what is and is not covered — which is the whole basis of the compatibility-cell
   exclusion argument.
3. **Called the inner `osv-scanner-action` directly, not the reusable workflow.** The
   reusable workflow needs `security-events: write` for SARIF and carries its own unreviewed
   pins. See spec-049 Decision 5.
4. **`compatibility_only` as a matrix key rather than a renamed matrix label.** Adding a
   tier field to all 16 dispatch rows would have been noise; a key on the three `5.2.0` rows
   plus a conditional job-name suffix touches only the rows that mean something different.
5. **Corrected the stale `5.2.14` comment** in `django.yml`'s Django-install step in the
   same change as the lock refresh (spec-049 Decision 9). It named the version Slice 1 moved.
