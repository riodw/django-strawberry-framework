# DRY review: `django_strawberry_framework/optimizer/` (Folder Integration)

Status: verified

## System trace

`django_strawberry_framework/optimizer/` is the unified query optimization and batch execution subsystem of the framework ([spec-002][spec-002], [spec-003][spec-003], [spec-004][spec-004], [spec-006][spec-006], [spec-010][spec-010], [spec-016][spec-016], [spec-018][spec-018], [spec-020][spec-020], [spec-023][spec-023], [spec-025][spec-025], [spec-028][spec-028], [spec-030][spec-030], [spec-033][spec-033], [spec-035][spec-035], [spec-036][spec-036], [spec-044][spec-044], [spec-045][spec-045], [spec-047][spec-047], [spec-051][spec-051], [spec-053][spec-053], [spec-055][spec-055], [spec-063][spec-063]). It automatically analyzes incoming GraphQL request selection trees, inspects Django model relations and field descriptors, constructs optimal database query plans using `select_related`, `prefetch_related`, and `.only(...)` column projections, and executes multi-backend nested Relay connection pagination (via SQL `ROW_NUMBER()` window functions, PostgreSQL `CROSS JOIN LATERAL` subqueries, or single-parent degenerate fast paths) to eliminate N+1 queries across complex graph operations.

The subpackage acts as the foundational query-planning substrate for read-side queries ([`django_strawberry_framework/schema.py`][schema]), Relay connection pagination ([`django_strawberry_framework/connection.py`][connection], [`django_strawberry_framework/connection/fields.py`][connection-fields]), post-mutation payload re-fetching ([`django_strawberry_framework/mutations/resolvers.py`][mutations-resolvers]), relation resolvers ([`django_strawberry_framework/types/resolvers.py`][types-resolvers]), and row-preserving filter predicates ([`django_strawberry_framework/filters/sets.py`][filters-sets]).

### Rejected candidates

1. **Merging `nested_planner.py`, `nested_fetch.py`, `lateral_fetch.py`, and `single_parent_fetch.py` into a monolithic `nested.py` module:**
   - Disproved in [spec-033][spec-033], [spec-051][spec-051], and [spec-063][spec-063]. Nested connection prefetching spans four distinct architectural layers: strategy-independent query planning and transactional AST isolation (`nested_planner.py`), pluggable strategy registry and lifecycle protocols (`nested_fetch.py`), vendor-specific PostgreSQL lateral SQL compilation and execution (`lateral_fetch.py`), and degenerate single-parent ORM fast paths (`single_parent_fetch.py`). Keeping these four layers separated into cohesive files preserves clean separation of concerns and prevents vendor-specific SQL compilers from tangling with pure AST walkers.
2. **Re-implementing dictionary and attribute dispatch locally within `_context.py` rather than delegating to `utils/context.py`:**
   - Disproved in [spec-047][spec-047]. Both the optimizer (`optimizer/_context.py`) and resource policy (`resource_policy.py`) subsystems require safe, shape-agnostic read, write, and delete operations on GraphQL `info.context` objects (handling `None`, plain dicts, objects, `__slots__` mappings, and locked `QueryDict` instances). Centralizing this dispatch in `utils/context.py` eliminates cross-subsystem duplication.
3. **Merging `field_meta.py` and `join_taxonomy.py` into `utils/relations.py`:**
   - Disproved in [spec-016][spec-016] and [spec-051][spec-051]. `field_meta.py` captures frozen, class-creation-time static metadata snapshots (`FieldMeta`) for GraphQL types. `join_taxonomy.py` evaluates query-time parent/child join expressions (`RelationJoinDescriptor`) from active Django descriptors. `utils/relations.py` provides semantic relation topology classification (`RelationKind`). Merging them would blur the boundary between build-time type definitions, query-time join taxonomy, and generic relation topology helpers.
4. **Re-exporting internal query planning machinery (`OptimizationPlan`, `plan_optimizations`, `classify_relation_join`) from `optimizer/__init__.py`:**
   - Disproved per [spec-006][spec-006]. The public consumer interface of the optimizer subpackage is `DjangoOptimizerExtension`. Internal query planning mechanics reside at their dedicated dotted module paths (`optimizer.plans`, `optimizer.walker`, etc.) and are internal implementation details consumed by `DjangoOptimizerExtension`, `DjangoConnectionField`, and test suites. Cluttering `optimizer/__init__.py` would weaken encapsulation.
